## 0. 三个核心事实

### 0.1 压缩期间输入被**拒绝**，不是排队

`frontends/ink/bridge.py:571`（`submit`）：

```python
def submit(self, text: str, display_text: str | None = None, images: list | None = None) -> int:
    text = str(text or "")
    if not text.strip() and not images:
        self.emit({"type": "error", "code": "empty_input", "message": "input is empty"})
        return -1
    if getattr(self.agent, "is_running", False) or self._is_consuming():
        self.emit({"type": "error", "code": "busy", "message": "agent is running"})
        return -1
```

用户得到的是一句 `{"type": "error", "code": "busy"}`，**消息被丢弃**。

> ⚠️ 这里有个容易搞错的因果：压缩阶段 `agent.is_running` 其实还是 `False`
> （见 §0.2）。真正命中拦截的是 `self._is_consuming()` —— 它检查
> `_consume_thread.is_alive()`（`bridge.py:3414`），而该线程在 `submit()`
> 里就被启动了（`bridge.py:652`），一直活到回合结束。
>
> ⇒ **修的时候要改的是 `_is_consuming()` 这一支，不是 `is_running`。**

### 0.2 压缩发生在 `is_running = True` **之前**

`genericagent/core/app.py` 的 `run()`：

```python
if source == "user" and not str(raw_query or "").strip().startswith("/"):
    self._auto_compact_before_task(raw_query, display_queue)   # line 1956
    self._emit_context_usage(display_queue)
...
self.is_running = True                                          # line 1988
```

【S】压缩 → 置忙 → 开跑。顺序本身是对的（压缩不该算「回合进行中」）。

【A】但**没有任何机制在压缩开始时通知前端**，所以前端的状态机仍停在
「上一轮刚结束 / 马上就要开始」之间，而 `_consume_thread` 已是活的。

### 0.3 压缩全程零事件

`grep` 结果（`genericagent/core/context.py`）：

```
compact 相关行里含 emit / display_queue / put( 的语句数 = 0
```

`maybe_auto_compact`（`context.py:371`）与 `compact_agent_context`
（`context.py:433`）都是纯同步计算，成功时只返回一个字符串，由调用方
`display_queue.put(...)` **在压缩结束后**才写：

```python
note = maybe_auto_compact(self, pending_text=raw)
...
if note:
    display_queue.put({"done": f"{note} (auto, before this request)", "source": "system"})
```

⇒ **压缩开始没有事件、压缩中没有任何事件、结束后才有一条 `done`。**
这就是「界面静止、看起来卡住」的完整根因。

## 1. GA vs CC 行为对照

| 维度 | CC 2.1.319 | GA（现状） |
| --- | --- | --- |
| 压缩中的可见指示 | 专用行 + 150ms 思考帧 + 蓝色 | **无** |
| 压缩期输入 | 接受并排队（`wait`） | **拒绝（`error/busy`），丢弃** |
| 压缩期事件 | `compact_progress` 三阶段 + 30s 心跳 | **零事件** |
| 完成提示 | `Conversation compacted` + 旧消息路径 | `Auto <msg> (auto, before this request)` |
| 独立计时 | `compactingStartTime` | 无 |
| 进度条/百分比 | 没有 | 没有 |

【A】两边的输入行为是**语义不同**，不只是实现差异：
- CC 的 `wait` = 「消息留着，压缩完就发」；
- GA 的 reject = 「这条没了，用户得重打」。

后者对用户的伤害更大 —— 用户打了字、按了回车、字消失、什么都没发生。

## 2. 为什么会变成 reject（设计溯源）

【B】推断（源码里没有注释说明这一点，下面是依据代码结构做的推理）：

`submit()` 的忙检查是为**普通运行中**准备的 —— 防止用户在模型正在生成时
插入第二条请求打乱回合。压缩复用了同一条路径，于是顺带把「压缩期」也
当成「运行中」拦掉了。

差别在于：普通运行中拒绝输入是合理的（GA 没有 CC 那样的排队投递机制），
而压缩是一次**用户不可见、也不该被打断**的内部操作，此时拒绝输入没有道理。

> 【未验证】GA 是否另有排队机制（`queuedPrompts`）在别的入口生效。
> `bridge.py` 里有 `_start_queued_turn_after_end`，说明回合结束后会排空队列 ——
> 但那是「回合进行中通过别的方式入队」的路径，与 `submit()` 被拒不是一回事。
> 要确认「用户在压缩期打字会不会进那个队列」，得看 Ink 前端在收到
> `error/busy` 之后有没有自己兜底。**本次未查，标为待办。**

## 3. 修复建议

### P0：压缩期发一个状态事件（解决「界面静止」）

最小改动，两处：

1. `_auto_compact_before_task` 在调 `maybe_auto_compact` **之前**，
   往 `display_queue` 写一条 `{"system": "Compacting conversation"}`；
2. 结束后写 `{"done": ...}`（已有）。

【A】这样 UI 至少能显示一行文字。配合前端已有的 spinner 动画，
就能达到 CC 的「看起来在动」效果。

### P0：压缩期不要 reject 输入

两个选项，选一个：

- **A. 放行 + 排队**（对齐 CC）：`submit()` 的忙检查里排除「正在压缩」这一种忙，
  把消息推进 `queuedPrompts`，压缩完 / 回合结束后自动发出。
- **B. 放行 + 直接作为下一轮**：不排队，等当前回合结束再发。

【B】推荐 A —— GA 已有 `_start_queued_turn_after_end` 基础设施，语义与 CC 一致。

> 实现时**不要**简单地把 `_is_consuming()` 从条件里删掉：那会让「模型正在
> 生成时」也能插话，破坏回合完整性。要区分「压缩中」与「生成中」两种忙。

### P1：完成提示带上下文信息

CC 的做法是告知旧消息存到哪个文件。GA 的 `record_compact_transcript`
（`context.py:402` 调用）已经落了 transcript，可以顺手把路径写进提示。

### 3.4 输入框在请求发出**之前**就被清空了【S】

这条决定了「被拒」的实际伤害有多大 —— 答案是**全丢**。

`frontends/ink/ui/src/inputController.ts:464`（回车提交分支）：

```js
return decision('', 0, {
  command: images.length
    ? { type: 'submit', text: expanded, images }
    : { type: 'submit', text: expanded },
})
```

`decision('', 0, ...)` 的第一个参数就是**新的输入框内容**（空串），
由 `App.tsx:2408` 应用：

```js
if (decision.input !== undefined) {
  setInput(decision.input)
  setCursorOffset(decision.input.length)
}
```

【S】时序因此是：

```
用户回车
  → handleInput 返回 decision('', 0, {command:'submit'})
  → 输入框立即清空（App.tsx:2408-2410）
  → bridge.submit() 发到后端
  → 后端因 _is_consuming() 返回 error/busy
  → 前端没有 busy 专属处理（grep 'busy' 在 App.tsx 零命中）
  ⇒ 字没了，只有一条泛化 error
```

【A】这是比 CC 更糟的失败形态：CC 是「留着排队」，GA 是
**「先清空、再拒绝、不还原」**。用户感受就是「打了字按回车，字消失了，
什么都没发生」。
