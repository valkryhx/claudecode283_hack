## 0. 一句话结论

Claude Code 的工具层不是一个"给模型几个函数"的薄壳，而是一套**有类型契约、有并发语义、有预算管理、
有权限与沙箱双层门禁、有前后台状态机**的运行时。它稳的根因不是某个工具写得好，而是：

1. **每个工具都是一个声明式对象**，字段固定（`name` / `inputSchema` / `outputSchema` / `call` /
   `validateInput` / `checkPermissions` / `isReadOnly` / `isConcurrencySafe` / `maxResultSizeChars` / `prompt`），
   调度器、权限器、UI、遥测、remote executor 全部按同一套字段驱动 —— 新增工具不用改调度器。
2. **shell 工具永远跑 POSIX shell（Git Bash / zsh / bash），并且提示词明说"这是 Git Bash 不是 cmd/PowerShell"**。
   Windows 上的 PowerShell 是**另一个独立工具**，带自己的版本感知速查表 —— 这是它不像 Codex 那样
   频繁吃 PS 语法错误的根本原因。
3. **工具输出的预算是硬约束**：超长输出落盘 + 头尾保留 + 中间省略标注；单工具结果超限直接进
   `tool-results/` 文件，模型只看到摘要路径。上下文永远不会被一个 `cat` 撑爆。

## 2. Bash 工具：为什么在 Windows 上不吃 PowerShell 语法错误

这是本项目最关心的部分。结论先给：

> **Claude Code 在 Windows 上默认根本不用 PowerShell 跑 Bash 工具。**
> 它强制解析出一个 **Git Bash**（`bash.exe`），Bash 工具的一切都按 POSIX sh 语义执行，
> 并且在系统提示里明写"这是 Git Bash，不是 cmd.exe 也不是 PowerShell，用 Unix 语法"。
> PowerShell 是**另一个独立工具**（`PowerShell`，`kt`），只有在 Git Bash 完全找不到、
> 或用户显式 `CLAUDE_CODE_USE_POWERSHELL_TOOL=true` 时才上场 —— 而且那个工具有全套 PS 版本感知速查表。

配套的 cwd 语义说明（`Yrn()`，`:77027`）：

macOS 老 bash 的专项警告（`Urn()`，`:76766`）：`/bin/bash` 3.2 不能在 `$(...)` 里跑 heredoc，
提示模型改用 `git commit -F - <<'EOF'` / `gh pr create --body-file -`。

**这才是"没有 PS 语法错误"的真正机制**：不是运行时容错，而是
**① 执行面统一到 POSIX sh（Git Bash）②提示词里逐条列出 Windows 上最容易混的语法差异**。
模型不是在猜"这台机器是什么 shell"，提示词直接告诉它了。同一个 prompt 还按 `i.platform` 分支，
Windows 上多两行、macOS 上多两行、Linux 上没有。

**关键设计对比**：`process.env.SHELL` 在 Windows 启动时被 `HFr()` 改写成 Git Bash 路径（`m0097:75`）——
这让**子进程**（git、npm、`node` 里 `child_process` 的 shell）也继承 POSIX 语义，
而不只是 Claude Code 自己那一条命令。

### 2.3 提示词里的工具分工（为什么它敢"少出错"）

`Vrn()` 拼出的 instructions 段（`:76999` 起）核心几条：

```js

          : "`find`, `grep`, `cat`, `head`, `tail`, `sed`, `awk`, or `echo`";
```

- 提示里点名"不要用 cat/sed/echo 替代专用工具"，同时**告诉模型专用工具的准确名字**
  （`${ze}` = `Read`、`${dt}` = `Edit`、`${Yt}` = `Write`、`${Qr}` = `Glob`、`${_r}` = `Grep`），
  这些名字来自运行时的工具注册表，不是硬编码字符串 —— 工具被禁用/重命名时提示自动跟着变。
- Windows 上额外点名 `cat/head/tail/sed/awk/echo` 是"别拿 shell 干文件活"的重点对象，
  Linux/macOS 上则把 `find/grep` 也算进去（因为那两个平台有更惯用的替代）。
- git 相关固定三条（`:76950` 的 `G`）：优先新提交而非 amend、破坏性操作先想替代方案、
  绝不 `--no-verify` / `--no-gpg-sign`。
- sleep 相关（`Ce`）：命令能立刻跑就别 sleep、不要 sleep 轮询、失败不要在 sleep 循环里重试、
  要等就用 `run_in_background` / `Monitor`（另有"长 sleep 被拦截"的规则，见 §2.8）。

### 2.4 shell snapshot：让每次 `bash -c` 都像登录 shell

**问题**：`bash -c "cmd"` 不读 `.bashrc`，用户的 alias / 函数 / PATH 全没了；而用 `bash -lc`
每次都 source 一遍 `.bashrc` 又慢（可能有 `nvm`/`conda`/`direnv` 几十秒）。

**Claude Code 的解法**：会话开始时跑一次登录 shell，把**可复现的状态**序列化到一个
临时 snapshot 脚本；之后每次执行都是 `source <snapshot> && <cmd>`。

`aDn()`（`m0591_0x11be624e.js:142680`）：

snapshot 脚本本体（`fUr()`，`:142637`）长这样：

```bash
SNAPSHOT_FILE=<path>
source <用户的 .bashrc|.zshrc> < /dev/null     # 或 "# No user config file to source"

echo "# Snapshot file" >| "$SNAPSHOT_FILE"
echo "unalias -a 2>/dev/null || true" >> "$SNAPSHOT_FILE"   # 先清空 alias，避免冻结进函数
echo "shopt -s expand_aliases" >> "$SNAPSHOT_FILE"

```

收集段（`iUr()`，`:142488`，bash 分支）关键设计：

```bash
shopt -p >> "$SNAPSHOT_FILE"                 # 先 shopt 再函数：extglob/globstar 语法才能重解析
declare -f > /dev/null 2>&1                  # 强制 autoload 所有函数
declare -F | while read func; do
  func=${func##* }
  if [[ "$func" == [-+]* ]]; then printf 'eval -- %q > /dev/null 2>&1\n' "$(declare -f -- "$func")" >> "$SNAPSHOT_FILE"
  else [[ "$func" == _[!_]* ]] || printf 'eval %q > /dev/null 2>&1\n' "$(declare -f "$func")" >> "$SNAPSHOT_FILE"; fi
done
set -o | awk '$2 == "on" || $1 == "monitor" {print "set -o " $1}' >> "$SNAPSHOT_FILE"
```

三个细节值得抄：

1. **每个函数单独 `eval`**，坏了只丢自己（源码注释："One eval per function so a body that no longer
   parses (rc=2, not fatal in non-POSIX bash) drops only itself"）。
2. **`printf %q` 而非 base64**：source 时不需要 fork 子进程。
3. **过滤单下划线开头的补全函数，保留双下划线 helper**（`[[ "$func" == _[!_]* ]]` 跳过
   `_git` 之类补全函数，但保留 `__zsh_like_cd`、`__pyenv_init`）。

**Windows/Git Bash 专项**（`iUr()` 同段）：


**为什么要删 winpty alias**：Git Bash 在 mintty 里自动生成 `alias node='winpty node.exe'`，
但 Claude Code 执行时没有 TTY，`winpty` 会报 `stdin is not a tty` 直接失败。
**这是"Windows 上 bash 工具稳"的一个具体细节。**

**PATH 的取法**：`aUr()`（`:142553`）先跑 `bash -lc 'echo "$PATH"'` 取登录 shell 的真实 PATH
（带校验：必须是 `/` 开头且不含 `;`，否则告警并回退）；`sat()` 把 PATH 合成
`export PATH=<...>` 写进 snapshot；插件 `bin/` 目录用去重循环追加（`cUr()`，`:142600`）。

`d2s()`（`:223330`）是真正的执行状态机，一次调用要同时处理**5 种归宿**：

| 归宿 | 触发 | 结果字段 |
| --- | --- | --- |
| 正常完成 | 命令结束 | `stdout/stderr/code/interrupted` |
| 显式后台 | `run_in_background: true` | `backgroundTaskId` |
| 超时自动后台 | 前台超时后 `onTimeout` 触发 | `backgroundTaskId` + `timedOutAfterMs` |
| 用户 Ctrl+B | 终端快捷键 | `backgroundTaskId` + `backgroundedByUser: true` |
| 轮次中止 | abort，且允许 turn-abort 后台化 | `backgroundTaskId` + `backgroundedByTurnAbort: true` |

超时计算（`:223353`）：


### 2.7 heredoc / stdin 的保护（`< /dev/null`）

**问题**：`bash -c "cmd"` 的 stdin 继承了 Claude Code 自己的 stdin（终端或管道的另一头），
一条 `cat` 或 `read` 就会把父进程的输入吃掉，导致会话卡死。

`cDn()` / `uDn()`（`m0591:142806` / `:142823`）：

四条规则，值得逐条复刻：

1. **有 heredoc 就不追加 `< /dev/null`** —— 会截断 heredoc 正文。
2. **已有重定向就不追加** —— `cmd < file` 再变成 `cmd < file < /dev/null` 是语法错误。
3. **跨行引号字符串走单引号包裹 + `'\''` 转义** —— 避免 `"$VAR"` 被外层展开。
4. **Windows 上把 `NUL` 改写成 `/dev/null`**（`fDn`）—— 因为跑的是 Git Bash。

`fDn()` 是很好的例子：**同一份模型输出，在不同平台被翻译成该平台 shell 能懂的形式**，
而不是要求模型记住"Windows 上要写 NUL、Git Bash 里要写 /dev/null"。

### 3.5 Windows 的 shell launcher（长命令绕开 8191 字符上限）

## 6. 沙箱与 Bash 的关系

### 6.1 平台矩阵

| 平台 | 沙箱机制 | 证据 |
| --- | --- | --- |
| Linux / WSL | **bubblewrap**（`bwrap`）+ **socat** 做网络代理 | `m0094:5466`/`5467`（`bwrapPath`/`socatPath` 设置项）、`m0302:32950`（"Sandbox profile has N bwrap arguments and bwrap accepts at most Hf"） |
| macOS | 内置 sandbox（`sandbox-exec` 风格） | `m0191:35163` 附近按机制返回 `"bubblewrap"` 等 |
| Windows | **不强制**（"Bash does **not** yet enforce it"、"Not enforced on Windows hosts"） | `m1764:38430` 的长文案 |

Windows 上沙箱的降级文案（`m1764_0x12ee5476.js:38430`，节选）：

```

...

and only as far as that sandbox goes: keep read-only folders outside writable ones, and use the operating
system's permissions where a folder must not change. The sandbox does not cover a path with `* ? [ ] ( ) { } | +`

```

**这是诚实的文档**：直接写"没覆盖哪些情况"，而不是宣称"沙箱保护一切"。

### 6.2 `sandbox.excludedCommands` 的精确语义

`m0094_0x112cc57f.js:5461`（schema 描述原文）：

```
Command patterns (Bash permission-rule syntax) for commands to run outside the sandbox.
An entry takes a call out of the sandbox only when **every command in the call matches an entry**:
in a Bash pipe or a chain such as `a && b`, each part needs its own match.
Some calls stay sandboxed whatever the entries, such as one with a `cd`, a command substitution,
or a redirect other than a file-descriptor duplication like `2>&1`, a heredoc included.
A convenience, not a security boundary: excluded commands still go through the permission flow.
```

四个精确规则：

1. **每个子命令都要匹配**（`a && b` 里两段都得有人匹配才出沙箱）；
2. **含 `cd` / `$(...)` / 非 `2>&1` 重定向 / heredoc 的调用一律留在沙箱内**；
3. **不是安全边界**（仍然走权限流）；
4. 跨 settings 源**合并**（Merged across settings sources）。

### 6.3 `dangerouslyDisableSandbox` 的三重锁


## 7. 只读判定：为什么"多数命令不弹权限框"

这是 Claude Code 体验上最"现代化"的一块：`ls`、`cat`、`git status`、`grep` 这些**不弹框**，
不是因为它们被硬编码为安全，而是因为有一个**结构化的只读分析器**，能证明"这条命令只读"。

### 7.1 判定入口（`Ydt()`，`m0591:61805`）

```js

  let y = Ah().parse(s),                                    // shell 解析器

  if (S.kind === "too-complex") return {behavior:"passthrough", message: `Not a simple read-only command: ${S.reason}`};
  ...

```

返回值只有两种：`{behavior: "allow"}`（免权限、可并发）或 `{behavior: "passthrough", message}`（走正常权限流）。
**没有"大概安全"这种模糊状态** —— 证明不了就 passthrough。

### 7.2 结构性拒绝清单（先否决，再逐命令判定）

按源码顺序，任一条命中就 passthrough，并给出**具体原因**（这些原因字符串会进日志，不展示给用户）：

| 条件 | 函数/判断 | 拒绝理由（源码原文） |
| --- | --- | --- |
| 命令长度超限 | `s.length > pE` | `Command too long for read-only analysis` |
| 解析成 `too-complex` | `S.kind === "too-complex"` | `Not a simple read-only command: <reason>` |
| 含子 shell | `ZXt(y)` | `Not a simple read-only command: contains a subshell` |
| 含 `&` 后台执行 | `q9t(y)` | ``Not a simple read-only command: `&` defers execution past approval-time checks`` |
| 裸赋值改了非白名单环境变量 | `Zee(bareAssignmentNames, w)` | `Bare assignment to a non-allowlisted environment variable can alter behavior of subsequent commands` |
| 未加引号的变量展开 | `P6e(s) === "variable"` | `Command contains unquoted variable expansion` |
| Windows UNC 路径 | `BI(s)` → **ask**（不是 passthrough） | `Command contains Windows UNC path that could be vulnerable to WebDAV attacks` |
| `cd` + `git` 复合 | `tte(cmd.text)` 且 `OE(...)` | `Compound commands with cd and git require permission checks for enhanced security` |
| 目录像 bare 仓库 | `ISt()` | `The current directory has bare-repo indicators (HEAD/objects/refs outside a .git/ directory). Git may treat it as a git dir and run config/hooks from here, so git commands need approval.` |
| `.git` 是重定向的符号链接 | 同上另一分支 | `The .git file or symlink here redirects to a location Claude cannot verify is safe (it may have been planted by an untrusted archive).` |
| 复合命令造 git 内部文件再跑 git | `Xee(s)` | `Compound commands that create git internal files and run git require permission checks ...` |
| 沙箱开启时在原始 cwd 外跑 git | `pe() !== Ee()` | `Git commands outside the original working directory require permission checks when sandbox is enabled` |

**几条特别值得注意的**：

- **`&` 单独成罪**：`cmd &` 让命令在权限检查返回后继续跑，中间可以改文件 —— 这是典型的 TOCTOU。
- **裸赋值**：`FOO=bar cmd` 里 `FOO` 若不是已知无害变量，可能改变后续命令行为（`LD_PRELOAD`、`GIT_DIR`、`PAGER`…）。
- **裸仓库检测**：在 `HEAD`/`objects`/`refs` 直接躺在 cwd（不是 `.git/` 里）的目录里，
  `git` 会把这个目录当仓库，然后**执行里面的 config 和 hook** —— 一个解压出来的恶意 tar 就能 RCE。
  这条的注释写得很直白："may have been planted by an untrusted archive"。

### 7.3 逐命令判定：白名单 + 参数级校验

`b7e` 的判定细节（`m0293:9010` 起）：

- `--` 之后：若条目 `respectsDoubleDash !== false` 就**停止解析**（后面是文件名/路径），否则继续当 flag 读；

### 7.6 对复刻的直接建议

1. **别做"命令名黑名单"，做"只读证明"**：命令名白名单 + flag 级白名单 + 正则兜底 + git 子命令表，四层；证明不了就走权限流。
2. **先跑结构化 shell 解析**（`bash-parser` 一类），拿到子命令、重定向、env 赋值、子 shell，
   再逐项判定。不要对原始字符串做正则判断（`echo "rm -rf /"` 会误判）。
3. **必须拦的四类结构**：子 shell、`&` 后台、裸环境变量赋值、未加引号变量展开。
4. **危险参数表要细到参数级**：`find -exec/-delete`、`printf` 格式串、`jq` 的 `-f/--rawfile`、
   `sed -i`、`xargs` 的目标命令（`IYo()` 会检查 `xargs` 后面真正执行的是什么）。
5. **`git` 要额外考虑仓库形态**：bare-repo 检测和 `.git` 符号链接检测是防"解压即 RCE"的关键，

## 8. 并发调度：只读并行、写串行

### 8.1 分组算法（`Fd()`，`m0779_0x12409ec4.js:2576`）

```js
function Fd(e, n, s) {                      // e = 本轮全部 tool_use

        A = h?.success ? (() => {
          try { return Boolean(S?.isConcurrencySafe(h.data)) } // ★ 用解析后的数据判定
          catch { return !1 }                                  // 判定抛错 → 当作不安全
        })() : !1;
    if (A && y.at(-1)?.isConcurrencySafe) y.at(-1).blocks.push(r);   // 并入上一个并发块
    else y.push({ isConcurrencySafe: A, blocks: [r] });              // 开新块
    return y
  }, [])
}
```

四个设计点：

1. **先 `safeParse` 再判定**：`isConcurrencySafe` 拿到的是**校验后的入参**，
   不是原始 JSON —— 判定函数可以放心假设字段存在。
2. **抛错 = 不安全**（`catch { return !1 }`）：判定函数有 bug 时降级为串行，不会并发出错。
3. **相邻合并**：连续的安全工具并成一个块，遇到不安全的就切开。
   所以 `[Read, Read, Bash(npm i), Read]` 变成 `[并发(Read,Read), 串行(Bash), 串行(Read)]` —— 
   **保持了模型写的顺序语义**，同时能吃满并行。
4. **每个块内部**（`Ud()`，`:2634`）：

```js
async function* Ud(e, n, s, y) {
  yield* Nxt(e.map(async function*(r) { ... }), Nd())     // Nd() = 并发上限
}
function Nd() { return i.CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY ?? 10 }   // 默认 10
```

串行块走 `Ld()`（`:2597`），逐个执行并 `set_in_progress_tool_use_ids` 更新 UI。

### 8.2 Bash 的特殊之处

```js

isReadOnly(e, n) { return !Iv(Me) && wTt(e, sfo(n)) }          // :222588
```

即 **Bash 是否可并发 = 它是不是只读命令**（§7 那套只读判定）。
所以：

- 一轮里三个 `cat` → 全部并发；
- 一轮里 `cat` + `npm install` + `cat` → 第一个 `cat` 单独串行块（因为后面是不安全的），
  `npm install` 串行，最后一个 `cat` 串行。**这是刻意的顺序保守**：
  不确定后一条命令是否依赖前一条的副作用时，不并发。

`Read` 恒为安全（`m0591:147157` 附近 `isConcurrencySafe() { return !0 }`），
`Glob`/`Grep` 也是（`backgrounding: "never"` + 只读）。
`Write`/`Edit`/`NotebookEdit` 不安全（会改文件），串行。

### 8.3 上下文合并（`B_e()`）

并发块里每个工具可能产生 `contextLayers`（例如 `Read` 读到的文件被登记进 readFileState）。
`us()`（`:2521`）在块结束后统一 `r = B_e(r, M)` 合并，**避免并发写同一个 context 对象**。
这是"并发执行但状态更新串行"的标准做法。

## 12. AskUserQuestion：会"打断"的工具怎么设计

模块 `m0403_0x119fe322.js`（纯提示词模块）。

### 12.1 定位约束（`X_s` / `A$i`，`:38` / `:60`）

```
Use this tool only when you are blocked on a decision that is genuinely the user's to make:
one you cannot resolve from the request, the code, or sensible defaults.
...
Reserve this for decisions where the user's answer changes what you do next — not for choices with a
conventional default or facts you can verify in the codebase yourself. In those cases pick the obvious
option, mention it in your response, and proceed.
```

**这条规则直接写进了工具的 prompt**，所以模型不会拿它当"确认按钮"。

### 12.2 三种问题类型（`R$i`，`:52`）

```
- Omit "kind" for an ordinary choice question.
- Use "kind": "text" for an open-ended question (a text box, no options).
- Use "kind": "number" with "min"/"max" (optionally "step", "defaultValue", "unit") for a quantity.
- Prefer choices whenever the likely answers can be listed.
- Do not add "Other" or "Skip" options: the user can always type their own answer or leave a question unanswered.
```

`Do not add "Other"/"Skip"` 是关键：这两个由 UI 保证，模型加会重复。

### 12.3 "用户要求再来一轮"的协议（`kZt` / `v$i`，`:12`）

```js
var kZt = "The user asked for more questions",
    v$i = `${kZt} before answering; this is a request for another round, not an answer.`;
```

也就是用户可以不回答、而是说"再多问几个" —— 结果里带这个标记，模型据此**再调一次本工具**。
这是把"人机对话"建模成**可循环的协议**，而不是一次性的问答。

### 12.4 转录层面的三个新概念

- **`unanswered`**（`m0165:10190` 的 capability 描述）：
  `annotations[question].unanswered` 可取 `'skipped' | 'replied_in_chat' | 'dismissed'`，
  工具结果会回显。**"没答"和"答了"是不同状态**，模型能据此决定是否继续等。
- **capability 协商**：`ask_user_question_unanswered_v1` 是能力名，
  旧 CLI 不支持时**整份答案会被拒**（"an older CLI on a strict host refuses the whole answer"），
  而不是静默丢字段。
- **`k$i = 12`**（`:10`）：问题/选项数量上限（4 问 × 最多 4 选项的约束在 schema 里，12 是别的计数上限）。

### 12.5 preview 的双格式（`T$i`，`:24`）

同一个字段 `preview` 在 **markdown 宿主**和 **HTML 宿主**里语义不同：

| 宿主 | 允许内容 |
| --- | --- |
| markdown | 任意 markdown（ASCII 图、代码片段、表格），等宽框内渲染 |
| html | 自包含 HTML 片段，**不许 `<html>/<body>/<script>/<style>`**，只能内联 style |

而且明确："previews are only supported for single-select questions (not multiSelect)"。
**同一份工具定义按宿主给出不同约束**，而不是让模型猜。

### 12.6 一个容易被忽略的细节（`x$i`，`:62`）

```
The user may see only the question dialog: tool results and text you wrote earlier in this turn may not be
on their screen while it is open. Make each question stand on its own: if it depends on something you found,
say so briefly, and name the items you are asking about in the question itself.
```

**它承认 UI 是模态的**，并据此要求每个问题自包含。这是"工具设计和 UI 现实对齐"的好例子 ——
很多 agent 框架在这里出错，问出"上面说的那个要改吗？"这种脱离上下文的问题。

## 13. 工具渐进式披露（ToolSearch / deferred tools）

### 13.1 为什么需要

工具多了以后，把所有 tool schema 塞进系统提示代价太大（CC 有 20+ 内置 + 任意多 MCP 工具）。
Claude Code 的解法：**工具可以声明 `shouldDefer: true`，默认不进系统提示，模型按需检索加载**。

源码里多处可见这个字段（`m0591:107218` WebFetch、`m0591:213281` NotebookEdit、
`m0806` 三个、`m0816` 多个），以及对立的 `shouldDefer: !1`（Glob 等常驻）。

### 13.2 开关逻辑（`m0275_0x11744206.js`）

```js

  if (o === 0) return "tst";                       // auto:0  → 全 defer
  if (o === 100) return "standard";                // auto:100 → 全常驻
  if (S(e)) return "tst-auto";                     // auto / auto:N
  if (Pe(e)) return "tst";                         // "true"/"1" 之类
  if (rs(e)) return "standard";                    // "false"/"0"
  return "tst"                                     // 未设 → 默认 defer
}

function WTs(e) {                                  // :175 解析 auto:N
  if (!e.startsWith("auto:")) return null;
  let o = Qf(e.slice(5));
  if (isNaN(o)) return t(`Invalid ENABLE_TOOL_SEARCH value "${e}": expected auto:N where N is a number.`), null;
  return Math.max(0, Math.min(100, o));            // clamp 到 [0,100]
}
```

`auto:N` 是**渐进阈值**：工具数量超过 N% 的可用预算时开始 defer。
`GRr()`（`:47`）还要求 `Te() === "firstParty"`（只有官方 API 才启用），
第三方网关/Bedrock/Vertex 上默认不 defer —— 因为它们的 tool schema 缓存行为不同。

### 13.3 select 语法

```

ToolSearch("+slack send")                         // 必须含 "slack"，按剩余词排序
```

`select:` 是**精确点名**，逗号分隔，一次可加载多个。提示词里反复强调要批量加载
（`m0275:70` 附近）：

```

load every tool you expect to need in ONE ToolSearch call — the select query accepts a comma-separated list —
never one call per tool. ... Do NOT load tools one at a time; each separate ToolSearch call wastes a full round-trip.
```

**"每个 ToolSearch 调用浪费一整个往返"** —— 把成本讲清楚，模型就会批量。

### 13.4 `searchHint`

每个工具的 `searchHint`（§1.1）就是这个检索用的索引文本。
`m0591:77419`：`if (e.searchHint) return e.searchHint;` —— 有 hint 用它，否则退化到描述。

**这是给复刻的直接建议**：如果要实现工具渐进披露，
每个工具都应该有一个**短的、面向检索的 hint**（"execute shell commands"），
而不是拿完整 description 去做向量检索。

## 14. 其它值得注意的工具机制

### 14.1 `REPL` / `JavaScript`

## 15. 路径安全层（所有文件工具的共同底座）

模块 `m1551_0x12c8430b.js`（导出 80+ 个路径相关函数）是文件工具的公共依赖，值得单列。

### 15.1 危险目录表（`m0293_0x1177df9f.js:9738`）


写这些目录里的文件会导致**后续任意代码执行**：
`.git/hooks/*`、`.vscode/tasks.json`、`.husky/pre-commit`、`.devcontainer/*`、`.yarn/plugins`
—— 所以它们需要额外确认，而不是"在工作目录内就放行"。

### 15.2 大小写归一的国际化细节（`To()`，`:9742`）


`\u0131` 是土耳其语无点 ı，`\u017f` 是长 s ſ。**Windows 文件系统大小写不敏感**，
所以路径比较必须先归一；但 JS 的 `toLowerCase()` 在土耳其语 locale 下会把 `I` 变成 `ı`，
导致 `README` 和 `readme` 比对失败。这两行是"路径比较国际化 bug"的补丁。

1. **先解析成真实路径再判定**：`realpath` + 拒绝含 `..` 的段 + 拒绝 NT 设备路径。

3. **区分三类根**：工作目录、额外允许目录、受信任网络根。规则要对"相对哪个根"分别匹配。
4. **符号链接单独处理**：写操作要检查**叶子节点的符号链接**（`leafSymlinkWriteRefusal`），

六个稳健性细节：

1. **默认拒绝写符号链接**（`Refusing to write through symlink`），要写就显式给真实路径。
   这堵住了 `ln -s /etc/passwd x; write x` 这类逃逸。
2. **`wx` 独占创建**：临时文件已存在就失败，避免 pid 复用导致的串写。
3. **保留原文件权限**（`chmod` 到 temp 再 rename），换写法不会把 `0755` 变 `0644`。
4. **`fsync` 容忍不支持**（某些网络文件系统），且失败**不中断**（"fsync failed, and the write stands"）。
5. **硬链接保护**：`p.nlink > 1n && (r.refuseHardLinkedInPlace ?? zFr())` → 抛 `DFr`。
   改一个硬链接会让**所有链接**看到变化，可能是意外的。
6. **in-place 回退**：rename 不行时（如某些 Windows/网络盘）改原地写，仍然 fsync + 校验，
   且失败时**把新内容留在 temp 路径并告诉用户**（`The new content was preserved at ${w}`）。

**这也解释了 §17.6 的两道写后校验为什么必要**：in-place 回退路径没有 rename 的原子性保障。

### 17.10 Edit 的匹配容错（`m0520_0x11b936b1.js:254`，这是最值得抄的一处）

模型写 `old_string` 时经常犯两类错：**引号形状不对**（文件里是弯引号 `“”‘’`，模型写直引号 `"'`）
和 **Unicode 转义形式不同**（文件里是字面 `é`，模型写 `\u00e9`）。Claude Code 的处理是**自动纠正**：

```js

var A = "\u2018", m = "\u2019", y = "\u201C", T = "\u201D";        // 弯引号
function b(e) { return e.replaceAll(A,"'").replaceAll(m,"'").replaceAll(y,'"').replaceAll(T,'"') }

```

**关键是 `hWe` 返回的是"文件里的真实片段"**，不是模型给的那份。后续替换用真实片段做锚点，
所以替换后的文件保留原有引号形状。

反过来，`Mmr()`（`:254`）负责把 **`new_string` 的引号风格对齐到文件**：


**文件的 old 区域是 literal，模型写了 `\u` 转义，就把 new_string 也 unescape 成 literal**。
两个方向都处理了，靠"文件里实际是什么"决定。

### 17.11 三条实用结论

1. **不要因为 `old_string` 不匹配就报错**。先做弯引号归一、`\u` 转义归一，再判断唯一性。
   这一步能消掉模型相当大比例的 "String to replace not found" 失败。
2. **用文件里的真实片段做替换锚点**，用 `new_string` 做内容 —— 两者分开处理，
   不要拿模型给的 `old_string` 去 replace。
3. **替换的引号/转义风格要跟着文件走**，否则每次编辑都会把文件的排版风格搞乱。

### 20.7 新增：Write 强制 LF，Edit 保留原行尾

原稿 §4.7 说"写回时保持文件原行尾"，**这只对 Edit 成立**：

- **Write 硬编码 LF**：`VSt(ioPath, n, At, "LF")`（`m0591:73996`）→ `XHe(text, "LF")` 不转换（`m0099:630`）。

- **Edit 保留原行尾**：`VSt(ioPath, newContent, encoding, lineEndings)`（`m0591:213051`），

### 20.8 新增：Write 的 `fXt`/`Vxt`/`pio` 不是 checkpoint

| `fXt(...)` | **只是遥测**：`l("tengu_file_changed", ...)`，产 `{lines_added, lines_removed}` | `m0432:380` |
| `Vxt(e, n, r)` | **空实现**：`let s = bt().vscodeClient; return` | `m0591:71247` |

### 20.11 新增：Grep 的输出格式细节

`content` 模式走 `rg --json`，`nJo()`（`m0591:75766-75812`）解析成 `path\0line: text`：

- `type:"match"` 用 `:`，`type:"context"` 用 `-`（这就是 §17.21 那个 `[:-]` 的来源）；
- 不同文件或行号不连续时插入 `--` 分隔行；
- 单行 > 500 字符 → 匹配行为 `[Omitted long matching line]`，上下文行 `[Omitted long context line]`；
- `type:"end"` 且带 `binary_offset` → 追加 `<path>\0binary file matches (found "\0" byte around offset N)`，
  并丢弃该文件此前的中间行。

`files_with_matches` 模式：`--null` 输出后用 `Buo()`（`m0302:39780`）按 `\0` 切分，
**再按 mtime 降序重排**（`m0591:75708-75713`，相同则 `localeCompare`）—— 这不是 rg 的顺序，
是工具自己排的（最近的改动在前）。

三种模式的收尾文案：

| 模式 | 文案 |
| --- | --- |
| `content` | 内容 + `[Showing results with pagination = limit: N, offset: M]`；无结果 `No matches found`；offset 越界 `No entries at this offset` |
| `count` | 逐文件 `path:N`，末尾 `Found X total occurrences across Y files.` |
| `files_with_matches` | `Found N file(s) [limit: N]` + 路径列表；N=0 → `No files found` |

#### 21.8.1 结论错误：`gOn` 不是"不可绕过的内置 deny 集"

早先 §7（权限链第 1 级）、§20.3、§20.21 都说 `gOn` 是"内置 deny 表，`bypassPermissions` 也压不住"。
读 `m0591:140474-140486` 全函数后确认**这个说法不成立**：

```js
function gOn(e, n, r, s = !1) {
  let h = se(r);
  if (o8e(h) && !Gq(e) && !(...)) return { behavior:"deny",
    decisionReason:{ type:"other", reason: YCn },     // YCn = "tools_held_until_a_person_types"
    message: eeo(e.name) };                            // "Tool calls are paused ... until the user sends a new message"
  let y = lo(h, e);                                    // ← 查 alwaysDenyRules，不是内置表
  return y === null || ("classifierOnly" in e && Ybe(e, n, r, s)) ? void 0
    : { behavior:"deny", decisionReason:{ type:"rule", rule: y }, message: `Permission to use ${e.name} has been denied.` }
```

两支都不是"内置工具黑名单"：
**①会话冻结**（`o8e` 读 settings 的 `toolsHeldUntilAPersonTypes`，`m0591:67330`）；
**②用户配置的 deny 规则**（`lo`，`m0288:764`，内部走 `alwaysDenyRules`）。

那"什么能压过 `bypassPermissions`"的正确答案是：**会话冻结**和**deny 规则**，
两者都不是"某个内置表"。原文把机制拟人化成一个不存在的表，属于过度概括。

额外发现：`Gq(e)`（`m0288:576`）是"整工具豁免"判据 ——
`!e.mcpInfo && ce.has(e.name)`，而 `ce` 只含 `EndConversation` 一个工具名（`m0288:574`）。
所以**唯一能跳过 deny 规则的工具是 `EndConversation`**，且必须不是 MCP 工具。
