# CC 压缩可取消 + 中断不丢原文：机制核实

> 用户记忆核对：「CC 源码中好像就算遇到了自动压缩，按 Esc 仍然能取消压缩」。
> **核实结论：记忆是对的，而且比记忆更彻底 —— CC 做了三层保护。**
>
> 全部【S】级：源码字面 + 行号可复算。

---

## 0. 结论先行

CC 在压缩被中止时做了三件 GA 完全没做的事：

1. **中止信号贯穿压缩全程** —— `abortController.signal` 从调用方一直传到摘要器内部，
   在多处检查点生效；
2. **中止后主动丢弃已算完的结果** —— 即使摘要已经成功返回，只要 abort 被触发，
   结果会被改成 `ok: false`，**历史不会被替换**；
3. **总结请求「交出去续跑」** —— 用户按 Esc 时，那个还没跑完的摘要请求不会被杀，
   而是转交给预计算缓存继续跑完，下次压缩可直接复用。

第 3 点正是你说的「让下次压缩能在上次中断的基础上重新执行」。

## 2. 第二层：已成功但已中止 → 结果作废【S】

这是最反直觉、也最关键的一段（`m0591:105155`）：

```js
if (ne.ok && n.toolUseContext.abortController.signal.aborted) ne = {
  ok: !1,
  reason: "aborted",
  attempts: ne.result.attempt,
  totalGroups: ne.result.totalGroups
};
```

【S】注意条件顺序：`ne.ok && ...aborted`。即**摘要明明成功了，只要用户按过
Esc，就把 `ok` 强制改成 `false`**。

为什么这样做【A】：压缩的语义是「用户接受这次历史替换」。用户已经喊停，
就不该在他不知情的情况下替换历史 —— 哪怕算完了。

紧接着 `if (!ne.ok)` 分支（`m0591:105161`）只做遥测上报，然后
`return { ok: !1, reason: ne.reason, detail: ne.detail }`（`:105192`），
**不进入 `vno(...)`**。只有 `ne.ok` 为真才走 `:105198` 的
`return vno({ compactResult: ne.result, ... })` → 应用压缩结果。

⇒ **中止后历史保持原样。**

## 3. 第三层：摘要请求交出去续跑并缓存【S】

这是 `cyn` 函数（`m0591:104710`）：

```js
async function cyn(e, n, r) {
  let s = n.toolUseContext,
      h = s.abortController.signal;          // 用户的 abort 信号
  if (h.aborted) return e(n);
  let y = Xn(),                               // 新建**独立** controller
      S = wno(s.onRetryStatus, h),
      w = performance.now(),

      });

        N.then(() => !1, () => !1),
        new Promise((Y) => { h.addEventListener("abort", () => Y(!0), { once: true }) })
      ])) return N;                           // 压缩先完成 → 正常返回

  // 用户先按了 Esc ↓
  try {
    let Y = s.session.precompute,
        ke = Dwe(s.agentId),
        ne = EJi(h.reason) && !Y.has(ke) ? r.readSent() : void 0;
    ...

      status: "pending",
      coverage: s$r(ne, ve),
      preCompactTokens: r.preCompactTokens,
      model: s.options.mainLoopModel,
      startedAt: w,
      abortController: y,        // ← 用的是那个**独立** controller，没被中止
      preCompactHookDisplay: r.hookDisplay,
      armTrigger: "stop",
      ...
    }), { ok: !1, reason: "aborted", attempts: 0, totalGroups: 0 }
```

【S】三个要点：

1. **压缩用的是新建的 `y = Xn()`，不是用户的 signal** —— 所以用户按 Esc
   只中止了「等待」，没有杀掉摘要请求本身；
2. 用户按 Esc 后，把请求存进 `session.precompute`，状态 `"pending"`；
3. 交给它的是一个**独立的 abort controller**，因此后续可以继续跑完。

后续回调（`m0591:104740-104770`）：

```js
settled: N.catch(...).then((Re) => {
  if (Re?.ok) g("compact_kept_through_stop");        // 遥测：中断后仍算成功
  else c("compact_kept_through_stop", y.signal.aborted ? ... : Re?.reason ?? "threw");
  let xe = Y.get(ke);
  if (xe?.status !== "pending" || xe.abortController !== y) return;
  if (Re?.ok) Y.put(ke, { ...xe, status: "ready", result: Re.result, readyDurationMs: ... });
  else Y.remove(ke)                                   // 失败就移除，不留坏缓存
})
```

【S】算完之后状态从 `"pending"` 变 `"ready"`，结果存在缓存里。
失败则 `remove`，不留脏数据。

### 3.1 但「交出去续跑」是有门禁的【S】

`cyn` 只在 `handOverAtStop` 非空时才走（`m0591:105148`）：

```js

  ...r.handOverAtStop,
  preCompactTokens: s
})
```

而 `handOverAtStop` 在调用方被一个复合条件 `Do` 门禁（`m0591:104949`）：

```js

  readSent: () => ({ messages: h, rowUuids: mCe(h) }),
  hookDisplay: Lo.userDisplayMessage
} : void 0,
```

`Do`（`m0591:116350`）：

```js

     && Mde(Mo, n.agentId)
     && e.findLast(ar => ar.type === "user")?.uuid === i$r(e)
```

逐项【S】：

| 项 | 含义 |
| --- | --- |
| `!So` | 未被硬性判为 `level === "blocked"`（没有严重超窗） |
| `!ne` | `keepNoRound` 为假 |
| `ot === void 0` | 手上**还没有**可用的预计算结果 |
| `!gt` | 无其他前置阻断 |
| `Sn === 0` | `consecutiveRapidRefills === 0`（没有连续快速回填） |
| `Mde(Mo, n.agentId)` | `agentId === undefined && Rfe(Mo)` ⇒ **只在主 agent**（`Rfe` = `e===void 0 \|\| ls(e)==="main"`，`m0191:18008`） |
| `lastUser.uuid === i$r(e)` | 最后一条真实用户 prompt 就是最后一条 user 消息（没有悬空的助手回合） |
| `Afs()` | 开关 `tengu_serene_rain` **且** `precomputeCompactionEnabled`（`m0522:85`/`:28`） |

【A】所以第二层/第三层保护（结果作废 + 交接续跑）**在自动压缩的主路径上是开着的**，
但门禁说明这是**有条件启用的优化**，不是无条件行为。
不过**第一层的「中止 → 不替换历史」不受门禁影响**：`m0591:105155` 那段在
`Ers` 里无条件执行，跟 `handOverAtStop` 无关。

⇒ 对你的问题而言：**「Esc 能取消压缩、原文还在」是无条件的；
「中断的成果能被下次复用」受门禁与开关约束。**

## 4. 下次压缩如何使用这份「中断时留下的成果」【S】

`hOo`（`m0040:2193`），在 `m0591:104834` 被调用：

```js
let ko = S && hOo({
  coverage: S.coverage,
  kept:   S.compactResult.messagesToPreserve,
  sent:   { messages: h,      rowUuids: mCe(h) },
  received: { messages: Tn,   rowUuids: mCe(Tn) },
  instructions: vn
});
if (ko?.kind === "refuse") {
  if (S?.reportRefused(ko.reason), e.precomputedOnly)
    return At = !0, { skip: "the ready summary no longer fits the conversation" };
}
if (S !== void 0 && ko?.kind === "reuse") {
  let Mo = ko.tail;
  ...
}
```

【S】校验三样东西是否仍然吻合：
- `coverage`（上次覆盖到哪一行、哪些 uuid 已见过）
- `kept`（上次保留的消息）
- `sent` / `received` 的 `rowUuids`（内容指纹）
- `instructions`（hook 是否重写过消息）

### 4.1 六条拒绝理由，逐条【S】

`hOo`（`m0040:2193`）全文只有 6 个 `refuse` 出口，全读完如下：

| # | `reason` | 判定式 | 含义 |
| --- | --- | --- | --- |
| 1 | `boundary_uuid_missing` | `!sentUuids.has(coverage.lastUuid)` | 上次覆盖到的最后一条消息已不在待发列表里（被删/被改了） |
| 2 | `covered_messages_changed` | `!coverage.rowUuids.every(u => sentUuids.has(u))` | 上次覆盖过的消息里有缺失 |
| 3 | `kept_message_missing` | `kept.some(k => seen(k) && !sentUuids.has(k.uuid))` | 上次说好要保留的消息不见了 |
| 4 | `unseen_reply` | 边界之前存在 `type==="assistant" && !Ub(m) && !seen(m)` | 出现了上次摘要**没见过**的助手回复（即摘要已过期） |
| 5 | `hook_rewrite` | `instructions \|\| !received有lastUuid \|\| received.rowUuids !== f` | 有 hook instructions，或收到侧行指纹与发出侧前缀不一致 |
| 6 | `would_not_fit` | `x?.givesWay`（`Ct(fit, ...)`） | 复用后的组合仍超出窗口 |

全部通过才返回：

```js
return { kind: "reuse", tail, earlyTailCount, displayOnlyLeftOutCount,
         headReordered: !_e(received.rowUuids, coverage.rowUuids), sizes };
```

【S】`tail` 是 `received` 里边界之后、去掉 `progress` 条目后的消息 ——
即「上次摘要之后新产生的对话」直接接在旧摘要后面。

【A】第 4 条 `unseen_reply` 最关键：只要上次摘要之后又跑出新的助手回复，
旧摘要就作废。这正对应你说的场景 —— 中断后如果用户又聊了几轮，
下次压缩会重新算；**如果没聊，就直接复用上次已算好的摘要**。

### 4.2 判定结果

| `kind` | 动作 |
| --- | --- |
| `"reuse"` | **直接复用**，不重新请求 LLM |
| `"refuse"` | 丢弃预计算，重新压缩；若 `precomputedOnly` 则 `skip` 并报原因 |

【A】这就是「下次在上次中断的基础上重新执行」的完整机制 —— 而且做了严格的
正确性校验：对话变了就不复用，防止拿旧摘要覆盖新历史。

## 5. GA 对照：三层只沾了半层

| 能力 | CC | GA（已核实） |
| --- | --- | --- |
| 中止信号传入压缩 | ✅ `abortController.signal` 全程 | ❌ 无（`compact_agent_context` 签名里没有 signal，`context.py:433`） |
| 中止后丢弃结果 | ✅ `ne.ok && aborted → ok:!1` | ❌ 无此逻辑 |
| **失败时历史不变** | ✅ 结果作废，不进入 `vno` | ✅ **有**（`context.py:576` 的 `except` 里显式回滚，见 §5.2） |
| 请求交出去**续跑** | ✅ `cyn` 把在跑的请求交给 `precompute`（`status:"pending"`） | ❌ 预计算是**同步阻塞**算完再存，没有"在跑"这个状态 |
| 复用前校验 | ✅ `hOo` 6 条（§4.1） | ⚠️ `_take_precomputed` **3 条**（§5.3） |
| 压缩期间 Esc 可用 | ✅（异步事件流） | ❌ **不可用**（bridge 单线程被占，已实证延迟 2.00s） |

【A】GA 最大的差距不是「没有 precompute」（它有），而是
**压缩占用 bridge 命令循环导致 Esc 根本传不进去** —— 连"取消"这个动作都发不出来。
第二差距是它没有「中断」这个语义，所以 §6 那套保护无从谈起。

## 6. 对你提的「数据丢失」的直接回答

你担心的是：压缩失败 / 无法停止 → 数据丢失。

**CC 的保证**：
- 中止时**不替换历史**（§2）→ 原文天然还在；
- 摘要请求不浪费（§3）→ 下次可直接复用；
- 复用有严格校验（§4）→ 对话变了就不复用，不会拿旧摘要覆盖新历史。

**GA 的现状**：
- 压缩发生在 bridge 命令循环里，Esc 传不进去（已实证）；
- **原文不会丢**：`compact_agent_context` 在函数入口 `deepcopy` 了
  `backend.history`（`context.py:445`）与 `agent.history`（`:458`），
  任何异常都在 `except` 里显式回滚（`context.py:574-580`）→ 见 §5.2；
- 但它**没有「中止」这条路** —— 没有 signal，也就谈不上"取消"。
  唯一的"停止"方式是进程被杀，那就和 CC 的可取消完全不是一回事。

## 5.2 GA 失败时是否保证历史不变【S】

`compact_agent_context` 的入口先把要改的东西全部 `deepcopy` 一份（`context.py:445`/`458`）：

```python
old_backend_history = copy.deepcopy(getattr(backend, "history", []) or [])
...
old_agent_history = copy.deepcopy(getattr(agent, "history", []) or [])
...
old_last_tools = copy.deepcopy(getattr(client, "last_tools", "")) ...
```

然后整段实质工作在 `try:` 里，`except` 是（`context.py:574`）：

```python
except Exception as exc:
    backend.history = old_backend_history
    if hasattr(agent, "history"):
        agent.history = old_agent_history
    if client is not None and hasattr(client, "last_tools"):
        client.last_tools = old_last_tools
    return CompactResult(False, _exception_message(exc))
```

【S】摘要请求抛异常 / 返回空串（`raise RuntimeError("compact summary is empty")`）
都会走到这里，历史被还原成压缩前。

【A】但**回滚不完整**：`backend.history` / `agent.history` / `client.last_tools`
回滚了，而 `backend.last_usage_tokens`、`agent.handler`、`_PRECOMPUTED_KEY`
是在 try 块**成功路径**里改的 —— 异常时这些没被改过，所以不需要回滚；
但 `compact_working_state` 相关字段已经算出来了、没写回，也无害。
⇒ **结论：GA 在"失败"这一路径上是安全的，原文不丢。**

真正的问题不是"失败丢原文"，是**"成功但用户不想要"没有出路** ——
用户按不了 Esc，只能等它跑完，然后接受一次他没同意的历史替换。

## 5.3 GA `_take_precomputed` 的 3 条校验【S】

`context.py:307`，比 CC 的 6 条**弱得多**：

| # | 条件 | 失败动作 |
| --- | --- | --- |
| 1 | `coverage > 0`、`summary` 非空、`len(history) >= coverage` | 清缓存，返回 `None` |
| 2 | `cached["instructions"] == instructions` | 同上 |
| 3 | `_history_fingerprint(history[:coverage])` 与缓存一致（整段前缀的 sha256） | 同上 |

【A】第 3 条其实**比 CC 更严格**：它是对整个前缀做 sha256，
任何一处字节改动都失效；CC 的 `hOo` 是按 uuid 粒度查，允许"边界之后追加"。

但 GA 缺了 CC 的这几条：
- 无「上次摘要之后有没有新的助手回复」检查（CC 的 `unseen_reply`）；
- 无「复用后是否还装得下」检查（CC 的 `would_not_fit`）；
- 无「hook 是否重写过消息」检查（CC 的 `hook_rewrite`）。

【A】不过 GA 的预计算**只在回合边界算、只覆盖 `len(history)-kept_tail` 的前缀**，
且 sha256 兜底，所以实际风险不大 —— 真正缺的是
**"中断时把在跑的请求转成 pending 缓存"这个能力**，不是校验强度。
