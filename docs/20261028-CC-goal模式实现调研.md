## 1. 结论先行

CC 303 的 **goal 模式不是一套独立子系统，而是一层“会话级 Stop hook + 活跃目标状态机”**：

- “设一个目标”等价于**向当前会话注册一条 session-scoped `Stop` hook**，hook 的 `prompt` 就是目标的完成条件文本；
- 这个 Stop hook 会在**每次回合要结束（stop）时被求值**；求值是一个独立的**模型（prompt-hook evaluator）**只读
  会话转录、判断“条件是否已满足”，回答 `{ok, reason, impossible?}`；
- 未满足 → 阻塞 stop、把原因注入会话并继续工作（`preventContinuation` / `blockingError`）；
- 满足（`ok:true`）或判定不可达成（`impossible:true`）→ 移除该 Stop hook、清空 `activeGoal`、落一条 `goal_status` 附件；
- 后台任务仍在跑时求值会**推迟**，并周期性注入“goal check-in”消息；用户中途打断时会**自动重试注入**；
- 两个入口：用户输入的 `/goal <条件|clear>` 斜杠命令；以及模型主动提议的 **`ProposeGoal` 工具**（带一键审批对话框）。

一句话：**“目标 = 一条带 prompt 的会话级 Stop hook；达成检测 = 一个专用的只读模型求值器。”**

### 1.1 端到端链路（一句话版）

```text
/goal <条件> 或 ProposeGoal 工具
   │  设置：注册 session Stop hook(prompt=条件) + appState.activeGoal 状态
   ▼
每次回合终止（stop / loop_tick / blockable_turn_end / fork_dispatch）
   │  执行 Stop hooks；命中目标 hook 时
   ▼
prompt-hook evaluator（独立模型, 只读转录, 返回 {ok, reason, impossible?}）
   │
   ├─ ok:true         → 移除 hook + 清 activeGoal + 写 goal_status{met:true}
   ├─ impossible:true → 同上，写 goal_status{met:false, failed:true}
   ├─ ok:false        → 阻塞(stop) + 保留目标 + 注入 reason + iterations++ / lastReason 更新
   ├─ 后台任务在跑    → 推迟求值 + 定时 goal check-in 注入
   └─ 超时/错误       → 记 goal_met/evaluator_* 遥测，按 cancelled/error 处理
```

## 3. 核心状态机：`activeGoal` + session Stop hook（`m0274_0xe951929.js`）

这是 goal 模式的“心脏”，全文件仅 200 行，逻辑很集中。

### 3.1 `activeGoal` 结构与设置（`rmt`）

设置目标时（无论来自 `/goal` 还是工具直设），统一走 `rmt(condition, ctx, origin)`：

```js
let activeGoal_2 = {
  condition: t,          // 目标条件文本（即 Stop hook 的 prompt）
  iterations: 0,         // 已求值轮数
  setAt: Date.now(),     // 设置时刻（用于 durationMs 结算）
  origin: origin_2,      // "user" | "proposal_direct" | "proposal_approved"
  tokensAtStart: Th()    // 起始 token 计数（用于 tokens 结算）
};
```

`rmt` 做的事（按源码顺序，`m0274:142-174`）：

1. `O(t, e)`：若 appState 里有匹配该条件的 `queuedGoalOrigin`，取出并清掉它，作为本次 origin，否则按“user 手输”处理；
2. `Dsn()` 门禁（详见 §3.3），非空则记 `goal_set` 并返回错误消息；
3. 若已有 `activeGoal`，先发 `tengu_goal_cleared`（`superseded`——被新目标顶替）；
4. **清掉旧的目标 Stop hook**（`j1e` 找 `Stop` 事件下 `matcher==""` 且 type 为 `prompt` 的 hook 全部移除）；
5. **注册新 Stop hook**：`sessionHooksRegistry.add(sessionId, "Stop", "", { type:"prompt", prompt: t })`；
6. 写 `appState.activeGoal`，并 `applyMessageOp` 追加一条 **`goal_status` 附件（sentinel）** `COr(false, t)`；
7. 发 `tengu_stop_hook_added`（`via:"goal"`）与 `goal_set` 遥测，返回 `null`。

> 重要：**设置目标并不直接设任何“开关”，只是往 hooks 注册表塞了一条 prompt Stop hook。**
> Stop hook 的 `prompt` 就是条件；之后每次要停，引擎都会去求值这条 prompt。

### 3.2 清除（`omt`）与 clear 词表（`nmt`）

- `omt(ctx)`：把 `Stop` 事件下所有 goal 型 prompt hook 移除，若 `activeGoal` 存在则记 `tengu_goal_cleared`（`user_clear`）、
  清空 `activeGoal`，再追加一条 cleared 的 `goal_status` 附件，返回被清条件的文本。
- `nmt(t)`：clear 关键字检测，命中则走清除分支：`{"clear","stop","off","reset","none","cancel"}`（`m0274:80`）。

### 3.3 门禁 `Dsn()`（`m0274:110-124`）

设置前必须通过三关，任一不过即拒绝并给出具体文案：

| 关卡 | 判断 | 返回 |
| --- | --- | --- |
| hooks 门禁 | `kae()`（`disableAllHooks` / `allowManagedHooksOnly` 由设置或策略打开） | “/goal can't run while hooks are restricted…” |
| org 设置未就绪 | `SO()`（`WNt()` 已读到 org 设置 + `v_()==="unanswered"`，即 hooks 权限仍是"未回答"） | “/goal can't run yet: your organization's settings haven't been read…” |
| trust 门禁 | 交互式(`!we()`) 且非 trusted(`!Ms()`) 时拒绝 | “/goal is only available in trusted workspaces…” |

所以 **goal 只存在于交互式、可信工作区且 hooks 未被禁用/受限的会话**。

### 3.4 会话 transcript 的 `goal_status` 附件（`VVn` / `COr` / `EAo` / `Msn`）

`goal_status` 附件是目标状态在会话消息流里的载体，函数互相配合：

- `VVn(met, condition)` → `{type:"goal_status", met, sentinel:true|…, condition}`；
- `COr(met, condition)` → 包装成带 `uuid` / `timestamp` 的 `attachment` 消息（`m0274:193-200`）；
- `Msn(msgs)` → 从后往前找最近一条**尚未达成/未失败**的 `goal_status` 条件文本（求值前后判断“是否还挂着目标”）；
- `EAo(msgs)` → 从后往前找最近一条**非 sentinel** 且满足/结束的 `goal_status`，返回 `{condition, iterations, durationMs, tokens}`（用于恢复此前达成过目标的状态）。

### 3.5 kickoff 系统提示 `qVn`（`m0274:98`）

设置成功并注入会话的“开跑”提示词原文（节选）：

> A session-scoped Stop hook is now active with condition: “…”. Briefly acknowledge the goal, then immediately
> start (or continue) working toward it — treat the condition itself as your directive and do not pause… The hook
> will block stopping until the condition holds. It auto-clears once the condition is met — do not tell the user to
> run `/goal clear` after success; that's only for clearing a goal early.

这解释了模型何时知道“有个目标在盯我”：目标设置那一刻，系统已经把这条 kickoff 作为用户侧元消息排队注入。

## 4. 两个入口

### 4.1 用户入口：`/goal` 斜杠命令

#### 声明（`m1247_0xfbd7712.js`）

```js
// local-jsx（交互 UI 用）
{ type: "local-jsx", name: "goal",
  description: "Set a goal Claude checks before stopping",
  argumentHint: "[<condition> | clear]", immediate: true }
// local non-interactive（--print 等）
{ type: "local", name: "goal", supportsNonInteractive: true,
  thinClientDispatch: "post-text",
  description: "Set a goal — keep working until the condition is met",
  isHidden: () => !we(), isEnabled: () => we() || Bn(),
  load: () => import(".../chunk-kr8fsq5z.js") }
```

要点：交互版是 `immediate`（输入即执行）；非交互版 `supportsNonInteractive`，加载 handler（`m1927`）。

#### 处理器（`m1927_0x108e5d7b.js:122-158`）三分支

```js
let e = raw.trim();
if (e === "")        // /goal（无参）→ 状态查询
   → activeGoal ? "Goal active: {condition} ({iterations} turns){lastReason}" : "No goal set. Usage: `/goal <condition>`"
if (nmt(e))          // /goal clear|stop|off|reset|none|cancel → 清除
   → omt(ctx) 非空 ? "Goal cleared: {condition}" : "No goal set"
if (e.length > GNt)  // 超过 4000 字符
   → "Goal condition is limited to {GNt} characters (got {len})"
let value = rmt(e, ctx);   // 设置（走 §3.1）
   → value!==null ? value(错误文案) : { type:"query", value:"Goal set: {e}", prompt: qVn(e) }
```

- 状态查询会显示 `iterations`（“not yet evaluated / N turns”）和 `lastReason`（“Last check: …”）。
- 设置成功返回的是一条 `{type:"query", value:"Goal set: …", prompt:qVn(…)}`，即把 kickoff 文本作为后续模型输入注入。
- 长度上限 `GNt = 4000`（`m0274:78`）。

### 4.2 模型入口：`ProposeGoal` 工具

#### 工具说明（`m0418_0xecc9ad4.js:11-20`）

- `Gjn = "ProposeGoal"`（名字）；
- 一句话描述：Propose a session goal condition, with one-keypress user approval; once set, Claude keeps working
  until a separate evaluator confirms it is met；
- 长描述（`NPs`）要点：**Non-blocking**（提议机制不阻塞当前工作）；`ask_user true`（默认）先弹一键审批，
  **用户拒绝不会通知模型，不得追问或重复提议**；`ask_user false` 只有在“用户原话已表达该结果”时才可直设；
  每个条件 ≤ 500 字符，求值器**只从会话对话判断、不能跑命令读文件**；同一时刻只有一个活跃目标，新目标覆盖旧目标。

#### schema 与结果（`m1718_0x10577b1d.js:146-158`）

输入 `{ condition: string(1..Vjn=500), ask_user?: boolean }`；输出 `{ condition, askUser: boolean }`。

#### 调用内部门禁与直设路径（`call()`，`m1718:205-283`）

按源码顺序检查/执行：

1. `e.agentId` 存在 → 拒绝（ProposeGoal 只能主会话用）；
2. 非交互 / 远端 / 非本地 → 拒绝（`we()/Bn()/Ht()`）；
3. 条件规范化（`yqe` 把 `\r\n\u2028\u2029` 折叠成空格，`yTe` 往返解析）后 `.trim()` 为空 → 拒绝；
4. 规范化后长度 > `Vjn=500` → 拒绝（“must be readable in the approval dialog”）；
5. `nmt(condition)` 命中 clear 词 → 拒绝（ProposeGoal 只提议，不负责 clear）；
6. `Dsn()` 门禁非空 → 拒绝（hooks/org/trust，同 §3.3）；
7. **Plan mode 激活**（`permissions().mode === "plan"`）→ 拒绝（“plan 之后才可以提议目标”）；
8. 读 `modelProposedGoals` 设置 `qHo(storageV5)`，为 `"disabled"` → 拒绝；
9. 计算 `askUser = (设置==="alwaysAsk") || (ask_user !== false)`；
10. 需要交互 `requestDialog` 否则拒绝；若已有待决提议（`toolState.get(qCt).id` 非空）→ 拒绝（防重入）；
11. 发 `tengu_goal_proposed`/`goal_propose` 遥测。

**直设路径（`askUser === false`）**：`recordQueuedGoalOrigin(condition, "proposal_direct")`，
再 `messageQueue.enqueue({value:"/goal <condition>", origin:{kind:"task-notification"}})`，
返回 `{condition, askUser:false}`。也就是**工具自己不直接设目标，而是把 `/goal` 塞进命令队列**，
由主循环经 `rmt` 真正落目标（来源经 `queuedGoalOrigin` 恢复为 `proposal_direct`）。

**审批路径（`askUser === true`）**：`requestDialog(Foe /* goal_proposal */, {condition}, {place:"under"})`，
`.then` 里重新校验（`approved && r.id===m && 未disabled && 非plan`）后，命中才
`recordQueuedGoalOrigin(condition, "proposal_approved")` + enqueue `/goal`（`origin:{kind:"auto-continuation"}`）；
`.finally` 清 `toolState` 标记。审批对话框 `Foe`（`m1171_0xfb04dfe.js:14-24`）：

```js
{ kind: "goal_proposal", payload:{ condition }, result:{ approved, explicit? }, default:{ approved:false } }
```

#### 结果回填文案（`mapToolResultToToolResultBlockParam`，`m1718:285-289`）

- `askUser:false` → 告知“已在本次回合结束生效，届时收到 kickoff；此前旧目标仍有效；继续工作，勿等”。
- `askUser:true` → 告知“已展示给用户审批；拒绝不会通知你，勿追问勿重复提议”。

> 两个入口殊途同归：最终都调 `rmt()` 在 hooks 注册表落一条 Stop hook。

## 5. 求值器：`prompt-hook evaluator`（`m0459_0xecff32a.js:154360-154560`）

Stop hook 落在 `type:"prompt"` 上后，执行引擎调这段求值器。它**不是规则判断，而是一次独立、只读、无工具的模型调用**。

### 5.1 系统提示词（goal 分支，`Xe`）

求值器根据当前是 **stop-condition hook（goal）** 还是普通 prompt hook（`et`）用两套提示词。goal 的 `Xe` 核心：

> You are evaluating a stop-condition hook in Claude Code. Read the conversation transcript carefully, then judge
> whether the user-provided condition is satisfied.
>
> Your response must be a JSON object with one of these shapes:
> - `{"ok": true, "reason": "<quote evidence from the transcript that satisfies the condition>"}`
> - `{"ok": false, "reason": "<quote what is missing or what blocks the condition>"}`
> - `{"ok": false, "impossible": true, "reason": "<explain why the condition can never be satisfied>"}`
>
> Always include a "reason" field, quoting specific text from the transcript whenever possible. If the transcript
> does not contain clear evidence that the condition is satisfied, return `{"ok": false, "reason": "insufficient evidence in transcript"}`.
>
> Only use `{"ok": false, "impossible": true}` when the condition is genuinely unachievable… the assistant claiming
> the goal is impossible is evidence, not proof… When in doubt, return `{"ok": false}` without "impossible".

关键语义：**只看对话、不跑命令不读文件**；`reason` 必须引用转录中的具体文本；拿不准就 `ok:false`；
`impossible` 是“真不可达成”才用（自相矛盾、依赖不可得的资源、或已穷尽手段），且要独立确认，不轻信模型自述。

### 5.2 调用参数（`ot()` / `RZ(...)`）

```js
systemPrompt: _i([ isGoal ? Xe : et ]),
thinkingConfig: { type:"disabled", mechanical:true },
tools: [],
signal: abortSignal,
options: {
  model: be,                    // 求值器模型
  toolChoice: void 0,
  isNonInteractiveSession: true,
  hasAppendSystemPrompt: false,
  agents: [], mcpTools: [],     // 无工具无 agent
  querySource: "hook_prompt",
  promptTooLongIsHandled: true,
  outputFormat: { type:"json_schema",
    schema: { type:"object", properties:{ ok:{type:"boolean"}, reason:{type:"string"}, impossible:{type:"boolean"} },
              required:["ok","reason"], additionalProperties:false } }
}
```

- **无 tools、无 mcp、无 agent、非交互、thinking 关闭（mechanical）**，限定“只读判断”，从机制上保证求值器跑不了工具。
- 输入是结构化输出 `json_schema`，模型必须返回合法 `{ok, reason[, impossible]}`。

### 5.3 转录截断（`UYr`，`m0459:154554-154575`）

把 Stop 转录按模型上下文预算裁剪：预算 = `floor(s · r)`，`s` 是求值器模型的上下文预算
（`gf(n)||KE(n) ? 1e6 : tJe`），`r = jRn = 0.5`。若超限，从后往前保留到预算内的消息，在最前面插入一条元消息：

> [Earlier conversation truncated to fit the hook evaluator's context window — N earlier messages omitted.
> Evaluate the condition against the recent transcript below; if the required evidence may be in the omitted
> prefix, return {"ok": false, "reason": "insufficient evidence in transcript"}.]

并记 `tengu_hook_prompt_transcript_truncated` 遥测（含 `droppedMessages / keptMessages / budget / evaluatorModel`）。

### 5.4 结果映射（`m0459:154463-154533`）

解析→schema 校验（`mee().safeParse`）后：

| 模型返回 | 求值器输出 | 含义 |
| --- | --- | --- |
| `ok:true` | `outcome:"success", stopReason:reason` | 条件已满足 |
| `ok:false, impossible:true` | `outcome:"success", impossible:true, stopReason:reason` | 判定不可达成（goal 失败） |
| `ok:false`（普通） | `outcome:"blocking", blockingError:"[condition]: reason", preventContinuation:…` | 条件未满足 → 阻塞 stop |
| API 错误 / JSON 解析失败 / schema 失败 | 生成 `hook_*_error` 附件 | 求值器错误 |
| 超时（`Le.aborted`） | `outcome:"cancelled", timedOut:true` | 求值超时 |

对 goal 而言，`ok:false` 时 `preventContinuation = !isGoal && continueOnBlock!==true`——**它阻塞的是“停止”**，
让主循环不能正常收尾，而是把 `blockingError` 作为元消息注入并继续下一轮。

### 5.5 这是 LLM 智能判定，不是规则匹配

需要特别说明：`{ok, reason, impossible?}` 是**一次强约束的 LLM 智能判定**，而不是关键词 / 规则匹配。

- 求值器是一次**独立模型调用**（`ot()` / `RZ()`），用上面 5.1 的专用系统提示词，让模型完整读会话转录后裁决；
- 它是**工具隔离、只读**的：`tools: []`、`mcpTools: []`、`agents: []`、`isNonInteractiveSession: true`、
  `querySource: "hook_prompt"`——模型手里只有转录文本，跑不了命令、读不了文件，只能靠“读对话”来判断；
- 输出被**结构化强约束**：`outputFormat.json_schema` 限定 `{ok, reason, impossible}` 三种形状，非法 JSON 判为求值失败；
- 语义裁决：
  - `ok:true` → 达成，`reason` 必须引用转录中的具体证据；
  - `ok:false` → 未达成（默认答案 “insufficient evidence in transcript” 表示证据不足）；
  - `ok:false, impossible:true` → 仅“真不可达成”才用（自相矛盾 / 依赖不可得资源 / 已穷尽手段），且须独立确认、不轻信模型自述。

这也解释了 goal 为何既能匹配 “bun test exits 0” 这类可验证条件，也能判断“重构后测试全绿”这类需要理解上下文的完成度——
都由 LLM 做语义化裁决。

## 6. 主循环：求值结果如何落地（`m0671_0xf53ce11.js:3298-3460`）

`blockable_turn_end`（可阻塞的回合结束点）是 goal 求值真正发生并落地的位置。前置：`xe = getAppState().activeGoal`
（仅主会话，`agentId? void 0`），`goalPass` 记录本次 outcome。

### 6.1 后台任务在跑 → 推迟求值（`m0671:3304-3348`）

若 `activeGoal` 存在且非 agent 上下文：取**正在跑、会“推迟”**的任务（agents / shells 等，`pl(...)`）。

- 若能找到与 `activeGoal.condition` 相同的 goal Stop hook（`ae`），**先把它从注册表摘掉**，`goalPass="deferred"`，
  记录 `{activeAgents, activeShells}`；
- 调用 `Wi(activeGoal, deferringTasks, now)` 计算 check-in 文本（见 §7），`ie = Wi(...).nextGoal`；
- 若 nextGoal 变了 → `yield {type:"active_goal", value: ie}`；若有 check-in 文本 → 以元用户消息注入
  `blockingErrors.push(...)` 并 `yield` 该消息（让模型继续，而不是现在判目标）；
- 若 `deferredSince` 已清（背景任务都没了）→ 把 `deferredSince/checkinCount/lastDeferralPassAt` 从 activeGoal 里剥掉，
  `yield {type:"active_goal", value}`。

**为何推迟**：后台 agent/shell 还在产出时，判定“条件是否满足”为时过早，且不应打断它们——
所以**把目标 hook 从 Stop 集合里摘掉，交给定时 check-in 机制**去周期性提醒主模型继续/收尾其产出。

### 6.2 真正执行求值（`Spe` = executeStopHooks）

之后照常执行 `Stop` hooks（`ut` 迭代器）。目标 hook 的求值结果在迭代里被消费：

- `se.timedOut && hook.prompt===activeGoal.condition` → `goalPass="cancelled"`、`p("goal_met","evaluator_timeout")`；
- **成功且 hook 是目标**（`hook_success` 附件，`Ce=Q(hook)` 能找到对应 goal hook）：
  - 先 `sessionHooksRegistry.remove(sessionId,"Stop",Ce)`（**摘掉目标 hook**）；
  - 取 `activeGoal`，`iterations=activeGoal.iterations+1`，`durationMs=Date.now()-setAt`，`tokens=Th()-tokensAtStart`；
  - 先 `yield {type:"active_goal", value:void 0}`（清活跃目标）；
  - `goalPass = he.impossible ? "impossible" : "met"`；
  - **impossible** → 写 `goal_status{met:false, failed:true, condition, reason:stopReason, iterations, durationMs, tokens}`，
    记 `tengu_goal_failed`、`m("goal_met","impossible")`；
  - **met** → 写 `goal_status{met:true, condition, reason, iterations, durationMs, tokens}`，
    记 `tengu_goal_achieved`、`g("goal_met")`，并 `notifyMetadataChanged({goal:{condition,set_at,iterations,last_reason:null,met:true}})`；
- **blocking（未满足）** → `makeUserMessage` 注入 `aOt(blockingError)`（把 reason 摆给模型看）、`Zt=true`；
  若命中的是目标 hook → `goalPass="not_met"`，`yield {type:"active_goal", value:{...activeGoal, iterations:iterations+1, lastReason:stopReason}}`，
  并写 `goal_status{met:false, condition, reason:stopReason}`（保留目标，下轮继续求值）；
- **目标 hook 报错**（`hook_non_blocking_error` / `hook_error_during_execution`）→ `goalPass="error"`、`p("goal_met","evaluator_error")`。

### 6.3 结束后返回与“是否还要模型再跑”

- `Ne`（`preventContinuation`）→ 走 `$t`(turn-end reactions) 后 `return {blockingErrors:[], preventContinuation:true}`；
- 有 `blockingErrors`（含未满足目标注入的元消息）→ `return {blockingErrors, preventContinuation:false, goalPass}`，
  主循环据此**不结束回合、继续请求模型**；
- `fork_dispatch` 版本（`m1592_0x10166c92.js:262-302` 的 `wt()`）逻辑同构，只是面向“fork 派发边界”的 Stop hooks。

> **goal 的“持续工作”就是这么实现的**：每轮要结束时求值一次，未满足就注入原因并让回合继续，直到 met/impossible 摘掉目标 hook。

## 7. 后台 deferral 与 idle check-in（`m0671_0xf53ce11.js:128-338`）

当目标求值被推迟且后台任务还在跑，goal 机制会周期性地给主模型注入“check-in”消息，逼它保持对目标的注意力。

### 7.1 时间与退避

- 检查间隔 `ur()`：读 flag `tengu_saffron_wren`（默认开）+ 环境 `CLAUDE_CODE_GOAL_CHECKIN_MINUTES`（默认 `Du=30` 分钟）× 60000；
- 指数退避 `Ni(count) = base * 2 ** min(count, Uu=2)`（每次翻倍，最多翻 4 倍到 2h）；
- 空闲上限 `Lu=3`：`dr(goal) = (idleCheckinCount ?? 0) >= 3`，到上限后只重排 tick 不再注入（“idle check-ins paused until your next message”）。

### 7.2 定时器 `fn/as/Wu`

`fn`（每次 goal 状态/背景变化后调度）→ `as` 用 `setTimeout(Wu, delay)`（`unref`；延迟下限 60s，
  由 `Math.max(lr=60000, …)` 保证，上限 `Hu` 从共享 chunk 导入），`Wu` 到点执行：清 pending，
  若目标仍是当前 activeGoal 且 `deferredSince!==void 0`：

- 无后台任务可等、但有更严格的 `hasQueued(B0n)`/`getDeferringTasks()` 空判据 → 重新调度；
- `dr(goal)` 到上限 → 只重排；
- 否则 `ji(...)` 判定是否“新一轮 deferral”（后台任务换过）→ 是则重置 `checkinCount`；
- 写 `activeGoal{deferredSince, checkinCount+1, lastDeferralPassAt, idleCheckinCount+1}` → `deliver(Bi(...))` → 重新 `fn`。

### 7.3 check-in 文案 `Bi`（选择“后台是否还在跑”）

- 后台任务列表为空 → “Goal check-in: background work no longer running… Its evaluation was deferred for N min… Continue toward the goal.”
- 后台仍在跑 → 列出每个任务 `- id · type · description`，提示“Check on their progress (e.g. read their output)… waiting / fix or stop them and continue toward the goal.”
- `ju(B)`：追加“idle check-ins paused until your next message / Claude Code won't wake this session for another check-in until the user sends a message…”（被动化提示）。
- 遥测 `tengu_goal_checkin_injected`（trigger/deferredMs/activeShells/activeAgents/checkinCount/idleCheckinCount）。

## 8. 中断与自动重试（`m0671_0xf53ce11.js:3763-3860`）

用户可能在目标进行中手动 Stop（abort / 清空 / usage_limit 等）。goal 用 `goalInterruptionStreak`（`m0017` 会话标记）做**自动续跑**。

### 8.1 常量

- `Us = [60000, 300000, 900000]` → 重试间隔 1min / 5min / 15min；
- `Ds = Us.length = 3` → 最多自动重试 3 次；
- `jp`（抖动系数）、`$p/Wp/Us/…` 分别对应给用户的展示文案与 cause 描述。

### 8.2 分支（`m0671:3803-3860`）

在回合结束、目标仍 active 时按“结束原因”处理：

- `completed` 且 `goalPass===void 0` → **不碰 streak**（保持现状直接 return）；`kind==="none"` 的其它情况
  （`goalPass` 为 `met` / `impossible` / `deferred`，或非 completed）→ 清 streak；
  `goalPass` 为 `error/cancelled/not_met` 时才“保留”并进入下面的 retry/pause 分支（由 `Vp()` 判定）；
- `stop` 类 → 清 streak，若 flag `tengu_quartz_pipit` 开 → `bl(...)`（进“waiting/cleared”展示）后 return；
- 非交互会话 → 清 streak return（不自动续）；
- `retry`：若已在等 pending reprompt 或 `hasQueued(B0n)` → return；`retries>=Ds` → 记 `announced:"gave_up"`、
  注记 “Goal paused after {Ds} automatic retries · {cause} · send a message to continue”（warning），不再自动续；
  否则把 retries+1，`$i(...)` 按 `Us[retries]·(1+rand·jp)` 调度 `Qu`（pendingGoalReprompt），
  注记 “Goal still active · {cause} · retrying in N min (k/Ds) · send a message to retry now”；
- 其他：`reason` 记 `announced`（如 `usage_limit_waiting`）后注记对应 `$p[...]`。

### 8.3 重试注入 `Qu`（`m0671:353-376`）

到点后若目标仍是当前 activeGoal、且会话仍在交互式状态下：`deliver({summary:"Goal check-in: continuing after the last turn ended early",
body:"{condition} is still active. The last turn ended before the goal could be evaluated: {cause}. Continue toward the goal."})`，
记 `goal_interruption`，并清 pending。也就是**把“上回合没判、目标还在”这个事实主动重新塞给主模型**，让工作继续。

## 9. 会话转录、状态通知与 UI/SDK 暴露

### 9.1 `goal_status` 附件生成（`Met`，`m0459:140122-140129`）

Transcript 生成消息时用 `Met(e, prev, next, enabled)` 决定是否追加 `goal_status`：

```js
function Met(e, n, r, s) {
  if (!s) return null;                       // 特性未开
  let h = e.getAppState().activeGoal;
  if (h !== void 0) return en(VVn(false, h.condition));   // 仍有活跃目标 → met:false(condition)
  let y = Msn(r);                            // 找 next 里最近未决的 goal_status
  if (y === null || Msn(n) === y) return null;
  return en(VVn(true, y));                   // 目标被清、但转录里还挂着 condition → met:true
}
```

即“activeGoal 还存在就写未决；目标被摘掉且消息里仍有该 condition 就写达成”。sentinel 附件（设置/清除时写的）用于在
transcript 里标记状态而不视为求值结果。

### 9.2 状态变更通知（`m0696_0xf5a08ff.js:291-309`）

App 状态 diff 时，若 `activeGoal` 变化：

```js
if (!B(newState.activeGoal, oldState.activeGoal)) {
  let activeGoal = newState.activeGoal;
  r?.notifyActiveGoalChanged(activeGoal);          // 推给内部订阅者
  if (activeGoal) r?.notifyMetadataChanged({
    goal: { ...Mqr(activeGoal), last_reason: activeGoal.lastReason ?? null, met:false }
  }); else r?.notifyMetadataChanged({ goal: null });
}
```

`Mqr(activeGoal) = { condition, iterations, set_at, tokens_at_start, last_reason? }`。
`B` 用字段 `["condition","setAt","iterations","tokensAtStart","lastReason"]` 做浅比较，避免无意义刷新。
`m1809_0x106dad73.js:13832,22021`、`m0609_0xf492442.js:4674` 把 `activeGoal` 注入 `toolUseContext.options` 或
订阅 `onActiveGoalChanged` → 每个工具调用/主循环都能看到当前目标（SDK 元数据 `goal` 字段）。

### 9.3 前端渲染

- `active_goal` 卡片渲染在 `m2146_0x10d36021.js:200-246`：显示 `Goal active`（标题）、`running {duration}`、
  `{tokens}`、`iterations`（`iterations>0 ? "N turns" : 未显示`）、`Goal: {condition}`、`Last check: {lastReason}`；
  注意 `m1575_0x1010709c.js:634` 的 `active_goal` 分支在 SDK message adapter 里是被 **忽略（ignored）** 的，
  真正落到 UI 的是 `notifyMetadataChanged({goal})` / `active_goal` 事件经 `m2146` 渲染；`m1575:214-224`
  负责对 `activeGoal` 元数据做 JSON schema 校验并映射 `last_reason`。
- `goal_status` 附件（`m1556_0x1006d7b6.js:7324-7340`）：达成/失败时渲染徽标（含 `durationMs` 人类可读时长、
  `iterations`、`met`、`failed`、`tokens`），sentinel 隐藏不显示；
- transcript/分支逻辑（`m1563_0x100b015f.js:8905`、`m1186_0xfb0d823.js:138`）：`goal_status` 且带 `reason` 视为

### 9.4 会话 nudge（`m1837_0x10837277.js:1227-1231`）

3. **求值**：每次 Stop（回合要结束）对该 prompt hook 跑一次只读模型求值，返回 `{ok, reason, impossible?}`；
4. **落地**：met/impossible → 摘 hook + 清 activeGoal + 落 goal_status；not_met → 注入 reason 并让回合继续；
5. **deferral**：后台任务在跑时摘目标 hook，改走定时 check-in（退避、上限）；
6. **中断**：被打断后按退避自动重试注入“目标仍在”消息；
7. **门禁**：交互式、可信工作区、hooks 可用；Plan mode 下禁止提议；
8. **设置**：`modelProposedGoals`（auto/alwaysAsk/disabled），consent-affecting（只读 trusted sources）；
9. **限长**：用户手输 4000，模型提议 500；
10. **UI/SDK**：activeGoal 变化推 `notifyMetadataChanged({goal})`；transcript 落 `goal_status` 附件并在前端“达成/失败”徽标与“Goal active”卡显示。
