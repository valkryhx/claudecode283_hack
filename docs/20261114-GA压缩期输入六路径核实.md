第一轮的错误结论与订正：

| 第一轮说 | 实际情况 |

## 2. 最关键的结构问题：bridge 命令循环是单线程【S】

`run_jsonl_loop`（`bridge.py:3599`）：

```python
for line in stdin:
    ...
    if cmd_type == "submit":
        bridge.submit(...)          # ← 同步调用，内部可能跑完整次压缩
    elif cmd_type == "queue_prompt":
        bridge.queue_prompt(...)
    elif cmd_type == "stop":
        bridge.abort_current_turn()
```

【S】循环体里**没有任何线程分派**。`submit()` 里调 `_auto_compact_if_needed()`
（`bridge.py:634`），后者同步跑 `compact_agent_context()` —— 一次 LLM 摘要请求。

⇒ **压缩期间整个 bridge 命令循环被占用**：`submit`、`queue_prompt`、`stop`
全部读不进来。用户按 Esc 也停不下来。

> 【S】**这条比「输入被拒」更严重：`stop` 也在同一个循环里，所以压缩期间
> 按 Esc 无效。UI 看起来完全死了。**
>
> **已实证**（`tests/probes/python/bridge_blocking_probe.py`）：
> 伪造压缩耗时 3s，期间在 t=1.0s 发出 `stop`，它直到 **t=3.00s**
> （submit 退出的同一时刻）才被处理 —— 延迟 2.00s，正好等于压缩剩余时间。
>
> ```
> t= 0.00s  submit_enter
> t= 3.00s  submit_exit
> t= 3.00s  stop_handled     ← 等了整整 2 秒
> ```

## 3. Ink 侧的分流：`running` 走 queue，`idle` 走 submit【S】

`inputController.ts:435`：

```js
if (status === 'running' || status === 'stopping') {
  ...
  return decision('', 0, { command: { type: 'queue_prompt', text: expanded } })
}
```

`decision('', 0, ...)` ⇒ **输入框被清空**，文本转交给 `queue_prompt`。

对比 `idle` 分支（`inputController.ts:464`）：

```js
return decision('', 0, { command: { type: 'submit', text: expanded } })
```

【S】两条分支都清空输入框。区别只在发出的命令类型。

⇒ 结合 §1 的表：

- 路径 1 / 3 / 4 / 5（Ink 以为是 `idle`）→ 发 `submit` →
  - 路径 1：阻塞排队（文本没丢，但要等）
  - 路径 3/4/5：**被 `busy` 拒，文本丢了**（`busy` 无前端兜底，见下）
- 路径 2 / 6 / 7（`running`）→ 发 `queue_prompt` → 文本进队列，但命令本身
  可能因循环阻塞而延迟

## 4. 前端对 `busy` 无兜底【S】

`grep 'busy' frontends/ink/ui/src/App.tsx` → **零命中**。

`bridge.submit` 的拒绝（`bridge.py:576-578`）：

```python
if getattr(self.agent, "is_running", False) or self._is_consuming():
    self.emit({"type": "error", "code": "busy", "message": "agent is running"})
    return -1
```

【S】前端没有 `code === 'busy'` 的分支去还原草稿。而输入框在 `inputController.ts:464`
已经清空。

⇒ 路径 3/4/5 的失败形态：**用户打了字、按回车、字消失、只出现一条泛化 error**。

## 6. 修复建议（按根因，不按症状）

### 根因：压缩不该占用 bridge 命令循环

**P0 — 把 `_auto_compact_if_needed` 挪出同步路径**。
`submit()` 里只做「是否需要压缩」的判定（快），真正的摘要请求放到
task 线程或独立线程。这样命令循环不被占用，`stop`/`queue_prompt` 仍可处理。

**P0 — 压缩开始时发状态事件**。
`_auto_compact_if_needed` 与回合 `finally` 里的三条路径都应在开始前
`emit({"type": "system", "text": "Compacting conversation"})`，
结束后发完成提示。这样前端至少知道「在压缩」。

**P1 — 前端对 `busy` 兜底**。
收到 `code === 'busy'` 时把文本还原回输入框（或用 `queue_prompt` 重试）。
这样即使后端拒绝，用户也不会丢字。

**P1 — 回合结束的三条路径前移**。
`_compact_after_hard_trim` 等发生在 `done` 已发之后，前端已判定 `idle`。
要么在 `done` **之前**做，要么在开始时发一个「仍在忙」的事件。

### 明确不要做

- ❌ 不要只删 `_is_consuming()` 条件 —— 那会让回合生成中也能插话。
- ❌ 不要假设「Ink 会走 queue_prompt 所以没问题」—— 路径 1/3/4/5 时 Ink 以为是 idle。
