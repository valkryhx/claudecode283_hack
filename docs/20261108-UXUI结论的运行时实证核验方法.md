## 0. 为什么不能直接套用 transcript 方法

那套方法的 L2 是 **transcript JSONL**。它对「subagent 是否阻塞」这类**业务事件**极有效，
但对 UX/UI 几乎无能为力 —— transcript 里根本没有这些字段：

| UX/UI 结论 | transcript 里有吗 | 为什么没有 |
| --- | --- | --- |
| 每帧是否被 `?2026h…?2026l` 包住 | ❌ | 终端字节流从不写盘 |
| 帧间隔是不是 16ms | ❌ | 同上 |
| 输入框高度是否随内容变化 | ❌ | 布局在内存里，渲染完即丢 |
| 滚动增量按什么曲线衰减 | ❌ | 同上 |
| 备用屏到底进没进 | ❌ | 只有屏幕上的最终像素，没有转义序列 |

结论：**UX/UI 的 L2 必须是「终端字节流」或「模块执行结果」，不是 transcript。**

本文给两条互补路线，**各有明确的适用边界**（这一点比方法本身更重要，见 §5）：

- **路线 A：PTY 抓包** —— 看真实进程实际往终端写了什么。
- **路线 B：叶子模块直执行** —— 把 deminified 的纯函数/常量模块直接跑起来，读返回值。

## 1. 路线 A：PTY 抓包（看"真的写了什么"）

### 1.1 为什么是 PTY 而不是管道

CC 检测 `stdout.isTTY`：不是 TTY 就走纯文本路径（`nf.render` 里 `if (!this.options.isTTY)`），
**拿不到任何差分/转义序列**。所以必须给它一个真 PTY。

Windows 上用 `pywinpty`（本机已装）：

```python
from winpty import PtyProcess
p = PtyProcess.spawn([CLAUDE_EXE], dimensions=(40, 120), env=env, cwd=REPO)
raw = p.read(65536)      # 返回 str（winpty 已做过编码转换）
```

工具：`tools/ux-verify/pty-probe.py`（带时间戳、可选注入按键、可隔离配置目录）。

### 1.2 三条必须先做的环境隔离（否则测的是别的机器）

这是本次实测踩出来的，**不做会得到完全错误的结论**：

**(1) 清掉继承来的 `CLAUDE*` / `ANTHROPIC*` 环境变量**

子进程会继承"我正跑在 Claude Code 里"的全部环境变量，从而走嵌套/降级路径。

**(2) 用 `CLAUDE_CONFIG_DIR` 指向隔离目录，不要读用户的真配置**

否则会读到用户 `settings.json` 里的 `tui`、`permissions` 等设置。

**(3) ⚠️ 最重要：探针自己会污染被测对象**

实测事故：第一次探针跑完 `terminate(force=True)` 强杀，CC 判定"全屏渲染器上次没起来"，
在 `~/.claude.json` 写下：

```json
"fullscreenBootStrikes": { "count": 1, "version": "2.1.319" }
```

之后**所有启动都自动降级到经典渲染器**，并打印：

> Claude Code's fullscreen renderer didn't finish starting last time on this machine,
> so this launch is using the classic renderer.

**这就是方法论 §5.1「观测反噬」的 UX 版**：你的测量手段改变了被测对象的下一次行为。
→ 必须用隔离配置目录，跑完不污染真实 `~/.claude.json`。

### 1.3 受控实验设计（沿用方法论 §3.1 的哨兵思路）

| 手法 | 在 UX/UI 上的用法 |
| --- | --- |
| 正样本 | 注入 `CLAUDE_CODE_NO_FLICKER=1` / `tui=fullscreen`，看某序列是否出现 |
| 负对照 | 同一条序列，在"应该不出现"的配置下确认它真的不出现 |
| 唯一锚点 | 用完整的转义序列（`\x1b[?2026h`）而不是 `2026` 这种短数字去 grep |

## 2. ⚠️ 路线 A 的致命边界：ConPTY 会篡改字节

**这是本文最重要的一节。** 在 Windows 上，PTY 抓包**不能**用来判断"某个控制序列是否包裹了某段内容"。

### 2.1 负对照实验：让普通 Python 只写一行

子进程（`tools/ux-verify/_child_onewrite.py`）**单次 write** 写出：

```
ESC[?2026h  +  LINE-A×5  +  ESC[?2026l
```

即在真正的终端上，`LINE-A` 确实被 BSU/ESU 包住。抓包实际结果：

```
CAPTURED: '\x1b[?2026h\x1b[?2026l\x1b[2J\x1b[m\x1b[HLINE-A\r\nLINE-A\r\n...'
           ^^^^^^^^  ^^^^^^^^
open at 0  close at 8  inner = ''      ← 中间 0 字节
VERDICT: ConPTY REORDERED -> capture not faithful
```

**ConPTY 把 `?2026h` 和 `?2026l` 提到了内容之前，嵌套关系被破坏。**
内容一个字没少（`LINE-A` 全在），但**"谁包住谁"这个信息丢了**。

### 2.2 负对照实验：ConPTY 还会直接丢弃控制序列

子进程（`tools/ux-verify/_child_modes.py`）逐条写出，**每条序列后面跟一个纯文本标记
`MARK_<name>`**。标记一定保真，所以判据是硬的：

> 看到 `MARK_ALT_SCREEN` 却抓不到 `\x1b[?1049h` ⇒ 该序列被仪器丢弃。

复跑：`python tools\ux-verify\control-conpty-fidelity.py`

**backend=0（ConPTY）实测：保留 5 条，丢弃 7 条**

| 序列 | 抓包是否保留 |
| --- | --- |
| `ESC[?2026h` / `ESC[?2026l` BSU/ESU | ✅ 保留（但位置被重排） |
| `ESC[?2004h` 括号粘贴 | ✅ 保留 |
| `ESC[?25l` 隐藏光标 | ✅ 保留 |
| `ESC[?9001l` | ✅ 保留 |
| **`ESC[?1049h` 备用屏** | ❌ **被丢弃** |
| **`ESC[?1000h` / `?1002h` / `?1006h` 鼠标** | ❌ **被丢弃** |
| **`ESC[1;10r` DECSTBM** | ❌ **被丢弃** |
| **`ESC[3S` SU / `ESC[2T` SD** | ❌ **被丢弃** |

**backend=1（WinPTY）更糟：保留 1 条，丢弃 11 条** —— 只剩 `ESC[?25l`，
连 `?2026h`、`?2004h` 都丢。**永远不要用 WinPTY 做这项核验。**

> 注意口径：这里的"丢弃"指**抓包中看不到这个字节序列**，
> 不等于终端上没发生效果（ConPTY 可能已经把它消化成屏幕状态了）。
> 但对"用抓包裁决 CC 发没发某序列"这个用途来说，后果是一样的：**不可裁决**。

### 2.3 由此得到的硬结论

> **在 Windows + ConPTY 下，用 PTY 抓包"没看到 `ESC[?1049h`"不能证明 CC 没用备用屏。**
> 因为仪器会把这个序列吃掉。

这条极其重要：我在本轮实测中一度据此写下"备用屏没有启用"，**那是仪器的假阴性，不是 CC 的行为**。
真正的裁决必须落到路线 B（读源码常量）或真实终端的录像。

### 2.4 路线 A 仍然能做什么

丢弃是"部分保真"，不是"全不可信"。**可以**用路线 A 结论的：

- ✅ 进程是否走 TTY 路径（有没有差分序列）
- ✅ **帧的内容与时序**（可见文本、`ESC[K` 清行、`ESC[H` 定位的出现顺序）
- ✅ 启动横幅、提示语、状态行的实际文案
- ✅ 打字后多久出现回显（输入延迟，秒级精度）
- ✅ 某些私有模式的**有无**（`?2004h` / `?2031h` / `?1004h` / `?9001l` 这些是保真的）

**不能**用路线 A 结论的：

- ❌ 控制序列的**嵌套关系**（被重排）
- ❌ `1049` 备用屏 / 鼠标模式 / DECSTBM / SU / SD 的**有无**（被丢弃）
- ❌ 精确字节数（不同后端保真度不同）

## 3. 路线 B：叶子模块直执行（本仓库最可靠的 UX 核验手段）

### 3.1 核心思路

deminified 的模块里有一大批是**纯函数/纯常量**：ANSI 转义构造、帧节流常量、字形表、手势阈值……
它们**不依赖 React、不依赖终端**，可以直接用 Node 跑起来，**读返回值与文档结论逐字对比**。

这就是 UX/UI 版的"运行时实证"：**被测对象是源码本身，没有任何仪器在中间**。

### 3.2 操作步骤

**(1) 剥掉 Bun 虚拟路径的 import**

模块头部有 `import {...} from "B:/~BUN/root/chunk-xxx.js"`，Node 无法解析（`ERR_UNSUPPORTED_ESM_URL_SCHEME`）。
工具 `tools/ux-verify/strip-imports.mjs` 会自动剥离，并报告**是否还残留外部依赖**：

```
OK   m0108_0x1136a56c.js: 无残留外部依赖      ← 可独立执行
OK   m0697_0x122b525a.js: 无残留外部依赖
WARN m0660_0x121ce66a.js: 仍引用未定义符号 -> zl   ← 需要注入 shim
WARN m1082_0x12798259.js: 仍引用未定义符号 -> S, As, s, Re, e, Jt, ve, A, j  ← React，跳过
```

**判据很简单**：`OK` 的直接跑；`WARN` 但只有一个纯函数依赖的，注入 shim 后跑；`WARN` 出一堆
React API（`Jt/ve/A/y` = `createContext/useContext/useRef/useState`）的，放弃（它需要渲染器）。

**(2) shim 注入**

`m0660` 只依赖 `m0108` 的 `zl`（它是个纯函数）。`verify-leaves.mjs` 已把这一步自动化：
剥完 import 后若**残留符号恰好只有 `zl`**，就给模块头加一行 `const zl = globalThis.__zl;`，
并在加载 `m0660` **之前**先 `globalThis.__zl = ansi.zl`。

手工做同样的事是这样：

```js
import { zl } from "./m0108_0x1136a56c.mjs";
globalThis.__zl = zl;
const mod = await import("./m0660_0x121ce66a.mjs");
```

残留符号不止一个、且都是 React API（`Jt/ve/A/y` = `createContext/useContext/useRef/useState`）的，
脚本会打印 `SKIP`——它需要渲染器，不是叶子模块。

**(3) 写断言并跑**

工具：`tools/ux-verify/verify-leaves.mjs`（**自包含**：自己从 `reconstructed319/deminified/`
取源、剥 import、落到 `.tmp_probe/eval/` 再执行，不依赖任何预先准备好的中间产物）。
输出形如：

```
PASS  Lg  基础帧间隔 16ms
PASS  BSU 字节 == ESC[?2026h
PASS  DECSTBM(1,10) == ESC[1;10r
...
===== 结果: 26 PASS / 0 FAIL =====
```

脚本里的模块名是**全名**（模块号 + `0x` 哈希），跨版本会变 —— 找不到时会打印
`MISS <file> 不在 ...（版本变了？用 INDEX.tsv 重新定位）`，按 `INDEX.tsv` 的 tokens 列重新定位即可。

### 3.3 本次实测覆盖范围（26/26 全通过）

| 文档结论 | 模块 | 实测值 |
| --- | --- | --- |
| 基础帧间隔 16ms | `m0697` | `Lg = 16` ✅ |
| 输入优先间隔 4ms | `m0697` | `AJs = 4` ✅ |
| 输入优先窗口 50ms | `m0697` | `RJs = 50` ✅ |
| stdout 积压阈值 16KB | `m0697` | `xJs = 16384` ✅ |
| 积压退避 250ms | `m0697` | `sBo = 250` ✅ |
| 同步输出模式号 2026 | `m0660` | `zb.SYNCHRONIZED_UPDATE = 2026` ✅ |
| BSU/ESU 具体字节 | `m0660` | `"\x1b[?2026h"` / `"\x1b[?2026l"` ✅ |
| 备用屏模式号 1049 | `m0660` | `zb.ALT_SCREEN_CLEAR = 1049` ✅ |

| 鼠标三档组合序列 | `m0660` | `full` = `1000h+1002h+1003h+1006h`；`scroll` = `1000h+1006h`；`off` = `""` ✅ |

> 因此排除了"我抄错了转义序列""我把常量记反了"这类错误。**

## 4. 两条路线怎么配合（决策表）

| 要验的结论 | 用哪条 | 理由 |
| --- | --- | --- |
| 常量数值（16ms / 2026 / 1049 / 16384…） | **B** | 纯执行，零误差 |
| 转义序列的确切字节 | **B** | 同上 |
| 某个函数在给定输入下的输出（如 `hxe(1,10)`） | **B** | 同上 |
| 进程是否真的走了 TTY 路径 | **A** | 需要真实 `isTTY` |
| 实际启动文案 / 提示语 | **A** | 需要完整运行 |
| 帧的内容与时序（可见文本层） | **A** | B 拿不到（依赖 React 树） |
| 某个函数**是否被调用**（而不仅是存在） | **A** | 靠它的可见副作用判断；B 只能证明"调了会返回什么" |
| 依赖 React 的组件内部逻辑 | **都不行** | B 缺渲染器跑不起来（会 `SKIP`）；需要读码 |
| **控制序列的嵌套关系** | **都不行** | A 被 ConPTY 重排；B 拿不到运行时 |
| **备用屏/鼠标/DECSTBM 是否实际发出** | **都不行（Windows）** | A 被丢弃；B 只能证明"代码里构造得出来" |
| 布局是否真的不抖 | **都不行** | 需要人眼或屏幕录像 |

最后三行必须**如实标注"未验证"**，这正是方法论 §7 第 5 条的要求。

## 5. 假阳性 / 假阴性排查（UX/UI 专有）

| 陷阱 | 具体表现 | 正确做法 |
| --- | --- | --- |
| **仪器假阴性** | ConPTY 丢弃 `1049h`，误判"CC 没用备用屏" | 先跑 §2 的保真度对照，确认仪器能保留哪些序列 |
| **观测反噬** | 强杀进程 → 写入 `fullscreenBootStrikes` → 下次自动降级 | 用隔离 `CLAUDE_CONFIG_DIR` |
| **环境继承** | 继承 `CLAUDE_CODE_*` 导致走嵌套路径 | 启动前清掉全部 `CLAUDE*`/`ANTHROPIC*` |
| **非 TTY 路径** | 用管道抓，拿到的是纯文本，误判"没有差分渲染" | 必须用 PTY |
| **把"构造得出"当"实际发出"** | 路线 B 证明 `\x1b[?1049h` 能构造，就说"运行时进了备用屏" | B 只证明**能力**，不证明**行为**，措辞必须区分 |
| **短串 grep** | `grep "2026"` 命中版本号/时间戳 | 用完整转义序列 `\x1b[?2026h` |
| **单次样本** | 一次抓包就下结论 | 至少 3 次 + 正负对照 |
| **多套一层 shell** | `spawn([cmd, "/c", ...])` 会引入 cmd 的转义/换行改写，看起来像"程序行为异常" | 直接 `spawn([exe, ...])`，子进程参数用 argv 列表传 |
| **不设终端尺寸** | 默认 80×24 会走窄屏降级分支（§3.4 宽度降级），结论与正常窗口不同 | 显式 `dimensions=(40,120)` 并记进结果文件 |
| **把"跑了很久"当"帧率低"** | PTY 读侧有缓冲，读到的块边界≠写侧的帧边界 | 时序类结论一律标 `未验证`，除非能用高精度采集 |

## 6. 标注分级（在 UX/UI 文档里怎么写）

沿用姊妹篇的分级，但 L2 的定义改为"终端字节流或模块执行结果"：

| 证据情况 | 标注 | 措辞 |
| --- | --- | --- |
| 只有静态读码 | `静态推得` | 「代码构造了……」「从 `X()` 可推出……」 |
| 静态 + **模块直执行**吻合 | `实测证实（执行级）` | 「实跑 `hxe(1,10)` 得 `\x1b[1;10r`」 |
| 静态 + **PTY 抓包**吻合 | `实测证实（抓包级）` | 「抓包中观察到……」 |
| 抓包与静态冲突 | `以抓包为准`，并**先排查仪器** | 「疑为 ConPTY 丢弃，需换手段」 |
| 无法验证（见 §4 末三行） | `未验证` | 「机制如此，但本机未能实测」 |

**纪律**：`实测证实（执行级）` 只能用于**值/字节**类结论，
不能用来给**行为**类结论背书（执行了 `hxe()` 不等于运行时真的发了 DECSTBM）。

## 7. 本次核验的实际收获

1. **26 条常量/转义序列全部实测证实（执行级）** —— 见 §3.3 表。
2. **发现并修正了一个方法学错误**：曾试图用 PTY 抓包判断备用屏是否启用，
   经负对照发现 ConPTY 会丢弃 `1049h`，该结论**不可用仪器裁决**。
3. **把仪器的保真度量化了**：ConPTY 12 条常见控制序列**保留 5 / 丢弃 7**，
   WinPTY **保留 1 / 丢弃 11**（§2.2）。这张表比"ConPTY 可能有问题"有用得多 ——
   它直接告诉你**哪些结论可以靠抓包，哪些必须换手段**。
4. **发现观测反噬的具体形态**：`fullscreenBootStrikes` 计数器 ——
   强杀一次，后续所有启动静默降级，且只在首次打印一行提示。
5. **确认 `?2026h/?2026l` 在本机抓包中呈"空对"**，但这**不是** CC 的行为，
   而是 ConPTY 重排所致（§2.1 用普通 Python 复现了同样的重排）。

## 8. 复现命令

```powershell
# 版本锚定（必须第一步）
claude --version

## 9. 一页纸

```
UX/UI 结论无法用 transcript 核验（那里没有渲染数据）。

两条路：
  A. PTY 抓包    —— 看真实字节。但 Windows ConPTY 会【重排嵌套】+【丢弃 1049/鼠标/DECSTBM/SU】，
                    所以 A 只能验「内容与时序」，不能验「控制序列的嵌套与有无」。
                    实测保真度：ConPTY 12 条测 5 条、WinPTY 12 条测 1 条。
  B. 叶子模块直执行 —— 剥掉 Bun import，用 Node 直接跑纯函数/常量。
                    能验「值/字节」，不能验「行为」（构造得出 ≠ 运行时真的发）。

  ① 版本锚定（claude --version + SHA256）
  ② 隔离配置目录（CLAUDE_CONFIG_DIR）—— 否则探针自己写下 fullscreenBootStrikes，

  ③ 保真度负对照 —— 先证明仪器能保留你要找的序列，再下结论

不许含糊的措辞：
  「构造得出」≠「运行时发了」≠「用户看到了」—— 三者分级标注。
