## 问题与重试（均非 GA 缺陷）

### R1（D 首次 FAIL → 重试 PASS）：多子代理驱动期望的模型名格式不匹配

- 现象：`real_ink_ui_multi_subagent_e2e.ts` 首次设 `GA_MULTI_SUBAGENT_E2E_MODEL=default/A-Deepseek-V4-Flash-0731`，
  断言报 `selected model 设计院-ds-v4-0731/A-Deepseek-V4-Flash-0731 does not match default/...`。
- 初步原因：该驱动的模型断言拿 `model_status.models[].current.name`，格式是 **profile/model**，
  而我给的期望值用的是 `default/model` 前缀，与「设计院」profile 前缀不一致。属**测试驱动期望值错误**，非运行时异常。
- 处置/重试：把 `GA_MULTI_SUBAGENT_E2E_MODEL` 改为实际选择的 `设计院-ds-v4-0731/A-Deepseek-V4-Flash-0731`
  → 重试 1 次 PASS。bridge 实际已切到设计院模型（`model_switch_result` 正常）。

### R2（C 首跑 FAIL → 重试 PASS）：子 agent 探针读 agent_snapshot 用错字段名

- 现象：探针 `_zh_subagent_probe.py` 首跑 7 项里「child appeared in agent_snapshot」「child reached succeeded」
  两项 FAIL，但端到端（spawn→wait→read→close→中文产物→最终文本含该句）全部正常。
- 初步原因：探针按 `r.get("path")`/`r.get("name")` 匹配子代理，但 `agent_snapshot.snapshot.records[].to_dict()`
  实际字段是 `taskName` 和 `agentPath`（如 `/root/zh_child_*`），状态字段是 `status`/`turnStatus`。
  属**探针字段名错误**，不影响 GA 行为。
- 处置/重试：改按 `taskName`/`agentPath` 匹配、`status==succeeded`（或 `turnStatus==completed`）判定
  → 重试 1 次 PASS（7/7）。

### O1：workflow 激活时 `plannerMode` / `mode` metadata 展示字段为空

- 与上一轮一致：`taskType=dynamic_workflow`、执行成功，但 `plannerMode`/`mode` 未填充。
  判定为 metadata 展示层缺失，非激活/执行问题，未深挖。

### J. workflow degraded semantics —— FAIL（确定性，测试驱动脚本本身缺 `meta`）

- 驱动：`tests/real_workflow_degraded_semantics_e2e.py`
  （`GA_RUN_REAL_WORKFLOW_DEGRADED_E2E=1`，`GA_WORKFLOW_LLM_PROFILE=default`）。

  因不允许改动 GA 源码，未修补驱动；重试（确定性失败）无信息增益，已停止。建议后续在 GA 侧
  把该驱动的 `DEGRADED_SCRIPT` 等补上 `meta` 首条语句后再启用。
- 证据：`{passed:false, issues:["exception"], error:"RuntimeError: ... meta ... FIRST statement ..."}`

## L. workflow wait/barrier（依赖栅栏）—— FAIL（确定性，同一 meta 缺陷）

- 驱动：`tests/real_workflow_wait_barrier_e2e.py`
  （`GA_RUN_REAL_E2E=1`，`GA_WORKFLOW_LLM_PROFILE=default`，`GA_REAL_API_EXPECTED_MODEL=A-Deepseek-V4-Flash-0731`）。
- 场景：2-job workflow（`module-analysis` 先 `file_read` 并写 `analysis.md`，`test-suggestions` 依赖上游写
  `test_suggestions.md`），断言下游必须在上游 terminal 后才启动（依赖栅栏）并校验两个产物 + 编译通过。
- 现象：立即抛 `RuntimeError: Invalid workflow script: \`export const meta = { name, description, phases }\`
  must be the FIRST statement in the script`，发生在 LLM 调用**之前**。
- 重试：共 3 次（初跑、retry2、retry3），每次完全一致 → **确定性失败，非瞬态**。
- 初步原因：与 J 同根因。GA `parseWorkflowScript` 强制 `export const meta` 必须为首条语句；

# 第七轮（workflow 失败传播 / 依赖跳过 —— 发现一个真实 finalize hang bug）

- 主题：验证多 agent workflow 的「依赖失败 → 下游跳过」传播，以及失败后 workflow 的收尾行为。
- 探针：`claudecode283_hack/temp/probe_workflow_failure_recovery.py`（不改 GA 源码）。
  构造 2-job workflow：agent_1 `fails-on-purpose`（`maxTurns:1` 且 `retryableErrors:[]`，
  必须 `file_read` 一个不存在的文件 → 确定性耗尽 1 步预算失败）；agent_2 `depends-on-failure`
  通过 `dependsOn:['fails-on-purpose']` 依赖前者，脚本用 `Promise.allSettled` 接住两者。

## 已验证正确：失败 → 依赖跳过 的传播语义

两轮运行（run `wf_real_failure_propagation`）journal 逐字一致：

| 事件 | 内容 |
| --- | --- |
| `agent_failed` | job `agent_1` 失败，`error=max_turns_exceeded: child reached 1 steps` |
| `agent_skipped` | job `agent_2` 跳过，`{reason: dependency_failed, dependsOn:[fails-on-purpose]}` |

`run.json` 的一致持久化：`childSummary={total:2, failed:1, skipped:1, terminal:2, succeeded:0}`；
job `agent_1`→`failed`，`agent_2`→`skipped`（`error=dependency_failed`、`skipReason=dependency_failed`）。
→ **失败传播、依赖跳过、agent_skipped 事件记录全部按契约工作。**

## 发现的真实 bug：失败后 workflow 无法正常收尾（finalize hang）

- 现象（两轮完全一致，确定性）：job 都落地了（agent_1 failed、agent_2 skipped），journal 也写了
  `agent_skipped`，但 worker **永远不发 `done`/`workflow_finished`**；workflow 一直空转到
  运行时限（360s→900s 都超时），最后由 deadline 的异常路径才写出一条 `workflow_failed` 并以 `failed`
  收场。也就是说：**不是正常失败收尾，而是挂死到超时被强制终止**。
- 根因（已读源码定位，非推断）：
  - `runtime._complete_pending_rpc`（`runtime.py`）是 `agent()` rpc 回 `rpc_result` 的**唯一**途径，
    而它只在 `scheduler.tick()` 返回的 `completed` 列表里的 job 上被调用。
  - 被 `_skip_blocked_jobs` 标记为 `skipped` 的依赖 job 直接由 `queued→skipped`，**从不进入
    `tick()` 的返回值**（`tick()` 只收集从 `running` 经 poll 终态的 job）。
  - 于是被跳过那个 `agent()` 的 rpc 永远没有应答 → worker 里 `await agent(dependent)`（或
    `Promise.allSettled` 里那条）永不 resolve → 整个 workflow 脚本挂住 → 不发 `done` → 宿主空等
    到 deadline 才在异常分支写 `workflow_failed` 并把 run 置 `failed`。
- 影响面：任何「上游失败 + 下游 dependsOn」的 workflow 都会遇到：**状态机记录了跳过，却忘了 settle
  对应的 pending rpc**，导致整个 workflow 只能靠超时终止，而不是正常收尾成一个「失败 + 依赖跳过」的结果。
- 判定：这是 **GA 的 workflow 失败收尾缺陷（真实 bug）**，不是测试驱动/模型抖动。因为不允许改源码，
  本轮仅记录与复现，不修。rpc 应答缺失是 100% 确定性的（两轮 journal 一致 + 源码旁证）。

# 修复实施与回归验证（2026-10-29，deepseek-v4.1-flash）

> 本节记录依据前面各轮真实复现（尤其第七/八/十/十七轮）对两个真实 bug 的**修复实施**与**回归验证**。
> 关键前提：修复**不改语义契约**——`run.status="succeeded" + executionOutcome="partial"` 是仓库既有设计
> （`parallel()`/`allSettled()` 部分失败按 CC 语义返回、脚本层算完成；由 `test_workflow_runtime.py` 三个用例锁死）。
> 真正的缺陷是**状态层不一致**：`executionOutcome=partial` 时仍对外报 `integrationStatus=accepted` / `finalAuditStatus=passed`。

## 一、bug#1：dependsOn + skip 导致 worker 挂死

- 根因（已在源码逐行核对）：
  - `scheduler.py` `_skip_blocked_jobs()` 把依赖失败的 job 置 `skipped`，但 `skipped` **从不进入** `tick()` 返回的
    `completed` 列表（旧 `_start_queued_jobs()` 返回 `None`，skip 发生在取值前）。
  - `runtime.py:287` 主循环只对 `tick()` 返回的 `completed_job` 调 `_complete_pending_rpc()`，于是 skipped job 的
    `agent()` RPC 永远不被应答，worker 端 `await agent(dependent)` 悬空 → 挂到 runtime deadline（旧复现 100s 被杀）。
- 修法：
  1. `_skip_blocked_jobs()` 改为返回本次被跳过的 job 列表；
  2. `_start_queued_jobs()` 改为返回 skipped 列表（`return []` 分支、末尾 `return skipped`；`slots<=0` 用 `break` 而非 `return`）；
  3. `tick()` 用 `completed.extend(self._start_queued_jobs())` 把这些 skipped job 纳入本 tick 的 completed；
  4. `_complete_pending_rpc()` 新增 `skipped` 分支：发 `rpc_result ok:false, error=dependency_failed`，让
     `allSettled/parallel` 观测到依赖失败并正常收尾（`cancelled/killed` 仍按 CC 语义保持 promise 不结算，不动）。

## 二、bug#2：child 失败却报 succeeded/passed（状态层不一致）

- 根因：`runtime.py` 收 `done` 时先算 `degraded = (run.status=="degraded") or bool(workflowIssues)`（**不含 child 失败**），
  非 degraded 就统一 `integrationStatus="accepted"`、`finalAuditStatus="passed"`；`run.status` 仍 `succeeded`。
  而 `models.py project_workflow_execution_outcome()` 已能正确给出 `partial`，随后写回 `executionOutcome=partial` →
  形成 `outcome=partial` 却 `audit=passed` 的自相矛盾。
- 修法（保持契约，只修状态层）：
  1. **先定最终 `run.status`**（`degraded` 或 `succeeded`），**再** `refresh_workflow_execution_metadata()` 从最终状态算 `executionOutcome`；
  2. 以 `executionOutcome == "succeeded"` 作为唯一「干净通过」判据：是 → `integrationStatus="accepted"` / `finalAuditStatus="passed"`；
     否则（`partial`/`degraded`/`failed`）→ 一律 `integrationStatus="degraded"` / `finalAuditStatus="degraded"`。
  - 说明：这一步顺序很关键。若在设最终 `run.status` 之前先算 outcome，`running` 状态下全失败会被算成 `failed`，
    从而误判为「干净」——首版即踩过此坑（bug#1 探针暴露），已按「先定状态、再算 outcome」修正。

## 一、bug#2「全失败」文案规整（degraded → failed）

- 问题：上一阶段把「非 succeeded 一律降级为 degraded」，但**全失败（所有 child 都 failed/skipped、无一交付）**

- 修法：
  1. `models.py project_workflow_execution_outcome()` 的 `succeeded/degraded` 分支：`success_like == 0 and total > 0`

| degraded | degraded | degraded | degraded | 低保证交付（schema fallback 等） |
| failed | **failed** | **rejected** | **failed** | 全失败/无交付 |

## 二、子代理输出预算：`max_output_tokens` 截断 —— 已加固
