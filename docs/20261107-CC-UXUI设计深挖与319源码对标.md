## 0. 一句话结论

CC 的终端 UI 不是「一个 React 组件库套壳」，而是**自己实现了一个带差分渲染的终端 compositor**：

```
React 树 ──▶ Yoga 布局 ──▶ 屏幕格子缓冲(frontFrame/backFrame)
                                │
                                ▼
                        逐格 diff → 最小 ANSI 编码
                                │
                                ▼
           DECSTBM 滚动区 + 同步输出(2026) + 帧节流(16ms)
                                │
                                ▼
                            终端
```

「丝滑」「不抖」「不跳」这三件事分别由三个独立机制保证，可以分开复刻：

| 观感 | 机制 | 源码位置 |
| --- | --- | --- |
| 输出时终端不抖 | 同步输出 `CSI ?2026h/l` 包住整帧 + 双缓冲差分（只写变化格） | `m0660_0x121ce66a.js`、`m0701_0x122b603a.js:12489` |
| 滚动丝滑 | ① 滚轮增量不直接改 scrollTop，进 `pendingScrollDelta` 按帧衰减（§5.1）；② 一次滚轮折成几行由加速度曲线决定（§5.3） | `m0701_0x122b603a.js:14149-14240`、`14790-14810`、`m2124_0x1363573f.js:8428` |
| 输入框/底栏不上下晃 | 布局分区：根 `height=rows`、正文区 `flexGrow:1 + overflow:scroll`、底栏 `flexShrink:0`，正文自己内部滚动 | `m2124_0x1363573f.js:96123-96130`、`96202-96220`、`m0701_0x122b603a.js:14750` |
| 该折叠折叠 | 「高度锁」组件：渲染后测量子内容高度，用单调递增的 `minHeight` 把盒子钉死 | `m1083_0x12798610.js`（全文）、`m1791_0x130ab0ea.js` |
| 流式输出不闪 | 每个消息块有高度锁 + `overflowY:hidden`；增长时只抬 `minHeight`，不整块重排 | `m1791_0x130ab0ea.js`、`m1083_0x12798610.js` |

### 1.2 帧节流常量（`m0697_0x122b525a.js` 全文）

```js
var Lg  = 16,      // 基础帧间隔（ms）≈ 60fps
  RJs = 50,        // 输入优先窗口时长（ms）：每次输入后 50ms 内保持高帧率
  AJs = 4,         // 输入优先帧间隔（ms）：有键盘输入时几乎立即出帧
  xJs = 16384,     // stdout 积压阈值（byte）：超过就不再排帧
  sBo = 250;       // 积压退避（ms）：等 250ms 再看
export { Lg, RJs, AJs, xJs, sBo };
```

调度逻辑（`m0701_0x122b603a.js:16101-16118`，**源码原文**，只删了无关的空行）：

```js
scheduleFrame() {
  if (this.frameMicrotaskQueued) return;
  let n = this.pacerNow(),
    u = n - this.lastPacedFrameAt,
    c = n < this.inputPriorityUntil ? AJs : Lg;    // 输入优先 AJs=4ms，否则 Lg=16ms
  if (u >= c) {
    this.queuePacedFrame();
    return;
  }
  let m = this.lastPacedFrameAt + c;
  if (this.frameTimer === null || m < this.frameTimerDueAt) this.cancelScheduledFrame(), this.frameTimerDueAt = m, this.frameTimer = setTimeout(() => {
    this.frameTimer = null, this.queuePacedFrame();
  }, Math.max(0, m - n));
}
queuePacedFrame() {
  if (this.cancelScheduledFrame(), this.nonBlockingStdout !== null && this.nonBlockingStdout.queuedBytes() > xJs) {
    this.frameHeldForBacklog = !0, this.frameTimerDueAt = this.pacerNow() + sBo, this.frameTimer = setTimeout(() => {
      this.frameTimer = null, this.queuePacedFrame();
    }, sBo);
    return;
  }
  this.frameHeldForBacklog = !1, this.frameMicrotaskQueued = !0, this.inputPriorityUntil = 0, this.lastPacedFrameAt = this.pacerNow(), queueMicrotask(() => {
    this.frameMicrotaskQueued = !1, this.onRender();
  });
}
```

**复刻要点（这是"丝滑"的第一层）**：

1. **帧率上限 60fps**，不是「数据来了就画」。CC 里任何 setState 都只调 `scheduleRender`，
   真正的绘制被压到 16ms 一帧。这直接消掉了「token 一个个到、屏幕一行行追加」的抖动。
2. **输入优先**：每次键盘输入都会调 `requestInputPriorityFrame`（`m0701_0x122b603a.js:16094`），
   把 `inputPriorityUntil` 设成"现在 + 50ms"；在这 50ms 窗口内帧间隔降到 4ms，
   保证打字/滚动的反馈不被 60fps 卡住 → 主观上"跟手"。窗口过后自动回到 16ms。
3. **背压**：`stdout` 待写字节 > 16KB 时**主动不发帧**，等 250ms。
   这一条是「终端慢的时候 CC 不会越写越卡」的原因——很多自研 CLI 死在这里。
4. 用 `queueMicrotask` 而不是 `setTimeout(0)` 出帧：微任务在当前 tick 末尾，
   不会多插一个 event loop 轮次。

### 1.3 双缓冲 + 逐格 diff

渲染器的核心状态（`m0701_0x122b603a.js:15868`）：

```js
this.stylePool = new wd(),          // 样式池：样式对象 ↔ 整数 id（避免重复 SGR 串）
this.charPool  = new Ad(),          // 字符池
this.hyperlinkPool = new ps(),      // 超链接池
this.frontFrame = nr(rows, cols, stylePool, charPool, hyperlinkPool),  // 即将显示的帧
this.backFrame  = nr(rows, cols, stylePool, charPool, hyperlinkPool),  // 上一帧
this.log = new nf({ isTTY, stylePool }),   // 差分器 + 滚动历史
```

`frontFrame` / `backFrame` 是两块**整屏格子缓冲**（不是字符串）。每帧流程：

```js
// m0701_0x122b603a.js:16382-16402
let _ = this.renderer({ frontFrame, backFrame, isTTY, terminalWidth, terminalRows, altScreen, ... });
this.backFrame = this.frontFrame;
this.frontFrame = _;
// q = 差分出来的最小操作序列
let q = this.log.render(frontFrame_2, _, this.altScreenActive, <是否用同步输出>);
```

差分器本体 `nf.render`（`m0701_0x122b603a.js:12489` 起）关键在：

- 只遍历变化格：`Cg(prevScreen, nextScreen, cb)` 是一个**逐格比较回调**；
- 每格输出前用 `stylePool.transition(prevStyleId, nextStyleId)` 生成**最短 SGR 迁移串**
  （不是每次都 reset 再设，而是算差值）；
- 相同样式的连续格会**合并成一段 stdout**；
- 一次性写宽度为 2 的字符（CJK）会跳过它的尾格（`if (cell.width === 2) return`）。

**复刻要点（第二层）**：不要「清屏 + 重画整屏」，也不要「只追加新行」。
正确做法是**维护 prev/next 两块格子缓冲，逐格比对，把变化编成最小 ANSI 序列**。
清屏重画会闪；只追加则无法做「同一行内文字变化」（流式输出、spinner、计时器）——CC 两者都要。

### 1.4 同步输出：让整帧"原子可见"（不抖的关键）

`m0660_0x121ce66a.js` 把终端私有模式做成常量表：

```js
var zb = {
  CURSOR_VISIBLE: 25,
  ALT_SCREEN: 47,
  ALT_SCREEN_CLEAR: 1049,
  MOUSE_NORMAL: 1000, MOUSE_BUTTON: 1002, MOUSE_ANY: 1003,
  MOUSE_SGR: 1006, MOUSE_SGR_PIXELS: 1016,
  FOCUS_EVENTS: 1004,
  BRACKETED_PASTE: 2004,
  THEME_NOTIFY: 2031,
  SYNCHRONIZED_UPDATE: 2026,     // ◀ 关键
  WIN32_INPUT_MODE: 9001
};
function kK(E) { return zl(`?${E}h`); }   // set
function Y7(E) { return zl(`?${E}l`); }   // reset
var Mhn = kK(zb.SYNCHRONIZED_UPDATE),   // "\e[?2026h"
  mEt = Y7(zb.SYNCHRONIZED_UPDATE);     // "\e[?2026l"
```

所有帧写出都走同一个函数 `E$o`（`m0692_0x122af64b.js:186`），它把同步标记**首尾包住整帧**：

```js
function E$o(terminal, ops, skipSync, viewportRows, kept = "") {
  if (ops.length === 0) { if (kept !== "") J5n(terminal, kept); return; }
  let useSync = !skipSync;                    // ◀ 默认开
  let buf = kept + (useSync ? Mhn : "");      // 帧前：?2026h
  for (let op of ops) switch (op.type) { ... }  // 拼接所有操作
  if (useSync) buf += mEt;                    // 帧后：?2026l
  J5n(terminal, buf);                         // 一次性单次 write
}
```

**这就是「输出时终端不抖」的第一性原因**：

- `CSI ?2026h` … `CSI ?2026l` 之间，终端会**把这一段的绘制缓冲起来，收到结束符时整屏一次性上屏**。
  不被包住的逐条写入，终端会按自己节奏刷新，于是能看到「上一帧被擦、新一帧正在写」的中间态 = 闪烁。
- 整帧**只 `write` 一次**（`J5n` 一次调用），而不是每个小操作写一次——减少 syscall 与 PTY 分包。
- `skipSync` 是**降级开关**：终端不支持（DECRQM 2026 回 no）、或在 tmux/zellij/JetBrains 终端/`xterm.js` 里，
  就不发同步标记（发了反而会卡住不刷新）。

门控逻辑（`m0692_0x122af64b.js:99-125`）：


> **探测机制**：CC 会先发 `DECRQM 2026`（`CSI ?2026$p`）问终端支不支持同步输出，
> 用回复把 `synchronizedOutput` 从 `pending` 推到 `settled`（`m0701_0x122b603a.js:11403` 里
> `u.answer("synchronizedOutput", status === 1 || 2 || 3, ...)`）。
> 未确认前用 `likely` 的概率值兜底，且只在 `beforeTheAnswer`（正式回答前）时才乐观启用。

**复刻清单**：
1. 每帧用 `\e[?2026h` … `\e[?2026l` 包住，单次 write。

### 1.5 滚动区（DECSTBM）：让"滚动"变成终端的原生动作

`DECSTBM`（`CSI top;bottom r`）+ `SU`/`SD`（`CSI n S` / `CSI n T`）是 CC 的"零成本整体位移"手段：

```js
// m0108_0x1136a56c.js
function hxe(t, r) { return zl(t, r, "r"); }   // DECSTBM：设定滚动区 top;bottom
var Zpe = zl("r");                              // 复位滚动区
function Bta(t = 1) { return zl(t, "S"); }      // SU：向上滚 n 行
function jta(t = 1) { return zl(t, "T"); }      // SD：向下滚 n 行
```

用法（`m0701_0x122b603a.js:12507-12516`，差分器发现某区域整体位移时）：

```js
if (c && next.scrollHint && m) {          // c = altScreen，m = 同步输出可用
  let { bottom, delta } = next.scrollHint, top = Math.max(next.scrollHint.top, 1);
  if (top < bottom && bottom < prev.screen.height && bottom < next.screen.height) {
    gs(prev.screen, top, bottom, delta);        // ① 本地缓冲同步"滚动"（copyWithin）
    ops = [{ type: "stdout",
             content: hxe(top + 1, bottom + 1)   // ② 设滚动区
                    + (delta > 0 ? Bta(delta) : jta(-delta))  // ③ 让终端自己滚
                    + Zpe                        // ④ 复位滚动区
                    + content }];                // ⑤ 然后只画变化的那几行
  }
}
```

> ⚠️ **适用范围必须写准（易错点）**：这条路径的开启条件是 `c`，而 `c` 是 `nf.render` 的
> **第三个入参 `altScreen`**（调用点 `m0701_0x122b603a.js:16240`：
> `this.log.render(frontFrame_2, _, this.altScreenActive, ...)`）。
> 同时渲染器返回时也只在全屏模式下给出 scrollHint：
> ```js
> // m0701_0x122b603a.js:15542
> scrollHint: p.altScreen ? m.scrollHint : null,
> ```
> **所以 DECSTBM 滚动区只服务于 fullscreen（备用屏）模式，inline（主屏）模式根本不用它。**
> 主屏模式下承当"不重画历史"职责的是另一个机制：`scrolledOutRows` 水位跳过（见 §2.2）。
> 复刻时若把它当成主屏优化去实现，会得到一个永远不会生效的分支。

**为什么这很重要**（在它生效的场景里）：如果一段内容整体上移 N 行，逐格 diff 会输出「每一格都变」= 整屏重画；
而告诉终端「在这个矩形区内滚动 N 行」是**零成本**的，之后只需补画真正新出现的行。

**scrollHint 的生成条件**（`m0701_0x122b603a.js:14566-14600`）非常保守，值得抄：

```js
if (cachedLayout && cachedLayout.y !== newY) {
  let delta = cachedLayout.y - newY;                  // 位移量
  ... // 必须同时满足：
  //  ① 宽度铺满终端（x<=0 且 x+width>=终端宽）
  //  ② 前后两帧的 x / width 完全一致
  //  ③ 位移量 < 视口高度（|delta| < viewportHeight）
  //  ④ 没有 pending 的滚轮增量（ue === 0）
  //  ⑤ 高度变化量与位移量吻合，或是整体高度不变
  Le = { top, bottom, delta };   // 满足 → scrollHint
  else c.layoutShifted = true;   // 任一不满足 → 标记"布局变了"，走完整重画
}
```

再叠一层安全校验（同文件 `14604-14611`）：

```js
// 若这一块里有 paintsPastRect 的子节点（会溢出自身矩形绘制的元素）、
// 或上下文有选区/覆盖层、或有绝对定位元素跨越了这块，一律放弃 scrollHint
Le && !safeCondition ? c.scrollHint = null : ...
```

**复刻要点（第三层）**：
- 只有当**一块矩形区域整体位移、宽度没变、没有溢出绘制**时，才用滚动区优化；
- 否则老老实实逐格重画；
- 滚动区用完**必须立刻复位**（`CSI r`），否则后续所有输出都会被限制在区内 —— 这是最经典的坑。

## 2. 两种渲染模式：inline（主屏）与 fullscreen（备用屏）

CC 有两套完全不同的呈现架构，**这是「不晃」问题在架构层的答案**。

> ⚠️ **319 里有两个容易混淆的开关，必须先分清（这是本节最重要的一条）**：
>
> | 函数 | 位置 | 语义 | 默认（无设置、无环境变量时） |
> | --- | --- | --- | --- |
> | `N9e()` | `m0499_0x11b4eb5d.js:155` | **是否用备用屏渲染**（`AlternateScreen` 组件是否挂载） | **`true`（默认开）** |
> | `Kd()` | `m0499_0x11b4eb5d.js:123` | **是否认定当前为 fullscreen 产品形态**（灰度/引导闸门） | 取决于灰度开关，可能为 `false` |
>
> `N9e` 的最后一行就是 `return !0` —— 只要没被显式关掉、没在 tmux -CC / Windows-SSH / 屏幕阅读器下，
> **319 默认就走备用屏**。而 `Kd` 末尾是 `return e.gbGateCached`（灰度），是**另一件事**：
> 它控制「是否把 UI 当成 fullscreen 形态来排布（侧栏、鼠标交互、粘性提问等）」。
>
> 由此产生了三种实际组合：
>
> | 备用屏 `N9e` | 形态 `Kd` | 实际表现 |
> | --- | --- | --- |

### 2.2 inline 模式（主屏）——「输出进终端 scrollback」

主屏模式的核心特征是**历史输出被"提交"给终端自己的 scrollback**，不再由 App 持有：

- 屏幕高度 = 内容高度，从光标处继续打印；用户可以用终端自带的 scrollback 翻历史；
- App 只重画「视口内的最后若干行」（`viewport.height`）；
- 一旦某行滚出视口顶端，就**再也不改它**。

对应源码：`nf.render`（`m0701_0x122b603a.js:12489`）里的关键量 `q`（`m0701_0x122b603a.js:12353`）：


逐格比较回调里的处理（`m0701_0x122b603a.js:12554-12559`），注意两个布尔量的含义
（`m0701_0x122b603a.js:12523-12525`，`z = next.screen.height - prev.screen.height`）：


**注意这里不是"直接跳过"，而是"标记需要重置"** ——
如果一行已经滚出视口，却检测到它变了（说明 App 试图改历史），
CC 不会硬改，而是**标记 `ae = true` 触发一次 `clearTerminal`（`Nl(..., "offscreen", ...)`）整屏重置**。
这是"宁可整屏重置一次，也绝不在主屏上重画历史"的取舍。

`this.scrolledOutRows.set(next, q)` 把这个水位记下来，下一帧继续用。

**这是「不抖」在主屏模式的核心保障**：App 从不试图重画已经滚出去的历史，
于是不会出现「整屏往上挤、又往下弹」的抖动。
代价是：一旦真的需要动历史，就得整屏重画（会闪一下）——
所以 §1.5 的 scrollHint / §3 的布局分区都是在**避免走到这一步**。

### 2.4 两种模式的选择建议（给复刻者）

| | inline（主屏） | fullscreen（备用屏） |
| --- | --- | --- |
| 终端原生 scrollback（`Shift+PgUp`、tmux copy-mode） | ✅ 可用 | ❌ 被备用屏挡住 |
| 输出不闪 | 同步输出 + 差分 + 已滚出行水位（§2.2） | 整屏自己管 + DECSTBM 滚动区（§1.5）+ 每帧 park 光标 |
| 底栏/输入框不动 | 靠「正文区+底栏分区」（§3.1） | 靠外层 `height: rows`（`m1003`）+ 内层三段分区 |
| 鼠标滚动/选区/点击 | 有限（终端自己处理） | 全部自己实现（`MOUSE_*` 私有模式 + SGR 坐标） |
| 实现复杂度 | 中 | 高 |

CC 的选择是：**备用屏默认开启（`N9e` 默认 `true`），交互形态（`Kd`）按灰度逐步升级**。
产品自述把"不闪"等同于"备用屏 + 虚拟化滚动历史"，说明 CC 团队自己也认为
主屏模式下的不闪是"尽力而为"，备用屏才是"根治"。

> 复刻时如果只想要"不晃"，做完 §3 的分区 + §1.4 的同步输出 + §2.2 的已滚出行水位，
> 就已经拿到大部分体验；备用屏是"再上一个台阶"，但它会牺牲终端原生 scrollback，需要自己权衡。

## 3. 布局分区：为什么输入框永远不上下晃

这是用户明确指出「最厉害」的那一点。答案不是某个魔法组件，而是**三层叠加的约束**。

> ⚠️ **先说清楚这一节的取码对象（重要）**：
> 主 REPL 的界面在 319 里被拆成多个视图函数，且**同一套 flex 约束在多处重复出现**
> （主会话视图、`/diff` 面板、任务面板…）。下面引用的是**结构最清晰、能完整看到三段分区的那一处**
> （`m2124_0x1363573f.js` 里的 `QNe`，`/diff` 面板），
> 以及各视图共用的 `ScrollBox`（`m1047`）与备用屏外层（`m1003`）。
> **复刻时照抄的是这套"约束组合"，不是某个具体视图**；具体数值（padding、分割比例）各视图不同。

### 3.1 第一层：外层限高 + 三段分区

**① 备用屏外层把高度钉成终端行数**（`m1003_0x126e602e.js` 末尾，`_Pe` 组件）：

> 如果自研时只写 `100%` 而外层高度不确定，flex 会退化成"由内容决定"，界面立刻开始上下晃。
> **这是本节最容易抄错的一行。**

```js

  flexDirection: "column",
  paddingX: 1,
  paddingY: 1,
  flexShrink: 0,        // ◀ 绝不收缩
  children: [kd, Hi, nl, bc]   // [状态行, 提示, 进度, 文件变更块]
```

**这三条一起成立才有效果**：

| 约束 | 作用 | 缺了会怎样 |
| --- | --- | --- |
| 外层 `height: rows` + 内层 `height:"100%"` | 整个应用恰好占满终端，不多不少 | 内容变多 → 根变高 → 终端整体上滚 → 输入框上移 |
| 正文区 `flexGrow:1 + overflow:hidden`（内层 ScrollBox 再 `overflow:scroll`） | 正文只吃"剩下的"高度，且绝不把根撑大 | 正文变长 → 挤压底栏 → 输入框被顶上去 |
| 底栏 `flexShrink:0` | 底栏永远拿到自己需要的高度 | 正文变长 → 底栏被压缩 → 输入框变形 |

**这就是"输入框不晃"的全部秘密**，Yoga（flexbox）的 `flexGrow`/`flexShrink` 语义在这里用得极其准确。
复刻时如果用的是「直接打印 + 手动算光标位置」，几乎不可能做对；必须用一个真正的 flex 布局引擎。

> 注意区分两种 `overflow`：**正文区外层用 `hidden`**（只要"不许溢出"），
> **内层 `ScrollBox` 用 `scroll`**（要建立滚动视口）。两者混用才不会既溢出又滚不动。

**翻译成产品语言**：

- 输入框有**两个版本**：「完整版（standing，带上所有提示行/状态行）」和「精简版（bare，只留最必要的）」；
- 每次内容可变时，先测「完整版 + 这次的正文」能不能放进可用高度；

**这一条是"不抖"的最后一道保险**：很多自研 CLI 的输入框在"该不该显示提示行"之间反复横跳，
用户看到的就是输入框一会儿高一会儿矮。CC 的做法是**测量 → 决策 → 锁定**，且用 `contentKey`
（内容指纹）避免对同一内容重复决策（`N?.contentKey === contentKey` 的缓存判断遍布全程）。

### 3.8 折叠组的计数「只增不减」：避免摘要行数字回跳

CC 会把一串读文件/搜索的工具调用合并成一行摘要（`collapsed_read_search`）。
摘要行上的数字（"3 searches, 5 reads"）如果每帧都按实时值渲染，会在某些中间态**变小**，
视觉上就是数字乱跳。

CC 的解法在 `m2057_0x1350b61e.js:8826-8841`：

```js

      mcp = message.mcpCallCount ?? 0, bash = message.bashCount ?? 0;

      search2 = Math.max(prev.search, search),
      list2   = Math.max(prev.list,   list),
      mcp2    = Math.max(prev.mcp,    mcp),
      bash2   = Math.max(prev.bash,   bash);

if (next.read !== prev.read || next.search !== prev.search || next.list !== prev.list
    || next.mcp !== prev.mcp || next.bash !== prev.bash) setPrev(next);
```

**为什么必须这样**：一次工具调用在被 `grouped_tool_use` 吸收/拆出的过程中，
计数会短暂地"少算一个"。如果不做单调化，用户会看到 "5 reads" → "4 reads" → "5 reads"。
`Math.max` 让它在任何中间态都保持最大值，**数字只会涨，永不跌** —— 视觉上就稳定了。

**这条可以推广成一条通用原则**：
> 任何"累计型"的展示数字（工具调用数、token 数、文件数、耗时），
> 只要真实值可能因为数据重组而短暂回退，就应该对展示值做单调化。

- 后续内容**只增不减**（`if (height > minHeight)`），所以 `minHeight` 是单调的台阶，

- 内容变多时**新的一帧只是把 minHeight 抬到新高度**，抬升是"一次跳"而不是"连续抖"；

- `lock:"offscreen"` 那个分支是纯优化：在 `ScrollBox` 内且当前不可见时，**连 setState 都不做**，

### 4.2 工具结果行：`⎿` + 高度锁（`m1791_0x130ab0ea.js` 全文）

- `height` prop 允许上层显式指定行数（用于"折叠到 N 行"的场景）——显式指定时**跳过高度锁**（更省）。

折叠加预算，让"超长工具输出"不会卡住渲染。

## 5. 滚动为什么"丝滑"（核心：增量不直接改 scrollTop）

### 5.1 滚轮 → pendingScrollDelta → 每帧衰减

滚轮事件**不直接改 `scrollTop`**，而是累加到一个 `pendingScrollDelta`，然后**每帧只消耗一部分**
（`m1047_0x12733eb9.js:78`）：

```js

```

每帧在布局阶段消耗它（`m0701_0x122b603a.js:14790-14805`）：


两条衰减曲线（`m0701_0x122b603a.js:14215-14240`）：

```js
// ── 自适应曲线（useAdaptiveDrain）：大增量一次吃掉大头，留一点余量
var oR = 4, lR = 5, aR = 12, sR = 2, uR = 3, bf = 30;
function drainAdaptive(node, delta, step) {
  let sign = delta > 0 ? 1 : -1, mag = Math.abs(delta), out = 0;
  if (mag > bf) out += sign * (mag - bf), mag = bf;         // 超过 30 的部分一次性吃光
  let chunk = mag <= lR ? mag : mag < aR ? sR : uR;          // ◀ 小增量全吃，中增量吃 2，大增量吃 3
  out += sign * chunk;
  let rest = mag - chunk;
  let cap = Math.max(1, step - 1);
  if (Math.abs(out) > cap) {                                 // 超过每帧上限 → 把溢出退回 pending
    let over = Math.abs(out) - cap;
    node.pendingScrollDelta = sign * (rest + over);
    return sign * cap;
  }
  node.pendingScrollDelta = rest > 0 ? sign * rest : undefined;
  return out;
}

// ── 比例曲线（默认）：每帧吃掉剩余量的 3/4（至少 4 行）
function drainProportional(node, delta, step) {
  let mag = Math.abs(delta);
  let cap = Math.max(1, step - 1);
  let take = Math.min(cap, Math.max(4, (mag * 3) >> 2));     // ◀ 75%
  if (mag <= take) { node.pendingScrollDelta = undefined; return delta; }
  let out = delta > 0 ? take : -take;
  node.pendingScrollDelta = delta - out;
  return out;
}
```

**这就是"滚轮手感"的配方**：

- **永不瞬移**：一次滚轮 delta=100，不会一帧跳到 100，而是分多帧（每帧 75%）走完；
- **大增量有紧急通道**：`mag > 30` 时超过 30 的部分**立即**吃掉（`out += sign * (mag - bf)`），
  所以"猛滚一下"不会慢吞吞；
- **小增量立即完成**：`mag <= 5` 全吃（`chunk = mag`），所以单格滚动是**即时**的，没有黏滞感；
- **中增量分 2-3 步**：`5 < mag < 12` 每帧吃 2，`mag >= 12` 每帧吃 3 —— 形成"快-慢"的自然减速感；
- **每帧上限**（`step - 1`）防止一帧内跳太多导致跳帧；
- **撞边界降到 1/8** → 橡皮筋效果。

**这是整个产品里最值得抄的一段代码**。它把"滚轮事件的不确定性"（不同终端 delta 单位不同、
触控板 vs 鼠标差异巨大）归一化成了一条可控的动画曲线。

### 5.3 滚轮加速度曲线（`m2124_0x1363573f.js:8391`）

§5.1 管的是「一次滚轮 delta 怎么分帧消耗」，而**一次滚轮事件该折成多少行**由另一层管：
`mNt`（`m2124_0x1363573f.js:8428`）。它有两种模式，由 profile 的 `useDecayCurve` 选。

常量表（`m2124_0x1363573f.js:8391-8417`）：

```js

  VOt = 0.3,     // 非 decay 模式的加速度增量
  KOt = 6,       // 非 decay 模式的倍率上限基数

  M0e = 5,       // 同一方向的"突发"阈值（ms）：小于则只算 1 行
  oNt = 80,      // decay：慢速段阈值（ms）
  nNt = 3,       // decay：慢速段倍率上限
  rNt = 36,      // decay：快速段倍率上限

  dNt = 0.008,   // JetBrains：每次累加的加速度
```

decay 模式的核心（`m2124_0x1363573f.js:8479-8494`）：

```js
// decay 分支

let sameDir = dir === state.dir;
state.time = now; state.dir = dir;

else {
  let decay = Math.pow(0.5, gap / A0e);                 // ◀ 半衰期 150ms
  let cap   = gap >= oNt ? nNt : rNt;                   // 慢速上限 3 / 快速上限 36
  state.mult = Math.min(cap, 1 + (state.mult - 1) * decay + tNt * decay);
}
let total = state.mult + state.frac;

state.frac = total - rows;                              // ◀ 小数部分保留到下次，避免"丢步"

```

**这条曲线的含义**（这是"滚轮手感"的第二层）：

- **越滚越快**：连续同向滚动时 `mult` 按半衰期 150ms 向上累积（`1 + (mult-1)*decay + 7*decay`），
  快速连续滚动时倍率能到 36 —— 这就是"想快速翻页时滚轮很给力"；
- **停一下立刻恢复**：gap > 500ms 直接重置 `mult = base`；
- **方向翻转清零**：`!sameDir` 时同样重置 —— 反向滚动不会延续之前的加速；
- **小数部分不丢**（`state.frac`）：保证长期平均速率准确，不会因为 `floor` 而"越滚越慢"；
- **慢速上限只有 3**：gap >= 80ms 时倍率封顶 3 —— 慢慢滚就是精确的逐行，不会突然加速。

非 decay 分支（`m2124_0x1363573f.js:8432-8478`）是"窗口计数"模式，更保守：
`wheelMode` 状态机 + `burstCount >= 5` 退出、`pow(0.5, gap/150)` 衰减、倍率上限 `min(base*2, ...)`。
它用于**不支持 decay 的终端**（wheelFlood 时 `base = 3`），避免在会"滚轮洪水"的终端里加速过头。

JetBrains 分支（`m2124_0x1363573f.js:8420`）是纯手工拟合的：

2. 阈值（5ms 去抖 / 40ms 停顿 / 150ms 半衰期 / 80ms 慢速上限）直接照抄，这套数值是调过的；
3. 如果终端会把滚轮转成方向键，把这部分计数补回加速度，不要简单丢弃。

### 5.4 粘底（sticky scroll）：新内容自动跟随，但不打断用户

`m0701_0x122b603a.js:14775-14789`：

**注意三个细节，都是"不打断用户"的关键**：

1. **必须 `pendingScrollDelta >= 0`** 才跟随 —— 用户一旦向上滚（负增量），**立刻停止跟随**；
2. **"已经贴底"才恢复粘底**（`O >= maxScroll`），且位移 > 3 行才打日志 —— 避免在临界点反复切换；
3. **`scrollHeightHwm`（历史最高）**：非粘底时记住"内容曾经有多高"，
   这样内容缩短时 `maxScroll` 不会突然变小、把用户"甩"到底部。

`scrollHeightHwm` 的清空时机也很讲究（`m1047_0x12733eb9.js`）：只有在
`scrollTo` / `scrollToElement` / `scrollBy` / `scrollToBottom(sticky=false)` 时才清 —— 即**只有用户主动操作才重置**。

### 5.5 锚点滚动：`scrollAnchor`（内容重排后仍停在原位置）

当某块内容高度变化（比如折叠展开），需要"保持某个元素在视口里的位置不变"，CC 用 `scrollAnchor`
（`m0701_0x122b603a.js:14750-14773`）：


## 6. 其余让体验"丝滑"的细节

### 6.1 帧内操作合并（`ff`，`m0701_0x122b603a.js:13240`）

差分产出的操作序列在写出前会再压一遍：

```js
function coalesceOps(ops) {
  let out = [], n = 0;
  for (let op of ops) {
    if (isEmptyOp(op)) continue;                     // 空 stdout / 零位移 / 零样式 / 零清行 → 丢
    if (n > 0) {
      let prev = out[n - 1];
      if (op.type === "cursorMove" && prev.type === "cursorMove") {   // 相邻光标移动合并
        let x = prev.x + op.x, y = prev.y + op.y;
        if (x === 0 && y === 0) out.pop(), n--; else out[n - 1] = { type: "cursorMove", x, y };
        continue;
      }
      if (op.type === "cursorTo" && prev.type === "cursorTo") { out[n - 1] = op; continue; }
      if (op.type === "styleStr" && prev.type === "styleStr") {       // 相邻样式串拼接
        out[n - 1] = { type: "styleStr", str: prev.str + op.str }; continue;
      }
      if (op.type === "hyperlink" && prev.type === "hyperlink" && op.uri === prev.uri) continue;
      if ((op.type === "cursorShow" || op.type === "cursorHide") &&
          (prev.type === "cursorShow" || prev.type === "cursorHide")) { out[n - 1] = op; continue; }
    }
    out.push(op), n++;
  }
  return out;
}
```

**收益**：一次 diff 可能产出几百个小操作，合并后往往只剩几十个。
每次合并都减少了写出的字节数 —— 对 PTY（尤其是 SSH / tmux）是数量级的差别。

### 6.2 样式池：避免重复生成 SGR 串（`wd`，`m0701_0x122b603a.js:9833`）

每个格子只存一个 `styleId`（整数）。输出时：

```js
stylePool.transition(fromStyleId, toStyleId)   // 返回最短的 SGR 迁移串（可能为空）
```

`transition` 比"reset + 重新设"短得多，且**相同样式之间的连续格子不产生任何字节**。
配合 §6.1 的合并，一次滚动可能只输出"滚动区序列 + 几十字节的文字"。

### 6.3 光标"停车"（park）与声明式光标

CC 不用终端的真实光标做输入光标，而是**在屏幕缓冲里画一个光标格**，每帧把真实光标 park 到固定位置。

- 非全屏：park 到内容末尾之后（`cursor.y = screen.height`）；
- 全屏：park 到 `min(screen.height, terminalRows) - 1`（最后一行），并每帧追加 `altScreenParkPatch`；
- 若开了 `nativeCursor`，才把真实光标移到 `cursorDeclaration` 算出的位置
  （`m0701_0x122b603a.js:16282-16349`）。

好处：**真实光标不会在绘制过程中乱窜**（那会被用户看到），一切可见的光标都是缓冲里的一格。

### 6.4 池压缩：长时间运行不退化

`charPool` / `stylePool` / `hyperlinkPool` 会在超过阈值时压缩（`m0701_0x122b603a.js:17325`）：

```js

  this.lastPoolResetTime = now; this.resetPools();
}

                needStyle ? this.stylePool.compact() : undefined);

```

门控函数 `_v`（`m0701_0x122b603a.js:15560`）：

```js
function _v(sinceMs, stylePool, lastLiveSize) {
  let minGap = stylePool.isNearCapacity ? 1000 : 30000;      // 接近容量 → 1s 检查一次，否则 30s
  return sinceMs > minGap && (sinceMs > 300000 || stylePool.needsCompaction(lastLiveSize));
}
```

即：**平时 30 秒检查一次、接近容量时 1 秒一次、最多 5 分钟强制检查一次**。

**这是"CC 开一整天也不变卡"的原因之一**：池不会无限增长。
复刻时如果每帧都 new 一堆样式对象/String，跑几小时一定退化。

**粘性提问（StickyPrompt）**：滚动时在顶部固定显示"当前正在看的是哪个用户提问"（`m2064_0x13551547.js:8773`，函数 `ED`）：

```js
function ED({ messages, start, end, offsets, getItemTop, getItemElement, scrollViewport, scratch, releaseReveal }) {
  let { setStickyPrompt } = useStickyPromptStore();
  let isSticky = useSyncExternalStore(scrollViewport, vp => vp?.isSticky() ?? true);
  let scrollTop = Math.max(0, useSyncExternalStore(scrollViewport, vp => vp ? vp.getScrollTop() + vp.getPendingDelta() : 0));

  // ① 找出第一个"还在视口内"的项 Q
  let Q = start, X = -1;
  for (let i = end - 1; i >= start; i--) {
    let top = getItemTop(i);
    if (top >= 0) { if (top < scrollTop) break; X = top; }
    Q = i;
  }

  // ② 从 Q 往前找最近的一条用户提问，且它已经滚出视口顶部
  let promptIdx = -1, promptText = null;
  if (Q > 0 && !isSticky) for (let i = Q - 1; i >= 0; i--) {
    let text = lf(scratch.promptText, messages[i]);   // 从一条消息里抽出"用户提问文本"，非用户消息返回 null
    if (text === null) continue;
    let top = getItemTop(i);
    if (top >= 0 && top + 1 >= scrollTop) continue;
    promptIdx = i; promptText = text; break;
  }

  // ③ 压成单行：只取第一段，压平空白，截断
  let text = promptText.trimStart();
  let blank = text.search(/\n\s*\n/);
  let line = (blank >= 0 ? text.slice(0, blank) : text).slice(0, TD).replace(/\s+/g, " ").trim();

  setStickyPrompt({ text: line, scrollTo: () => { ...点一下能滚回去... } });

```

细节全在"不抖"上：

- **只取第一段**（`text.search(/\n\s*\n/)` 切），压平成单行（`.replace(/\s+/g, " ")`），截断到 `TD = 500` 字符；
- **粘底时不显示**（`!isSticky`）：用户已经贴底时不需要"你在看哪一条"；
- **`getScrollTop() + getPendingDelta()`**：把"还没消耗完的滚动量"也算进去 ——
  否则滚轮刚开始的几帧里，粘性标签会算错位置、闪烁；
- **点击能滚回去**（`scrollTo`）：粘性标签不只是装饰，是可交互的跳转。

### 6.7 大模型的"叙事感"文案（spinner 动词 + 计时）

spinner 的动词表在 283/303/319 基本一致（`m1027_0x127059de.js` 的帧序列，

（`m2124_0x1363573f.js:80628`）：

```js

  context: () => this._freshTipContext(),
  show: (h) => {
    let { setAppState } = this._requireHost();
    this._publishTipBetweenTurns(() => setAppState((D) =>
      h === undefined
        ? (D.spinnerTip === undefined ? D
           : { ...D, spinnerTip: undefined, spinnerTipLabel: undefined })
        : (D.spinnerTip === h.text && D.spinnerTipLabel === h.label ? D     // ◀ 内容相同 → 返回原对象

```

两个可抄的点：

1. **内容相同就返回原 state 对象**：React 的 `setState` 收到同一引用会跳过重渲染 ——

2. **`_publishTipBetweenTurns`**：提示的更新被推迟到「两个 turn 之间」发布，

## 7. 复刻清单（按性价比排序）

### P0 —— 不做就一定抖

1. **用真正的 flexbox 布局引擎**（Yoga / Taffy），而不是手算行列。
   没有它，§3 的所有约束都无处落地。
2. **根容器限高 + 三段分区**（§3.1）：
   `root{height:rows} > [body{flexGrow:1,overflow:scroll}, footer{flexShrink:0}]`。
3. **每帧用 `CSI ?2026h` … `CSI ?2026l` 包住，且只 write 一次**（§1.4）。
   探测不支持就关掉。
4. **格子缓冲 + 逐格 diff**，不要清屏重画（§1.3）。
5. **所有"会变的单行文本"加 `height:1 + overflow:hidden + truncate-end`**（§3.5）。

### P1 —— 决定"手感"

6. **帧节流**：基础 16ms，输入时降到 4ms；stdout 积压 >16KB 时停帧 250ms（§1.2）。
7. **滚轮 → pendingDelta → 每帧消耗 75%（小量全吃，大量有紧急通道）**（§5.1）。
8. **滚轮加速度曲线**：同向连续加速（半衰期 150ms）+ 停顿/翻向重置 + 小数位保留（§5.3）。
9. **粘底 + 历史最高（HWM）**：向上滚立即取消跟随；已贴底才恢复；内容缩短不甩到底（§5.4）。
10. **高度锁（单调递增的 minHeight）**：流式块、工具结果块各包一层（§4.1、§4.2）。
11. **提示文案三级降级**，永不让它换行（§3.4）。
12. **折叠保留 3 行 + 恰好剩 1 行时不折叠 + 动态键位提示**（§4.3）。

### P2 —— 锦上添花

13. **DECSTBM 滚动区**：整块矩形位移时用 `CSI t;b r` + `CSI n S/T`，用完立刻 `CSI r` 复位（§1.5）。
14. **操作合并 + 样式池**（§6.1、§6.2）。
