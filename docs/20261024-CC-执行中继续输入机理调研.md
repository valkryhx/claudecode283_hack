
# 20261024-CC 执行中继续输入机理调研（Claude Code 2.1.303）

> 对象：Claude Code 2.1.303 反编译产物 `reconstructed303/deminified/`
> 问题：agent 正在跑（模型调用中 / 工具执行中）时，用户继续输入会发生什么？消息什么时候被读到？
> 结论口径：全部结论附 `模块:行号`，模块路径前缀 `reconstructed303/deminified/`。

---

## 0. 结论先行

1. **CC 没有"边跑边把新输入塞进当前模型请求"这种能力**。它做的是**命令队列**：
   忙碌时 Enter 不打断当前回合，而是把这条输入**入队**；队列在三个时机被消费。

2. 队列是**单一全局对象** `messageQueue`（`m0459:30870` 起暴露完整 API），
   主线程、子 agent、任务通知、peer 消息、poll 事件**共用同一个队列**，靠 `mode` / `priority` / `agentId` 区分。

3. 三个消费时机：
   - **轮内吸收（mid-turn fold）**：每个工具批次结束后，把 `priority=next` 的用户消息作为
     `queued_command` attachment 插进**同一回合**的工具结果之后（`m0671:9353-9411`）。
   - **轮末起新回合**：当前回合结束后，drain 循环取队头，开下一回合（`m1809:4852-4870`）。
   - **中断提前**：`priority=now` 一出现，立刻 abort 当前回合，让这条消息马上开始（`m1809:9817`）。

4. 模型看到的不是"队列"，而是一段被包装过的 user 文本：

   ```text
   The user sent a new message while you were working:
   <原文>

   This is how Claude Code surfaces messages the user sends mid-turn — within the running turn,
   often alongside the next tool result, rather than as a separate conversation turn.
   Address the message above as you continue this turn.
   ```

   前缀定义在 `m0108:219`（`QJe`），包装函数 `z4n` 在 `m0459:214545`。

5. **入队前先过 `prompt.submit` hook**（`m0649:363` `dPn`）。hook 可以改写文本、直接回答、或拒绝；
   被拒绝的消息**退回草稿**，不会静默消失。还没跑完 hook 的消息带 `screeningPending`，
   轮内吸收会**跳过它**并让后面的消息一起等待，保证顺序。

6. 队列有**三档优先级**：`now=0` / `next=1` / `later=2`（`m0459:29824`）。
   人类输入默认 `next`；任务通知默认 `later`；"立即发送"把它抬到 `now`。

7. **同一次取队可以合并多条**：队头 + 兼容的 followers 合并成一条命令（`Bc`，`m1809:2186`；
   兼容判定 `ek`，`m1809:2237`），所以连发几条会在同一个回合里被模型一起看到。

8. **Esc 有两级语义**：先退出"队列编辑"态；再按才取消。取消时**默认清空排队的人类消息**
   （`reason: "cleared_on_cancel"`，`m1635:24017`、`m1809:9336`），系统类条目按 `keep` 谓词保留。

9. **上箭头编辑队列**：`popAllEditable` / `popEditableAt` 把排队消息拉回输入框
   （`m1635:44321`、`m1635:46362`），`queueEditIndex` 记录当前选中第几条（0=最老）。

10. SDK / 远程侧能看到队列深度：结果里带 `queued_turn_count`（`m0120:7756`），
    含义是"本次 result 产生时还有多少条用户发送在排队"。

## 2. 命令队列数据模型

### 2.1 优先级

```js
// m0459:29824
e1 = { now: 0, next: 1, later: 2 };
```

取值越小越优先。`Ls`（`m0459:30659`）取队头时按 `e1[priority]` 升序挑；
同优先级按入队时间（FIFO）。

### 2.2 模式（`mode`）

| mode | 来源 | 默认优先级 |
| --- | --- | --- |
| `prompt` | 人类输入（键盘 / 粘贴 / 语音） | `next` |
| `bash` | 输入框 `!command` | `next` |
| `task-notification` | 后台任务 / 子 agent 完成通知 | `later` |
| `poll-event` | 轮询事件（channels、外部回调） | `later` |
| `orphaned-permission` | 失去宿主的权限请求 | `later` |

默认值来自两处：用户类 `Lr`（`m0459:30430`）默认 `"next"`；
通知类 `Fo`（`m0459:30483`）默认 `"later"`。

### 2.3 条目字段

入队对象（`m1635:71848` 一带的真实字段 + `m0459` 队列实现里读到的字段）：

| 字段 | 含义 |
| --- | --- |
| `uuid` | 条目唯一 id |
| `value` | 文本 / 命令内容 |
| `mode` | 见上表 |
| `priority` | `now` / `next` / `later` |
| `origin` | 来源标记（人类 UI、SDK、peer、channel…） |
| `timestamp` | 入队时间 |
| `isMeta` | 元信息条目（不作为用户消息投喂） |
| `screeningPending` | **prompt.submit hook 还没跑完**，暂不可投递 |
| `screeningOwed` | 需要跑筛查（用于结算/超时） |
| `drainOnly` | 只在 drain 阶段消费，不参与轮内 fold |
| `promptSubmitted` | 已跑过 submit hook |
| `shouldQuery` | `false` 表示"只记录、不触发新回合" |
| `skipSubmissionHooks` | 明确跳过 hook |
| `handedOffTurn` | 已移交给某个回合 |
| `workload` / `wakeupSource` | 唤醒来源（后台任务、cron、peer） |
| `passive` | 被动条目，不计入"用户意图" |
| `unlogged` | 不进 transcript |

> 判定"这是不是人类意图"的谓词是 `Mo()`（`m0459:30330`），
> 组合了 `Cf(e)`（`m0459:29873`：`mode` 是 prompt/bash 且非 `isMeta` 且 `origin` 合法）
> 与 `Rf(e)`（`m0459:29902`：主线程且 `passive !== true`）。
> 它决定了"按 Esc 时该清掉谁""有没有必要提示用户"。

### 2.4 API（`m0459:30870` 起）

## 3. 输入侧：忙碌时按 Enter 到底做了什么

### 3.1 分叉点

输入框的提交函数（`m1635` 中负责 Enter 的那段）第一句就是忙碌判定：

```js
// m1635:71938
if (Lt.isActive || Qt || Kt) {
```

- `Lt.isActive`：当前回合正在跑（`Lt` 是 `mr()` 拿到的 turn guard）
- `Qt`：有正在进行的提交
- `Kt`：还有待处理的 UUID 批次

三个都为假 → 走 `gmt()`（`m1635:72090`），**直接开新回合**；
任一为真 → 走**入队分支**。

### 3.2 入队分支的关键步骤（`m1635:71938-72060`）

1. **只允许 `prompt` / `bash` 入队**：
   ```js
   if (eo !== "prompt" && eo !== "bash") {
     m("prompt_queued", "mode_not_queueable");
     return
   }
   ```
   其它模式在忙碌时直接拒绝（不会排队）。

2. **清空输入框**（`h.composerClearedAtEnter !== !0` 时）：`de("")`、`Pt(0)`、`ve({})`。
   即**Enter 后输入框立刻清空**，内容已经"搬进队列"。

3. **`Ct.enqueue({...})`**：把 `fn`（含 `pastedContents`、`origin`、`mode`）连同
   `value: zo.trim()` 一起入队；如果消息带 IDE 选区，会附 `ideSelection`。

4. **三种"需要先跑 hook"的标记**：

   | 条件 | 加的字段 | 含义 |
   | --- | --- | --- |
   | `jo`（本地模型正在跑、且不是"下一条输入"路径） | `screeningPending: true` | hook 未完成，轮内 fold 必须跳过它 |
   | `uo` 或 `mn` | `drainOnly: true` | 只能等回合末 drain，不进轮内 fold |
   | `mn` | `screeningOwed: true` | 明确记账：这条还欠一次筛查 |

   > `drainOnly` 的用意：某些消息（例如带 slash 展开、或需要完整上下文的）在**当前回合中途**投递
   > 会造成语义错位，所以强制留到回合边界。

5. **`jo === false` 时立即返回**（`m1635:71968`：`g("prompt_queued"); return`），
   不跑 hook —— 这类条目会在 drain 阶段补跑。

6. **`jo === true` 时同步跑 `prompt.submit` hook**：

   ```js
   zn = await dPn({
     submission: { text, input: text, pastedContents },
     origin, bridgeOrigin, mode, turnId,
     shouldWait: h.wait === !0,
     context, result: Zn, isStartInput: false,
     promptSource: ...,
     enter: async (En) => { ur = true, jn(En) }
   })
   ```

   - `dPn` 定义在 `m0649:363`，返回 `arrived` / `answered` / `dropped` 三态。
   - `enter` 回调 = hook **决定让消息进入**时触发，`ur` 置真，之后不再重复结算。
   - 结果通过 `Ct.settleScreening(co, {...})` 写回队列条目：
     成功则填 `promptSubmitted`（含改写后的 `text`、`context`、`messages`），
     并视情况把 `drainOnly` 置真。

7. **hook 拒绝（dropped）**：`settleScreening(co, { dropped: true })` 后，
   把文本**放回输入框**（`h.restoreHandedBackPrompt` 或 `de($I(当前输入, to))`），
   并弹一条通知：
   ```js
   h.addNotification?.({
     key: "prompt-submit-dropped",
     kind: "feedback",
     text: zn.ended.resultText ?? "Prompt dropped by a hook",
     priority: "immediate",
     requeueOnPreempt: true
   })
   ```
   即**被 hook 拦下的输入不会丢**，用户能在输入框里看到它、改一改再发。

8. **hook 异常**：只记日志 `"prompt.submit at Enter failed, leaving it to the drain"`，
   **条目留在队列里**，等 drain 阶段再处理 —— 不因为 hook 崩了就把用户输入丢掉。

9. **`answered`**：hook 自己给出了回答，`ir(or.text, ...)` 直接当回复展示，
   消息不进模型上下文。

### 3.3 空闲分支（`gmt`，`m1635:72090`）

空闲时不是"入队再出队"，而是**直接开回合**：
`gmt({ inputSource, queuedCommands: [fn], ... })`。
但内部仍然用同一个 `queuedCommands` 结构，所以"刚输入"和"排队后执行"走的是**同一套投递代码**，
差别只在 `inputSource`（`"typed"` vs `"queued"`）和 `dequeuedAtMs`。

## 4. 轮内吸收（mid-turn fold）—— 边跑边被"看见"

这是"用户在执行时继续输入，模型不用等回合结束就能看到"的核心机制。

### 4.1 位置：每个工具批次之后、下一次模型调用之前

`m0671` 的 query 循环里，一批工具执行完后会进入这段（`m0671:9301-9420`）。
它位于"工具结果已拿到、下一次 `callModel` 还没发"的缝隙里。

### 4.2 候选集合 `wi()`

```js
// m0671:9323
let wi = () => jxe(
  messageQueue.getCommandsByMaxPriority("next")
    .concat(queuedNotificationsRegistry.heldNudge({ agentId, messageQueue, ccrTurnId, nobodysTurn })),
  { isMainThread, currentAgentId }
).filter(nu(vZr(() => updatedToolUseContext_2, { latch: true })));
```

三个过滤器：
- `getCommandsByMaxPriority("next")`：**只要 `next` 档**（`now` 会走中断，`later` 不参与）；
- `jxe(..., {isMainThread, currentAgentId})`：只要**本 agent、本线程**的条目；
- `nu(vZr(ctx, {latch: true}))`：按"入队时看到的上下文"做去重/时效判定（`latch` 表示锁定入队时的快照）。

另外并入 `heldNudge`：本该提示但被压住的系统提醒，也走同一条投递通道。

### 4.3 两个门禁

```js
// m0671:2914
function sl({ foldSuspended, isMainThread, lastIteration }) {
  return !foldSuspended && (!isMainThread || !lastIteration)
}
```

- `foldSuspended`：队列被显式挂起（`suspendMidTurnFold`，例如用户正在编辑队列）；
- `lastIteration`：**主线程的最后一轮不吸收** —— 这一轮结束后就该开新回合了，
  再"塞进当前回合"反而会让顺序错乱。

```js
// m0671:9340
let deliverable = messageQueue.isMidTurnFoldSuspended() || maxTurns_2 !== void 0 ? [] : wi();
```

`maxTurns` 用尽时也清空 —— 已达上限就不该再往本回合加东西。

### 4.4 逐条筛查 `lc`（`m0671:566`）

```js
for (let T of e) {
  if (pr(T, s)) continue;              // pr = (e,o)=> o && e.mode==="prompt"  —— 前面有"等待"的，后面的 prompt 一起等
  if (!mr(T) || !k) { n.push(T); continue; }   // mr = 已提交 hook 且 shouldQuery!==false 且未 skip
  f = true;
  let v = await ia(T, o);              // ia = 投递前筛查（可跑 hook）
  switch (v.fate) {
    case "surfaces": n.push(T); break; // 投递
    case "waits":    s = true; break;  // 本条目等待，且**阻塞后续 prompt**
    case "dropped":  notices.push(...), dropped.push(T); break;
    case "left":     break;            // 留在队列
  }
}
```

**关键不变量（顺序性）**：一旦某条 `prompt` 判定为 `waits`，`s = true`，
后面所有 `prompt` 条目在 `pr(T, s)` 处被跳过 —— 保证**不会越过一条还没准备好的消息去投递后面的**。

异常兜底：`catch` 时返回 `deliverable: Ji(e, messageQueue)`（= 只保留仍在本线程队列里的），
`notices` / `dropped` 照常返回 —— 筛查崩了也不会误删。

`f`（是否有条目真的跑过筛查）决定返回值要不要再过一遍 `fr`（`m0671:443`，过滤"已不在队列"的）。

### 4.5 投递与"发送失败要退回"


- `wpe` 是"把队列条目变成 attachment 事件"的生成器；产出 `{type:"queued_command"}` 的 attachment，
  与工具结果**同批**进入下一轮模型输入。
- 每条 `queued_command` 还会补发 `of(Ee.promptSubmitted, ctx)` 产出的事件
  （hook 改写后的附加上下文 / messages）。
- `command_lifecycle` 事件（`started` / `completed`）用于 UI 展示"某条排队命令开始/结束"。

### 4.6 结算：只有真正发出去的才出队

```js
// m0671:9394

```

三条硬规则：

1. **发出 0 条 → 全部留队**（degraded），绝不"以为发了其实没发"地丢掉；
2. **只发出一部分 → 只删已发的**，未发的留在队列（并记 error 级日志）；
3. **abort 或 fold 被挂起 → 全部留队**，下一轮再来。

`consume(reason:"absorbed_mid_turn")` 是唯一的"出队"动作，带 reason 便于审计。

## 5. 轮末起新回合（drain loop）

### 5.1 主循环

```js
// m1809:4844
let intake = new qf({ messageQueue, drain, prewaitLatch, deliveryLedger, io, ... });
...
for (;;) {
  let Ie = V.waitForHead(ve);          // 等队头出现（无队头就挂起，不空转）
  if (Ie) await Ie;
  ...
  let me = intake.take();              // 取一批
  if (me === void 0) { break; }        // 没有可跑的 → 退出循环
  ...
  // 跑这一回合
}
```

要点：
- **没有忙等**：`waitForHead` 是一个可 await 的 latch，队列为空时整个循环挂起，
  入队事件把它唤醒（`m1809:1593` 的 kick）。
- 每一轮迭代 = **一个回合**。回合结束回到 `for(;;)` 顶部，重新等队头。

### 5.2 `take()` 的取头规则（`m1809:4508`）

```js
let command = drain.endSessionRequested
  ? startGate.takeHead(endSessionHead, () => messageQueue.dequeue(endSessionHead))
  : startGate.takeHead(s => Rf(s) && !selector.holdsBack(s), () => selector.takeHead());
```

- `Rf(s)`：**只取主线程的条目**（`Gp(e) = e.agentId === Ze()`，`m0459:13682`）；
- `!selector.holdsBack(s)`：选择器可以压住某些条目（等前一个回合的收尾、等 eval 结算、
  等 task-notification 合并窗口等）；
- 结束会话时改取 `endSessionHead`（一条专门的"结束"条目）。

取不到时还有一条**兜底**：如果 `heldCompletionChars > 0`（后台任务完成通知被压着没发），
就**造一个合成的空 prompt**（`mode:"prompt"`, `isMeta:true`, `skipSubmissionHooks:true`）
去触发一次模型调用，好把那些完成通知一并交付。

### 5.3 followers 合并（`m1809:4536`）

```js
let members = [command];
if (command.mode === "prompt" && !drain.endSessionRequested) {
  members.push(...selector.takeFollowers(command, h => startGate.admits(h)));
  ...
  if (members.length > 1) command = Bc(members);
}
```

- `takeFollowers`：把队头后面**同批次可合并**的条目一起取走；
- `Bc`（`m1809:2186`）：合并成一条。文本用 `FI` 拼接（都是字符串就 `join("\n")`），
  `fileAttachments` 取并集，`uuid` 用**最后一条有 uuid 的**，`turnAttributionKey` 重新算；
- 合并兼容性由 `ek`（`m1809:2237`）判定，条件非常细：`mode`、`workload`、`isMeta`、
  `shouldQuery`、`wakeupSource`、`origin`（含 peer / slack / channel 各类来源标记）、
  `priority`、`skipAttachments`、`skipSlashCommands`、`inlinedImagePaths`、`textNotTyped` …
  只要有一项不同就不合并。

> 效果：用户连发三条短消息，agent 通常**只被唤醒一次**，三条作为一段合并文本进入同一个回合。

### 5.4 取消标记在取队时就生效

```js
let s = members.filter(item => item.uuid !== void 0 && messageQueue.consumeCancelPending(item.uuid));
if (s.length > 0) {
  this.revokeCodeliveredFollowups(s);
  for (let S of s) this.io.onCommandLifecycle?.(S.uuid, "cancelled");
  this.deliveryLedger.dropTaken(s.map(item => item.uuid));
  let h = members.filter(item => !s.includes(item));
  if (h.length === 0) { this.prewaitLatch.reset(); continue; }
  members.length = 0; members.push(...h); command = h[0];
}
```

`consumeCancelPending` 是**一次性**的：用户取消某条排队消息后，即使它已经被取出来，
只要还没真正开始跑，就会被剔除。`commit()`（`m1809:4568`）里还会再查一次，
覆盖"取出后、开始前"这个窗口。

### 5.5 `commit()` 与 `start()`

- `commit(e)`：最终确认这一批要跑（再次处理取消、再次应用 `headYields("before_start")`），
  然后 `start(e)` 记录 `deliveryLedger.startBatch(uuids)`、发 `cli_turn_started` 遥测。
- `headYields`（`m1809:4834`）：某些情况下队头要让位（`Cw(...)` 判定），
  比如前面还有未完成的 turn-end summary、或该条目属于一个已失效的 turn。

### 5.6 与"轮内 fold"的关系

同一个队列，两种消费：
- **轮内 fold** 只碰 `next`，且要求 `!foldSuspended && !lastIteration`；
- **drain** 碰所有优先级，在主循环顶部取。

所以一条 `next` 消息的典型命运是：**要么在当前回合的某个工具批次后被抓走（fold），
要么等当前回合彻底结束再起新回合（drain）**。`lastIteration` 那条门禁正是两者的分界线。

## 6. 中断与"立即发送"

### 6.1 `now` 优先级 → 立刻 abort

```js
// m1809:9817
return messageQueue.subscribe(() => {
  if (drain.abortController && !drain.endSessionRequested && !bn() &&
      messageQueue.getCommandsByMaxPriority("now").length > 0)
    drain.abortController.abort(jl("interrupt"));
});
```

只要队列里出现一条 `now`，就 abort 当前回合（reason 是 `"interrupt"`）。
回合被 abort 后，主循环回到顶部，`take()` 立刻取到这条 `now`（优先级最高），开新回合。

### 6.2 谁会把条目抬到 `now`

1. **用户按"立即发送"**（UI 层 `promoteToNow`，`m1809:9941` `giveBackStop`；
   `m1596:1540` `#w` 里 `messageQueue.promoteToNow(n)`）。
2. **低延迟提交判定为 `interrupt`**（见 6.3）。
3. **按 Esc 的"停止"路径**（`press` / `giveBackStop` 一对，`m1809:9941-9955`）：
   先标记 `taken`，发送成功后放入 `pressed`，若发送被拒则 `giveBackStop` 把条目恢复并抬到 `now`。

### 6.3 低延迟提交（low-latency submit，`m1596:1211` `fi`）

这是"用户希望新消息尽快生效"时的决策器，输入是一组状态：

```js
{ head, hasFoldTakenPrompt, isLocalTurnActive, isLocalTurnRunning,
  isHeldByDialog, holderCount, unmovableHolderCount,
  isExecuting, isAwaitingMovedResult, isBackgroundingDisabled,
  isCompacting, isUnmovableGraceOver, isMainRequestInFlight }
```

输出四种动作，判定顺序（`m1596:1211-1254`）：

| 顺序 | 条件 | 动作 |
| --- | --- | --- |
| 1 | `head === "ended_by_hook"` 或 `hasFoldTakenPrompt` 或回合未激活 | `stand_by`（什么都不做） |
| 2 | 被对话框占着 | `wait: held_by_dialog` |
| 3 | `head === "not_ready"` 或回合没在跑 | `wait: not_ready` |
| 4 | `head === "behind_earlier"` | `wait: behind_earlier`（前面还有更早的） |
| 5 | `holderCount > unmovableHolderCount`（有**可移动**的持有者） | `background` |
| 6 | 正在 compact | `wait: compacting` |
| 7 | 正在等被移走的工具结果 | `wait: moved_result` |
| 8 | 还有持有者或正在执行工具 | 宽限期内 `wait: unmovable_grace`；宽限过了 → `interrupt`（禁用后台化时 `cancel`） |
| 9 | 主请求不在飞 | `wait: not_sampling` |
| 10 | 其余 | `interrupt` |

对应实现（`m1596:1487-1548`）：

- **`background`**：把"可移动"的持有者（可后台化的工具调用）挪到后台，让出前台；
  `outcome = "delivered_early"`。一个都挪不动且宽限期已过 → 退化到 `interrupt` 或 `cancel`。
- **`interrupt`**：`promoteToNow(uuid)` —— 抬到 `now`，由 6.1 的订阅者 abort 当前回合。
- **`cancel`**：`interruptForSubmit()`（回合没提供这个钩子时记 `nothing_moved`）。
- **`wait`**：什么都不做，等下一次状态变化再评估。

> 一句话：CC 不是"一按就打断"，而是**先尝试把可后台的工具挪走**（`background`），
> 挪不动才 `interrupt`，再不行才 `cancel`。宽限期常量 `$n`、`ci` 在同模块内。

### 6.4 控制协议入口

外部（SDK / IDE）可以通过控制请求 `interrupt_if_running`（`m1809:26430-26490`）实现同样效果：
仅在真的有回合在跑时才 abort。

### 6.5 Esc 的两级语义

`m1635:23941`：

```js
if (queueEditIndex !== null || Kt("chat:cancel")) ...
```

- 第一下：如果正在"编辑队列"（`queueEditIndex !== null`），先退出编辑态；
- 否则：`chat:cancel` → 取消当前回合。

取消时会清队列（`m1635:24017`）：

```js
clearCommandQueue({ reason: "cleared_on_cancel", keep: Qw })
```

`keep: Qw` 决定哪些条目**不被清掉**（系统类 / 非用户意图的条目）。
`m1809:9336` 的 `cm` 是另一条取消路径，用 `removeByFilter(Gp, {reason:"cleared_on_cancel"})`
只清主线程的条目。

> 语义：**Esc 取消 = 当前回合停 + 排队的人类消息一起作废**（避免用户以为取消了却还在排队）。

## 8. 队列里的其它条目（不是人类输入，但共用同一条队列）

### 8.1 可入队的模式

```js
// m0459:13678
function qmr(e) {
  return e === "prompt" || e === "orphaned-permission" || e === "task-notification" || e === "poll-event";
}
```

流式模式下**只允许 `prompt`**（`m1809:4535`：`if (!qmr(command.mode)) throw Error("only prompt commands are supported in streaming mode")`）。
`bash` 走单独的解析与执行路径，不在 `qmr` 白名单里。

### 8.2 `task-notification`

- 后台任务 / 子 agent 完成时入队，默认 `priority: "later"`（`m0459:30483`）。
- **合并**：连续的短通知会合并成一条（`m1809:4520` 一带）：
  ```js
  if (command.mode === "task-notification" && typeof command.value === "string" &&
      heldCompletionChars + command.value.length <= tk && coalesceTaskNotifications() &&
      selector.holdsQueryForFollower(...))
    command = { ...command, shouldQuery: false, queryHeldForNextTurn: true, stampThreadState: void 0 };
  ```
  合并窗口常量 `tk`，开关是 `tengu_swirling_meteor`（`m1809:4830`）。
- 通知被压着时（`heldCompletionChars > 0`），`take()` 会造一个**合成空 prompt** 触发一次调用，
  把欠下的完成通知一并交付（`m1809:4503-4516`）。
- 有专门的 `wakeRouter`（`m1635:18137`）把属于某个 agent 的条目投递给它：
  成功 → `consume(reason:"delivered_to_agent")`；被 hook 拒绝 → `remove(reason:"dropped_by_hook")`；
  失败 → 重试（退避 `eGr(attempt)`），彻底失败 → `remove(reason:"agent_stopped" / "resume_failed")`，
  并显示 `Failed to deliver queued message to agent: ...`（`m1635:18265`）。

### 8.3 `poll-event`

- 轮询类事件（channels、外部回调）。`enqueuePollEvent` / `drainPollEventChunk` 成对出现，
  说明它按"块"投递而不是逐条。
- `Eps`（`m0459:13674`）：`mode === "poll-event" && (pollEvent.wake === true || r) && !n`
  —— 只有带 `wake` 标记的 poll 事件才会**唤醒**回合。
- 投递形态是 `{type:"poll_events"}` attachment（`m0459:12704`），与 `queued_command` 并列。

### 8.4 `orphaned-permission`

- 权限请求的宿主（发起它的会话 / 子 agent）消失后，请求变成"孤儿"，入队等待新的宿主。
- 在 `qmr` 白名单里，说明它可以跨回合存活。

### 8.5 attachment 类型白名单

```js
// m0671:1880
var fp = new Set(["queued_command", "teammate_mailbox", "poll_events"]);
```

这三类是"会改变模型输入"的 attachment；`m0459:11336` 反过来定义哪些不算：
`n !== "queued_command" && n !== "poll_events"`。

### 8.6 子 agent / teammate 的队列

- 每个 agent 有自己的 `agentId`，`Gp(e) = e.agentId === Ze()`（`m0459:13682`）决定"是不是我的"。
- `teammate_mailbox` 是 teammate 之间的消息通道，走同一个 attachment 机制。
- teammate 的待处理消息数直接显示为 `${count} queued`（`m1635:22748`）。

## 9. 关键不变量与坑

1. **顺序不能越过"未就绪"的消息**。`lc` 里一旦某条 `prompt` 判为 `waits`，`s = true`，
   后面所有 `prompt` 都跳过（`m0671:577` 的 `pr`）。想复刻就必须保留这个"闸门"。

2. **`screeningPending` 的条目绝不能被 fold 投递**。
   hook 还没跑完就把文本塞给模型，等于绕过了用户的 hook 配置。

3. **"以为发了"是最危险的失败模式**。CC 的做法是：
   发出 0 条 → 全留队；部分发出 → 只删已发的；abort/suspend → 全留队。
   宁可重复投递一次，也不能静默丢失用户输入。

4. **出队只有一个口子**：`consume(commands, {reason})`，且 reason 必填
   （`absorbed_mid_turn` / `delivered_to_agent` / `cleared_on_cancel` / …）。
   便于审计"这条消息到底怎么没的"。

5. **`lastIteration` 不吸收**。主线程最后一轮如果还 fold，就会出现
   "这条消息属于本回合还是下一回合"的歧义。

6. **合并有严格兼容判定**（`ek`）。别图省事只比较 `mode`：
   `origin`、`workload`、`shouldQuery`、`priority`、图片路径、`textNotTyped` 等任何一项不同，
   合并都会改变语义（比如把"投递给 peer 的消息"和"用户输入"并成一条）。

7. **取消是一次性标记**（`consumeCancelPending`）。取队时查一次、commit 时再查一次，
   覆盖"取出后、开始前"的窗口；漏了这一步就会出现"用户已取消但还在跑"。

8. **hook 拒绝 ≠ 丢弃**。文本必须回到输入框 + 通知，否则用户以为发出去了。

9. **Esc 会清队列**。这与"排队消息应该保留"的直觉相反，但产品上是对的：
   用户按 Esc 的意图是"都停下"。

10. **`now` 是唯一能打断的优先级**。不要用"新消息到达"本身去 abort；
    否则每条排队消息都会打断当前回合，退化成"永远只跑第一步"。

## 10. 可复刻清单（给自研 agent 的"边跑边收"）

按依赖顺序，最小可用实现：

### S1：单一命令队列

- 一个全局 `queue`，条目 `{uuid, value, mode, priority, origin, timestamp, agentId}`；
- 优先级 `now/next/later`，同优先级 FIFO；
- 对外只暴露 `enqueue` / `peek` / `take` / `consume(commands, reason)` / `subscribe`。
- **DoD**：任何入队都能在 UI 上看到；任何出队都有 reason 日志。

### S2：忙碌判定与入队

- 提交入口先判 `isTurnActive || isSubmitting`；
- 忙 → 清空输入框 + `enqueue(priority:"next")`；
- 闲 → 直接开回合（复用同一套投递代码，用 `inputSource` 区分）。
- **DoD**：忙碌时连按 Enter 不丢消息、不乱序。

### S3：回合内 fold

- 在每个工具批次结束、下一次模型调用前，取 `priority=next` 且属于本 agent 的条目；
- 先过"就绪筛查"（有 hook 就跑 hook），未就绪的**阻塞后续 prompt**；
- 把就绪条目作为一条 user 消息插到工具结果之后，文本加包装前缀；
- 投递成功的 `consume(reason:"absorbed_mid_turn")`；0 条成功则全部留队。
- **DoD**：模型在同一个回合里能看到用户中途输入，且顺序正确。

### S4：回合末 drain

- `for(;;) { await waitForHead(); const batch = take(); if (!batch) break; await runTurn(batch); }`
- `take()`：取最高优先级队头 + 兼容 followers，合并成一条；
- 合并判定至少比较 `mode/priority/origin/workload/shouldQuery`。
- **DoD**：连发三条只触发一次模型调用。

### S5：立即发送与中断

- "立即发送" → `promoteToNow(uuid)`；
- 订阅队列，出现 `now` 就 `abort("interrupt")`；
- 低延迟提交决策：可后台的工具先 `background`，挪不动再 `interrupt`，再不行 `cancel`。
- **DoD**：用户点"立即发送"后，当前回合在秒级内让位，且新消息第一个被处理。

### S6：UI

- 上箭头：按索引把队列条目拉回输入框（带 `unpassed` 标记）；
- 提示文案随编辑态切换；
- 取消时清队列并提示；
- 队列深度暴露给 UI / SDK。
- **DoD**：排队中的消息可见、可编辑、可撤回、可立即发送。

### 不建议照搬的部分

- `wakeRouter` 的多 agent 投递与退避重试（自研单 agent 时不需要）；
- `poll-event` 的"块投递 + 声明轮次"（没有外部轮询源时是纯负担）；

## 12. 一句话总结

**CC 的"执行中继续输入"不是把新消息塞进正在飞的请求，而是维护一条统一命令队列：
忙碌时 Enter 入队（先过 prompt.submit hook），
队列在每个工具批次之后被"轮内吸收"进当前回合（`queued_command` attachment + 包装文本），
或在回合结束时由 drain 循环合并成新回合；
`now` 优先级是唯一能打断当前回合的通道，Esc 则取消并清空排队的人类消息。**
