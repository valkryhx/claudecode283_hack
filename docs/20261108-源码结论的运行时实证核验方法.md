## 0. 为什么需要这层核验

本仓库的研究全部建立在**静态阅读**上：从 `claude.exe` 抠出明文 JS，格式化、去混淆，再逐行读。
这条链能读出「代码写了什么」，但读不出三件事：

| 静态阅读读不出的 | 具体表现 | 在本仓库已发生的实例 |
| --- | --- | --- |
| **静态歧义** | 同一行为有两条形状相似的分支，读不出这次走哪条 | `SendMessage` 有两处 `resumedAgentId`（`m1928:3108` / `m1928:3264`）。**这个例子连 L2 都裁决不了**——因为区分字段被 mapper 剥掉了（§4.3），最终只能写「静态未裁决」 |
| **不可达代码** | 源码里有、名字也对，但本 build 永不执行 | `did:` 路由（`m0159:1243` 有解析，但 `m2328:36-39` 的数据源是硬编码 `Promise.resolve({peers:[]})`，且被当作 `Promise.all` 第 4 项，`m.peers` 恒空）；`installSubagentSends()` 全 exe 无调用方（字节级扫描：2 处 vs 有调用方的 3 处） |
| **口径误判** | 从正确的数据里推出错误的语义 | 从 `cost` / `modelUsage` 汇总读出「main 跑 opus」，实际读 `assistant.message.model` 是 `deepseek-v4.1-flash-1017` |

结论：**静态阅读是必要条件，不是充分条件。** 本文给的是「怎么补上充分性」的一套可复用做法。

## 1. 双层证据模型

每条行为结论都由两层构成，**L2 不替代 L1，而是裁决 L1**：

- **L1 静态**：源码坐标（`文件:行号` + 代码片段）。回答「机制是什么」。
- **L2 运行时**：产品自己写的持久化日志。回答「这次实际走了哪条」。

标注规则（写文档时必须照这个分级，不许含糊）：

| 证据情况 | 标注 | 措辞 |
| --- | --- | --- |
| 只有 L1 | `静态推得` | 「代码路径表明……」「从 `X()` 可推出……」 |
| L1 + L2 吻合 | `实测证实` | 「实测吻合」「运行时逐字段对应」 |
| L1 与 L2 冲突 | `以 L2 为准` | 立即回头改 L1——**冲突几乎总意味着读错了分支**，不是日志错了 |
| 只有 L2 | `行为观察` | 「观察到……但未定位到机制」 |

**最重要的一条纪律**：L1 与 L2 冲突时，不要保护已写下的结论。本仓库已因此改正两处
（`did:` 是否可达、`t9()` 是否恒假），都是 L2/字节级证据推翻了先前的静态叙述。

## 2. 数据源：transcript JSONL

### 2.1 它是什么

Claude Code 把每个会话的完整事件流追加写入：

```
~/.claude/projects/<cwd-slug>/<sessionId>.jsonl
```

- `<cwd-slug>`：工作目录转义，`D:\git_repos\claude_hack` → `D--git-repos-claude-hack`。
- `<sessionId>`：`claude --output-format json` 的返回里带 `session_id`，用它 glob 可精确定位。

**关键性质：这不是调试插桩，而是产品自己的正式持久化通道。** `--continue`、`--resume`、
fork、转录视图读的都是同一份文件（见 `docs/20261025-CC-resume机制调研.md`：
SSOT 表记 `Rd()=\`${...}.jsonl\``、会话列表 = 扫 `<projectKey>/*.jsonl`、resume = 把 JSONL 反序列化成事件树）。
所以它的字段语义是稳定的、有版本维护的，比任何临时 hook 都可靠。

> ⚠️ 引用那份文档时注意：它的坐标（`m0167` / `m0673` …）是 **283 的模块编号**。
> 319 的模块划分不同，**编号不可直接套用**（AGENTS.md §9 明令），
> 要用就得按导出名/字符串在 `reconstructed319/` 里重新定位。

格式是 **append-only 的 JSON Lines**，一行一个事件，靠 `type` 区分。

### 2.3 读取姿势

```python
import json, glob, os

p = max(glob.glob(os.path.expanduser(r"~/.claude/projects/*/*.jsonl")), key=os.path.getmtime)
for i, ln in enumerate(open(p, encoding="utf-8", errors="replace")):
    try: o = json.loads(ln)
    except Exception: continue
    print(i, o.get("type"), o.get("timestamp"), o.get("operation", ""))
```

`errors="replace"` 不是偷懒：个别行含截断内容，硬解码会整份读不出来。

**按 `session_id` 精确定位**（比按 mtime 取最新可靠）：

```python
sid = "<从 claude -p --output-format json 的 session_id 拿>"
p = [x for x in glob.glob(os.path.expanduser(r"~/.claude/projects/*/*.jsonl")) if sid in x][0]
```

**把一轮里的工具调用还原成「调用 → 结果」表**（§5.4 的配对 + §4.2 的时序，合起来就是这个）：

```python
import json, glob, os
sid = "..."
p = [x for x in glob.glob(os.path.expanduser(r"~/.claude/projects/*/*.jsonl")) if sid in x][0]
tu, tr = [], {}
for ln in open(p, encoding="utf-8", errors="replace"):
    try: o = json.loads(ln)
    except Exception: continue
    if o.get("type") == "assistant":
        for b in o.get("message", {}).get("content", []) or []:
            if isinstance(b, dict) and b.get("type") == "tool_use":
                tu.append((o.get("timestamp"), b.get("id"), b.get("name"), b.get("input")))
    elif o.get("type") == "user":
        for b in o.get("message", {}).get("content", []) or []:
            if isinstance(b, dict) and b.get("type") == "tool_result":
                tr[b.get("tool_use_id")] = (o.get("timestamp"), b.get("is_error"), b.get("content"))
for ts, tid, name, inp in tu:
    r = tr.get(tid)
    print(ts, name, json.dumps(inp, ensure_ascii=False)[:80])
    if r: print("   ->", r[0], "is_error=", r[1], repr(r[2])[:100])
```

这个脚本是 §13.3 / §13.5 判定所依据的原始数据来源。
**判据看的是这里的 `is_error` 与两个 `timestamp`，不是模型说了什么。**

## 3. 三条采集手法

### 3.1 受控实验：哨兵 token（证明「不阻塞」类结论的唯一手段）

**问题**：想证明「A 不等待 B」，静态读只能看到「代码没写 await」，但 runtime 里可能
有隐式等待（锁、串行化、队列 drain）。

**手法**：让被测对象在「如果真的阻塞、就绝不可能出现」的时刻产出一个可搜的标记。

```
prompt = "... 派发 <子任务> 后，立刻输出标记 TOKEN_XYZ 然后停止。"
```

判据不是「标记出现了」，而是**标记的时间戳早于它本该等待的事件**：

```
16:12:48.118  assistant  text = AGENT_NOTIFICATION_TEST_DONE   ← main 自己的输出
16:12:48.416  queue-operation  enqueue  (通知才入队)
```

相差 298 ms，这才是「不阻塞」的运行时证据。

**设计要点**：

1. **标记必须唯一且可 grep**（`AGENT_NOTIFICATION_TEST_DONE`，不要用 `done` 这种词）。
2. **标记必须在被测事件之前产出**——顺序写反了实验就失效。
3. **限制工具集**（`--allowedTools`），否则模型会自己加戏，把时序搅乱。
4. **一次实验只验一条结论**。想同时验「不阻塞」和「断点续跑」，时间线会缠在一起。

### 3.2 主动构造负对照

只看到「预期的 A 形态」不够，必须同时看到「A 不该有的 B 形态也确实是那个样子」，否则
无法排除「我以为在观察 A，其实在观察一个通用模板」。

实例：抓 `local_agent` 通知时，另外去历史 transcript 里捞 `bash` 类通知做对照。
两者长得**不一样**（bash 无 `<note>`、无 `<usage>`、summary 前缀是 `Background command "`），
而源码里 `nne = "Background command "` / `dcn = 'Agent "'` 本就是两套前缀、两条 body 组装路径。
**对照组对上了，正样本才可信。**

### 3.3 历史 transcript 回捞（零成本，但有陷阱）

`~/.claude/projects/` 下攒着本机所有历史会话，可以零成本找旧样本。

- ✅ 适合：找罕见事件的形态、扩大样本量、验证 field 稳定性。
- ⚠️ **陷阱：版本漂移。** 旧 transcript 可能是别的 CC 版本写的。
  用之前必须先核对「写这份文件的版本 == 你正在研究的版本」，否则会把 2.1.303 的行为
  当成 2.1.319 的。

### 3.4 采集时的两个工程陷阱（2026-11-08 实测踩到）

**① 长 prompt 不能走命令行参数。** 想把一条 30 KB 的命令拼进 prompt 交给 `claude -p`，
在本机会直接失败：

```text
timeout: failed to run command 'claude': Argument list too long
```

这与 `AGENTS.md` §1 记的 Windows 命令行长文本坑是同一类。**正确做法是 stdin**：

```bash
claude -p < prompt.txt --output-format json      # ✅ 实测可用
claude -p "$(cat prompt.txt)" ...                # ❌ 长文本必挂
```

若必须用参数，就要拆成多次调用（一次一断言，本来也更符合 §3.1 的"一次实验只验一条"）。

**② 读子进程输出必须显式按 UTF-8 解码。** 用 Python `subprocess.run(..., capture_output=True)`
不加 `text=True` 时拿到 bytes；加了 `text=True` 则用系统编码（本机 GBK）解码，
遇到 `claude` 输出的非 ASCII 字符会直接抛：

```text
UnicodeDecodeError: 'gbk' codec can't decode byte 0xa6 in position 1666
```

正确姿势：

```python
r = subprocess.run([...], capture_output=True)          # 不要 text=True
out = r.stdout.decode("utf-8", errors="replace")        # 显式 UTF-8 + replace
```

这与 §2.3 里"`errors='replace'` 不是偷懒"是同一个理由，只是换了一层。

## 4. 五条判据（缺一条就不要写「实测证实」）

### 4.1 逐字比对

拿 L2 抓到的**原文**去对 L1 的**拼装代码**，逐字段、逐顺序对。

实例：`zi()`（`m0502:23-43`）按固定顺序拼 tag（**照抄源码原文，压缩名不美化**）：

```js
let d = [[vM, taskId], [R5, toolUseId], [Ej, taskType], [Yqe, outputFile], [av, status], [M_, summary]],
  o = `<${Bu}>`;
for (let [a, T] of d) if (T) o += `
<${a}>${T}</${a}>`;
```

实测通知的 tag 顺序是 `task-id → tool-use-id → output-file → status → summary`，
且 **`task-type` 缺席**——因为它是空值，被 `if (T)` 跳过。

附带发现：`trailing` 会被转义（`replaceAll(/<(?=\s*\/\s*task-notification\b)/gi, "&lt;")`），
防止外部内容伪造闭合标签——这类「细节对得上」比主干结构更能证明不是脑补。

**为什么这条最有说服力**：一个"恰好缺了该缺的那个字段、且缺在正确位置"的结果，
脑补不出来。伪造的证据通常"太完整"。

### 4.2 时序

不读代码逻辑，只读时间戳。能证伪「阻塞」「同步」「直投」三类说法。

- `enqueue(.416)` → `dequeue(.420)` 相隔 4 ms ⇒ **排队**，不是直接注入。
- main 输出(.118) 早于 enqueue(.416) ⇒ **不阻塞**。
- `.427` 进上下文 → `.471` 发起 `api-request` → `50.886` main 复述结果 ⇒ **闭环**。

三步齐了才算「模型真的看见了」；只有入队没有后续调用，不能算。

**省事的替代品**：`system` / `subtype: turn_duration` 事件直接带 `durationMs` 与 `messageCount`
（实测 `durationMs=353374, messageCount=141`）。想证明「这一轮跑了多久」不必自己遍历时间戳，
但要证明「某两个**局部**事件的先后」，仍必须用各自的时间戳 —— `turn_duration` 只给整轮粒度。

**并发验证的读法（§13.5 用的就是这个）**：同一轮里多条 `tool_use` 的 `timestamp` 很接近（几十 ms），
那就看它们的 `tool_result` 时间戳**差值**：

- 若两条 `sleep 2` 的 result 相差约 2 s ⇒ 串行；
- 相差几 ms ⇒ 并发（实测 12 ms）。

这个判据比「总耗时约 2 秒」硬：总耗时受 API 往返、模型思考影响，差值只受调度影响。

### 4.3 反查分支（用运行时裁决静态歧义）——**先确认该字段真能到观察点**

当源码里有多条形状相似的分支，本能想法是「看运行时结果里某个字段有没有」来判定命中哪条。
**但在用之前必须先查一件事：这个字段是不是在中途被剥掉了。**

本仓库的现成反面教材（我踩过）：`resumedAgentId` 在 `m1928` 里出现两处
（`3108` 的 `case "agent-stopped"` / `3264` 的 `case "agent-evicted"`），
**两处都带 `revivedAgentId`**，所以「有没有 `revivedAgentId`」根本区分不了分支。
更关键的是，`revivedAgentId` 在 `mapToolResultToToolResultBlockParam`（`m1928:1977-1990`）
解构时就被**主动摘掉**了：

```js
let { display, revivedAgentId, inlineHandback, ...b } = {...};
// 之后只用 b —— revivedAgentId 是给宿主内部用的（m2068:557 读它记账），
// 模型永远看不到
```

所以「运行时没看到它」只有「被 mapper 剥掉」这一个解释，**不构成任何分支证据**。
初版据此写的「命中的是 3108 那条」是错的，已撤回。

**正确的用法（三条前提，缺一不可）**：

1. 该字段在**所有候选分支里互斥**（不是「都有」或「都没有」）。
2. 该字段**一路不被剥离**——要顺着 `mapToolResultToToolResultBlockParam` /
   serializer / redaction 链查到底，确认它能活到被观察的位置。
3. 观察点拿到的确实是**那个函数**的返回值，不是中间层加工过的产物。

**如果这三条不成立，就不要用字段有无来判分支**，改判：
- 打点（如果该版本允许）
- 或用「分支的结果差异」判（不同分支产出的**文案/副作用**通常不同，比字段有无可靠）
- 或老实写「静态未能裁决」

本次的教训写进了 §8 反模式表。

### 4.4 负对照（见 §3.2）

### 4.5 跨次一致性

同一实验跑两次，结构必须一致，数值可以不同。

实例：两次跑（`b000c088…` / `0c4e9c58…`），信封结构、`origin` 形状、`async_launched`
返回体全部一致，只有 `agentId` / `runId` / `<usage>` 数值变化。
**改动恰好只落在「本就该每次不同」的字段上**——这种"差得很干净"也是可信度指标。
如果两次连 `runId` 都一样，反而说明实验没真的重跑。

| 行 | 命中内容 | 实际是什么 |
| --- | --- | --- |
| 第 10 行 | `\| **subagent 异步执行 + agent 间通信四通道**…` | **AGENTS.md 的文档索引文本**被当成上下文注入了 |
| 第 24 行 | `…a <task-notification> arrives when the workflow completes…` | **`Workflow` 工具的 schema 描述** |

两者都只是「文本里出现了这个词」，不是通知本身。

**通用规则**：

> 先按 `type` 过滤，再按**字段断言**，最后才看文本。
> 真通知必须满足 `type=="queue-operation" && operation=="enqueue" && content.startswith("<task-notification>")`，
> 或 `type=="user" && origin.kind=="task-notification"`。

文档正文、工具 schema、system-prompt 片段都会被注入进 `api-request-blob`，因此
**任何跨越 prompt 内容的文本检索都必然产生假阳性**。

### 5.2 从正确数据推错语义

同一份 transcript 里，`cost-state` / `modelUsage` 汇总会列出多个模型（含子代理的），
照它写「main 跑 X」会错。**会话模型只能读 `assistant.message.model`。**

类似陷阱：

- `attachment` 里出现某工具的名字，不代表该工具**被调用**（可能只是 schema 注入）。
- `tools-used` 是汇总，不是调用序列；调用序列读 `assistant.content[].tool_use`。

**还有一类更隐蔽的：模型会改写你给它的入参。** 实测里，
我让它「执行这条命令」，它失败了之后**自己构造了替代命令**（循环、`printf`、加 `wc -l`），
于是同一个实验里出现了 4 条不同 sha 的 `tool_use`。
如果直接拿「最后一条成功的」当「我那条命令的结果」，结论就全错了。

> **判据**：拿 `tool_use.input` 的 **sha256** 和你原本想验的那条比对。
> 不相等就不是同一个实验对象。§13.6 的二分之所以可信，正因为
> 失败的那条命令 sha12 是稳定的（`1963f3da0d87`，连跑两次都一样）。

### 5.3 模型的自我报告不是证据（2026-11-08 实测踩到）

受控实验里，模型会主动给你一份「结果摘要」——**这份摘要可以完全正确，也可以是错的**，
而且它的语气和真证据一模一样。两个实例：

| 模型的说法 | 实际情况 |
| --- | --- |
| 「我还原了 exit code，是 1」 | 它**没看到** exit code，是从 `grep` 的文档语义**推断**的（它自己也标注了"是推断"） |
| 「两个命令确实并行，总共约 2 秒」 | 数字是**估的**；真正的并行证据是两条 `tool_result` 时间戳差 **12 ms** |
| 「R2 在 R1 完成后运行」 | 工具结果里根本没有先后信息，它是**编**的 |

**规则**：

> 模型说的话只是**线索**，用来决定去 transcript 里查什么。
> 判据永远是 transcript 的原始字段（`is_error`、`timestamp`、`content`、`tool_use.input`）。

这条与 §3.1 的哨兵 token 手法是一体两面：**哨兵 token 的价值就在于它绕开了模型的自我报告**，
把证据落在时间戳上。

### 5.4 `tool_use` 与 `tool_result` 靠什么配对

不是靠顺序，是靠 **`id`**：`tool_use.id`（形如 `call_00_tZh9dTOPv9caWbxpMNCq1409`）
与 `tool_result.tool_use_id`。

这意味着：

- 并发场景下**不能用数组下标配对**（结果可能乱序写盘）。
- 想还原「这次调用到底返回了什么」，必须建 `id → result` 的映射，再按 `timestamp` 排序。
  §13.5 的并发判定就是这么做的。

## 6. 版本锚定（每次实验前的第一步）

CC 会自更新，`~/.local/bin/claude.exe` 随时可能变版本。开跑前必须确认：

```bash
claude --version          # 与输入物版本一致？例：2.1.319
```

并把本机二进制的 SHA256 与 `claudecode319/MANIFEST.md` 比对。
**不一致就说明本机已不是被研究的版本，结论不能回填到 `claudecode319/`。**

同理，引用历史 transcript 前要确认它是哪个版本写的（§3.3）。

**不用猜，transcript 自己就带版本。** 实测：`assistant` / `user` / `api-request` / `attachment` /
`system` / `api-request-shape` 这六类事件都带 `version` 字段（`"2.1.319"` 这种）。
所以可以直接筛：

```python
# 只取某个版本写的样本，避免把 302/303 的行为当成 319
def is_ver(o, v="2.1.319"):
    return o.get("version") == v
```

**本机实测的版本分布**（56 份 transcript）：`2.1.319` 38 份、`2.1.303` 12 份、`2.1.302` 6 份；
**同文件内混版本的情况为 0**（每次 CC 升级后都开新 session 文件，不会在旧文件里续写新版本）。

> ⚠️ 但**不要假设所有事件都带 `version`**。`queue-operation`、`file-history-*`、`cost-state`、
> `last-prompt`、`atis-latch`、`mode`、`ai-title`、`permission-mode`、`tools-used`、`api-request-blob`
> **都不带**。用「按文件过滤」比「按行过滤」稳：先看该文件里 `assistant.version` 是什么，
> 再信任整份文件。这与上面"同文件不混版本"互为印证。

## 7. 这套方法的局限（必须随结论一起写出来）

1. **不是调试器、不是抓包。** 看不到进程内存、promise 图、队列对象的实际结构。
   只能看到产品**选择写入文件**的那部分。
2. **一次样本不构成规律。** 验到的是「这个版本这次这样跑」，不是「所有配置下都这样」。
3. **`api-request-blob` 是产品自述的快照**，不等于发出去的字节流（上游可能另有包装/截断）。
4. **"不在 `--help` 里"只证明不以常规选项暴露，不证明不存在。**
   要证明存在与否，仍得回读源码（本例靠 `process.argv.includes("--agent-teams")` 定了案）。
5. **验不到就写「未验证」。** 不要用间接迹象充数。
6. **flag / 灰度开关不落盘。** 本仓库最痛的一点：很多机制挂在 `v("tengu_*", false)` 这种
   远端 flag 后面，而 **flag 的求值结果不进 transcript**。所以「机制没触发」只能观察到现象，
   推断不出是哪个开关挡住的。§13.1 与 §13.6 两个发现都受这个限制——
   能确证「未触发」，不能确证「因为 flag X」。
   要坐实，只能靠**变量对照**（改环境变量/改 PATH，看行为是否翻转），而不是去日志里找 flag。
7. **实验环境本身会污染结论。** `claude -p` 是**非交互模式**，它与交互式会话在
   snapshot、权限提示、UI 路径上都可能不同。本仓库实测 `~/.claude/shell-snapshots/` 始终为空，
   很可能就是非交互模式导致的。**用 `-p` 验出来的结论，不能直接当成交互式会话的结论。**

## 8. 反模式清单

| ❌ 反模式 | 为什么错 | ✅ 正确做法 |
| --- | --- | --- |
| `grep 关键词 \| wc -l` 当证据计数 | 文档正文、schema 描述全都会命中 | 按 `type` + 字段断言 |
| 从 `cost` / `modelUsage` 推断会话模型 | 汇总含子代理模型 | 读 `assistant.message.model` |
| 看到源码有某路径 ⇒ 认为运行时会走 | 可能是死代码（`did:` / `installSubagentSends`） | 全 exe 扫调用方 + 运行时验证 |
| **用「字段有没有」判分支，却没查它是否被剥离** | mapper/serializer 可能在半路摘掉它（`revivedAgentId` 被 `m1928:1977` 解构丢弃） | 先顺链确认字段能活到观察点（§4.3） |
| 只看「标记出现了」就断言不阻塞 | 标记可能出现在事件之后 | 比时间戳先后 |
| 用旧 transcript 论证新版本行为 | 版本漂移 | 先核 `claude --version`；再用事件自带的 `version` 字段筛（§6） |
| L2 与 L1 冲突时改日志解释 | 保住旧结论的典型自欺 | 以 L2 为准，回头改文档 |
| 只跑正样本 | 无法排除「这是通用模板」 | 必须配负对照 |
| **把模型自述当证据** | 模型的"结果摘要"语气和真证据一样，但它可能在推断甚至在编（§5.3） | 只信 transcript 原始字段 |
| **并发场景按数组下标配对 tool_use/result** | 结果可能乱序写盘 | 用 `id` / `tool_use_id` 建映射（§5.4） |
| **长 prompt 塞进命令行参数** | Windows/Unix 都有 argv 上限，直接 `Argument list too long`（§3.4） | `claude -p < prompt.txt` |
| **用 `subprocess(text=True)` 读 claude 输出** | 系统编码（GBK）解码 UTF-8 会抛 `UnicodeDecodeError`（§3.4） | 收 bytes，再 `decode("utf-8","replace")` |
| **只看到「没触发」就断言「有 bug」** | 也可能是灰度 flag 关着，或 `-p` 非交互模式不走该路径（§7.6/§7.7） | 做变量对照让行为翻转，再下结论 |

## 9. SOP（可直接照做）

```
① 版本锚定
   claude --version  ==  输入物版本？  SHA256 一致？
   引用历史样本时，用事件自带的 version 字段筛（§6）

② 写清要验的断言
   把「我认为 XX」写成一句可证伪的话（例：「派发后 main 会继续跑而不是等待」）
   同时写下「什么现象会推翻它」——没写推翻条件就等于没设计实验

③ 设计受控实验
   - 唯一哨兵 token
   - --allowedTools 收窄
   - 一次只验一条
   - 预想「如果断言为假，时间线会长什么样」
   - 长 prompt 走 stdin：claude -p < prompt.txt（§3.4）

④ 正样本 + 负对照
   正：制造目标事件
   负：找一个「长得应该不一样」的同类事件做对照
   更强的负对照是「变量对照」：只改一个环境变量/PATH，看行为是否翻转（§13.1）

⑤ 采集
   --output-format json 取 session_id → 定位 jsonl
   读子进程输出用 bytes + decode("utf-8","replace")，别用 text=True（§3.4）

⑥ 判据过五关
   逐字比对 / 时序 / 反查分支 / 负对照 / 跨次一致
   并发问题看 result 时间戳「差值」，不看总耗时（§4.2）

⑦ 假阳性排查
   先按 type 过滤，别用文本 grep 计数
   再排除「模型自述」：模型说的话只当线索（§5.3）

⑧ 回填文档（带分级标注）
   实测证实 / 静态推得 / 行为观察 / 未验证 —— 四选一，不许含混
   「没触发」要么坐实原因（有变量对照），要么标为推断（§7.6）

⑨ 同步更新
   §复现坐标（加上本次的采集命令）
   §一页纸总结（把结论升级为实测的，标出来）
```

## 12. 一页纸

> **用产品自己的持久化日志拿原始字节，用源码当标尺逐字段对齐，
> 用负对照和跨次一致性排除幻觉，验不到的就写「未验证」。**

四句话对应四件事：

1. **数据源要正**：`~/.claude/projects/*/*.jsonl` 是产品的正式持久化通道，不是插桩。
   事件自带的 `version` 字段能防版本漂移；配对 `tool_use`/`tool_result` 靠 `id` 不靠下标。
2. **对齐要逐字**：tag 顺序、字段有无、缺席的字段——细节对上了才算对上。
3. **排除要主动**：负对照 + 跨次一致 + 先 type 后文本 + **别信模型自述**，四道防线防自欺。
   最强的负对照是**变量对照**：只改一个环境变量/PATH，看行为是否翻转。
4. **诚实要前置**：`实测证实` / `静态推得` / `行为观察` / `未验证`，四选一写清楚。
   「没触发」不等于「有 bug」——可能是灰度 flag 关着，或 `-p` 非交互模式不走那条路径；
   坐实原因要有变量对照，否则标为推断。

## 13. 实例：把这套方法用在「内置工具」调研上（2026-11-08 实测）

> 本节是对 `docs/20261107-CC内置工具实现调研.md` 的运行时核验。
> 全部实验可复现，命令见 §13.6。

### 13.0 版本锚定（SOP ①）

```text
claude --version                       → 2.1.319 (Claude Code)
where claude                           → C:\Users\Administrator\.local\bin\claude.exe
SHA256(本地)                           → 2E055732C9D03D22700D9046251A8370B673607BFCC9E4D16A1B0E8FB1345CBD
SHA256(claudecode319/claude.exe)       → 2E055732C9D03D22700D9046251A8370B673607BFCC9E4D16A1B0E8FB1345CBD
```

**一致**，可以回填结论。

### 13.1 实测证伪了一条静态结论：Git Bash 自动检测有缺陷

**断言（来自 `20261107-CC内置工具实现调研.md` §2.1）**：「Windows 上 Claude Code 会解析出 Git Bash，
第 ③ 级是 `join(gitPath, '..','..','bin','bash.exe')`」。

**受控实验**：让 claude 自己列出可用工具，变量只有 `where git` 的返回顺序。

| 条件 | 观察到的 shell 工具 |
| --- | --- |
| 默认 PATH（`where git` 首条 = `E:\Git\mingw64\bin\git.exe`） | **只有 `PowerShell`** |
| `PATH` 前置 `E:\Git\cmd`（首条 = `E:\Git\cmd\git.exe`） | **有 `Bash`** |
| `CLAUDE_CODE_GIT_BASH_PATH='E:\Git\bin\bash.exe'` | **有 `Bash`** |

**负对照**：`CLAUDE_CODE_USE_POWERSHELL_TOOL=0` 且不设 `GIT_BASH_PATH` 时，
Claude Code 直接报错退出：

```text
Claude Code on Windows requires a shell tool. Git Bash was not found and the
PowerShell tool is disabled (CLAUDE_CODE_USE_POWERSHELL_TOOL=0).
```

而 `E:\Git\bin\bash.exe` **确实存在**（`Test-Path` 为 True）。这就是 L2 与 L1 的冲突现场。

**排除干扰**：

- 不是 tool search 隐藏：`ENABLE_TOOL_SEARCH=false` 后结果不变。
- 不是灰度 flag：显式设环境变量就恢复（环境变量是第 ① 级，绕过第 ③ 级）。
- 不是 settings 干扰：`~/.claude/settings.json` 里没有 shell 相关项。

**结论（`以 L2 为准`，已回改 L1）**：第 ③ 级的推导对
`<GIT>\mingw64\bin\git.exe` 这种布局**算错目录**：

```text
join("E:\Git\mingw64\bin\git.exe", "..","..","bin","bash.exe")
  = "E:\Git\mingw64\bin\bash.exe"     ← 标准安装里不存在
join("E:\Git\cmd\git.exe", "..","..","bin","bash.exe")
  = "E:\Git\bin\bash.exe"             ← 正确
```

### 13.2 实测发现一个「机制存在但未启用」：shell snapshot

`20261107-CC内置工具实现调研.md` §2.4 描述了 snapshot 机制。实测：

```text
ls ~/.claude/shell-snapshots/          → 存在但为空（连续 4 次调用后仍为 0 个文件）
find ~/.claude -name 'snapshot-*.sh'   → 零命中
```

**跨次一致**：连跑两次，两次都是 0。
**判定**：`行为观察` + `静态推得` —— 观察到"没有生成"，
代码里最可能的门是 `aDn()` 第一行 `if (ME()) return;`（`ME()` ≡ `q()`，
源码把 `q()` 用在 diskless-session 判定上），但**没有直接读到 flag 求值，属推断**。

### 13.3 实测证实：exit code 语义化

**断言（`20261107-CC内置工具实现调研.md` §2.11）**：`grep` 无匹配（exit 1）**不算错误**；`exit >= 2` 才算。

**受控实验**：同一会话内跑两条命令，读 transcript 的 `tool_result.is_error` 原始字段
（不读模型自述 —— 见 §5.2）。

| 命令 | bash exit | `tool_result.is_error` | 结果文本 |
| --- | --- | --- | --- |
| `grep ZZZ_NO_SUCH_TOKEN /etc/hosts` | 1 | **`False`** | `(Bash completed with no output)` |
| `ls /nonexistent_dir_zzz` | 2 | **`True`** | `Exit code 2\nls: cannot access ...` |

**逐字段对应源码**：`VL = (e) => (n,r,s) => ({isError: n >= 2, ...})`，
`Qio = (e,n,r) => ({isError: e !== 0, ...})`，`T1s` 表里 `grep`/`rg` → `VL`。
**实测吻合**，从 `静态推得` 升级为 `实测证实`。

### 13.5 实测证实：并发分组（只读工具并行）

**断言（文档 §8）**：只读工具相邻合并并行，写工具串行。

### 13.6 实测证伪：Windows 长命令分段携带**未生效**（本仓库最重要的发现）

**断言（`20261107-CC内置工具实现调研.md` §2.6）**：超 8000 字节的命令走"分段携带 + sha256 校验 + `exit 126`"。

**受控实验**：构造合法 bash 命令（`echo P0000_xxx && echo P0001_xxx && ...`，零引号），
逐档加长，用 `bash -n` 先确认语法合法，再交给 Bash 工具执行。

| 命令字节 | 结果 |
| --- | --- |
| 6,016 | ✅ OK 172 |
| 6,996 | ✅ OK 200 |
| 7,416 | ✅ OK 212 |
| 7,626 | ✅ OK 218 |
| 7,766 | ✅ OK 222 |
| **7,801** | ❌ `Exit code 2` / `unexpected EOF while looking for matching '` |
| 8,116 / 8,501 / 10,196 / 17,627 | ❌ 同上 |
| 64,766 | ❌ `ENAMETOOLONG: name too long, uv_spawn` |

**三条判定证据**：

1. **`exit 126` 一次都没出现**。分段协议的所有失败路径都会
   `\builtin exit 126` + 打 `"Claude Code did not run this command: ..."`
   （`IDn`/`DDn`/`FDn`，`m0591:142896`）。扫全机 transcript 的 15 条「长命令+失败」样本，
   **126 与 "did not run" 零命中** → 代码没走到分段协议。
2. **报错是「单引号未闭合」，而命令里 0 个引号**。对失败样本原文跑 `bash -n`，**rc=0**。
   那个孤立的 `'` 只可能来自包装器自身（`zDn`/`mat` 里都有 `\builtin echo '${ODn}'`）。
3. **边界落在 7,766 与 7,801 之间**，两者都远小于 8,000 → 阈值量的是
   **「命令 + 包装」的全串**，不是用户命令。

**跨次一致性**：同一条 10,196 字节命令（sha12 `1963f3da0d87`）连跑两次，两次都 `exit 2`，**结果稳定**。

**结论**：`以 L2 为准`。`20261107-CC内置工具实现调研.md` §2.6 描述的机制在**代码里存在**，但本机**未启用**。
最可能的门是 `HDn()` 的第五个条件 `v(RUr, !1)`（灰度 flag 默认 false），
但这属**推断**（flag 求值不落盘），实测能确证的只有"未触发 + 走非 126 路径"。

### 13.7 本轮核验小结

| 断言 | 证据等级（核验后） | 变化 |
| --- | --- | --- |
| Git Bash 三级解析 | `实测证实`（且**发现第 ③ 级缺陷**） | L1 → L2，并订正 |
| shell snapshot 会创建 | `行为观察`（**本机未创建**） | L1 被降级 |
| exit code 语义化（grep≠错） | `实测证实` | L1 → L2 |
| 结果落盘 `<persisted-output>` | `实测证实` | L1 → L2 |
| 并发分组 | `实测证实` | L1 → L2 |
| 长命令分段携带 | `实测证伪`（本机未启用） | L1 被推翻 |

**三升一降一推翻**。降级的那个（snapshot）和推翻的那个（分段携带）都不是"文档写错了"，
而是**同一个教训**：*代码里有这条路径，不等于这次运行走了这条路径*。
这正是本文 §0 表格里「不可达代码」那一格的现实版本。
