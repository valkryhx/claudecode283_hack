# Claude Code 2.1.283 的 ACP 支持调研

> **结论先行：Claude Code 2.1.283 核心本身不原生实现 ACP（Agent Client Protocol）。**
>
> Claude Code 可以通过外部 adapter 接入 ACP；当前生态中的官方适配器是
> `@agentclientprotocol/claude-agent-acp`，它通过 **Claude Agent SDK** 驱动 Claude Code CLI，
> 再把 SDK 事件翻译成 ACP 的 JSON-RPC 消息。CC 核心真正内置的是自己的
> `stream-json + control_request/control_response` SDK 控制协议，**不是 ACP**。
>
> 因此，若要把 ACP 能力复刻到 GA/自研 Agent，正确方向不是“把 ACP 塞进 Agent 主循环”，
> 而是增加一个 **独立 adapter 层**：`ACP Client ↔ ACP adapter ↔ Agent Runtime/SDK`。
>
> **【复刻时暂时不需要参考 claudecode 云端会话的实现】**
> 本文只讨论本地 ACP adapter、stdio、本地 session、权限与事件映射；不讨论
> `isolation:"remote"`、云端会话、远程 worker、hosted session 或远程 ACP 基础设施。

## 1. 先说结论：CC 到底支持不支持 ACP？

### 1.1 核心二进制不包含 ACP

对 `claudecode283/claude.exe` 和 `claudecode283/modules/` 做精确字符串检索：

```bash
grep -aF -m1 'agent-client-protocol' claudecode283/claude.exe
grep -aF -m1 'agent_client_protocol' claudecode283/claude.exe
grep -aF -m1 'Agent Client Protocol' claudecode283/claude.exe
grep -aF -m1 'session/new' claudecode283/claude.exe
grep -aF -m1 'session/prompt' claudecode283/claude.exe
grep -aF -m1 'session/update' claudecode283/claude.exe
```

本次结果：上述字符串在 `claude.exe` 与 `claudecode283/modules/` 中均为 **0 命中** `[S]`。

这只能证明“2.1.283 这个 build 的核心没有 ACP 协议字符串/方法定义”，不能反过来证明
“所有历史版本或未来版本都永远不会有”。但就本 build 的源码事实而言，答案是明确的：

> **Claude Code 2.1.283 核心不是 ACP agent，也不内置 ACP server。**

`ACP` 三个字母在二进制中出现过一些大小写不敏感的噪声命中（例如 Windows API、chunk 文件名等），
但没有 ACP JSON-RPC 方法、ACP session 生命周期或 ACP capability 定义 `[S]`。

### 1.2 ACP 支持来自外部 adapter

ACP 生态提供的适配器是：

```text
@agentclientprotocol/claude-agent-acp
```

其 README 第一行就是：

> “ACP adapter for the Claude Agent SDK”

并明确说明它使用 **Claude Agent SDK** 来提供 ACP-compatible agent `[A]`。

因此准确的表述应当是：

```text
Claude Code 核心
  ≠ ACP agent

Claude Code + claude-agent-acp adapter
  = 可以被 ACP client 使用的 Claude Code
```

这和“Claude Code 原生支持 ACP”是两件不同的事。

### 1.3 为什么容易误判

Claude Code 确实支持一种“宿主通过 stdin/stdout 驱动 CLI”的协议：

```text
--print
--input-format stream-json
--output-format stream-json
--permission-prompt-tool stdio
```

它还支持 `control_request`、`control_response`、`can_use_tool`、`interrupt` 等控制消息。
这些能力在功能上与 ACP 有相似之处，但它们是 **Claude Code 自己的 SDK control protocol**：

- 不是 ACP 的 JSON-RPC 2.0 方法名；
- 不是 `session/new`、`session/prompt`、`session/update`；
- 不是 ACP capability negotiation；
- 不是 ACP 的 permission request schema。

所以不能因为“都能用 stdio、都能流式输出、都能请求权限”就把两者等同 `[S]`。

## 2. CC 2.1.283 原生协议：stream-json SDK control protocol

### 2.1 SDK 启动参数

`reconstructed/full/m1246_0xd50bcf5.js` 中，SDK 启动子进程时直接拼接：

```js
let y = [
  "--output-format", "stream-json",
  "--verbose",
  "--input-format", "stream-json"
];
```

位置：`m1246_0xd50bcf5.js @ 577` `[S]`。

当提供 `canUseTool` 时，又追加：

```js
y.push("--permission-prompt-tool", "stdio")
```

位置：`m1246_0xd50bcf5.js @ 609` `[S]`。

`m0392_0xca8039f.js @ 4396` 还能看到自托管 runner 的同类启动方式：

```text
--print --sdk-url ... --input-format stream-json --output-format stream-json
```

这里的 `--sdk-url` 不是 ACP。`m0635_0xcea6bb3.js @ 4910` 明确说明它要求双向
`stream-json`，并把它描述为 Remote Control worker 连接 Anthropic backend 的保留参数 `[S]`。

### 2.2 输入/输出是“每行一个 JSON 对象”的 NDJSON

`reconstructed/full/m0094_0xc0d9ae5.js @ 10115-10116` 对 stdin/stdout 的 schema 写得很清楚：

```text
Everything the CLI writes to its output stream (stdout in stream-json mode):
exactly one StdoutMessage per line, as a single JSON object.

Everything a client may write to the CLI's input stream
(stdin in stream-json input mode): exactly one StdinMessage per line,
as a single JSON object.
```

`[S]`

也就是说，CC 的 SDK 传输层是 **NDJSON（newline-delimited JSON）**，
每一行是一个 CC 自定义消息对象。它不是 ACP 规范中的 JSON-RPC 2.0 envelope。

### 2.3 control_request / control_response envelope

`m0094_0xc0d9ae5.js @ 10055` 附近定义了：

```js
{
  type: "control_request",
  request_id: "...",
  request: {
    subtype: "...",
    ...
  }
}
```

并说明请求方会等待一个携带同一个 `request_id` 的 `control_response` `[S]`。

这和 ACP 的方法调用有相似的目的，但 schema 不同：

| CC SDK control protocol | ACP |
| --- | --- |
| `{type:"control_request", request_id, request:{subtype,...}}` | `{jsonrpc:"2.0", id, method, params}` |
| `{type:"control_response", response:{request_id,...}}` | `{jsonrpc:"2.0", id, result/error}` |
| `subtype:"can_use_tool"` | `session/request_permission` |
| `subtype:"interrupt"` | `session/cancel` |
| `subtype:"initialize"` | `initialize` |

### 2.4 CC 原生控制消息的实际类型

从 `m0094_0xc0d9ae5.js` 可读到至少这些 subtype：

| subtype | 方向 | 用途 | 证据 |
| --- | --- | --- | --- |
| `initialize` | client → CLI | 初始化 SDK 会话/能力 | `m0094 @ 8916` |
| `interrupt` | client → CLI | 中断当前 turn | `m0094 @ 8992` |
| `can_use_tool` | CLI → client | 请求宿主批准工具调用 | `m0094 @ 9001` |
| `set_permission_mode` | client → CLI | 切换权限模式 | `m0094 @ 9032` |
| `mcp_message` | 双向/控制桥 | 转发 MCP 消息 | `m0094 @ 9702` |
| `hook_callback` | CLI → client | 宿主处理 hook | `m1246 @ 1248` 附近 |

`[S]`

`m1246_0xd50bcf5.js @ 1235-1310` 的 `processControlRequest()` 进一步显示：

- `can_use_tool` 会调用 SDK 的 `canUseTool` 回调；
- `hook_callback` 会走 hook 处理；
- `mcp_message` 会转发到 SDK MCP server；
- 控制请求由 `request_id` 关联，并有取消控制器。

### 2.5 原生 SDK 的 session/prompt 语义

CC SDK 不是 ACP 的 `session/prompt`。它通过 stream-json 输入用户消息，
通过 stream-json 输出 `SDKMessage`（assistant/user/system/result 等），
并由控制协议完成初始化、权限和中断 `[S]`。

因此，CC 原生的典型宿主集成链路是：

```text
IDE / Host
   │  spawn + stdin/stdout
   ▼
Claude Code CLI
   --print
   --input-format stream-json
   --output-format stream-json
   --permission-prompt-tool stdio
```

而不是：

```text
IDE / Host
   │  ACP JSON-RPC
   ▼
Claude Code CLI
```

后者必须经过 adapter。

## 3. ACP 协议本身是什么

### 3.1 传输和消息模型

ACP 官方 v1 文档规定 `[B]`：

- 使用 **JSON-RPC 2.0**；
- 有 request/response 方法，也有不要求响应的 notification；
- 典型 transport 是 stdio；
- Agent 通常是 Client 启动的子进程；
- 路径必须是绝对路径；
- 除 schema 特别说明外，ACP 自定义对象字段使用 camelCase；
- 支持通过 `_meta` 和以下划线开头的方法做扩展。

典型流程：

```text
Client → Agent: initialize
Client → Agent: authenticate（如需要）
Client → Agent: session/new
Client → Agent: session/prompt
Agent → Client: session/update（流式进度）
Agent → Client: session/request_permission（需要授权时）
Client → Agent: session/cancel（用户取消）
Agent → Client: session/prompt response（turn 结束）
```

### 3.2 基线方法与可选方法

ACP v1 文档列出的基线方法：

```text
initialize
authenticate
session/new
session/prompt
```

常见可选/扩展能力：

```text
session/load
session/list
session/resume
session/close
session/delete
session/fork
session/set_mode
```

客户端侧基线方法：

```text
session/request_permission
```

客户端侧可选能力：

```text
fs/read_text_file
fs/write_text_file
terminal/create
terminal/output
terminal/wait_for_exit
terminal/kill
terminal/release
elicitation/create
```

不同 ACP 版本和客户端 capability 支持程度不同；实现时必须先协商，不能假定所有客户端都支持
`session/load`、terminal、elicitation 或 subagent sessions `[B]`。

### 3.3 session/update 的常见类型

`session/update` 是 ACP 的流式通知，`params.update.sessionUpdate` 决定具体类型。常见值包括：

```text
user_message_chunk
agent_message_chunk
agent_thought_chunk
tool_call
tool_call_update
plan
available_commands_update
current_mode_update
config_option_update
usage_update
notice
compaction_update
subagent_update
```

其中：

- `agent_message_chunk`：模型正文增量；
- `agent_thought_chunk`：思考/推理增量；
- `tool_call`：工具调用出现；
- `tool_call_update`：工具调用状态/结果变化；
- `plan`：计划快照；
- `available_commands_update`：可用斜杠命令变化；
- `usage_update`：token/上下文用量；
- `subagent_update`：支持 subagent 扩展时的子会话状态 `[B]`。

### 3.4 permission 是客户端能力，不是 Agent 自己弹窗

ACP 把工具授权建模为 Agent 向 Client 发出的请求：

```t
ext
Agent → Client: session/request_permission
Client → Agent: allow / deny / allow-always 等结果
```

这意味着 adapter 不应该在 ACP 进程里直接假设“用户已经同意”。
它必须把权限决策交回 ACP client，并处理：

- 用户拒绝；
- 用户取消；
- 权限请求超时；
- 工具调用已开始但授权请求尚未返回的竞态；
- cancel 与 permission request 同时发生。

## 4. Claude Agent ACP adapter 的实现拆解

### 4.1 架构

```text
┌────────────────────┐
│ ACP Client          │  Zed / IDE / 其他 ACP 客户端
│ (JSON-RPC 2.0)      │
└─────────┬──────────┘
          │ stdio: initialize / session/new / session/prompt / session/cancel
          ▼
┌──────────────────────────────────────────────┐
│ @agentclientprotocol/claude-agent-acp        │
│                                              │
│  ACP method handlers                         │
│  ├─ initialize                               │
│  ├─ newSession / loadSession                 │
│  ├─ prompt                                   │
│  ├─ cancel                                   │
│  ├─ setSessionMode                           │
│  └─ session index / fork / list 等扩展       │
│                                              │
│  Session registry                            │
│  Event translator: SDK → ACP                 │
│  Permission bridge: canUseTool → ACP         │
└──────────────────────┬───────────────────────┘
                       │ Claude Agent SDK `query()`
                       │ 子进程 + stream-json/control protocol
                       ▼
┌──────────────────────────────────────────────┐
│ Claude Code CLI 2.1.283                      │
│ --print --input-format stream-json ...       │
└──────────────────────────────────────────────┘
```

关键点：**adapter 是独立进程/独立层，不是把 ACP 方法硬编码进 Claude Code 主循环。**

### 4.2 Adapter 的入口方法

本地核对文件：`temp/acp-adapter-src/src/acp-agent.ts`（仅作调研副本，不应提交）。

主要入口：

| ACP 方法/能力 | Adapter 位置 | 说明 |
| --- | --- | --- |
| `initialize` | `acp-agent.ts @ 2829` | 协商协议版本和 client capabilities |
| `newSession` | `@ 3036` | 创建 adapter session，准备启动 SDK query |
| `loadSession` | `@ 3152` | 恢复历史 session 并重放 transcript |
| `authenticate` | `@ 3239` | 认证流程 |
| `prompt` | `@ 3765` | 启动一个 prompt turn，turn 结束时返回 |
| `cancel` | `@ 8383` | 取消当前 turn，必要时中断 SDK query |
| `setSessionMode` | `@ 8936` | 切换权限/运行模式 |
| `query()` 创建 | `@ 11408` | 真正启动 Claude Agent SDK |
| SDK options | `@ 11214` 起 | `cwd`、`includePartialMessages`、`permissionMode`、`canUseTool`、MCP、resume 等 |

`[A]`

### 4.3 SDK options 如何被 adapter 设置

adapter 的 `Options` 中可以看到这些关键项 `[A]`：

```text
cwd
includePartialMessages: true
permissionMode
canUseTool
mcpServers
additionalDirectories
sessionId
resume
forkSession
```

其中：

- `includePartialMessages: true` 让 adapter 能收到增量文本/思考/tool_use 事件；
- `canUseTool` 是权限桥的入口；
- `mcpServers` 把 ACP client 提供的 MCP server 传给 SDK；
- `sessionId`、`resume`、`forkSession` 负责会话生命周期；
- `additionalDirectories` 支持 ACP 的额外工作目录。

### 4.4 ACP 方法注册

`acp-agent.ts @ 13568` 附近的 `v1AgentApp()` 注册了 `[A]`：

```text
methods.agent.initialize
methods.agent.session.new
methods.agent.session.load
methods.agent.session.fork
methods.agent.session.list
methods.agent.session.delete
methods.agent.session.resume
methods.agent.session.close
methods.agent.session.setMode
methods.agent.session.setConfigOption
methods.agent.authenticate
methods.agent.providers.list
methods.agent.providers.set
methods.agent.providers.disable
methods.agent.logout
methods.agent.session.prompt
methods.agent.session.cancel
```

这说明 adapter 把 ACP 视为一层完整的 session RPC 接口，而不是只做一次性文本转发。

### 4.5 SDK 事件到 ACP session/update 的映射

adapter 的核心翻译函数是 `toAcpNotifications()`，位于 `acp-agent.ts @ 12946` 附近 `[A]`。

典型映射：

| SDK / Claude 事件 | ACP session/update |
| --- | --- |
| assistant 文本增量 | `agent_message_chunk` |
| user 文本/消息 | `user_message_chunk` |
| thinking 增量 | `agent_thought_chunk` |
| tool_use 开始 | `tool_call` |
| tool_result / 状态变化 | `tool_call_update` |
| TodoWrite 或 Task* 计划 | `plan` |
| 可用命令变化 | `available_commands_update` |
| 用量变化 | `usage_update` |
| 子 agent 会话（可选） | `subagent_update` 或子 session |

实现时要注意：

- 同一 tool call 不能因为 permission 请求和 stream tool_use 两个来源而重复发 `tool_call`；
  adapter 用 `emittedToolCalls` 之类的状态去重；
- `tool_call_update` 只应发送发生变化的字段；
- 流式文本、工具事件和 plan 快照需要有稳定顺序；
- 取消后的迟到事件必须被丢弃或标记为 cancelled；
- 子 agent 的事件必须归属于正确的 parent session/tool call `[A]`。

### 4.6 权限桥

adapter 的 `canUseTool()` 位于 `acp-agent.ts @ 10033` 附近 `[A]`。

流程：

```text
Claude SDK 调用 canUseTool(toolName, input, context)
  ↓
adapter 找到 session / parentToolUseId / agentID
  ↓
adapter 确保对应 tool_call 已发给 ACP client
  ↓
adapter 调用 ACP client 的 requestPermission()
  ↓
用户 allow / deny / allow-always
  ↓
adapter 解码为 Claude SDK 的 permissionResult
  ↓
SDK 决定是否执行工具
```

关键实现细节：

1. **先发 tool_call，再发 permission request**：部分 ACP client 要求权限请求引用的 tool call 已经存在；
2. **cancel 要能释放被阻塞的 permission 请求**：不能只依赖客户端一定回复；
3. **不要重新应用 bypass 规则**：adapter 注释明确指出，CC 在调用 `canUseTool` 前已经处理了
   `bypassPermissions`，此时仍到达 callback 的请求通常是安全相关或必须交互的请求，宿主不应自行放行；
4. **拒绝要转成 SDK 能理解的 deny 结果**，而不是简单杀掉整个进程 `[A]`。

### 4.7 cancel 桥

adapter 的 `cancel()` 位于 `@ 8383` 附近 `[A]`。

大致语义：

```text
ACP session/cancel
  ↓
adapter 标记该 session 的 turn 为 cancelled
  ↓
settle 正在等待的 permission / elicitation
  ↓
调用 Claude SDK 的 interrupt
  ↓
必要时等待/强制让 prompt turn 返回
  ↓
发 terminal 状态，关闭未完成的 tool_call
```

这里有一个很重要的工程原则：

> **取消不是“关闭进程”这么简单。** 必须让当前 `session/prompt` 的请求得到终态，
> 否则 ACP client 会一直等待；同时还要处理后台子任务、工具进程和权限回调的收尾 `[A]`。

### 4.8 子 agent / subagent sessions

adapter 支持一种可选扩展：

- client 在 `initialize` 声明支持 subagent sessions；
- Agent/Task 子代理可以作为 ACP 的子 session 暴露；
- 父 session 通过 `subagent_update` 宣告子 session；
- 子 session 有 `running`、`requires_action`、`idle`、`cancelled` 等状态；
- 子 session 可以单独 `session/cancel` `[A][B]`。

但这不是 ACP 的必选基线能力。对 GA 的第一阶段复刻，建议先把子 agent 事件折叠到父 session 的
`tool_call` / `tool_call_update` / `plan`，等 session 和权限模型稳定后再增加子 session。

## 5. CC 原生协议与 ACP 的逐项对比

| 能力 | CC 2.1.283 原生 | ACP adapter 层 |
| --- | --- | --- |
| 传输 | NDJSON，一行一个 JSON 对象 | JSON-RPC 2.0 over stdio |
| 初始化 | `control_request.subtype:"initialize"` | `initialize` |
| 会话创建 | SDK/CLI 进程 + session 参数 | `session/new` |
| 用户输入 | stream-json user message | `session/prompt` |
| 流式事件 | `SDKMessage` | `session/update` |
| 工具开始 | SDK `tool_use` | `tool_call` |
| 工具结果 | SDK `tool_result` / result message | `tool_call_update` |
| 权限 | `can_use_tool` control request | `session/request_permission` |
| 中断 | `interrupt` control request | `session/cancel` |
| 计划 | TodoWrite / Task* / SDK 事件 | `plan` |
| 命令列表 | `commands_changed` 等 SDK system event | `available_commands_update` |
| 子 agent | CC SDK 的 task/subagent 事件 | 可选 `subagent_update` / child session |
| 协议版本 | CC SDK 自有版本/字段 | ACP initialize 协商 |
| 扩展方式 | CC control subtype | `_meta`、下划线方法、capabilities |

一句话：

> **CC 原生协议是 adapter 的下层传输/控制面；ACP 是 adapter 对外的标准接口。**

## 6. 对 GA / 自研 Agent 的复刻建议

### 6.1 不要先改主循环，先做 adapter

推荐边界：

```text
GA Core / Agent Runtime
  ├─ 现有 CLI / Ink UI / workflow / subagent
  ├─ 统一事件总线（新增）
  └─ ACP adapter（独立包/进程，新增）
        ├─ JSON-RPC dispatcher
        ├─ session registry
        ├─ event mapper
        ├─ permission bridge
        └─ cancel bridge
```

不要让 ACP 的 session 概念污染现有 Agent 内部；也不要把所有 ACP 方法都塞进一个巨大的
`main.py`。建议单独建目录，例如：

```text
adapters/acp/
  server.py
  protocol.py
  sessions.py
  events.py
  permissions.py
  cancel.py
  tests/
```

具体目录名可按 GA 现有结构决定，但必须满足“adapter 可单独启动、可单独测试”。

### 6.2 P0：最小可用 ACP Agent

第一阶段只实现：

1. `initialize`
   - 协商 ACP 版本；
   - 返回 agent capabilities；
   - 明确是否支持 `loadSession`、MCP、terminal、elicitation、subagent；
   - 不支持的 capability 不要虚报。

2. `session/new`
   - 生成稳定 `sessionId`；
   - 记录 `cwd`、额外目录、模型、权限模式、MCP 配置；
   - 创建 GA session/run 上下文。

3. `session/prompt`
   - 把 ACP content blocks 转成 GA 输入；
   - 启动一个 turn；
   - 流式发送 `session/update`；
   - turn 结束时返回 ACP stop reason。

4. `session/cancel`
   - 取消当前 turn；
   - 中断模型/工具/子 agent；
   - settle 所有未完成 permission 请求；
   - 让 `session/prompt` 请求得到终态。

5. `session/update` 映射
   - `agent_message_chunk`；
   - `agent_thought_chunk`；
   - `tool_call`；
   - `tool_call_update`；
   - `plan`；
   - `usage_update`。

6. `session/request_permission`
   - 工具调用前询问；
   - 支持 allow / deny / allow-always（按 client capability）；
   - 把结果映射回 GA 工具执行器。

### 6.3 P1：会话恢复和完整体验

- `session/load` / `session/resume`；
- `session/fork`（如果底层 Agent 支持 transcript fork）；
- `session/list` / `session/close` / `session/delete`；
- `available_commands_update`，把 GA 的斜杠命令暴露给客户端；
- `current_mode_update` / `config_option_update`；
- MCP server 转发；
- terminal 工具（若 client 声明支持）；
- 子 agent 的 parent/child 归属；
- 大工具结果的分页/持久化策略。

### 6.4 P2：ACP v2 与高级扩展

- ACP v2 目前应视为实验性，先不要作为 GA 的第一版协议；
- 等 v1 adapter、session、cancel、permission、resume 全部稳定后，再评估 v2；
- 不要为了“看起来支持更多方法”而虚报 capability；
- 自定义扩展使用 `_meta` 或下划线方法，不要篡改标准方法语义。

### 6.5 GA 的 workflow / subagent 如何映射

这是 GA 最需要避免“把内部实现直接泄漏成 ACP”的地方。建议：

| GA 内部事件 | ACP 对外表示 |
| --- | --- |
| workflow 启动 | 一个 `tool_call`（工具名如 `workflow`），状态 `pending/in_progress` |
| workflow 阶段开始/结束 | `tool_call_update` 的 status/content |
| workflow 的 plan/阶段树 | `plan` 快照 |
| 子 agent 开始 | 第一阶段：`tool_call`；后续可扩展为 `subagent_update` |
| 子 agent 文本 | 父 session 的 `agent_message_chunk`，或子 session 的 chunk |
| workflow 最终结果 | `tool_call_update` + 最终 `agent_message_chunk` |
| workflow 失败 | `tool_call_update` status=`failed`，并让 prompt turn 正常结束 |
| 用户取消 workflow | `session/cancel` → 停止 run → 未完成 tool call 收尾 |

关键原则：

1. **workflow 是一个对外工具/任务，不要把内部 `runId` 当作 ACP session id；**
2. **每个事件必须有稳定顺序和 parent 归属；**
3. **子 agent 的迟到事件在 cancel 后不能继续污染 UI；**
4. **大输出要使用摘要 + 持久化路径/分页，而不是无限塞进单个 `session/update`；**
5. **workflow 失败不能导致 ACP prompt 永远不返回。**

### 6.6 不建议复刻的部分

以下内容明确不属于本次目标：

- Claude Code 云端会话；
- `isolation:"remote"` 的远程执行；
- 云端 agent worker；
- hosted session / remote control backend；
- 需要服务端账号或远程容器的 ACP 路由；
- 把 ACP 直接做成 GA 主循环的唯一入口。

**【复刻时暂时不需要参考 claudecode 云端会话的实现】**

## 7. 推荐实施顺序（给 Codex / 开发者）

### Step 1：冻结内部事件模型

先定义与 ACP 解耦的 GA 事件：

```text
turn.started
text.delta
thought.delta
tool.started
tool.updated
tool.finished
plan.updated
usage.updated
permission.requested
turn.completed
turn.cancelled
turn.failed
```

要求：

- 有 `session_id`、`turn_id`、`tool_call_id`、`sequence`；
- 有 parent/child 归属；
- 事件可以持久化、重放、去重；
- 事件层不依赖 ACP 类型。

### Step 2：实现 JSON-RPC dispatcher

- 只接受 `jsonrpc:"2.0"`；
- 区分 request 和 notification；
- 对未知方法返回标准 JSON-RPC error；
- 对 invalid params 做 schema 校验；
- request id 不重复；
- 每个 connection 独立状态。

### Step 3：实现 session registry

- `sessionId` 生成；
- `cwd` 和额外目录校验；
- 模型、权限模式、MCP 配置；
- turn 队列/互斥；
- session 关闭和清理；
- 断线时的资源回收。

### Step 4：接 prompt turn

- `session/prompt` 启动 GA turn；
- 事件流通过 `session/update` 发出；
- 最终返回 stop reason；
- 确保 prompt 不会因为内部异常永远挂起。

### Step 5：接 permission 和 cancel

这是最容易出错、优先级最高的安全路径：

- 工具执行前发 permission request；
- permission 结果必须可审计；
- cancel 时释放权限等待；
- cancel 后拒绝迟到工具结果；
- 工具进程/子 agent 必须被真正终止或标记为 stopped。

### Step 6：加 session/load/resume

- 保存 transcript/事件日志；
- 恢复时重放必要事件；
- 恢复失败要返回明确 JSON-RPC error；
- 不要把旧 turn 的迟到事件混入新 turn。

### Step 7：再考虑 subagent sessions 和 ACP v2

只有在 P0/P1 稳定后，才做：

- child session；
- `subagent_update`；
- ACP v2；
- 更多客户端专属扩展。

## 8. 测试清单

### 8.1 协议级测试

- `initialize` 版本协商成功/失败；
- 未知 method 返回 `-32601`；
- invalid params 返回 `-32602`；
- request id 关联正确；
- notification 不应收到 response；
- 客户端断开时 session 被清理；
- 非法路径/相对路径被拒绝。

### 8.2 turn 生命周期测试

- 正常 prompt → 多个 text chunk → 最终 response；
- prompt 期间工具调用 → tool_call → tool_call_update；
- 工具失败 → failed update + turn 正常结束；
- 模型错误 → ACP error/stop reason；
- cancel → prompt 得到 cancelled 终态；
- cancel 后迟到事件被丢弃；
- 连续 prompt 不串流。

### 8.3 permission 测试

- allow；
- deny；
- allow-always（如支持）；
- permission 请求期间 cancel；
- 客户端不回复 permission；
- 权限请求引用的 tool_call 已存在；
- 不允许 adapter 私自 bypass。

### 8.4 workflow/subagent 测试

- workflow 启动、阶段更新、最终结果；
- workflow 失败不会挂死 prompt；
- 多个 subagent 事件归属正确；
- 取消 workflow 后子任务停止；
- 大输出不阻塞 UI；
- 断线重连后不会重复显示同一事件。

### 8.5 真实客户端 E2E

- 使用一个支持 ACP 的客户端（如 Zed/Neovim 等）；
- 从真实输入框发起 prompt；
- 检查文本、思考、工具调用、权限、取消、历史恢复；
- 检查 UI 是否把 `tool_call_update` 合并到同一张工具卡，而不是重复创建卡片；
- 检查进程退出后没有残留 session/子进程。

## 9. 风险与边界

1. **adapter 不是 CC 核心**
   - 不能把 `claude-agent-acp` 的能力写成“Claude Code 原生 ACP”；
   - adapter 版本、SDK 版本和 CC CLI 版本会漂移，需要兼容矩阵。

2. **ACP v1 / v2 差异**
   - v1 是当前稳定目标；
   - v2 在 adapter 中是实验性能力，不要作为第一版硬依赖。

3. **permission 是安全边界**
   - ACP client 的 allow/deny 必须真实生效；
   - 不能在 adapter 侧默认放行；
   - 取消、超时、断线都要 fail closed。

4. **session 语义容易错**
   - `session/prompt` 返回时机是 turn 结束，不是“消息已入队”；
   - 后台任务、workflow、subagent 必须与 turn 生命周期分离；
   - resume/fork 需要稳定 transcript 和事件序号。

5. **大输出/背压**
   - `session/update` 不能无限发送超大内容；
   - 需要摘要、分页、持久化引用和节流；
   - 否则真实客户端会卡顿，甚至把 UI 事件队列打爆。

6. **不要引入云端依赖**
   - 本地 ACP adapter 不需要 Claude Code 云端会话；
   - 不要把 remote worker、hosted session 当作复刻前置条件；
   - **【复刻时暂时不需要参考 claudecode 云端会话的实现】**

## 11. 最终判断

### 11.1 对“CC 是否支持 ACP”的一句话回答

> **Claude Code 2.1.283 核心不原生支持 ACP；它原生支持的是自己的 stream-json SDK control protocol。ACP 通过外部的 `claude-agent-acp` adapter 接入。**

### 11.2 对 GA 复刻方向的一句话建议

> **不要改 GA 主循环去说 ACP。先做独立 adapter：内部事件总线 → ACP session/update、permission、cancel、session 生命周期。**
>
> 这样既能复用 GA 现有 workflow/subagent 能力，又不会破坏 CLI/Ink UI，也符合 CC 自身的分层方式。

### 11.3 下一步最小交付

建议下一步先实现一个“可被 ACP client 启动”的最小 adapter：

```text
initialize
session/new
session/prompt
session/update
session/request_permission
session/cancel
```

只要这 6 条链路打通，ACP 复刻就已经从“概念”变成“可验证的产品能力”；
`session/load`、`fork`、subagent sessions 和 ACP v2 都应该排在其后。
