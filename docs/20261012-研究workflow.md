
# Claude Code 2.1.283 Dynamic Workflow 深度源码研究：脚本生成与执行引擎

## 一、研究目标

研究仓库：

https://github.com/valkryhx/claudecode283_hack

目标是完整还原 Claude Code 2.1.283 Dynamic Workflow 的内部工作机制，为后续在自己的 GenericAgent / Agent Runtime 中复用相关设计提供可靠依据。

本次研究分为两个最高优先级方向：

1. **工作流脚本如何生成**：谁触发大模型生成 JS 脚本，使用什么 Prompt，输出如何校验，失败后如何修复。
2. **工作流脚本如何执行**：`agent()`、`parallel()`、`pipeline()` 等核心 API 的真实实现、语义、参数、返回值、调度策略和异常行为。

不能因为已有研究文档提到某个函数，就认为它已经研究完整。请先阅读现有研究，再通过源码逐项核实，区分已有结论、缺失细节和需要纠正的结论。

## 二、第一部分：工作流脚本生成机制

重点追踪：

`用户任务 → 工作流启动入口 → Prompt 构造 → 模型请求 → 模型返回 → 脚本提取/解析 → 校验 → JS VM 执行`

必须回答：

1. 谁决定启动 Dynamic Workflow？
2. 谁负责生成第一份工作流 JS 脚本？
3. 模型选择逻辑是什么？
4. 实际传给模型的 Prompt 原文是什么？
5. Prompt 如何规定脚本格式、可用 API、任务拆分和依赖关系？
6. 模型返回的内容如何转换为可执行脚本？
7. 执行前是否存在语法检查、Schema 检查、静态分析或安全校验？
8. 生成失败、解析失败、运行失败时，是否重试或要求 LLM 修复？
9. 是否存在不经过 LLM 生成脚本的执行路径？

请追踪真实函数调用关系，不得仅凭 Prompt 字符串的存在推断其用途。

## 三、第二部分：核心执行 API 深度分析

分别研究以下 API：

- `agent()`
- `parallel()`
- `pipeline()`
- `workflow()`
- `phase()`
- `log()`
- `budget`

如果源码还暴露了其他重要的 Workflow API，也应列出并研究。

### 3.1 每个 API 的统一研究模板

对每个函数逐项回答：

**A. 定义与调用链**

- 函数定义在哪个文件、哪个函数或模块中？
- 如何注入 JS VM？
- 是普通 JS 函数、异步函数、包装器还是代理？
- 调用后经过哪些内部函数？
- 是否存在参数预处理、上下文注入、结果后处理？

**B. 参数语义**

- 参数数量、类型和默认值；
- 每个参数的实际作用；
- 参数校验规则；
- 非法参数如何处理；
- 是否支持对象形式、Schema、模型选择、阶段标记、工具限制、隔离模式等；
- 参数的说明是否与实际代码一致。

不能只根据类型定义或 Prompt 中的说明下结论，应核对执行代码。

**C. 返回值**

- 返回值类型与数据结构；
- 正常完成、失败、取消、预算耗尽等路径分别返回什么；
- 是否可能返回 `null`；
- 返回值是否经过 clone、sanitize 或序列化；
- 调用者如何使用返回值；
- 有 Schema 时，实际输出是否会被验证，以及验证发生在哪一层。

**D. 错误与异常**

- 哪些异常由函数内部捕获？
- 哪些异常会传播到调用者？
- 哪些错误会被转成 `null` 或其他普通返回值？
- 是否会重试？
- 是否会向 LLM 反馈错误并要求修复？
- 用户取消、AbortSignal、超时和预算耗尽如何处理？

请区分“异常被吞掉”“失败被隔离”“任务自动重试”和“LLM 自动修复”，这四者并不等价。

**E. 资源与状态**

- 是否占用 Agent 并发槽位？
- 是否增加 Agent 总数计数？
- 是否消耗共享 Token Budget？
- 是否读写 journal/cache？
- 是否受取消信号控制？
- 是否与外层 Workflow 共享状态？
- 是否存在执行超时、限流等待或生命周期清理？

**F. 源码证据**

每项结论提供文件路径、函数名、准确行号或可复核的代码片段，并注明证据等级：

- 已证实；
- 部分证实；
- 推断；
- 未定位。

### 3.2 `agent()`：子 Agent 执行机制

额外重点研究：

1. 如何创建子 Agent，如何构造其 Prompt 和上下文？
2. `label`、`phase`、`schema`、`model`、`effort`、`isolation`、`agentType`、`disallowedTools` 等选项是否真实存在，默认值是什么？
3. 子 Agent 是否有独立的会话、工具权限、取消信号和生命周期？
4. 子 Agent 的最终输出如何返回给工作流脚本？
5. Schema 是否只进行定义校验，还是也会验证模型输出？
6. journal/cache 命中后是否完全跳过 Agent 执行？缓存键包含什么信息？
7. 失败、跳过、取消和预算耗尽分别如何表现？
8. 子 Agent 的 system prompt 如何规定输出必须面向调用脚本，而非直接回复用户？
9. 是否存在重试、反思、自我修复或二次调用机制？

### 3.3 `parallel()`：并行执行机制

额外重点研究：

1. 入参必须是函数数组吗？支持哪些输入形式？
2. 每个 thunk 如何启动，是否同时启动？
3. 是否使用 `Promise.all`、`Promise.allSettled` 或其他调度机制？
4. 所有子任务是否必须结束后才返回？
5. 一个任务失败是否会取消其他任务？
6. 单项失败如何映射到最终数组？结果顺序是否保持输入顺序？
7. 是否支持超时、取消、预算限制和最大并发数？
8. 并发上限是如何计算和配置的？信号量如何实现？
9. 预算耗尽时，是拒绝启动新任务、取消已有任务，还是其他行为？
10. 是否存在嵌套并行的限制？
11. 返回结果中是否保留错误信息？调用者能否区分失败、跳过和有效的 `null`？
12. 是否存在对失败子任务自动重试或要求 LLM 修复的逻辑？

特别验证：如果源码使用 `Promise.allSettled()`，请说明它如何等待所有任务、如何转换失败结果，以及为什么这并不自动意味着重试。

### 3.4 `pipeline()`：流水线执行机制

额外重点研究：

1. 入参和 stage 的函数签名是什么？
2. 多个 items 与多个 stages 分别如何调度？
3. 对同一个 item，stage 是否严格按顺序执行？
4. 不同 items 是否可以同时执行？
5. 是否存在全局 stage barrier？请用源码和具体执行时间线证明。
6. 前一阶段的返回值如何传给下一阶段？
7. 某个 stage 返回 `null`、抛异常或被取消时，后续 stage 如何处理？
8. 不同 items 之间是否相互隔离？
9. pipeline 与 parallel 是否共享同一并发信号量和预算？
10. 是否存在部分成功、失败收集、重试和恢复机制？

请提供至少两个执行示例：

- 3 个 items、2 个 stages 的正常执行时间线；
- 一个 item 的第一阶段失败时，所有 item 和后续 stages 的实际行为。

示例必须根据源码语义推导，不能将建议行为写成当前实现。

### 3.5 `workflow()`：嵌套工作流机制

额外重点研究：

- 参数及返回值；
- 工作流如何加载和调用；
- 嵌套层数限制；
- 父子工作流共享或隔离哪些状态；
- 并发槽位、Agent 总数、取消信号和 Token Budget 的继承方式；
- 子工作流失败时如何传播；
- 是否存在嵌套工作流的独立 journal/cache；
- 是否支持递归或存在防止递归的保护。

### 3.6 `phase()`、`log()` 和 `budget`

分别说明：

- `phase()` 是设置状态、切换阶段，还是仅记录元数据？
- `log()` 的参数、输出通道和副作用是什么？
- `budget` 暴露了哪些字段或方法，是否只读？
- 预算单位、扣减时机、共享范围和超限行为是什么？
- 这些 API 是否影响调度，还是仅用于状态展示和日志？

不要根据名称推测功能，必须确认源码。
