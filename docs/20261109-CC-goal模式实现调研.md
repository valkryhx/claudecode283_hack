## 0. 一句话结论

**CC 的 goal 模式不是一个独立的 agent loop，而是"往 session 的 Stop hook 注册表里塞一个 `type:"prompt"` 的钩子"。**

`/goal <condition>` 做的事情是：

1. 把条件字符串当作一个 **prompt 型 Stop hook** 注册到当前 session 的 `sessionHooksRegistry` 的 `"Stop"` 事件上；
2. 把 hook 的 prompt 固定写成一段"`Based on the conversation transcript above, has the following stopping condition been satisfied? ... Condition: <用户条件>`"的评估指令；
3. 每次主循环要停下来时，Stop hook 链会调一次**独立的一次性 side query**（`querySource:"hook_prompt"`）当评估器；
4. 评估器返回 `{ok, reason, impossible}` 的 JSON。`ok:false` 让 Stop hook 返回 blocking error → 主循环不能停 → 继续干活；`ok:true` → hook 放行 + 自动注销 + 标记 achieved。

这个设计的巧妙点在于：**复用已有的 Stop hook 阻断机制**，因此"goal 未达成时不许停"这件事在主循环里是零侵入的，不需要 goal 专属的分支。

## 2. 核心：goal 状态库 — `m0266_0x1170dc8c.js`（4,483 B）【实码】

这个模块是 goal 的**唯一真源**（single source of truth），只有 4.5 KB，导出 14 个符号。全文结构如下。

### 2.1 数据结构

```js
// 消息流里的 goal 状态 attachment
function lCr(e,t){return{type:"goal_status",met:e,sentinel:!0,condition:t}}

// appState.activeGoal 的形状（由 HNt 构造）
{condition: string, iterations: number, setAt: number,
 origin: "user"|"proposal_approved"|"proposal_direct"|"restored"|...,
 tokensAtStart: number,
 lastReason?: string, deferredSince?: number, checkinCount?: number,
 lastDeferralPassAt?: number, idleCheckinCount?: number}
```

注意 `lCr` 造的 attachment 带 `sentinel:!0`——这是一个**占位哨兵**，用于"设 goal / 清 goal 时在消息流里留一条可见记录"，但它**不参与达成判定**（`uEs` 会显式跳过 `sentinel`）。

### 2.2 读回：从消息流反查当前 goal

```js
function KFn(e){          // 用于 resume：从消息流里找回"仍未达成"的 goal 条件
  if(!e) return null;
  for(let t=e.length-1;t>=0;t--){
    let n=e[t];
    if(n?.type!=="attachment"||n.attachment.type!=="goal_status") continue;
    if(n.attachment.met||n.attachment.failed) return null;   // 已 met/已 failed → 没有活跃 goal
    let o=n.attachment.condition;
    return typeof o==="string"&&o.length>0?o:null;
  }
  return null;
}

function uEs(e){          // 用于 UI：找回"最近一次达成"的记录以渲染 achieved 面板
  for(let t=e.length-1;t>=0;t--){
    let n=e[t];
    if(n?.type!=="attachment"||n.attachment.type!=="goal_status") continue;
    let o=n.attachment;
    if(!o.met||o.sentinel) continue;      // 只要真正达成的（非哨兵）
    return{condition:o.condition,iterations:o.iterations,durationMs:o.durationMs,tokens:o.tokens};
  }
  return null;
}
```

**两个函数的反查方向都是从后往前**（`for(...t>=0;t--)`），取最近一条。区别：
- `KFn` 遇到 `met` **或** `failed` 就立刻返回 `null`（终止，说明这一轮 goal 生命周期已结束）；
- `uEs` 跳过 `sentinel`，只认真正达成的记录。

> ⚠️ 注意 `KFn` 不看 `sentinel`：设 goal 时写入的哨兵 `met:false,sentinel:true` 会被它当作"活跃 goal 的条件"读出来。这正是 resume 恢复想要的语义。

三条拒绝消息原文：

| --- | --- |

关键细节：

1. **`fEs(e)` 造出的是 `{type:"prompt", prompt:<评估指令>}`**，见下；
2. **matcher 是空串 `""`**——意味着 Stop 事件下所有情况都匹配（Stop 本身没有 tool name，空 matcher 就是"全匹配"）；
3. **设置前会先删掉已有的同类 hook**（`G7e` 的筛选条件见 2.7），保证"同时只有一个 goal"；
4. `iterations` 从 0 开始、`setAt` 是时间戳、`tokensAtStart` 记 token 基线——这三者撑起了 TUI 的 "running X · N turns · M tokens"；
5. 返回值语义：**成功返回 `null`，失败返回错误消息字符串**。调用方（`m2564` / `m2331`）据此决定是否继续。

### 2.6 评估指令：`dCr` 与 `fEs`

```js
var dCr=(e)=>`A session-scoped Stop hook is now active with condition: "${e}". Briefly acknowledge the goal,
then immediately start (or continue) working toward it — treat the condition itself as your directive and do
not pause to ask the user what to do. The hook will block stopping until the condition holds. It auto-clears
once the condition is met — do not tell the user to run \`/goal clear\` after success; that's only for clearing
a goal early.`;

function fEs(e){let t={type:"prompt",prompt:e};return fGi(t,()=>!p()),t}
```

两个不同的东西，别混：

| 名字 | 用途 | 内容 |
| --- | --- | --- |
| `dCr(cond)` | **kickoff 文本**，设置成功后作为 metaMessage 注入给模型 | "A session-scoped Stop hook is now active with condition..." |
| `fEs(cond)` | **Stop hook 对象**，注册到 hook 注册表 | `{type:"prompt", prompt:<用户条件原文>}` |

注意 `fEs` 里的 `prompt` **就是用户条件原文**，不是 `dCr` 的文本。真正的"评估指令模板"是 hook 执行器在运行时拼的（见 §4.1），格式为：

```
Based on the conversation transcript above, has the following stopping condition been satisfied?
Answer based on transcript evidence only.

Condition: <用户条件>
```

`fGi(t,()=>!p())` 的第二个参数是个惰性求值的启用判据——hooks 被限制时该 hook 自动失效。

`G7e` 的筛选条件（同一个函数也被 `HNt` 用来做"清旧 hook"）：

```js
function G7e(e,t){
  let n=[];
  for(let o of e.get(t,"Stop").get("Stop")??[]){
    if(o.matcher!==""||o.skillRoot!==void 0) continue;   // 只看 matcher 为空、非 skill 的
    for(let s of o.hooks) if(s.type==="prompt") n.push(s);   // 只看 prompt 型

```

**这段代码揭示了一个重要的设计约束**：`G7e` 会把**所有** `matcher===""` 且非 skill 的 prompt 型 Stop hook 都当成 goal 候选。也就是说：

> **用户自己写一个 `{"type":"prompt"}` 的无 matcher Stop hook，会被 `/goal` 覆盖掉。**

这是实现上的取舍（简化到"只有一个 goal"），但对复刻者是**必须知道的行为差异**——如果自研 agent 允许用户自定义 prompt hook，就不能直接照抄这段的"删掉所有同类"逻辑。

## 6. 评估器的上下文预算：`Oqr` 转录裁剪【实码】

> 坐标：`m0591_0x11be624e.js` 偏移 **3,606,077** `lBn=0.5`、**3,606,402** `Oqr`、**3,606,157** `Pqr`、`Mqr`

### 6.1 预算计算

**三个关键数字**：

| --- | --- | --- |

| `1e6` | 1,000,000 | 若模型名带 `[1m]` 或 `uC()` 为真，窗口按 1M 算 |
| `lBn` | **0.5** | **预算比例——只用窗口的一半** |

### 6.2 裁剪算法：从尾部往前装，整组保留

```js
  let y = r4(e),                                 // ① 按"对话轮组"分组
      S = 0, w = y.length;                        //    S=累计 token，w=保留起始下标

      G = e.length - N.length;                    //    丢弃条数
```

**三个设计要点**：

1. **按组（group）而不是按条裁剪**：`r4(e)` 把"user message + 它触发的所有 assistant/tool 消息"归为一组。这样不会切出"有 tool_use 没有 tool_result"的半截对话——那种对话会让评估器困惑。
2. **从尾部往前装**：保留最近的对话（最相关），丢掉最早的。
3. **`w<y.length` 这个条件是必要的**：保证至少保留最后一组，即使它单独就超预算。否则可能裁成空。

### 9.3 三态判断：`ye()` 的两处相反用法【实码】

```js
// m0040:97915
function ye(){return !t().host.launchOptions.isInteractive()}

// m1516 —— 命令层
get isHidden(){return !ye()}                 // 非交互时隐藏这个"交互版"命令
isEnabled:()=>ye()||xn()                     // 交互 或 remote 才启用

// m0266 —— 门禁层
if(!ye() && !Us()) return {message:h, code:"trust_gate"};
```

**注意方向**：`ye()` 是 **"非交互"** 的判据（`!isInteractive()`）。
- 命令层：`isHidden = !ye()` → 交互时（`ye()===false`）**显示**；
- 门禁层：`!ye()` → 交互时（`ye()===false`）**才需要检查 trust**。

复刻时很容易把 `ye()` 误读成 "isInteractive"，导致所有分支反向。这是本轮读到的一个**高价值陷阱**。

### 9.4 `qFn()` 为什么必须存在

goal 建立在 Stop hook 之上，而 Stop hook 是**可以在用户/组织层面被禁用的**：

```
设置/策略 disableAllHooks = true    →  hook 根本不执行
设置/策略 allowManagedHooksOnly     →  只允许托管 hook，goal 的 hook 不执行
```

如果 goal 不检查这些门禁，就会出现：**用户设了 goal，hook 被禁用，goal 永远不评估 → 模型永远不停 → 无限循环烧钱**。

`qFn()` 的三道检查是**防止这个灾难**的唯一屏障。复刻时这一条绝对不能省。

`hooks_held` 这个特例（§2.8）也很讲究：组织设置还没读到时不阻止 resume 恢复，因为"暂时读不到"不等于"被禁用"；但设置读到后如果真被禁用，下一轮 Stop hook 会自然失败。

## 11. goal 与子 agent / Agent Team 的边界

> 这是第 1 轮挑刺的 E1。结论比预期更清楚：**goal 是严格 session 单例，子 agent 完全不参与。**

### 11.1 三道隔离，都靠"`agentId` 为空"这一个判据【实码】

**第一道：Stop hook 链入口**

```js

if(B && mt){ ... }                                           //    延迟评估分支也要求 mt
```

`St` 为空 → 后续所有 `St && ...` 的分支全部短路 → **子 agent 的 Stop hook 链里 goal 相关代码一条都不执行**。

**第二道：中断策略**

```js
// m0848, ou()
if(e.agentId || ls(r)!=="main") return;      // ← 子 agent 或非主循环 → 直接返回
```

**第三道：评估结果的落地**

```js

if(pe.hookEvent==="Stop" && Ee){ ... }
```

即使某个子 agent 意外触发了同名 hook，`ct()` 的身份校验 + `St` 为空也让它无法污染 `activeGoal`。

**结论**：`options.activeGoal` 的存在意义是**让埋点能知道"这一轮是在 goal 模式下跑的"**，不参与任何行为决策。子 agent 的 turn_end 事件也会带这个字段，因此可以分析"goal 模式下 spawn 的子 agent 表现有何不同"。

### 11.3 子 agent 的 Stop hook 是 `SubagentStop`，不是 `Stop`

评估器代码里这一行很关键【实码】：


| 事件 | 由谁触发 | goal hook 是否执行 |
| --- | --- | --- |
| `Stop` | 主 session 一轮结束 | ✅ |
| `SubagentStop` | 子 agent 结束 | ❌（goal hook 只注册在 `"Stop"` 上） |

**这个边界很重要**：子 agent 结束后**不会**触发 goal 评估。goal 的粒度是"整个主会话的一轮"，不是"每个子任务"。

### 11.4 Agent Team / teammate 场景

`m0848` 里 teammate 相关代码（`Ld(y.agentContext,...)`）与 goal 是**并列分支**，不是嵌套：

```js

// 之后才是 teammate 分支

if(so !== void 0 && y.agentId === so.agentId){ ... }
```

**顺序上 goal 先判、teammate 后判**。但因为 goal 要求 `!y.agentId` 而 teammate 要求 `y.agentId === so.agentId`（teammate 自己有 agentId），**两者永远不会同时成立**——是两个互斥的执行域。

### 11.5 后台任务导致的"延迟评估"与 Agent Team 的关系

§4.1 里 `Yd(y.taskRegistry.all())` 返回"仍在跑的后台任务"，其定义：

```js
function Yd(e){
  return Object.values(e).filter(n =>
    !nm(n) &&                                    // 排除已结束的
    !(n.type==="local_agent" && n.agentType==="main-session") &&   // 排除主 session 自己
    (iDt(n) || Qlo(n))                           // 是 agent 任务 或 shell 任务
  );

```

**所以 spawn 了一个后台 Agent 也会让 goal 评估延迟。** Agent Team 的 teammate 如果是后台型（`type==="local_agent"` 且非 main-session），同样会触发延迟评估 + check-in。

这是合理的设计：只要"还有别的东西在产出"，主 session 停下来评估 goal 就是过早的。

### 11.6 `isConcurrencySafe(){return !1}` 的含义

ProposeGoal 声明自己**不并发安全**。结合 `backgrounding:"never"`，意味着：

- 模型不能在**同一条消息里**并发调用多个 ProposeGoal（会有多个审批弹窗竞争）；
- ProposeGoal 不能被转到后台执行。

再加 §8.4 的去重检查（`if(e.toolState.get(Qqt).id) throw`），形成了三重的"同一时刻只有一个待审批提案"保证。

## 12. 持久化、SDK 面与远端同步

> 这是第 1 轮挑刺的 F1。核心问题：**goal 状态存在哪、怎么跨进程/跨会话传递。**

### 12.1 三个层次的存储

| 层次 | 载体 | 生命周期 | 谁写 | 谁读 |
| --- | --- | --- | --- | --- |
| **① 内存** | `appState.activeGoal` | 单个进程会话 | `HNt` / `$Nt` / `ijo` / 评估结果 | TUI、Stop hook 链、check-in |
| **② transcript** | `goal_status` attachment（JSONL 里的一条消息） | **持久化到磁盘，跨重启** | `Ngo()` 追加 | `KFn()`（resume 反查）、`uEs()`（UI 渲染） |

`ijo`（resume 恢复）就是靠读 ② 重建 ① 的（§2.8），而不是读任何配置文件。这意味着：

> **goal 状态天然跟随 transcript 走。** 复制一个会话的 JSONL 到另一台机器，resume 后 goal 会自动恢复——不需要额外的状态同步。

## 16. Prompt hook 的动态失效机制：`fGi` 全链

> 这是第 3 轮挑刺的 L1。`fGi` 只有 1 行，但它是 319 新增的"hook 运行时启用谓词"。

### 16.1 实现：一个 WeakMap 存谓词【实码】

> `m0264_0x1170cb71.js:2838–2860`

```js
var d = new WeakMap;

function fGi(o,e){ d.set(o,e); }                    // 挂谓词
function gEs(o){ return d.get(o)?.()===!0; }        // 求值：没挂 → false；挂了 → 调它
function pGi(o){ return d.has(o); }                 // 是否挂了谓词
```

**用 `WeakMap` 而不是给对象加属性**，两个好处：
1. 不污染 hook 对象本身（它可能被序列化/比较/传输）；
2. 对象被回收时谓词自动消失，无泄漏。

### 16.2 消费点：`mGi` 在装配 hook 时过滤【实码】

### 16.3 完整链路：goal hook 从注册到失效

```

       ├→ t = {type:"prompt", prompt:<条件>}

       ├→ 遍历每组 prompt hook
       └→ gEs(hook) → WeakMap.get(hook)() → !p()

            └→ p() 为假（hooks 正常）  → 保留
```

**这样做的价值**：用户在会话中途通过 `/config` 打开了 `disableAllHooks`，不需要重新走 `qFn()` 检查、也不需要清 `activeGoal`——下一轮装配时 hook 自然就不在了。

**但有个副作用值得注意**：hook 被过滤掉后，`activeGoal` 仍然存在（状态栏仍显示 `/goal active`），但永远不会被评估。这会造成"goal 卡住不动"的困惑状态。

> **待查（第 4 轮新增）**：是否有机制检测"goal 存在但 hook 被过滤"并给出提示？`qFn()` 只在设置/resume 时检查，运行中不检查。这是一个可能的体验缺口。

### 16.6 复刻建议

如果自研 agent 的 hook 注册表是"设置时校验"模式，可以照抄 283/303 的做法（简单）。如果要支持"运行中禁用 hooks 立即生效"，就需要 319 这套谓词机制：


3. 过滤有总开关 `Eee()`，关掉时不过滤。

**CC 在 319 里只有两个 `sessionHooksRegistry.add` 调用点**（`m0266` 设置、`m0848` 重新挂回），都用 `fEs` 包装。如果你的 agent 有更多动态注册 hook 的地方，必须记得都包一层，否则会被静默过滤掉——这是一个**很容易踩的坑**。

### 17.6 与普通（非 goal）Stop hook 的对比

`blockingError` 这条路径是**通用的 Stop hook 阻断机制**，goal 只是复用了它。区别在于：

| 维度 | 普通 Stop hook | goal |
| --- | --- | --- |
| `blockingError` 内容 | hook 脚本的 stdout/stderr | `[条件]: 评估理由` |
| 谁产生 | 用户配置的 command hook | 内部 prompt 型 hook |
| 长什么样 | `Stop hook feedback:\n<stderr>` | `Stop hook feedback:\n[<条件>]: <理由>` |

**所以模型无法从文本本身区分"这是 goal 在拦我"还是"用户的 hook 在拦我"**——除了那个 `[条件]:` 的方括号格式。

> 这可能是有意的（统一机制，不特殊化），也可能是个小瑕疵（模型不知道该"朝目标努力"还是"满足某个检查规则"）。从 kickoff 文本 `dCr` 强调 "treat the condition itself as your directive" 来看，CC 是**靠 kickoff 而不是靠每次反馈来维持目标感的**。

### 17.7 `preventContinuation` 的差异

```js
preventContinuation: !Y && e.continueOnBlock!==!0
```

- 对 `Stop`/`SubagentStop`（`Y` 为真）：`preventContinuation = false` → **不阻止继续**，正常走"再来一轮"；
- 对非 Stop 事件：`preventContinuation = true` → 阻止继续（除非 hook 显式 `continueOnBlock:true`）。

**这是语义正确的**：Stop hook 的"阻断"含义是"别停下来，继续干"，而不是"别继续了"。

**结论：`hooks_held` 被拒后，用户必须重新敲一次 `/goal <条件>`。**

> 第 3 轮挑刺的 K1。查证结果：`agent` 型 hook **不影响 goal**（`G7e` 只收集 `prompt` 型），但它是一条独立的、能力更强的评估路径，对复刻有直接参考价值。

### 20.1 六种 hook 类型【实码】

### 20.5 为什么 goal 用 `prompt` 而不是 `agent`

这是设计取舍，**我的推断（非源码直述）**：

| 用 prompt 的理由 | 依据 |
| --- | --- |
| **成本** | 每次评估若跑 agent 循环，token 消耗是数量级的差别。goal 可能触发几十次评估 |
| **确定性** | 无工具 → 判定可复现；有工具 → 每次评估看到的证据不同 |
| **防止作弊** | 评估器若能执行命令，agent 可能通过"改测试文件让测试通过"来骗过评估（虽然 agent 型 hook 也有 `oae` 的防注入指令） |
| **延迟** | 一次 query 秒级返回；agent 循环可能几分钟 |

**而 `agent` 型的价值在于**：能真正去验证（"跑一遍测试看是否通过"），而不是只看转录里写了什么。

> **这解释了 §8.2 ProposeGoal 提示词里那句**："The evaluator verifies the condition from the conversation alone — **it cannot run commands or read files** — so state one measurable end state with its check (e.g. 'bun test exits 0')."
>
> 因为评估器不能跑测试，所以条件必须写成"转录里能看出测试退出码为 0"的形式。**这是被架构约束倒逼出来的提示词要求。**

### 20.6 对复刻者的两种选择

| 方案 | 实现 | 适合场景 |
| --- | --- | --- |
| **A：照抄 CC（prompt 型）** | 无工具 side query，只读转录 | 成本敏感、要求确定性、用户能接受"条件必须可被转录验证" |
| **B：用 agent 型** | 给评估器工具，让它自己验证 | 条件需要实际执行验证（跑测试、查文件）、可接受成本 |

**混合方案（CC 没有，但我认为值得考虑）**：

1. 默认用 prompt 型做**快速判定**；
2. 当 prompt 型返回 `impossible` 或连续 N 次 `not_met` 时，**升级**到 agent 型做一次"实测验证"，避免"模型自己说做不到"就放弃；
3. 这正是 §3.2 里那句话的精神："the assistant claiming the goal is impossible is evidence, not proof; independently confirm".

**CC 目前把这个"独立确认"交给同一个无工具评估器**（让它"用自己的判断"），而没有升级到有工具的验证。这是一个可以改进的点。

## 21. 两个防止无限循环的硬上限（`max_turns` 与 `BLOCK_CAP`）

> 第 3 轮挑刺的 Q1。这两个上限是 goal 机制能安全存在的**前提**——没有它们，goal 的"不许停"可能变成真正的死循环。

### 21.1 Stop hook 连续阻断上限：`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`【实码】

> `m0848_0x124d7ee6.js:227960` 附近


**两个上限的区别**：

| 上限 | 值 | 触发后 `reason` | goal 策略 |
| --- | --- | --- | --- |
| `max_turns` | 由调用方传入（`w`） | `"max_turns"` | `{kind:"none"}`（§4.4） |
| `BLOCK_CAP` | **默认 8 次连续**，可被 `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` 覆盖 | `"completed"` | 看 `goalPass` |

### 21.2 为什么 `BLOCK_CAP` 触发后返回 `completed` 而不是 `max_turns`

这是个**容易被忽略但很关键**的细节：

```js
return yield* po(R, [...N,...ie,...ae], {stopHookActive:Xo}),
       {reason:"completed", goalPass:ge.goalPass};     // ← completed！
```

而 `max_turns` 分支返回的是 `{reason:"max_turns"}`。

回想 §4.4 的 `Bf()`：

```js
case "completed":   return qf(e.goalPass);   // met→none, not_met→pause(goal_check_capped), error→retry
case "max_turns":   return {kind:"none"};    // 什么都不做
```

**所以两条路径的 goal 后果截然不同**：

| 路径 | `goalPass` | `Bf()` 结果 |
| --- | --- | --- |
| `max_turns` | （不传） | `{kind:"none"}` — goal 继续有效，但**这一轮停了** |
| `BLOCK_CAP` + `goalPass="not_met"` | `not_met` | `qf("not_met")` = `{kind:"pause", cause:"goal_check_capped"}` |
| `BLOCK_CAP` + `goalPass="error"` | `error` | `qf("error")` = `{kind:"retry", cause:"goal_check"}` |

**`goal_check_capped` 的文案**（§4.7）：

```
Goal paused · goal checks kept finding it unmet this turn · send a message to continue
```

**这条文案对应的正是 `BLOCK_CAP` 场景**：评估器连续 8 次说"没达成"，主循环被强制结束，goal 被暂停等用户介入。

**这个设计非常合理**：如果 8 轮都没达成，继续自动硬转只会烧钱，应该让人看一眼。

### 21.3 `stop_hook_active` 这个约定

提示文案里有一句关键的**给 hook 作者的指导**：

> "For Stop/SubagentStop hooks, check `stop_hook_active` in the input and return success while it's true."

**含义**：Stop hook 的输入里有一个 `stop_hook_active` 字段。当它是 `true` 时，表示"这一轮已经被 hook 阻断过了"。

**正确的 hook 写法**应该是：

```python
# 用户自己写的 Stop hook（伪码）
def on_stop(payload):
    if payload.get("stop_hook_active"):
        return {"ok": True}      # 已经为这次停下努力过了，放行，避免死循环
    ...正常判定...
```

**goal 的 hook 不需要这个判断**，因为它有自己的 `BLOCK_CAP` 兜底，而且 `not_met` 的语义就是"继续干"。

但从 §21.2 的代码看，`po(R, ..., {stopHookActive:Xo})` 在 `BLOCK_CAP` 触发时显式传了 `stopHookActive` —— 这是给**后续 hook** 的信号。

### 21.4 两层防线的完整图景

```
用户设 goal
  ↓
每轮结束 → Stop hook 链
  ↓
goal hook 评估
  ├─ ok:true  → 达成，清 goal
  └─ ok:false → blockingError → BLOCK_CAP 计数 +1
       ↓
     BLOCK_CAP ≤ 8 → 继续本轮（再来一轮 agent 循环）
     BLOCK_CAP > 8 → 强制结束，goalPass=not_met → pause("goal_check_capped")
  ↓
若撞 max_turns → 直接停，goalPass 不传 → Bf() 返回 none（goal 保留，但本轮结束）
```

**加上 §4.5 的 retry 退避（3 次 × 1/5/15 分钟）和 §7 的 idle check-in（3 次 × 30/60/120 分钟），一共有四层"不许无限跑"的保护。**

### 21.5 对复刻者的强建议

**必须实现至少两层**：

1. **阻断计数上限**（对应 `BLOCK_CAP`）——防止"条件永远不满足"时死循环；
2. **重试退避上限**（对应 `Di` 的 3 次）——防止"评估器一直出错"时死循环。

**推荐照抄 CC 的 8 次 + 3 次组合**，因为：
- 8 次给了足够的"自查-修正"空间（一般任务 2-3 轮就够）；
- 3 次退避覆盖了绝大多数临时故障；
- 两者都是**用户可见的暂停**而不是静默失败，符合"让人接手"的原则。

**一个可以改进的点**：CC 的 `BLOCK_CAP` 是**全局常量 8**，对所有条件一视同仁。可以考虑按条件复杂度动态调整，或者让用户在 `/goal` 时指定（如 `/goal --max-checks 15 <条件>`）。

### 23.2 `/compact`：`preservedMessages` 机制

> `m0591_0x11be624e.js:322059`、`323328` 附近

compaction 时有一个 `preservedMessages` 概念，用来**显式保留指定的消息**：

```js
if(s?.preservedMessages)
  for(let ot of s.preservedMessages.uuids){
    let Ze = S.get(ot);
    if(!Ze) return {kind:"abort", reason:"preserved_uuid_missing"};   // ← 找不到就中止压缩
    G.add(Ze.idx);
    let gt = w.get(ot); if(gt!==void 0) G.add(gt);
    let At = N.get(ot); if(At) for(let Mt of At) G.add(Mt);
  }
else if(s?.preservedSegment){
  let ot = s.preservedSegment, Ze=ot.tailUuid, gt=new Set;
  while(Ze && !gt.has(Ze)){
    gt.add(Ze);
    let At=S.get(Ze);
    if(At){
      G.add(At.idx);
      let Mt=w.get(Ze); if(Mt!==void 0) G.add(Mt);
      let Tt=N.get(Ze); if(Tt) for(let wt of Tt) G.add(wt);
      if(Ze===ot.headUuid) break;
    }
    Ze = At?.parent;                    // ← 沿 parentUuid 回溯
  }
  if(Ze !== ot.headUuid) return {kind:"abort", reason:"preserved_walk_broken"};
}
```

**两种保留方式**：

| 方式 | 结构 | 语义 |
| --- | --- | --- |
| `preservedMessages` | `{uuids: [...]}` | 保留指定 uuid 的这批消息 |
| `preservedSegment` | `{headUuid, tailUuid}` | 保留从 head 到 tail 的整条链（沿 `parentUuid` 回溯） |

**关键细节**：两种都能**保留 goal_status attachment**，因为 attachment 在 transcript 里就是一条有 `uuid` 和 `parentUuid` 的普通记录。

**这也解释了 §2.2 的 `KFn` 为什么从后往前扫**：只要最靠近末尾的那条 `goal_status` 被保留下来，`KFn` 就能找回到它。

### 23.3 但"最靠近末尾的 goal_status"是否能存活？

从 §12.7 的形态看，`goal_status` 有两种：

| 类型 | 何时产生 | 位置 |
| --- | --- | --- |
| **哨兵**（`sentinel:true`） | 设置 / 清除 / resume 时 | 会话早期或某次操作时 |
| **评估结果**（无 `sentinel`） | 每次评估后（`met` / `failed` / 普通 `not_met`） | 每次评估的当下 |

**压缩策略对两者的影响不同**：

- 设 goal 时的哨兵在**很早期**，如果之后跑了很久、压了很多次，这条会进入被压缩的区间 → **`KFn` 找不回 goal**；
- 但每次评估都会追加一条新的 `goal_status`（`not_met` 的，不带 `sentinel`），这条通常较新，更可能被保留。

**所以 resume 恢复的可靠性取决于"最后一次评估是否足够新"**。这是一个**设计上的隐式依赖**，CC 没有显式把 goal_status 加进 `preservedMessages`。

> **这是一个我认为的真实缺陷**：`preservedMessages` 机制存在，但 goal 没有利用它。保守做法应该是"设 goal 时就把哨兵 uuid 记下来，compaction 时作为 preservedMessages 传入"。

### 23.4 对复刻者的建议：显式保活

```python
# 概念伪码
class GoalState:
    condition: str
    sentinel_uuid: str | None        # 设 goal 时记录

def on_before_compact(messages, goal: GoalState | None):
    if goal and goal.sentinel_uuid:
        return {"preservedMessages": {"uuids": [goal.sentinel_uuid]}}
    return {}
```

**或者更彻底**：不依赖 transcript，而是把 goal 写进**会话级独立存储**（如 `session.metadata.goal`），resume 时直接读。CC 已经有 `notifyMetadataChanged({goal:{...}})` 这条通路（§12.3），但 resume 走的是 transcript 反查而不是读 metadata。

> **这是一个架构层面的取舍**：transcript 是"事实日志"，metadata 是"当前状态"。goal 用 transcript 做真源，好处是天然可审计，坏处是受压缩影响。
>
> **我的看法**：复刻时应该**两者都做**——transcript 记录用于审计/UI，metadata 用于快速恢复。CC 只在 hm 一侧做了。

### 23.5 `/compact` 手动触发时的 hook 处理


`T !== "compact"` 说明**手动 `/compact` 这一轮不走 blocked 检查**。但 Stop hook 本身是否执行？

从 `querySource` 的角度看，`/compact` 是一次独立的 query（`T==="compact"`），它的 Stop hook 链：

- `y.agentId` 为空（主 session），所以 `St` 非空；
- 但 `/compact` 不是"用户任务的一轮"，它是内部操作。

> **待查**：`/compact` 的 query 是否触发 `executeStopHooks`？如果触发，goal 评估会不会在压缩过程中被误执行（比如拿压缩后的摘要去评估，误判 `not_met`）？

**这是一个值得实测的问题**。从设计意图看，压缩后应该重新评估（因为上下文变了），但如果压缩**进行中**评估，可能拿到不完整的转录。

| 操作 | goal 是否保留 | 机制 |
| --- | --- | --- |
| `/clear` | ❌ 清掉 | `setAppState` 重置不含 `activeGoal` |
| `/compact`（自动） | ✅ 保留 | `preservedMessages` / 每次评估追加新记录 |
| `/compact`（手动） | ✅ 保留（推断） | 同上 |
| `resume` | ✅ 恢复（若 transcript 里有记录） | `KFn` 反查 + `ijo` 重挂 |
| 会话结束 | ❌ 内存丢失 | 只能靠 transcript 恢复 |

## 24. 复刻清单：给你的 agent 实现 goal 模式

> 这是用户的核心需求（"我后面要复刻到自己的 agent 中"）。本节把前 23 节的机制**重新组织成实施指南**，按"最小可行 → 完整 → 可选增强"分层。

### 24.1 一句话架构

```
用户 /goal <条件>
   ↓
1. 门禁检查（trust / hooks 是否可用）
   ↓
2. 注册一个 Stop hook（评估型）
   ↓ 同时写入 activeGoal 状态 + 往消息流追加 goal_status 记录
3. 每轮结束时，Stop 链跑评估器（独立的、无工具的 LLM 调用）
   ↓
4. 评估器返回 {ok, reason, impossible}
   ├─ ok:true  → 注销 hook、清 goal、记 achieved
   ├─ ok:false → 阻断本轮结束、注入反馈、继续干
   └─ impossible → 清 goal、记 failed
   ↓
5. 主循环终止原因 → 分类为 none/retry/pause/stop 四种处置
```

### 24.2 MVP：最小可行实现（约 400 行）

**只需要 5 个组件**：

#### 组件 1：状态存储

```python
    tokens_at_start: int = 0     # token 基线（用于 UI 显示消耗）
```

存在 session 级内存（`appState.activeGoal`）。**不需要持久化到文件**——靠消息流记录恢复即可（见组件 5）。

#### 组件 2：设置 / 清除

```python

def set_goal(condition: str, session) -> str | None:
    """返回 None 表示成功，返回字符串表示拒绝原因。"""
    condition = condition.strip()
    if not condition:
        return "Goal condition is empty."
```

#### 组件 3：门禁（**不能省**）

#### 组件 4：评估器（核心）

```python

- {"ok": true, "reason": "<quote evidence from the transcript that satisfies the condition>"}
- {"ok": false, "reason": "<quote what is missing or what blocks the condition>"}

    trimmed = trim_transcript(messages, budget=context_window(model) * 0.5)
    user_msg = (f"Based on the conversation transcript above, has the following stopping "
                f"condition been satisfied? Answer based on transcript evidence only.\n\n"

```

| 约束 | 为什么 |
| --- | --- |
| `tools=[]` | 评估器只能看转录，不能执行命令 |

```python
def goal_status(met, condition, sentinel=False, reason=None, **kw):

def find_active_goal_condition(messages) -> str | None:
    """resume 时从消息流反查未完成的 goal。"""

        if rec.get("type") != "goal_status":
            continue
        if rec.get("met") or rec.get("failed"):
```

### 24.3 完整实现：加上状态机与上限（约 800-1200 行）

| 上限 | 值 | 作用 |
| --- | --- | --- |

#### 终止原因 → 四类处置

```python
def classify_termination(reason: str, goal_pass: str | None, err) -> tuple[str, str]:
    """返回 (kind, cause)。kind ∈ none/retry/pause/stop"""
    if reason == "completed":
        return {
            "error":     ("retry", "goal_check"),
            "cancelled": ("pause", "goal_check_timeout"),
            "not_met":   ("pause", "goal_check_capped"),
        }.get(goal_pass, ("none", ""))
    if reason in ("aborted_streaming","aborted_tools","max_turns",
                  "tool_deferred","background_requested"):
        return ("none", "")                       # 用户中断 / 不是失败
    if reason in ("stop_hook_prevented","hook_stopped"):
        return ("pause", "hook_stopped")
    if reason in ("blocking_limit","prompt_too_long","rapid_refill_breaker"):
        return ("stop", "context_limit")
    if reason == "image_error":
        return ("retry", "image")
    if reason == "model_error":
        return ("pause", "turn_error")
    if reason == "api_error":
        if err.kind == "rate_limit":  return ("pause", "rate_limited")
        if err.transient:             return ("retry", "api_unavailable")
        if err.kind == "invalid_request": return ("pause", "request_rejected")
        if err.kind in ("authentication_failed","billing_error","model_not_found"):
            return ("stop", err.kind)
        return ("retry", "unclassified")
    return ("none", "")
```

| kind | 行为 |
| --- | --- |
| `none` | goal 继续有效，本轮就结束 |
| `retry` | 按 `[60s, 300s, 900s]` 退避后注入一条"继续"提示（最多 3 次） |
| `pause` | 显示提示（"Goal paused · <原因> · send a message to continue"），等用户 |
| `stop` | 彻底清除 goal，显示"Goal cleared after an unrecoverable error" |

## 25. 条件规范化差异、`origin` 竞态与清理原因全集

> 第 7 轮，补齐 §22 的第 3/4/5/6 项缺口：U1（`queuedGoalOrigin` 竞态）、V1（规范化差异）、T1（`Uue` 的 reason 全集）、W1（多行条件）。

### 25.1 三条路径的条件规范化完全不同【实码】

这是 V1 + W1 的合并答案。三个入口对同一个"条件字符串"做了**三套不同的清洗**：

| 路径 | 代码 | 做了什么 |
| --- | --- | --- |
| `/goal`（交互，`m2564`） | `let t=a.trim()` | **仅 trim** |
| `/goal`（非交互，`m2331`） | `let e=l.trim()` | **仅 trim** |
| ProposeGoal（`m1949`） | `let t=Z4(QYe(n)).trim()` | **换行折叠 + 同形字折叠 + 剥离不可见字符 + trim** |

逐个拆解：

#### `QYe` —— 把换行压成空格【实码】

> `m1947_0x1331f2f0.js`（全文 554 B）

```js
function QYe(n){ return n.replace(/[\r\n  ]+/g, " ") }
```

顺带回答了 §22 的 **W1（多行条件）**：

- `/goal` 路径**完全不动换行**——用户粘贴一段多行文本，条件里就带换行；
- ProposeGoal 路径会把 `\r\n`、`\n`、` `（行分隔符）、` `（段分隔符）**全部压成单个空格**。

**为什么 ProposeGoal 需要这一步**：因为 §8.3 的 schema 上限是"用户必须能在审批弹窗里读完整条条件"，多行会让弹窗排版崩坏。而 `/goal` 是用户自己敲的，CC 假定他知道自己在干什么。

同一个模块里还有个 `ZYe(n, r)` 是**截断显示**（给 `renderToolUseMessage` 用）：

```js

  if(e.length<=r) return e;
  let t = Q(e,r),
      o = Array.from(e.slice(t.length)).length;

```

#### `Z4` —— 同形字折叠 + 剥离 Default_Ignorable【实码】

> `m0114_0x11371fff.js:6219`

```js

```

三层嵌套，从内到外：

**① `_h(e)` —— 同形字归一（最多 10 轮迭代）**

> `m0023_0x1121d2db.js:4864`

```js

  let t = Ey(e);
  for(let n=0; n<10; n++){
    let r = Gt(t);
```

即：反复应用一个"同形字映射"直到不动点，最多 10 轮。**作用是让 `а`（西里尔字母 a）折叠成 `a`（拉丁 a）**——防止视觉相同的条件字符串被判为不同。

**② `TSt(e)` —— 剥离 `\p{DI}`**

> `m0114:5756` `var Ur=/\p{DI}/gu;` → `5757` `function TSt(e){return e.replace(Ur,"")}`

`\p{DI}` = `\p{Default_Ignorable_Code_Point}`，包括零宽空格 `U+200B`、零宽连接符 `U+200D`、方向标记、软连字符等。**这些字符在终端里不可见，但会进字符串比较。**

顺带一提，同模块的 `Dh(e)` 是更激进的版本：


> `m0114_0x11371fff.js` 本模块内的私有函数（**不是**别处的同名 `Dt`）


**这里没有任何 NFKC**：不做全角→半角，不做大小写折叠。

外面再套 `.trim()`。

#### 这个不一致会造成什么【推断，有强依据】

`m0848` 里判断"这个 hook 是不是我的 goal hook"用的是**字符串严格相等**：

```js

if(Ve?.condition === Ee.prompt) { ... }   // §4.2
```

以及 §7 的 `Qa(e,n)`：

```js

```

**两条路径写入的 `condition` 与注册到 hook 的 `prompt` 是同一个字符串**（`HNt(t,...)` → `fEs(e)` → `{prompt:e}`），所以**同一次设置内部是自洽的**，不会出 bug。

**真正的风险在跨路径**：

- 用户敲 `/goal "测试 全部 通过"`，存的是 `trim()` 版本，含零宽字符；
- 模型之后调 `ProposeGoal` 提议**同样语义**的条件，存的是清洗后版本；
- 两者字符串不等 → 第二条会把第一条判为 `superseded`（这是**期望行为**）；
- 但**反过来**，如果某处依赖"条件相同则复用"，会失效。

> **结论**：当前实现内部没有因此出 bug，但**两条路径共用一个 `condition` 字段却用不同的规范化**是一个隐患。复刻时应统一——推荐全部用 ProposeGoal 那套（`Z4(QYe(x)).trim()`），因为它在显示与比较上都更稳。

#### 它和队列消息的 `origin` 是**两个东西**

`proposal_direct` / `proposal_approved` 存在**独立的旁路槽** `queuedGoalOrigin` 里。理由是：`/goal` 命令执行时拿不到"这条消息是谁排的"——命令层只有条件字符串。所以用"条件字符串"当关联键做二次匹配。

#### 竞态分析：三条边界

**边界 1：条件不匹配 → 静默退化为 `"user"`**

```js
if(n===void 0 || n.condition!==e) return "user";
```

只要暂存的条件与当前 `/goal` 的参数不等，就当作"用户手敲"。

后果：**埋点的 `origin` 维度会被污染**——一个由模型提议的 goal 可能被记成 `"user"`。这不会影响行为，只影响分析。

**边界 2：两个不同条件的提议同时排队 → 第二个覆盖第一个**

```js
function cGi(e,t,n){ e(o=>({...o, queuedGoalOrigin:{condition:t, origin:n}})) }
```

是**整体替换**，不是追加。所以：

| 时序 | 槽内容 | 队列 | 结果 |
| --- | --- | --- | --- |
| A 提议 `foo` | `{foo, proposal_*}` | `["/goal foo"]` | — |
| B 提议 `bar` | `{bar, proposal_*}`（覆盖） | `["/goal foo","/goal bar"]` | — |
| 处理 `/goal foo` | 读槽：`bar !== foo` → `"user"` | `["/goal bar"]` | foo 的 origin 记成 user |
| 处理 `/goal bar` | 读槽：命中 → `proposal_*`，清槽 | `[]` | bar 的 origin 正确 |

**结论：不会出错，只是前一个的 origin 埋点退化。** 而行为上，`/goal bar` 会 `superseded` 掉 `foo`，符合"同时只有一个 goal"的语义。

**边界 3：槽泄漏**

既然只在 `k()` 里读到时清空，而 `k()` 只在 `HNt` 里被调用（`let o=n??k(e,t)` —— 传了 `n` 就不读槽也不清槽）。

看 `m2025` 的 resume 恢复：

```js
function ijo(a,s,d,i){ ... d.add(z(),"Stop","",fEs(e)); ... }
```

它**不经过 `HNt`**，所以不会触发 `k()`。而 `m2124` 的远端采纳路径也只直接写 `activeGoal`。

**所以如果 ProposeGoal 写了槽、但排队的那条 `/goal` 消息因为某种原因没被执行（会话关闭、用户 Esc 清队列），槽会一直留着**，直到下一次成功的 `/goal` 设置时才被覆盖或消费。

**影响**：一个陈旧的 `{condition, origin}` 留在 appState 里。下一次用户手敲 `/goal <同一个条件>` 时会被误读为 `"proposal_*"`。**纯埋点问题，无行为影响。**

#### 与 319 的设计意图对照

这套旁路机制说明 CC 想区分 goal 的三种来源：

| `origin` | 含义 | 埋点用途 |
| --- | --- | --- |
| `user` | 用户手敲 `/goal` | 基线 |
| `proposal_direct` | 模型提议且 `ask_user:false` | 衡量"模型自作主张"的频率 |
| `proposal_approved` | 模型提议且用户批准 | 衡量提议-批准转化率 |
| `restored` | resume 恢复 | — |
| `superseded` / `user_clear` / `resume_swap` / `session_clear` / `context_limit` / `api_error` | **不是 origin，是清理原因** | 见 25.3 |

**复刻建议**：如果只想要行为正确，可以完全不要 `queuedGoalOrigin`——直接在排队时把 `origin` 编进消息里（比如 `/goal --origin=proposal_direct <条件>`），或者让 `/goal` 命令能读到队列消息的 origin。CC 选了旁路槽，代价是上面那三条边界。

| 相位 | session 函数 hook | session 其他 hook |
| --- | --- | --- |
| `turn_end`（默认） | 跑 | 跑 |
| `turn_end_reactions` | 跑（**只有它**） | **跳过** |
| `loop_tick` / `blockable_turn_end` 等 | **跳过** | 跑 |

### 26.6 修正前文的表述

§4 说"每轮结束时 Stop hook 链跑评估器"，**这不完整**。准确的说法是：

```
一轮结束
  ├─ loop_tick 相位         → 跑评估器，阻断丢弃（浪费一次调用）
  ├─ blockable_turn_end 相位 → 跑评估器，阻断生效（这是我们关心的）
  └─ turn_end_reactions 相位 → 只跑函数型 hook，goal 不参与
```

**对复刻者的直接影响**：如果自研 agent 也有"多个 hook 执行点"，必须明确 goal hook 只挂在**可阻断**的那一个上，否则会出现"评估了但不生效"的静默浪费。

### 26.7 为什么 CC 会这样设计【推断】

`EEe` 是**通用 Stop hook 执行器**，相位参数是为了服务所有 hook 类型（command/prompt/agent/http/mcp_tool/script）在不同时机的不同需求：

- `loop_tick`：可能是给"观察型 hook"用的（比如监控、日志），不期望它阻断；
- `blockable_turn_end`：给"门禁型 hook"用；
- `turn_end_reactions`：给"副作用型 hook"（函数注册的）用。

**goal 借用 prompt 型 hook 时，没有只为某个相位注册的能力**——它进了 session 注册表，就会被所有相位看见。这是 §2.7 提到的"复用 Stop hook 机制"的代价。

> **复刻建议**：给自己的 goal hook 加一个 `phases: ["blockable_turn_end"]` 之类的字段，在执行器里按相位过滤。CC 没有这个能力，所以只能靠 `loop_tick` 里手动丢弃阻断来兜底。

## 28. `loop_tick` 的真实触发频率（修正 §26.3.1）

> 第 9 轮。DD1（`loop_tick` 频率）与 FF1（三相位跨版本）都已查清，其中 DD1 的结论**推翻了我上一轮的推断**。

### 28.1 `loop_tick` 不是"每次工具调用"——是工具主动声明结束【实码】

上一轮我写：

> "**这可能是 319 的一个真实浪费**：如果一个 goal 跑了 20 轮、每轮有 5 次 loop_tick，就会有 100 次无用的评估调用。"

**这个估算是错的。** 真实门槛高得多。

#### 门槛链

**第 1 道：`toolRequestedEndTurn` 必须非空**

```js
// m0848:232736
if(xe.toolRequestedEndTurn && !vn && !va)
  return yield*Qg({endTurnSource: xe.toolRequestedEndTurn==="tool"?"tool":"mcp_meta", ...});
```

`toolRequestedEndTurn` 初值是 **`!1`**（`m0848:146156` 的 `oc()` 状态对象），只在 `Rs()` 里被更新：

```js
function Rs(R){
  if(xe.toolRequestedEndTurn = jbi(xe.toolRequestedEndTurn, zdt(R)), ...) ...
}
```

**第 2 道：`zdt(R)` 只对"工具自己声明要结束轮次"的 result 返回真值**【实码】

> `m0591_0x11be624e.js:1967143`

```js
function zdt(e){
  if(e.type !== "user") return !1;
  let n = e.toolEndsTurn ? "tool" : $fn(e.mcpMeta);   // ← toolEndsTurn 是工具自己设的标志
  if(!n || sts(e)) return !1;                          // ← 有 is_error 的 tool_result → 不算
  return n;
}

function sts(e){
  return e.type==="user" && Array.isArray(e.message.content) &&
         e.message.content.some(n=>n.type==="tool_result" && n.is_error===!0);
}
```

**所以触发条件是**：某个工具**自己**在 result 上设了 `toolEndsTurn: true`（或 MCP meta 声明），**且该批次没有错误结果**。

**第 3 道：优先级阶梯**

```js
var Ffn = [!1, "mcp_meta_blockable", "mcp_meta", "tool"];
function jbi(e,n){ return Ffn.indexOf(n) > Ffn.indexOf(e) ? n : e }   // 取"更强"的那个
```

`toolRequestedEndTurn` 单调向"更强"的方向升级，永不降级。四档语义：

| 档位 | 含义 |
| --- | --- |
| `!1` | 没有工具要求结束 |
| `"mcp_meta_blockable"` | MCP 元消息要求结束，且可被阻断 |
| `"mcp_meta"` | MCP 元消息要求结束 |
| `"tool"` | 工具直接要求结束 |

### 28.2 修正后的频率判断

`loop_tick` 相位的触发条件是"**本批工具结果里有工具声明了 `toolEndsTurn`**"。

这不是普通工具的行为。从 §26.3 那行日志可以反推它的语义：

```
[end-turn] Stop hook block discarded (turn ended by tool result, no model re-invoke)
```

`no model re-invoke` —— 这一层**本来就不打算再调用模型**，所以 hook 的阻断无意义。

**典型场景**（推断）：某个工具已经完成了任务、明确表示"这一轮可以到此为止"（比如 workflow 的收尾工具、MCP 的 end-turn 元消息）。

**结论**：`loop_tick` 是**低频事件**，不是每轮都发生，更不是每次工具调用都发生。我上一轮"100 次无用调用"的估算**不成立**。

> **但这仍然是一个真实的小浪费**：只要发生 `toolEndsTurn`，goal 的评估器就会被白调一次。复刻时仍建议按相位过滤。

### 28.4 BB1：`"absent"` 埋点值的含义（部分解开）

> `m0848` 的 `tengu_goal_evaluated`

```js
l("tengu_goal_evaluated", {
  outcome: f(Be ?? (Te ? "error" : ke ? "cancelled" : "absent")),
  durationMs: Date.now()-w,
  iterations: St.iterations + (Le?1:0),
  parentAborted: ke,
  origin: de(St.origin),
  ...nt
});
```

三级回退：

| 条件 | `outcome` |
| --- | --- |
| `Be`（`goalPass`）有值 | 直接用（`met`/`not_met`/`impossible`/`deferred`/`error`/`cancelled`） |
| `Be` 空 + `Te`（整段抛异常） | `"error"` |
| `Be` 空 + `ke`（`abortController.aborted`） | `"cancelled"` |
| 都不满足 | **`"absent"`** |

**`"absent"` 的含义**：跑到了 finally，但 `goalPass` 一次都没被赋值，且没抛异常、没被 abort。

**可能的成因**（推断，按可能性排序）：

1. **goal hook 被 `gEs` 谓词过滤掉**（§16）——hook 不参与本轮，`Be` 自然为空；
2. `blockable_turn_end` 相位里 `St` 为空（子 agent），但外层 `if(St)` 才打这个埋点，所以不成立；
3. 走了 `blockable_turn_end` 之外的分支（如 `loop_tick`），但埋点在 `blockable_turn_end` 的 finally 里。

**所以 `"absent"` 确实可能是"goal 存在但 hook 被过滤"的**唯一可观测信号**——这回答了 §16.4 那个待查的一半。**
