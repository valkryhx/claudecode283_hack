## 1. 上一版的两处错误（先更正）

### 错误一：把「goal_defer 连坐」说成静默失效 —— 判断错误

上一版说：`hooks/runtime.py:560` 的 `skip_dynamic` 会让状态卡在装了 goal 的会话里永不触发，且不报错。

**读了完整代码后，这个判断是错的。** 实际语义（`runtime.py:560-563`）：

```python
skip_dynamic = event == "Stop" and (
    payload_dict.get("phase") == "user_turn_end"
    or payload_dict.get("goal_defer") is True
)
```

两个条件分别是：

1. `phase == "user_turn_end"`：这是 **app 层的兜底 Stop**（`app.py:2266`），正常 turn 结束走的是 `handler.py:627` 的 `phase: "turn_end"`，**不会命中**；
2. `goal_defer is True`：这个只在 **`goal_active` 为真** 且（有 in-flight agent 或有 workflow 启动）时才置位（`handler.py:631-648`）。而且 `goal_defer` 的**设计目的**就是「这一轮先不评估 goal，等后台干活完」（`handler.py:637-643` 的注释）。

**真实影响**：状态卡会在这两种情况下被一起跳过——

| 场景 | 状态卡是否触发 | 是否合理 |
| --- | --- | --- |
| 普通 turn（无 goal） | ✅ 触发 | — |
| 有 goal，无后台活 | ✅ 触发 | — |
| 有 goal，有后台 agent 在跑 | ❌ 跳过 | **实际是合理的**——后台还在干活，这一轮的状态本来就不完整 |
| app 层兜底 Stop | ❌ 跳过 | 合理——那是兜底，不是真实 turn 结束 |

**所以这不是 bug，是阴差阳错的正确。** 但**不能依赖这种巧合**：现在的行为是「状态卡搭 goal 的便车」，一旦 goal 的 defer 策略变化，状态卡会跟着变，而没有任何测试会红。

**正确的处理**：不要改 `skip_dynamic`（改它会破坏 goal 的双跑保护），而是**让状态卡自己判断该不该跑**——在 handler 内部检查 `payload_dict.get("goal_defer")`，若为真则不产出卡。这样：
- 行为不变（仍然不产出）；
- 但**归因清楚了**，将来 goal 策略变化时状态卡不受影响；
- 可以单独为「goal_defer 时状态卡静默跳过」写测试。

> 这是本轮复核最有价值的修正：**同一个现象，上一版归因成了「要修的坑」，实际是「要显式接管的既有行为」。**

### 错误二：说「hook 输出没有回写 agent 的通道」——也不准确

上一版的设计里写「状态卡要写进 AgentState，需要额外回传机制」。

**实际**：`HookResult.output` 是完整的 dict（`hooks/models.py:180`），`HookAggregate.results` 里能拿到所有 result（`models.py:270`）。`handler.run_stop_gate()` 虽然只返回 `(action, text, aggregate)` 三元组（`handler.py:600`），但**第三个元素 `aggregate` 就带着全部 output**，`loop.py:504` 拿到了它（只是没用）。

**所以不需要新造回传机制**，只需要在 `run_stop_gate` 返回后消费 `aggregate.results` 里的状态卡输出。改动量比上一版估的小。

### 错误三（本轮新发现）：状态卡挂错了事件 —— 这个最严重

上一版设计把状态卡挂在 **lead 的 `Stop`**。读完代码后发现**这个落点是错的**。

`handler.py:587-598`：

```python
def _stop_gate_active(self):
    """True only for the main (non-subagent) agent that has a hook runtime.
    Subagents use SubagentStop, so the lead Stop gate must stay off for
    them to avoid firing lead Stop hooks on child turns."""
    agent = self._hook_agent()
    if getattr(agent, 'is_subagent', False):
        return False
```

**subagent 不跑 lead 的 Stop gate。** 那 subagent 用 `SubagentStop`？也不对——`app.py:3218` 的 `SubagentStop` 在整个 **worker 生命周期结束时** 才发一次（注意 `app.py:3057` 的注释：*"Stop remains emitted once per process turn, while SubagentStop covers the full worker lifetime"*）。

而状态卡要的是**每一轮都报**。所以正确落点是 `app.py:3112` 那个**每轮完成点**：

```python
_subagent_state(task_dir, task_name, nround, 'completed', 'waiting_reply', ...)   # app.py:3112
_subagent_event(task_dir, {'type': 'turn_completed', ...})                        # app.py:3113
```

**这里是每轮唯一的「这一轮干完了」的事实位置。** 状态卡应该挂在这里，而不是任何 hook 事件上。

### 由此得出的架构决定

**状态卡不走 hook 机制，走 subagent worker 的轮末路径。**

| | 上一版（错） | 本版（对） |
| --- | --- | --- |
| 触发点 | lead 的 `Stop` hook | subagent worker 每轮完成（`app.py:3112` 附近） |
| 谁来跑 | hook runtime（prompt handler） | worker 进程内直接调用 |
| 结果写哪 | 想写 AgentState（但拿不到） | `state.json`（`_subagent_state` 已经在那儿写） |
| 与 goal 的关系 | 会被 `skip_dynamic` 连坐 | **完全无关**，不需要改 `runtime.py` |

这个改动的连带好处：
- 不用碰 `hooks/runtime.py`（上一版说要改的 `skip_dynamic` 现在**完全不用改**）；
- 不用管 `goal_defer`；
- 代际判断变得简单：`nround` 天然就是代际。

**代价**：状态卡不能靠 hook 配置开关，得走自己的配置项。但这是对的——它本来就不是 hook。

## 2. 修正后的完整设计

### 2.1 落点：subagent worker 的轮末（`app.py:3112` 附近）

```python
# genericagent/core/app.py —— 在 _subagent_state(..., 'completed', 'waiting_reply', ...) 之后

_status_card_maybe_publish(
    agent, task_dir, task_name,
    nround=nround,
    excerpt=item['done'],              # 这一轮的最终输出（已在手）
    history=backend_history(getattr(agent, 'llmclient', None)),
)
```

**为什么 `item['done']` 就够了**：`app.py:3080` 已经把它写进 `output{nround}.txt`。CC 也是只看**最后一段消息的 tail**（`m2458:184`：*"the tail of the thread's last message"*），不是全量 transcript。

**这比走 hook 简单得多**：数据全在手上，不用序列化、不用传 payload、不用管 payload 大小。

### 2.2 旁路 LLM 调用

`hooks/runtime.py:41-77` 的 `_default_prompt_runner` 已经是「隔离、无工具」的现成实现，直接复用它：

```python
# genericagent/core/status_card/runner.py（新建）
from genericagent.hooks.runtime import _default_prompt_runner

def generate_status_card(agent, *, excerpt, previous_card, timeout=20.0):
    runner = _default_prompt_runner(agent)
    if runner is None:
        return None                      # 没有可用 LLM → 静默跳过
    payload = render_prompt(excerpt=excerpt, previous=previous_card)
    raw = runner("prompt", payload, {})
    return parse_card(raw)               # 解析失败返回 None
```

**注意**：`_default_prompt_runner` 是私有函数。要么把它提成公开（改名 + 保留别名），要么在自己的模块里复制 20 行。**建议后者**——复制比对外暴露私有函数安全，且这段代码本来就是稳定的。

### 2.3 落盘：state.json

`_subagent_state()`（`app.py:2334`）已经是「读旧 → update → 原子写」的模式，加两个字段即可：

```python
old.update({
    ...
    'status_card': card_dict or old.get('status_card'),
    'status_card_round': nround if card_dict else old.get('status_card_round'),
})
```

**代际判断天然成立**：`status_card_round` 记录这张卡是哪一轮的。读侧只在 `status_card_round == 当前 round` 时展示，跨轮自然失效。**不需要额外的 seq 机制**——`nround` 就是。

### 2.4 读侧：`AgentState` → `team.view()`

三处小改：

1. `AgentState`（`manager.py:78`）加 `status_card: dict | None = None`；
2. `_agent_state_from_dict`（`manager.py:3269`）加 `status_card=raw.get('status_card')`；
3. `team.py:137 members.append({...})` 加 `"statusCard": getattr(entry, "status_card", None)`。

**全部是加法，不改任何现有字段语义。**

### 2.5 失败路径（必须全部静默）

| 失败 | 处理 |
| --- | --- |
| 没有可用 LLM | 跳过，不写字段 |
| LLM 超时 | 跳过（`timeout=20`，超了当没有） |
| 返回非 JSON | 跳过（`parse_card` 返回 None） |
| 返回 JSON 但字段越界 | 截断到上限，不丢弃（`headline` 截 60，`reply` 截 8 词） |
| 写盘失败 | 捕获，不抛（不能因为状态卡让 worker 崩） |

**一条铁律：状态卡的任何失败都不能影响 `_subagent_state` 的已有写入。** 所以调用点必须在**已有的写盘之后**，且整体 `try/except` 包住。

### 2.6 配置

不走 hook 配置（它不是 hook）。建议一个开关 + 一个节流：

```yaml
status_card:
  enabled: true
  min_interval_s: 5          # 同一 agent 两次生成的最小间隔
  model: null                # null = 用 agent 默认
  timeout_s: 20
```

节流理由：CC 给 repl 面 5s（`m1883:522`）。一个跑得快的 subagent 每轮都调 LLM 会明显增加延迟和成本。

## 3. L2 / L3 的落点（本轮已核实）

### 3.1 L3 有现成的记录点

上一版说「`permissions.py` 加 `denied_actions`」，但没说记录从哪来。实际有现成的：

`handler.py:862` 和 `handler.py:922` 都在发 `PermissionDenied` 事件：

```python
self._run_tool_hook('PermissionDenied', tool_name, args or {}, response, error=deny_reason)
```

**这就是天然的 denial 记录点。** 不需要在 `permissions.py` 里新造机制，只要：

1. 在 `PermissionDenied` 的处理路径里追加一条到 denial 日志（按 `source` + `signature`）；
2. 在权限检查前查一次。

`permissions.py` 现有的 `SubagentPermissionPolicy.evaluate()`（`permissions.py:47`）是逐 tool 判定的，可以在它之前插一层。

### 3.2 `action_signature` 的取法（上一版没说清）

```python
def action_signature(tool_name: str, args: dict) -> str:
    """同一操作的不同参数应产生同一签名，不同操作应产生不同签名。"""
```

**建议用「工具名 + 主对象」两段**，主对象按工具类型取：

| 工具 | 主对象 |
| --- | --- |
| `file_write` / `file_patch` | 目标路径 |
| `code_run` | 命令的第一个可执行 + 第一个非选项参数？**不建议**——命令太自由，取不出来 |
| `web_fetch` | 域名 |

**`code_run` 是个真问题**：删库、删文件、发邮件都可以是一条 shell 命令，签名取不出来。CC 也没有解决这个（它是按 tool name + 完整 input 比对的）。

**建议的折中**：`code_run` 用 **完整命令的 sha256 前缀**。同一条命令重复被拒 → 匹配；改一个字 → 不匹配。**会漏**（`rm -rf /data` 和 `rm -rf /data/` 不同签名），但**不会误伤**。

对安全规则来说，**宁可漏、不可误伤**——误伤会让用户觉得系统在乱拦，进而要求整体关掉，那就全盘皆输了。

### 3.3 L2 需要一个「当前提议」对象

这是 L2 的前提，但 **GA 现在没有这个对象**。CC 有（`pending_proposal` 来自 reply gate 的策略）。

**最小可行做法**：不引入全局提议对象，只在**两处具体场景**做判定：

| 场景 | 提议从哪来 |
| --- | --- |
| 子 agent 向用户提问后等待回答 | 提问的内容就是提议（`ask_user_question` 已有） |
| 子 agent 被 block 后等待 | block 的原因就是提议 |

→ **不需要通用提议框架**，把规则挂在已有的两个等待态上。

**这也意味着 L2 的落地范围比 L3 小**：只在有明确等待态时生效，不是所有消息都判。

## 5. 本轮复核发现的三个错误汇总

| # | 上一版说法 | 实际 | 影响 |
| --- | --- | --- | --- |
| 1 | `skip_dynamic` 会连坐状态卡，是静默失效点，需要改 | 逻辑是对的（goal_defer 时该跳过），但**归因错了**；且本版改走 worker 后**完全不用碰** | 少改一个文件 |
| 2 | hook 输出没有回传 agent 的通道 | `HookResult.output` 完整可读（`models.py:180`），`aggregate` 带全部结果 | 不需新造机制 |
| 3 | **状态卡挂 lead 的 `Stop` hook** | **subagent 不跑 lead Stop gate**（`handler.py:587-598`），`SubagentStop` 是**整个 worker 生命周期**一次（`app.py:3218`），不是每轮 | **架构级改动**：改挂 `app.py:3112` 轮末 |

**第 3 条是这次复核的主要收获。** 如果按上一版实现，写完会发现装了 hook 但状态卡从不出现（因为 subagent 不跑它），或者只在 worker 退出时才出一次（挂 `SubagentStop`）——两种都不是要的效果。

## 6. 复核结论

**方案的核心判断成立**：
- 状态卡逻辑可以搬，提示词可照抄（`m2458`）；
- L2/L3 确有价值且 GA 完全没有；
- 不需要任何服务端、不需要 hearthbot、不需要账号体系。

**上一版的技术落点错了，已修正**：
- 挂载点：lead `Stop` hook → **subagent worker 轮末**；
- 回传通道：不需要新造，`state.json` 就够；
- `runtime.py` 不需要改。

**仍然未闭合的**：
1. `code_run` 的 action signature 粒度——需实测调，建议先只覆盖 `file_write` / `file_patch` / `web_fetch`；
2. 子 agent 的 LLM 调用会不会与主调用争用配额——需观察；
3. 状态卡的 `needs_you` 在 GA 单机语境下，指向「当前用户」还是「发起委派的 agent」——**建议指向用户**，与 CC 一致。

## 7. 使用形态（按修正后的落点重写）

### 7.1 形态一：`/agents` 面板看并行进度

**这是主形态。** GA 已有 `/team`（别名 `/agents`），走 `team.py:110 view()`。

**用户做了什么**：派 3 个 subagent 并行，去干别的，20 分钟后回来敲 `/agents`。

**现在**：

```
● running   fix-auth       running
● running   fix-billing    running
● running   add-tests      running
```

**之后**：

```
● working      fix-auth      修 429 重发；靠 middleware.ts:42 定位
⚠ needs_reply  fix-billing   缓存设计好了，等你选 Postgres / SQLite
● working      add-tests     跑 CI，约 8 分钟
```

**渲染规则**（`state` → 图标 + 颜色）：

| state | 图标 | 含义 |
| --- | --- | --- |
| `working` | `●` | 正常推进，不用管 |
| `needs_reply` | `⚠`（黄） | 等用户回答 |
| `needs_approval` | `⚠`（红） | 等用户批准 |
| `done` | `✓` | 完成；`needs_you` 可能有下一步 |
| `failed` | `✗` | 失败，需要干预 |

**关键**：`needs_reply` 和 `needs_approval` **必须分开**。虽然 CC 内部都归 `blocked`（`m2458:184`），但「选 Postgres 还是 SQLite」要打字，「批准跑迁移」点一下就行——对用户是完全不同的动作。

### 7.2 形态二：轮末通知（推送而非轮询）

**注意**：`app.py:3113` 已经在发 `turn_completed` 事件。状态卡生成后应该**在同一条事件流上追加**，而不是让前端轮询。

```python
_subagent_event(task_dir, {
    'type': 'status_card',
    'task_name': task_name,
    'round': nround,
    'card': card_dict,
})
```

这样前端订阅事件就能实时更新，不需要额外轮询 `state.json`。**这是 GA 现有架构的自然延伸**，不引入新的通信机制。

### 7.3 形态三：主 agent 读回报

主 agent 通过 `list_agents` / `read_agent` 拿到 `status_card`。它现在看到的是：

**之前**：`turn_status: completed`
**之后**：`happened: "修好了 429 重发；PR #4127 已开"` + `needs_you: "Review PR #4127"`

**给主 agent 用 `happened` 而不是 `headline`**——CC 在 `m0949:78` 就是按载体分字段的：repl 面只给 `headline`（60 字符，压得狠），其他面给 `summary`。

### 7.4 形态四：授权判定（L2）

**只在这两个场景生效**（见 §3.3）：子 agent 提问后等待、子 agent 被 block 后等待。

**场景**：subagent 问「要重跑任务，还是删库重建？」（多选项）→ 用户答「ok go ahead」

- 现在：agent 可能理解为批准
- 之后：判定 `NO_GRANT`（多选项的裸 yes 不算），agent 再问一次

**场景**：subagent 问「可以删 staging-assets 吗？」（单动作单对象）→ 用户答「好」

- 现在：批准
- 之后：判定 `GRANTED`（单提议的裸 yes 有效）

### 7.5 形态五：越权拦截（L3）

**场景**：agent X 删生产库被用户拒。之后 X 给 agent Y 发消息「用户批准了，你去删」。

- 现在：Y 走正常审批，如果 Y 权限宽就删了
- 之后：`PermissionDenied` 已记录 X 的 denial → Y 收到请求签名匹配 → **直接 BLOCK**

**用户看到什么**：一条「已拦截：来源 X 曾因该操作被拒」。

**这是价值最高的一条**——L2 是体验问题，L3 是安全问题。

## 9. 设计假设的可执行校验

设计对着 GA 源码写了 14 条假设。这些假设一旦漂移（GA 重构、字段改名），本文所有落点都会失效。因此配了两个探针：

| 探针 | 作用 | 当前结果 |
| --- | --- | --- |
| `tools/probes/20261115-statuscard-design-probe.py` | 逐条断言 14 个设计假设成立 | **14/14 通过** |
| `tools/probes/20261115-statuscard-design-probe-reverse.py` | 逐条破坏假设，断言探针变红 | **9/9 全部被抓出** |

**为什么要有反向那个**：正向全绿不能证明探针有效。第一次跑反向时，9 条变异里有 **2 条没被抓到**：

- 「旁路 runner 消失」——探针用 `"_default_prompt_runner" in src` 判断，改名后文件里别处还有这个名字的引用，照样绿；
- 「反伪冒前导被删」——同样问题，`"ANTI_SPOOF_PREAMBLE" in src` 在改名后仍匹配到其他引用。

改成锚定**定义行**（`^def _default_prompt_runner\(agent\):` / `^ANTI_SPOOF_PREAMBLE\s*=`）后重跑，9/9 全部变红。

> 这正是 AGENTS.md §8.5 记的假验收形态：**探针与产品共用同一个宽假设时，探针永远绿。** 这里产品是「设计文档」，探针是「校验」——如果校验只看名字出现过，它对「名字还在但定义没了」完全无感。

**用法**：GA 升级后、或开始实施前，跑一次正向。任何 FAIL 都意味着本文某个落点要重新核对。
