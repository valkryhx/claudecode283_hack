# GA resume「只显示部分 / 只剩最后一段」问题分析与优化设计

> 配套阅读：`20261025-CC-resume机制调研.md`（CC 2.1.303 的对照实现）。
> GA 仓库：`D:\git_repos\ga\GenericAgent`（本机路径；`claude_hack` 旧文档里的
> `D:\git_codes\GenericAgent` 是另一台机器上的路径，不是错误）。
> 证据等级：**S** 源码直接可见 / **B** 由多处源码交叉推断 / **C** 推测（需实测确认）。

## 0. 现状一句话

GA 的会话转录**没有消息级锚点，只有"整段 history 快照"**；
UI 显示层又依赖 append-only 的 `<Static>` 和"滚动到最底部"的视口。
所以一旦 history 被压缩/裁剪/截断，或显示层没有整屏重置，
resume 之后用户看到的就是"只有一部分"甚至"只有最后一段"。

## 1. 当前链路（源码坐标）

### 1.1 写入

`genericagent/core/transcripts.py`

| 函数 | 行为 | 坐标 |
| --- | --- | --- |
| `append_event` | 普通 `open("a")` 写一行；有 `seq`，**没有** `fsync`、没有 uuid、没有去重 | `transcripts.py:98-104` |
| `record_turn` | 每轮写 `user_text` / `assistant_text` + **整份** `backend_history_before` / `backend_history_after`（`copy.deepcopy`） | `transcripts.py:121-134` |
| `record_compact` | 只写 `message` + `backend_history_after` | `transcripts.py:137-145` |
| `record_rewind` | 写 `keep_turns` + `backend_history_after` | `transcripts.py:148-...` |
| `record_agent_turn` | turn_id 自增后调 `record_turn` | `transcripts.py:432-445` |

调用点：`genericagent/core/app.py:1203`、`:1238`（`backend_history_before=transcript_history_before`）；

**代价**：O(n²) 存储——第 k 轮要写 2×k 条消息的完整副本。长会话的 JSONL 会非常大，
`load_session` 每行 `json.loads` 又在做 `copy.deepcopy`。

### 1.2 读取

`load_session`（`transcripts.py:208-267`）逐行重放，规则：

- `turn`：先用 `_find_turn_count_for_backend_history` 在**已有 turns 的
  `backend_history_after`**里找与本轮 `backend_history_before` **深度相等**的那一轮，
  命中则 `_truncate_loaded_turns` 截断（推断出来的 rewind）；
  **没命中就什么都不做，直接追加**（`transcripts.py:241-246`）。
- `compact`：只把 `backend_history` 换成快照，**不动 turns / ui_messages**（`:248-249`）。
- `rewind`：按 `keep_turns` 截断（`:250-253`）。

`_find_turn_count_for_backend_history` 在 `backend_history` 非空但找不到匹配时返回 `None`
（`transcripts.py:179-185`），而 `_history_equal` 是裸 `==`（`:175-176`）。


### 1.3 恢复

`restore_agent_session`（`transcripts.py:385-408`）：

- `backend.history = deepcopy(loaded.backend_history)`；
- `agent.history = []`；

- `session_turn_id = loaded.rounds`。

## 2. 根因分析（按可能性排序）

### R1 — inline 模式下 resume 后视口停在旧位置（**最直接**，B）

`history_replace` 是"整体替换"语义，但只做了 `staticGeneration + 1`（重印 `<Static>`），
**没有**像 `rewind_done` 那样 `resetTranscriptViewport()`（清屏 + 清 scrollback + 光标归位）。
`<Static>` 的注释自己写着（`App.tsx:656-657`）：

> `<Static>` 只能追加、无法撤销已写出的行，所以「历史被替换/裁剪后重印」必须先重置，
> 否则旧行与新行叠加成重复。

在 inline 模式下又不执行"滚到底"（`:1750-1754` 直接 return，且 `pendingHistoryReplacementScrollRef`
被清掉）——于是旧 scrollOffset 被 `preserveTranscriptScrollOnContentChange` 按"保持相对位置"带到了
新的、更长的 transcript 上。若 resume 的会话比当前会话长，视口就停在**中间某处**；
用户感知为"只显示一部分"。若当前会话是空会话（offset 0），视口停在顶部附近，
叠加 `<Static>` 重印的时序，可能看到"像最后一段"的内容（C，需录像确认）。

### R2 — compact 后转录里没有压缩前内容（S）

`record_compact` 只写 `backend_history_after`，`load_session` 对 `compact` 事件**不截断
`turns/ui_messages`**（`transcripts.py:248-249`）——看起来 turns 还在，但：
- 压缩后 `backend_history` 已被替换成摘要，**下一轮**的 `backend_history_before`
  在新 history 里找不到对应的 `backend_history_after` ⇒ R3 触发；
- 若压缩前的轮次本身已被上游 `trim_messages_history` 影响过，`turns` 与 backend 的对应关系已经断了。

⇒ 用户感受："/compact 之前的东西 resume 后没了"（B）。

### R3 — turn 截断判定依赖整段深度相等，history 一被改写就失效（S + B）

`_find_turn_count_for_backend_history` 要求 **整个 list 深度相等**。
但 GA 在每个请求前都会：

- `compress_history_tags(history)` **原地**压缩旧消息里的 `<tool_use>`/`<tool_result>` 文本
  （`genericagent/llm/core.py:56-87`，在 `trim_messages_history` 内 `:127`、`:131` 被调用）；
- `trim_messages_history` **原地** `pop` 最旧消息（`core.py:115-...`，调用点 `:872`、`:1014`）。

所以历史一旦被改写，**旧的 `backend_history_after` 已不再是当初写进转录的那个字节序列**，
匹配失败 ⇒ `keep_turns = None` ⇒ **不截断，直接追加**。
配合 `load_session` 末行 `backend_history = turn.backend_history_after`，
resume 后 backend.history 是"全部事件顺序重放后的最后一份"，而 ui_messages 是"全部 turn"——
两者可能不一致（B）。另外，只要 `backend_history_before` 为空（首轮或 compact 后第一轮），
`_find_turn_count_for_backend_history` 直接返回 `0` ⇒ **清空所有已加载 turn**（`:180-181`），
这就是"只剩最后一段"的一个确定路径（S）。

### R4 — resume 后 backend 与 UI 不同源（B）

- backend.history：来自 `backend_history_after`（完整、含 tool_result / 压缩后的文本）；
- UI：来自 `user_text` / `assistant_text`（**只有正文**，没有工具调用与结果）。

两者天然不一致。CC 的做法是两套视图（见调研 §5），GA 没有区分，
因此在 resume 后继续对话时，模型看到的上下文和用户屏幕上的内容不同。

### R5 — 没有消息级 uuid，重放/推断只能靠快照比较（S）

`append_event` 不加 `uuid`/`parent_uuid`，也没有内容哈希去重（`transcripts.py:98-104`）。
后果：无法做 CC 的 "uuid 合并 last-wins"，无法对"同一个 turn 被写两次"幂等，无法区分
"rewind 到第 k 轮"与"第 k 轮被重写"。`_scan_session_summary`（`:274-...`）为了和
`load_session` 一致，把同一套脆弱的推断逻辑又抄了一遍（`:300-319`）。

### R6 — 显示层限制（B）

- `assistantDisplayText` 默认折叠到尾部 30 行（`messageWindow.ts:38-50`）——很长的回答"看起来像被截断"；
- tool call / tool_result 在 resume 显示里**完全不出现**（`_append_loaded_turn` 只取
  `user_text`/`assistant_text`，`transcripts.py:188-193`），与 live 运行时的 `**LLM Running (Turn n)**`
  文本形态（`continue_cmd.py:437-476` legacy 路径）不一致；
- `visibleMessages(80)` 是遗留 API，目前无人调用，但若将来接回会直接砍掉 80 条以前的历史。

### R7 — 附加静默失效（S）

`continue_cmd.reset_conversation`（`:273-293`）只清 `agent.history` / 所有 client 的
`backend.history`、`last_tools`、`handler`，**不重置 `agent.session_path` / `session_id` /
`session_turn_id`**；`bridge.resume_session` 依赖 `continue_reset` 先做清理再 `continue_restore`。
若 `continue_reset` 之后 `continue_restore` 失败或被吞异常（`bridge.py:2488-2492` 的
`except Exception: loaded = None`），会静默回退到 legacy 解析——用户看到的是"另一个来源的历史"。
另外 `handler.hook_runtime` 等运行时状态未在 resume 时重建（C）。

## 3. 优化设计

分 4 个阶段，**每阶段独立可发布、独立可回滚**，不改动已有 `session_*.jsonl` 的读取兼容性
（v1 事件继续可读，新事件用 `version: 2` / 新 `type` 区分）。

### 阶段 1：先止血——显示层（改动最小，先让"看不见"变"看得见"）

**1.1 `history_replace` 与 `rewind_done` 对齐**

`frontends/ink/ui/src/App.tsx:1014`：

```ts
if (event.type === 'history_replace') {
  const commandText = pendingLocalCommandRef.current
  setSelector(null)
  setFooterPanel(null)
  resumePendingRef.current = false
  flushDeltas()
  resetTranscriptViewport()          // ← 新增：与 rewind_done 一致
  resetStaticTranscriptOutput()      // ← 显式重挂 <Static>（reducer 里已 +1，这里防止其它路径漏）
  pendingHistoryReplacementScrollRef.current = false   // 替换后不滚到底，保持顶部开始阅读
  dispatch(event)
  ...
}
```

注意：`resetStaticTranscriptOutput` 会让 `<Static>` 全量重印，必须与
`resetTranscriptViewport()` 同一次刷新内发生，否则重复（参见现有注释 `:1021-1023`）。

**1.2 resume 后视口从顶部开始**

替换 `pendingHistoryReplacementScrollRef` 的语义为 `historyReplacementAnchor`：

- `/resume`：`anchor = 'top'`（offset = 0）——用户最想看的是"从哪开始的"；
- `/compact`：`anchor = 'bottom'`；
- rewind：`anchor = 'bottom'`（保持现有行为）。

inline 模式下同样应用 anchor（现在的 `:1750-1754` 直接忽略）。

**1.3 长回答默认展开尾部上限**

`messageWindow.ts:38-50` 的 `assistantDisplayText` 对 `done` 的消息默认 30 行，
对"历史消息"（非本轮）建议提高到 60 行或直接全文（`tailLines` 只截尾部，中间会丢）。
更稳妥：`done && isHistorical` 用全文，仅对运行中的消息限行。

**1.4 验收**

- 新增 `frontends/ink/ui/src/__tests__/historyReplaceViewport.test.tsx`：
  断言 `history_replace` 触发后 `staticTranscriptGeneration` 与 viewport reset 序列都被发出，
  且首帧可见行以第一条 user 消息开头；
- 手工回归：`resume_bug.png` 场景（resume 的会话比当前会话长）复现并截图对比。
- 精确改法与三条不能踩的约束见 **附录 A**；注意本机 `frontends/ink/ui/` 缺 `node_modules`，
  自动化验证要先 `npm install`，否则只能真机手测。


### 阶段 2：转录格式 v2——消息级 uuid + 增量事件（对照 CC 调研 §2/§6）

> 保持 v1 可读：`load_session` 遇到 v1 走原逻辑；v2 事件走新逻辑；
> 可以用"新会话写 v2，旧会话按 v1 只读"的方式灰度。

**2.1 事件类型**

```jsonc
// 会话开头
{"version":2,"type":"session_start","session_id":"...","created_at":"...","cwd":"...","frontend":"ink"}
// 每条消息（user / assistant 文本 / assistant tool_use / tool_result）
{"version":2,"type":"message","uuid":"<uuid4>","parent_uuid":"<uuid4|null>",
 "session_id":"...","role":"user","origin":{"kind":"human"},
 "text":"...","blocks":[{"type":"tool_use","id":"toolu_...","name":"Bash","input":{}}],
 "created_at":"..."}
// 轮次边界（用于列表计数与 rewind 锚点）
{"version":2,"type":"turn_end","turn_id":3,"first_uuid":"...","last_uuid":"..."}
// 历史被整体改写（compact / 硬裁剪 / 外部注入）
{"version":2,"type":"boundary","reason":"compact|trim|replay",
 "head_uuid":"<边界后第一条>","anchor_uuid":"<边界前最后一条>",
 "preserved":[{"uuid":"...","message":{...}}],   // 需要 UI 还原但已不在 backend.history 的消息
 "backend_history_len": 12}
```

要点（对应 CC 调研 §4）：

- **`boundary` 只追加，不覆盖**；`preserved` 保存"backend 里已没有、但 UI 要显示"的消息原文；
- `parent_uuid` 让 rewind 用"把 UI 截到某个 uuid"表达，而不再靠整段 list 深度相等；
- `origin.kind` 区分 `human` / `tool_result` / `hook` / `system`，列表预览只取 `human`。

**2.2 写入**（`transcripts.py` 新 `append_message`）

- 每行写完做一次 `fh.flush()` + `os.fsync(fh.fileno())`（或 Windows 上 `os.fsync` 不可用时至少 flush）
  ——避免进程被杀时最后一行半截；读取端对坏行已有 `errors="replace"` + 跳过（`:218-228`）；
- 内容哈希去重（`sha1(role + text + blocks)` 与上一行相同则跳过），对应 CC 的 `W6` + `Y_s` 预算；
- 不再每轮写整份 `backend_history_before/after`（v2 不再需要快照用于 rewind）。

**2.3 读取 + 重建**

新增 `load_session_v2(path) -> LoadedSession`：

1. 顺序读事件，维护 `messages: list[Entry]`（带 uuid）；
2. `message` → append；
3. `boundary` → 记录边界（不删 messages），`backend_cursor = adapter.build_backend(messages, boundary)`；
4. `turn_end` → `rounds += 1`，`user_texts` 取自该轮首条 `origin.kind == 'human'` 的消息；
5. `backend_history` 由 **adapter** 从消息列表重建（见 2.4），不再直接使用快照。

**2.4 新增 backend adapter**（`genericagent/core/history_view.py`）

```python
def build_backend_history(entries, boundary=None, max_messages=RH):
    # 1) 从边界之后开始（boundary=None 则从头）
    # 2) 超 max_messages 时 slice(-max)，再前推到第一条 role=='user' 且不含 tool_result 的消息
    # 3) 按 tool_use_id 把 tool_result 归并到对应 tool_use（成对重组）
    # 4) 每轮请求前只做"视图构造"，不再原地改写存储的历史
```

`max_messages` 建议取 **2048**（CC 的 `Rx=4096` 是对 message 行计数，GA 的 history 每条含 blocks，
按条数减半）；真正裁剪交给已有的 `trim_messages_history`，但它必须**改成对副本操作**（见 2.5）。

**2.5 修 `trim_messages_history` / `compress_history_tags`**

两者当前对 `self.history` **原地**改写（`core.py:127/131/872/1014`）。改为：

```python
messages = compress_history_tags(trim_messages_history(list(self.history), ...))
gen = self.raw_ask(messages)      # 只把裁剪结果发给 API，不写回 self.history
```

并在真正需要"永久丢弃"时追加一条 `boundary(reason="trim")`——这样转录与 UI 都不会静默丢上下文。


### 阶段 3：compact / rewind / 恢复的语义对齐

**3.1 compact**

`record_compact` 改为写 `boundary(reason="compact")`：

- `head_uuid` = 压缩后 history 的首条消息（若可定位）；
- `anchor_uuid` = 压缩前 UI 最后一条消息；
- `preserved` = 压缩前 UI 里存在、但压缩后 backend 里已没有的**消息原文**（按 uuid 差集算）。

`load_session` 对 `compact`：**不动 turns**，只推进 `backend_history` 基线；
UI 在压缩边界处渲染一行 `system: "Conversation compacted"`（对应 CC 的
`"Conversation compacted" / level: info`），该行可展开看 `preserved`。

**3.2 rewind**

`record_rewind` 改为写"截断到 uuid"事件：

```jsonc
{"version":2,"type":"rewind","keep_after_uuid":"<uuid or null>","backend_history_after":[/* 兼容旧逻辑 */]}
```

读取时按 uuid 截断 `messages`（不再比较整段 history）。快照里的 `backend_history`
保留一个版本周期用于兼容，v3 移除。

**3.3 `restore_agent_session` 补齐状态**

```python
def restore_agent_session(agent, path):
    loaded = load_session(path)
    agent.abort()
    backend.history = deepcopy(loaded.backend_history)
    agent.history = _ui_history_from_loaded(loaded)     # ← 用重建出的 user/assistant 文本，不再是 []
    agent.handler = None
    agent.session_id, agent.session_path = loaded.session_id, loaded.path
    agent.session_turn_id = loaded.rounds
    agent.restored_working = loaded.working             # ← key_info 等（若转录里有）
    client.last_tools = ""
```

- 转录里**新增** `working` 字段（每轮结束后写一次 `handler.working`，last-wins 策略）：
  这样 resume 后 `app.py:1049` 的 `if self.handler and 'key_info' in self.handler.working`
  可以改为 `or getattr(self, 'restored_working', None)`；
- rewind 快照：`bridge._resume_ui_messages_with_checkpoints`（`bridge.py:2497-2510`）
  继续按 turn 构造 `_rewind_snapshots`，但 `backend_history` 改为来自 2.4 的 adapter
  按 `first_uuid` 位置重建，而不是 `turn.backend_history_before` 快照。

**3.4 ui_messages 与显示一致**

`_append_loaded_turn` 增加 `tool_calls` / `tool_results` 文本行（沿用 legacy 路径
`continue_cmd.py:437-476` 的 `**LLM Running (Turn n)**` 形态），使 resume 显示
与 live 运行时一致；或在 Ink 侧新增 `role: 'tool'` 的折叠行（推荐，PC 端可折叠、移动端可默认收起）。


### 阶段 4：显示与列表的收尾

**4.1 分页加载 / load-more**

`history_replace` 只带最近 N 轮（建议 N=50），消息里带 `truncatedBefore: true` 标记；
Ink 侧顶部显示 `↑ 更早的 N 轮 (Ctrl+U / 上滚到底 加载)`，触发时 bridge 发
`history_prepend` 事件（reducer 前插并保持视口锚点 = 当前第一条消息所在行）。

这样即便超长会话也不会一次把几 MB 的文本塞进 Ink 渲染树（当前 `transcriptLines(state.messages)`
对全部消息做一次 wrap，长会话首帧很慢、也容易触发 §R6 的"看起来被截断"）。

**4.2 子代理转录分离**（对照 CC 调研 §1）

GA 已有子代理转录（`TempSessionsDir/<session_id>/subagents/<run_id>.jsonl` + `.meta.json`，
`genericagent/agents/transcript.py:232-235`，含 `replay` / `build_replay_timeline`），
缺的是主会话 resume 时不展示它。主会话 resume 显示时以一行 `system: "subagent <id> (N turns)"` 占位，可展开/跳转。

**4.3 列表页**

`_scan_session_summary` 只读必要字段：`type`、`turn_id`、`user_text`（或 v2 的 `origin.kind`），
**不** `json.loads` 整份 `backend_history_*`。v1 文件因整份快照无法避免解析成本——可按
"最近 M 条事件（例如 200 行）+ 文件头"估算 `rounds`，标明"估算值"；
新写 v2 文件则精确。对应 CC 的 `m0081_0xe583228.js` 轻量扫描。

**4.4 清理遗留 API**

`visibleMessages(80)`（`messageWindow.ts:27-29`）当前无调用者，删除或加 `@deprecated`
并补一条单元测试防止误用。

## 附录 A：阶段 1.1 的精确改动（2026-10-26 补记）

本轮曾在 GA 仓库试改后**按用户要求全部撤回**，GA 工作区无任何遗留改动。
下面是最终确定的改法，供后续实施时直接照抄。

### A.1 落点

`frontends/ink/ui/src/App.tsx:1014-1032`（`history_replace` 分支），在 `flushDeltas()` 之后：

```ts
        flushDeltas()
        // 历史被整体替换后必须整屏重置：<Static> 只能追加，旧行留在屏上与重印的新行叠加
        // 会重复/错位（与 rewind_done、resize 同一处理）。重挂 <Static> 的代数由下面的
        // reducer 在同一次 commit 里 +1，这里不再单独 bump。
        resetTranscriptViewport()
        // 替换后视口定位：full 模式保留「滚到底」（由下面的 effect 消费），inline 模式
        // 偏移归零 —— 屏幕已清空、完整历史由 <Static> 从顶部重印，旧的相对偏移不能带过来。
        if (mouseMode === 'inline') setTranscriptScrollOffset(0)
        pendingHistoryReplacementScrollRef.current = true
```

### A.2 三条不能踩的约束

1. **不要同时调 `resetStaticTranscriptOutput()`**：reducer 在 `state.ts:213` 已经
   `staticGeneration + 1`；再单独 bump 会先按「追加尾部」写一遍、再全量重印 →
   尾部重复（就是 `App.tsx:1021-1023` 注释里那张 `resume_bug.png`）。
2. **顺序与既有路径一致**：`rewind_done`（`App.tsx:1074-1081`）和 resize（`App.tsx:864-865`）
   都是「先 `resetTranscriptViewport()`，再 `dispatch` / 重挂」，照抄即可。
3. **inline 必须归零滚动偏移**：`:1690-1693` 的「滚到底」只在 `mouseMode === 'full'` 生效，
   inline 下 `:1750-1754` 直接 return 并清掉 ref，偏移交给
   `preserveTranscriptScrollOnContentChange` 按「保持相对位置」计算，
   会把自己带到新 transcript 的中段 —— 这正是 R1 的机制。

### A.3 改动量与验证成本（不成比例的其实是验证）

- 代码：**2-3 行**（一行 reset + 一行条件归零），无类型变更、无新 API；
