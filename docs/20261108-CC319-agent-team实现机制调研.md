## §0 一句话结论

Agent Team 在 v2.1.319 里是一个**完整、成体系的多智能体协作子系统**，不是残留字符串。
它由一条主轴 + 三条副轴组成：

- **主轴（spawn）**：lead 调 `Agent` 工具并带上 `name` → 走 `spawnTeammate()`
  （`m1984_0x13450de8.js:1186` 的 `export { wt as spawnTeammate }`，**S 级**）
  → 先做身份预留（写 team 文件的 CAS）→ 再按后端三分派：
  **tmux split-pane / tmux 独立窗口 / in-process**。
- **副轴 1（通信）**：`SendMessage` 工具 + 每个 agent 一个 JSONL 邮箱文件
  （`<configDir>/teams/<team>/inboxes/<agent>.json`），配合 lockfile 做并发安全；
  in-process teammate 用 **500ms poll loop** 主动拉邮箱。
- **副轴 2（协作）**：共享任务板（`TaskCreate/Update/List/Get` + `<taskListDir>/<id>.json`
  + `.highwatermark`），teammate 空闲时**自动认领**未阻塞的 pending 任务。
- **副轴 3（治理）**：plan 审批（`plan_approval_request/response`）、权限代答
  （worker 的 `ask` 变成本地邮箱请求、lead 回复 `permission_response`）、
  优雅停机（`shutdown_request/response`）、`TeammateIdle` 钩子、
  **反权限洗白**三条硬规则。

319 相比 283 的两个最大变化（详见 §2）：

1. **`team_name` 参数被废弃**：319 的 schema 里明确写着
   `team_name: z.optional().describe("Deprecated; ignored. The session has a single implicit team.")`
   （`m0795_0x1244ebd5.js:812`，**A 级**）。团队不再由模型指定，而是**每个会话一个隐式团队**，
   team 名由会话 id 派生（`qMn(sessionId)`）。
2. **团队必须"活着的 lead 进程"持有**：team 文件里新增 `leadProcess: {pid, pidSpace, claimedAt, procStart}`，
   并用 pid 存活探测 + procStart 比对来做**接管 / 抢占**（`m2024_0x134cbd14.js`）。

### 2.2 team 文件多出 `leadProcess`（进程级存活性）

283 的 team 文件 schema 是 `{name, createdAt, leadAgentId, leadSessionId, members[]}`。
319 多一层：

```js
// m2024_0x134cbd14.js:125-141  initializeSessionTeam 的创建分支

  name: e,
  createdAt: Date.now(),
  leadAgentId: s,          // RV("team-lead", teamName)
  leadSessionId: z(),
  leadProcess: leadProcess,   // { pid, pidSpace, claimedAt, procStart? }
  members: [{
    agentId: s, name: hl, agentType: hl, joinedAt: Date.now(),
    tmuxPaneId: "leader", cwd: Ee(), subscriptions: [], backendType: "in-process"

```

`leadProcess` 由 `A()`（`m2024:220`）构造：

```js
function A() {
  return {
    pid: process.pid,
    pidSpace: hte(),
    claimedAt: Date.now(),
    procStart: x() === "linux" || x() === "wsl" ? await tc(process.pid) : void 0

```

`hte()` 是 pid 命名空间标识（容器里 pid 会重复，必须带 namespace），
`tc(pid)` 读 `/proc/<pid>/stat` 的启动时间（Linux 上防 pid 复用）。

**为什么要这个**（`m2024:228-239`）：

```js
async function P(a, n, o) {                 // 接管判定 tryAdoptTeam
  let leadProcess_2 = n.leadProcess;

        || await w_t(leadProcess_2.pid)              // 或僵尸？
        || (leadProcess_2.procStart !== void 0
              ? (await Xy(leadProcess_2.pid, leadProcess_2.procStart)) === !1   // 启动时间变了 = 已换进程
              : ((await HFe(leadProcess_2.pid)) ?? 0) > leadProcess_2.claimedAt + k)))  // k=2000ms
    return !1;
  ...
}
```

**含义**：一个 team 目录只允许**一个活着的 lead 进程**持有。旧 lead 死了（或被复用 pid 顶掉），
新会话可以接管并把 `leadProcess` 改写成自己。

## §3 激活门禁：三层开关

### 3.1 结构


三层全过才开：

| 层 | 条件 | 默认 |
| --- | --- | --- |
| 1 | `process.env.CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` **或** CLI `--agent-teams` | 关（env 未设 / 无 flag 即关） |
| 2 | feature flag `tengu_amber_flint` | **`true`**（`v(name, !0)` 的第二参是默认值） |
| 3 | （调用点自行判断）非非交互会话、且没有 `--agent-id` | 见下 |

第 3 层在启动处显式再判一次：


- `ye()` = 非交互（headless / `-p`）→ **不开团队**。这与后端层的
  `LEn()` 逻辑相反（那里非交互**强制 in-process**），见 §7.4。
- `options.agentId` 已存在 → 说明本进程**就是**某个 teammate（不是 lead），不再初始化团队。

> **注意一处矛盾**：`m1984:1154` 的 `ge()` 用 `LEn()` 判「是否 in-process」，
> 而 `LEn()` 里 `if (ye()) return true;`（非交互 → in-process）。
> 但团队初始化在非交互会话里根本不跑。所以「headless 会话里的 teammate」实际走的是
> **`--agent-id` 子进程路径**（pane 里 `claude --agent-id ...` 那一条），不是这里的 in-process。
> 见 §7.5 的完整判定树。

### 3.2 `--agent-teams` 之外的隐藏开关

`cas()`（`captureTeammateModeSnapshot`）只在启用时懒加载，用来**给遥测拍一次后端模式快照**。
它不改变行为，只是观测。**B 级**（函数名 + 懒加载位置，未见实现体）。

### 3.3 teammate 子进程如何知道自己是谁

pane 后端 spawn 出来的命令行里显式带了一串 flag（`m1984:776`、`m1984:893`）：

```
--agent-id <agentId> --agent-name <name> --team-name <team> --agent-color <color>
--parent-session-id <sessionId> [--plan-mode-required] [--agent-type <type>]
```

子进程启动时这些 flag 被读进 `dynamicTeamContext`（`m0181_0x11543be8.js`）：

```js

```

**这是 319 最关键的一处设计**：`AsyncLocalStorage` 优先，`dynamicTeamContext` 兜底。

- **in-process teammate** 跑在 lead 同一进程里 → 用 `MXi(ctx, fn)` = `als.run(ctx, fn)`
  给整段执行套上上下文（`m0181` 的 `MXi`，**A 级**：`function MXi(e, t) { return u.run(e, t); }`）。
  这样同一个进程里**同时**存在 lead 和 N 个 teammate，谁调 `kc()` 都能拿到自己的 team。
- **pane teammate** 是独立进程 → 没有 ALS，只能读启动 flag 塞进来的 `dynamicTeamContext`。

**复刻建议**：如果你的 runtime 是单进程多 agent，一定要用「执行上下文（类似 ALS / contextvar）」
而不是「全局当前 agent」变量。否则并发下必串。

## §4 概念模型与数据模型

### 4.1 五个实体

```
Team（每个会话一个，名字 = "session-<8位hex>"）
 ├── lead        = 本会话主 agent，名字固定 "team-lead"，agentId = "team-lead@<team>"
 └── teammates[] = 具名队友（可 0..N）
        ├── pane teammate      : 独立进程，跑在 tmux/iTerm2 的 pane 里
        └── in-process teammate: 同一进程，AsyncLocalStorage 隔离上下文

Task（共享任务板，跨 agent 可见，可被自动认领）
Message（邮箱，每个 agent 一个 <agent>.json 文件）
```

- 不保留 `read: true` 记录，直接把已投递的条目从文件里**剪掉**（`pruned`）。

> 这是 **at-most-once** 的语义。它与「读成功不标记就重投」的 at-least-once 相互矛盾。
> 实际效果：**正常路径 at-most-once（可能丢），异常路径 at-least-once（可能重）**。
> 复刻时如果消息不能丢，建议改成「保留 read 标记 + 定期 GC」。

**两层防护**：

### 22.5 与 teammate 侧的五处关键差异

| 维度 | teammate 侧（`m1982` 的 `Se`） | lead 侧（`m2124` 的 `#R`） |
| --- | --- | --- |
| 轮询间隔 | 500 ms（`Me`） | 1000 ms（`BYo`） |
| `shutdown_request` | **最高优先**，先投积压再返回 | 归到 `po` 通道，与其它平级 |
| `forged` 消息 | **不投递** | **投递但标 `verified="false"`** |
| `plan_approval_response` | 在协议帧循环里处理 | **前置于一切**（前置 for 循环） |

**为什么 lead 侧对 `forged` 更宽松**：lead 是最终裁决者，需要看到所有内容才能判断；
teammate 是执行者，一条伪造指令可能让它做错事。

**为什么 lead 侧 `shutdown_request` 不优先**：lead 收到它是要**弹给用户确认**的
（teammate 不能直接关 lead），走正常 UI 流程即可。

代价：如果某个对话框永远不返回，消息就一直不标已读（但也因此不会丢）。

#### 24.5.6 复刻建议

**结论：不要照抄实现，但要理解意图。**

复刻时如果你的 runtime 是**自己构造消息对象**（而不是拼 XML 字符串给模型），
就完全不需要这套东西——把「谁说的」放在**结构化字段**里（如 content block 的
`type` / 自定义 `source` 字段），模型天然无法伪造。

319 之所以需要这一整套，是因为它用 **XML 文本**表达「agent 间消息」，
而文本可以被消息内容本身伪造，所以必须在文本层做防御。

**若你也要用文本信封，最小可行方案**：

1. 把消息正文里的所有「左尖括号造型」统一替换成一个固定 ASCII 标记；
2. 再套自己的信封；
3. 读侧做同样的替换，两边对称。

不必做完整的 Unicode 归一化——只要**替换集合覆盖面 > 攻击者能想到的集合**。
最省事的做法是把正文里的 `<` 全部转义成 `&lt;`（或换用非 XML 的分隔符，
例如用一个随机 per-session token 做分隔）。

### 26.3 两阶段认领：`needs_open_blockers`

存储抽象路径下，`We(task, taskId, owner, s)` 里的 `s` 是「未完成任务 id 集合」。
但读单个任务时并不知道全集。所以设计成两阶段：

```js

  if (task_2.owner && task_2.owner !== owner_2) return {result: {success: !1, reason: "already_claimed", task: task_2}};

  if (task_2.blockedBy.length > 0) {

  let f = rt(task_2, {owner: owner_2}, n);

```

**为什么这样设计**：`Me(storage, listId, taskId, mutator)` 是「在存储层的一次原子读改写」。
如果每次都要先读全部任务才能判 blockers，代价很高。
所以第一次尝试**只读单个任务**；只有当它确实有 `blockedBy` 时才去读全集重试。

**这是一个通用的优化范式**：把「需要全集才能判的谓词」做成两阶段，
第一阶段的快速路径覆盖「无前置依赖」的多数情况。

### 27.4 为什么不通传 `process.env`

代码里没有注释解释。从后果倒推（**B 级**）：

1. **不污染**：用户 shell 里一堆无关变量会把 teammate 行为搞乱。
2. **可复现**：白名单确定，teammate 行为只取决于这几十项。
3. **安全**：`HOST_CREDS_FILE` 这类必须排除；白名单天然只含「已知无害」项。
4. **小**：`env <60+ 项> <exe> <flags>` 整条要打进 pane 的 shell 行，
   太长会撞命令行长度上限（与 `docs/20261107-CC内置工具实现调研.md` 里 32767 的约束同类）。
