## 0. 一句话结论

**拉取内容里没有一篇是记忆系统调研**（10 个提交全部是 AskUserQuestion / 压缩 / Projects），
所以不存在「两份记忆调研互相矛盾」。真正的交叉点是 **`m0848` 的回合末**：

- 拉取侧说：**状态卡不走 hook**，走的是 `zd()` 这条独立的轮末路径（这是它推翻自己上一版的
  架构级订正，见 `20261115-CC319-Projects逻辑复刻设计.md` §2.1 / §6 第 3 条）；
- 本地侧说：**记忆写入不是 hook**，是 `post_turn_memory` 后台任务。

**两句都对，但都只说了一半。** 源码里：

```
Pi()  ──yield* zd(...)          -> 状态卡（zd 只对 main 生效）      [独立路径]
      └─ yield* EEe(..., "loop_tick")
Jd()  └─ yield* zd(...)          -> 状态卡（同一函数，第二次调用）   [Stop hook 执行器]
      ├─ executeExtractMemories -> 记忆写入  ←  受 Jd 入口门禁约束
      └─ EEe(..., "blockable_turn_end")   -> 真正的 Stop hook 相位
```

`zd` 与 `executeExtractMemories` 是 **`Jd` 里前后相邻的两步**（`m0848:3849` 与 `:3852`），
而 `Jd` 是 **Stop hook 的执行器**（`m0848:3829` 起，内部读
`sessionHooksRegistry.get(z(), "Stop").get("Stop")`，在 `:4094`）。

因此：**记忆写入确实不是"由 hook 派发"的，但它和 Stop hook 同处一个函数、共享该函数的入口门禁。**
本地文档只写了前半句，据此得出「记忆和 hook 无关」会漏掉整条门禁。

### 2.3 订正（2026-11-16 第二轮）：`settingsHooksOff` 是否真的会为真？

第一轮我把它写成「A 级未实证」，用户的质疑是对的：**hook 是 hook，不该被记忆功能关闭**。
本轮把这个问题查到底，结论要分两层，而且**上一轮的措辞有一处过头**。

**（a）没有任何证据表明它与记忆功能有关——这条已经坐实。**

对 `claudecode283/claude.exe`（233.6 MB）、`claudecode303/claude.exe`（276.8 MB）
做**全文逐字节**扫描（不只是 `modules/` 目录），`settingsHooksOff` 的用法形态分类：

| 版本 | 总出现 | `read(dot)` 读取 | 对象键 | 赋值 | 简写 | 字符串键 |
| --- | --- | --- | --- | --- | --- | --- |
| 283 | 21 | **20** | 0 | 0 | 0 | 0 |
| 303 | 26 | **25** | 0 | 0 | 0 | 0 |
| 319（仅 modules，无 exe） | 21 | **21** | 0 | 0 | 0 | 0 |

唯一的非 `read(dot)` 是 exe 里的 1 处属性名字符串池条目（`...settingsHooksOff\t\x00\x00\x80...`），
不是代码。**全仓没有任何一处把 `settingsHooksOff` 写成 `true`。**

**（b）CC 自己给出了这个模式的定义——这是本轮最硬的证据（S 级）。**

`m0094_0x112cc57f.js:7432`，`disableReplyCheck` 的官方 schema 描述原文：

> "…It is **not a hook**, so **disableAllHooks does not affect it**. …"

CC 用一句话把规则说清了：**`disableAllHooks` 的管辖范围 = hook；不是 hook 的东西不受它影响。**
这正是用户说的「hook 是 hook，不会被记忆功能关闭」。

**（c）所以上一轮的结论要订正为：**

| 上一轮写的 | 本轮订正为 |
| --- | --- |
| 「`disableAllHooks` 是否连带关掉记忆写入，属 **A 级未实证**」 | 「`disableAllHooks` **不**会关掉记忆写入——按 CC 自己的规则（非 hook 不受管辖）＋ `settingsHooksOff` 全仓无赋值点。归为 **B 级（强推，无直证反例）**」 |
| 「`settingsHooksOff` 必由 settings 加载层或插件注入写入」 | **撤回**。这个推断没有依据；更可能的解释是**该字段在客户端侧恒为 `undefined`**（从未被构造过），`Jd` 那道判断实际只由 `querySource === "agent_summary"` 触发 |

**（d）这对 §2.2 的影响：这道门禁实际是「半开」的。**

`Jd:3834` 的条件是 `A || B`：

- `A` = `options.settingsHooksOff` -> 全仓 0 处赋值，**实际恒 falsy**；
- `B` = `querySource === "agent_summary"` -> 真实存在（`m0779:6364/6394` 构造该 querySource），**会触发**。

所以 `Jd` 这道早退**真正生效的只有 `agent_summary` 这一支**。它是 319 新增的
（283/303 只有 `settingsHooksOff`），也就是说：**319 把一个「原本在客户端恒不成立的条件」换成了
「子代理摘要时真的会成立的条件」**——这才是 319 在这行的实质变化，比我第一轮写的「只是把
`agent_summary` 并进同一行」更准确。

**（e）我需要保留的谨慎。**

`settingsHooksOff` 恒为 falsy 这个结论的边界是：**只对 319 明文模块成立**。
如果某个插件通过非明文路径（Bun 内嵌字节码、`claude-code` 虚拟模块）构造了这个 options 字段，
我的扫描看不到。所以措辞是「客户端明文模块里 0 处赋值」，而不是「这个字段永远不可能为真」。
这条边界已写成探针 A4b，每次重跑。

> **错误模式（比结论更值得留）**：第一轮我因为「`settingsHooksOff` 有 0 处赋值」就推出
> 「必由别处注入」，再推到「可能被 `disableAllHooks` 关掉」——**两跳都是无证据的推断**。
> 正确做法是先找**规则本身**（CC 的 "not a hook, so disableAllHooks does not affect it"），
> 规则比个案强，而且一句话就否掉了整条猜测链。

## 5. attachment producer 到底是「固定流程」还是「agent 动作」

这是复核过程中被追问的一点，答案是**固定流程**，有三条独立证据。

### 5.1 证据一：它由主循环 `for await` 直接消费

```js
// m0591:154221  生成器
async function* tDe(e, n, r, s, h, y, S, w) {
  let N = new has,
    G = await LTi(N, () => izr(e, n, r, s, y, S, w));   // ← 算一遍
  if (G.length > 0) {
    l("tengu_attachments", eqr(G, S));
    for (let ke of G) yield an(ke, h);                  // ← 产成消息
  }
}
```

调用点在主 agent 的 query 循环里（`m0848:10518`）：

```js
for await (let et of tDe(null, updatedToolUseContext_2, null, deliverable_2, D, [...N, ...ie, ...it], querySource_15, {...}))
```

### 5.2 证据二：`dc(...)` 在数组字面量求值时就已经 `await`

```js
// m0591:151808
async function dc(e, n) {
  ...
  let S = await n(),     // ← 不是惰性；传函数只是"不调不算"
```

producer 数组构造完后统一并发汇集（`m0591:151791`）：

```js
let [Jt, fn] = await Promise.all([Promise.all(Ut), Promise.all(sn)]);
return Ce?.mark("ambient_wait"), ..., azr(Akn([...]))
```

**「惰性」的准确含义**：传的是函数而非值，不调用就不算；但**每一轮都会把全部 producer 调一遍**。

### 5.3 证据三：所有开关都是外部配置判定，没有一个是模型决策

条件包裹形如 `...Zo() ? [dc("teammate_mailbox", ...)] : []`、`...le() ? [dc(...)] : []`，
其中的 `Zo()` / `le()` / `wrt(n)` / `Z6()` 全是环境或配置判定。

唯一的「输入形态」分支（`m0591:151716`）：

```js
if (S?.inputMentionsOnly) return [];     // 只提交了 @ 提及、没有正文
```

这也不是模型能调的——它由用户这次提交的形态决定。

### 5.4 与 agent 的分界线

| | attachment producer | agent |
| --- | --- | --- |
| 谁触发 | 主循环每轮固定调用 | 模型发 `tool_use` / 人发 prompt |
| 模型能否跳过 | **不能** | 能（不发就不发） |
| 有无独立上下文与工具集 | 无，同进程内计算 | 有 |
| 产出去哪 | `type: "attachment"` 消息附进上下文 | `tool_result` 返回 |

### 5.5 但「写」和「dream」是 agent 动作，必须区分开

| | 读 `nested_memory` | 写 `extractMemories` | 巩固 auto-dream |
| --- | --- | --- | --- |
| 形态 | attachment producer | 后台 fork 子代理 | 后台 fork 子代理 |
| 谁触发 | 每轮自动 | `Jd` 轮末（三道门禁） | 时钟 + 会话数门禁 |
| 独立 agent | **否** | **是**（`fork:"extraction"`） | **是**（`fork:"dream"`） |
| 模型能否干预 | 只能间接触发（读文件） | 不能 | 不能（只能改配置） |

### 5.6 设计含义

因为 producer 是固定流程，**模型无法"决定这轮要不要加载记忆"**。记忆是否进入上下文，取决于：

1. 文件是否被读过（`nested_memory` 由文件读取事件触发）
2. 是否超单文件字符上限（`z8e(model)`，`m0591:69725`）或被 `withheld` 扣留（`nD=200` 只是记账上限，`m0591:69141`）
3. 是否被 `withheld` 扣留
4. 是否为 `inputMentionsOnly` 轮次

模型唯一能左右的是**显式读文件**这一步。这也正是「记忆读走 attachment 而非 hook」的准确含义——
它既不是 hook，也不是 agent 工具，是**第三条通道**。

## 6. auto-dream：后台记忆巩固（不是新管线，是第三类后台任务）

CC 319 里确实存在 auto-dream。它不是「记忆的第三种实现」，而是**对已有记忆做定期重整**的
后台 fork 任务。源码坐标全在 `m0833_0x124cce31.js`（`deminified` 行号，全文仅 410 行）。

### 6.1 它就是 Anthropic API 的 `/v1/dreams` 端点

`m0349_0x1193beaf.js:1805` 起的 SDK 客户端（S 级，字面可见）：


并在客户端聚合对象上注册为 `this.dreams = new Lr(this._client)`（`:6655`）。

### 6.2 触发条件：时钟 × 会话数 × 四道前置否决

默认阈值（`m0833:174`–`178`）：


`runner`（`m0833:197` 起）的执行顺序：

| 步 | 判定 | 跳过时 |
| --- | --- | --- |
| 1 | `he()` 总开关 | 直接 return |
| 2 | 读 `lastConsolidatedAt`，`(now - E)/3600000 < minHours` | return（静默） |
| 3 | `Math.round` 后距上次扫描 `< ce` | 打 `scan throttle` 日志 |
| 4 | `listSessionsTouchedSince` 后剔除当前会话，数量 `< minSessions` | `tengu_auto_dream_skipped` reason=`sessions` |
| 5 | 权限规则 `LGr(...)` 会拒绝记忆写入 | reason=`permission_rule` |

| 7 | 记忆项读不出（`unreadable`） | reason=`items_unreadable` |

| --- | --- |

注入是事件驱动的**——一个是「提醒你没看」，一个是「你看了才给」。

#### 8.6.6 并发写冲突怎么处理（第六轮核验）

**两层保护，一层在进程内，一层跨进程。**

**进程内（extractMemories）**：一个布尔标志 `b` 加尾随合并（`m0832:1285`）：

即：**上一次还没跑完时，新的不并行也不排队，只「暂存为尾随运行」**——
多次触发被**合并成一次**，中间那些轮次的改动靠「读取最新 messages」兜住。

**跨进程（auto-dream）**：靠 `storageV5` 上的锁文件，带 **PID + 时间戳 + 乐观并发**（`m0809:106`）：

```js

```

四个设计要点：

1. **`El(i.holderPid)` 判断持有者是否存活**——持有者崩了锁自动可抢，不会永久死锁
2. **CAS（`s?.version === o` 才写）**——两个进程同时抢，只有一个成功
3. **`h(process.pid, Date.now())` 把 PID 和时间戳写进锁**——既是归属证明，也是超时依据
4. **`gVt` 释放失败时回滚 `lastConsolidatedAt` 并延迟到 `minHours`**（`m0809:99`-`103`），
   而不是让它卡在中间态

> **对比**：`extractMemories` 的「合并」只在**同一进程内**有效。若两个 Claude Code 进程
> 同时写同一个记忆目录，它没有锁，此时只剩文件系统层面的最后写入者胜出。
> 而 auto-dream 因为有锁，反倒是三个后台任务里**唯一**做了跨进程互斥的。

中文不靠空格分词，所以 `Pe` 对中文句子的计数**恒等于 1**（整句无空格）或等于空格分隔的段数。
用真实输入实测：

| 输入 | `Pe` 值 | 阈值 `vt=3` 是否通过 |
| --- | --- | --- |

「记忆功能好像不存在」的体验；要么改 `chat` 模式（有 CJK 加权），要么把分词换成

### 14.2 工具身份判定看 MCP 服务器身份，不看工具名字符串

这一条对 GA 复刻很重要，因为「按名字前缀判断是不是记忆工具」是**不安全**的。

| 判据 | 证据 |
| --- | --- |
| 名字前缀 + 不许有二级 `__` | `m0316_0x118fc11c.js:8` `return e.startsWith(kWn) && !e.slice(kWn.length).includes("__") \|\| ...` |

| 非 sdk 来源判 `other_server` | `m0316:15` `return n === void 0 \|\| n === "sdk" ? "unplaced" : "other_server";` |

### 15.2 引用追踪：`injection` 三档 + `<cc-memory>` 标签

这是本轮最有价值的发现：**记忆被注入有三种方式，代码里有明确区分**。

`m0591_0x11be624e.js:69063` 的 `Pen` 类维护一个会话级的记忆可见性索引：

| 档位 | 含义 | 判定 |
| --- | --- | --- |
| `body` | 正文被完整注入（`nested_memory`） | `bodyKeys`（`:69076`） |
| `surfaced` | 通过检索露出（`relevant_memories`） | `surfacedKeys`（`:69080`） |
| `listed` | 只在索引里被列出（`MEMORY.md` 的一行） | `listedKeys`（`:69077`） |
| `none` | 完全没进上下文 | 默认值（`:69061`） |

判定函数 `injectionForKey` 的优先级写死为 `body` > `surfaced` > `listed`（`:69119`）。
访问状态另有四值 `none` / `read` / `written` / `read_written`（`:69090-69091`），
读后再写会合并成 `read_written`。追踪上限 `fTe = 2000`（`:69055`）。

配套的 **引用标签** 机制：模型被要求把引用了记忆的整句话包起来：

```
<cc-memory filenames="memory-a.md,memory-b.md">这句话来自记忆</cc-memory>
```

解析实现（`m0293`）考虑得相当细：

| 细节 | 证据 |
| --- | --- |
| 标签名 6 种容错写法（大小写 / 下划线） | `:3304` `Ja = ["cc-memory", "cc_memory", "ccmemory", "CC-MEMORY", "CC_MEMORY", "CCMEMORY"]` |
| 生成所有前缀，处理流式未闭合 | `:3306` `Km` |
| 属性总长上限 1024 | `:3307` `el = "[^>]{0,1024}"` |
| 展示时只取句子前 300 字符 | `:3345` `Qo = 300` |
| 单条消息最多 32 个引用 | `:3354` `Xm = 32` |
| 遥测按三档分别计数 | `:3363-3365` `injectedBody` / `surfaced` / `listed` |

**为什么这层重要**：它说明 CC 的记忆不是「注入了就完事」——
每条被用到的记忆，代码都能回答「它当时是正文、是检索结果，还是只出现在索引里」。
这个区分直接影响可信度判断：正文注入的记忆已被模型读过，只在索引里的则没有。

`citedStatus`（`:69100`）还会拒绝含 `..` 的路径（`:69104`），防止引用穿越。

### 15.3 team memory：多库配置与分区冲突

`CLAUDE_MEMORY_STORES` 是一个 JSON 环境变量，定义多个记忆库（`m0293:352`）。

| 字段 | 约束 |
| --- | --- |
| `path` | 必填 |
| `mode` | `rw` / `ro`，默认 `rw` |
| `scope` | `user` / `team`，默认 `team` |
| `mount` | `[A-Za-z0-9_-]+`，省略时从 path 推导 |
| `promptIndex` | 分段名，禁止 `.` 与 `..` |
| `skillsDirs` | 最多 10 个，末段必须是 `skills` |
| `promptIndexMaxBytes` | 正整数 |

校验规则（`:362-399`）：**mount 不许重复**（`:375`）、**`scope:"user"` 最多一个**（`:377`）。

同步靠一个 `.memory-sync` 清单文件（`m0293:1802` `vEr = ".memory-sync"`），

### 15.4 Projects 云端项目记忆：一套独立的乐观并发协议

前七轮完全没碰这块。`m1968_0x1340550d.js:1148`：

```
/v1/code/memory/channel/{projectId}/memories
```

它与本地 `MEMORY.md` 是**两套独立实现**，连前置条件的设计都不同：

| 操作 | 前置条件 | 冲突处理 |
| --- | --- | --- |
| 创建 | `not_exists`（`:1155`） | 409 且路径相同 → `kept-existing`（`:1170`）；路径不同 → 报「另一文件与你的路径重叠」（`:1173`） |
| 替换 | `content_sha256`（`:1266`） | 值来自上次读到的 `contentSha256` |

`Jt`（`:1285`）把两者串成「**先创建，撞了就改替换**」的两段式：

```js
let l = await Oe(e, n, s, r, a, !1);
if (l !== "kept-existing") return l;
// 读出现有 -> 拿 contentSha256 -> 用 content_sha256 前置条件替换
```

其它常量：重试退避 `[1000, 2000, 4000, 8000, 12000]`（`:1144`）、
分页 `limit=100` 最多 10 页（`:1215`、`:1145` `Bo = 10`）、
页数超限报「store has too many files to search」（`:1234`）、
超时 15s（`:1142`）、记忆 id 形如 `cmsg_[A-Za-z0-9_-]{1,160}`（`:1299`）。

**与本地记忆的差别**：本地 `nested_memory` 是「读到就注入、变了就通知」；
云端项目记忆是**每会话一次快照**（`m0247:229` 原文：Memory is read once per session），
并且**工具侧不可写**（`m0247:227`：this tool cannot write it）。
写入只发生在后台同步，模型改不了。

### 15.5 agent-memory：三作用域 + 符号链接越界防护

`m0293:4849` 的 `pho()` 按作用域分派目录：

| scope | 路径 |
| --- | --- |
| `project` | `<cwd>/.claude/agent-memory/<agent>`（`:4853`） |
| `local` | `<cwd>/.claude/agent-memory-local/<agent>`（`:4847`） |
| `user` | `<home>/agent-memory/<agent>`（`:4857`） |

目录名先规范化：非字母数字/下划线/连字符一律替换成 `-`（`:4842` `<name>` → `<slug>`）。

**安全层**（`:4863-4915`）是本轮另一个新发现：`agent-memory` 目录必须验证落在工作副本内，
否则整份 `MEMORY.md` **不读**：

> agent memory: `<path>` leads out of the working copy or through a dangling link;
> its `MEMORY.md` is not read

三种判定结果 `beneath` / `absent` / `elsewhere`（`:4902-4931`），
只有前两种放行。`user` 作用域跳过这层检查（`:4860` `Hl` 返回 `e !== "user"`），
因为用户级记忆本来就在工作副本外。

**三种作用域的提示语不同**（`:4980-4986`），这直接决定模型写什么：

| scope | 提示语 |
| --- | --- |
| `user` | Since this memory is user-scope, keep learnings general since they apply across all projects |
| `project` | Since this memory is project-scope and shared with your team via version control, tailor your memories to this project |
| `local` | Since this memory is local-scope (not checked into version control), tailor your memories to this project and machine |

被拒绝时提示词会改写成只读版本（`:4639`）：
> Treat this agent memory as read-only in this session: do not create or write `MEMORY.md` or other files in its folder.

另外 agent memory 在 API 层走 beta header `agent-memory-2026-07-22`（`m0349:3493`），
说明它还有一条服务端通道，不只是本地文件。

### 15.6 cowork 记忆的版本重放

`cowork_memory_context` 有 `anchor` 与 `version` 两个字段（`m0779:6121-6132`）：

- `anchor === false` 的条目带内容与版本号；
- `anchor === true` 的条目是**引用**，会按版本号把对应内容 `splice` 回消息流（`:6132`）；
- 若前一条已是同版本的无锚点条目，则跳过（`:6130`），避免重复。

这是记忆通道里**唯一一套按版本重放的机制**，其它通道都是「注入即固定」。

## 16. 记忆提示词到底属于「读」还是「写」？

> 这一节回答一个我自己先前提法不准确的问题。第七、八两轮我把 `li()` / `WNn()` 那段叫「记忆提示词正文」，
> 读起来像是某个环节的专属内容。**实际上它是系统提示词里的常驻段，读写两侧共用同一份。**

### 16.1 归属：系统提示词层，不是读通道也不是写闸门

三个装配入口（`excludeDynamicSections` 与 `analysisOnly` 都是排除开关）：

| 入口 | 位置 | 作用 |
| --- | --- | --- |
| 主系统提示词 | `m2159_0x138a5541.js:18127` `memoryMechanicsPrompt = customSystemPrompt !== void 0 && met() ? await WNn(...) : null` | 每轮常驻 |
| 压缩时重建 | `m0591_0x11be624e.js:110325` `Iy(Ye, \`memory${G}\`, async () => ago(await WNn(h, {...}), e))` | 压缩后重新注入 |
| 排除 | 两处都受 `excludeDynamicSections` / `analysisOnly` 控制 | 子代理与分析态不注入 |

`met()`（`m0191:2648`）的真实判据是 `va() !== void 0`，注意**不是** `customSystemPrompt !== void 0` 那个表面条件 ——
后者只是与它并列的前置判断。

**结论**：把它归到「读」或「写」任一侧都是错的。它是**法则层**：
读侧靠它判断「什么时候该去查、查到的东西能不能直接用」；
写侧的子代理则**回指**它来执行（见 §16.4）。

### 16.4 写入子代理有自己独立的任务书，但法则回指系统提示词

`m0832:494` 是记忆提取子代理的 prompt，与系统提示词**不是同一份**：

> You are now acting as the memory extraction subagent. Analyze the most recent ~N messages above and
> use them to update your persistent memory systems.

它**不重复**类型定义与禁止项，而是回指：

> Apply the memory types, scope guidance, what-not-to-save criteria, and frontmatter format from the
> **Memory section of your system prompt — it is already in your context above**.

子代理任务书里独有（系统提示词没有）的四条约束：

| 约束 | 原因 | 证据 |
| --- | --- | --- |
| 可用工具仅 Read/Glob/Grep/Edit/Write 与只读 Bash；**MCP、Agent、可写 Bash 一律 deny** | 子代理权限被收窄 | `m0832:492` `C`、`:533` `Ir` |
| 轮流预算策略：turn 1 并行读全部候选文件、turn 2 并行写；**不许跨轮交错** | Edit 要求先 Read 同一文件 | `:493` `M` |
| 只准用最近 N 条消息的内容，**不许 grep 源码验证** | 不浪费轮次 | `:494` |
| 无事可写就只输出 `Nothing to save.`，不解释 | 便于判定空轮 | `:494` |

`m0832:494` 还有一条与第八轮发现联动的条件分支：当
`scope guidance` 启用且 `mcp` 后端可用时，prompt 会追加

> The `memory_list` / `memory_read` / `memory_write` tools are unavailable here, so skip anything the
> scope guidance marks as shared with the project — the main conversation saves those; never file them
> in the personal directory instead.

这说明**子代理知道自己拿不到 MCP 记忆工具**，需要把「项目共享」那部分留给主对话去写，
而不是退而求其次塞进个人目录。这是第七轮「memory MCP 服务器」与第九轮写入链的交叉点。

### 16.5 一句话概括

```
系统提示词（常驻，每轮）        记忆提取子代理（后台 fork）
        │                              │
        │  四类型 / 存法 / 禁止项       │  「你是记忆提取子代理」
        │  何时查 / 查完要核实          │  + 工具白名单 + 轮流预算
        │  卫生规则 / 引用格式          │  + 只准看最近 N 条
        └──────── 法则 ────────────────┘ 回指上面那份，不重抄
```

**同一份法则、两个执行者**：主对话按它读和随手写，子代理按它批量写。
把它说成「读环节的」或「写环节的」都是错的 —— 它是两者的共同前提。
