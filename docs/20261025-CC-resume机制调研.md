# Claude Code 2.1.303 的 resume / 会话转录机制调研

> 对象：`claudecode303/modules/` 下的明文 JS 模块（Bun `--compile` 产物，minify 未混淆）。
> 目的：给 GA（GenericAgent）的 resume 优化提供**可对照的真实实现**。
> 读法遵循 `AGENTS.md` §10：全部为 `grep -a` 定位 + `sed -n` 取窗口，未整文件读取。
> 证据等级沿用 `reconstructed/AUTO-NAMING.md` 思路：**S**=源码字面量/字符串直接可见；
> **A**=源码控制流直接可见；**B**=由多处源码交叉推断；**C**=推测（会显式标注）。

---

## 0. 结论先行

CC 的 resume 之所以"稳定、不会只显示一部分"，靠的是四件事，而不是单纯的"把 history 打印出来"：

1. **转录是 append-only 的 JSONL 事件流**，每行一个独立事件，带 `uuid` / `parentUuid` /
   `logicalParentUuid`，损坏一行不毁全局（S）。
2. **"显示什么"与"喂给模型什么"是两套视图**：UI 视图从事件流投影出来，
   API 视图再按 token / 条数预算裁，裁的时候**从一条真正的用户消息开始**，并把
   `tool_result` 孤儿一起处理（A）。
3. **历史被改写不是"覆盖旧行"，而是追加"边界/替换"事件**：
   `compact_boundary` 记录 head/anchor/tail uuid + 被保留的消息快照；
   content replacement 用哈希做增量替换记录；fork 用新 session 文件继承前缀（S/A）。
4. **列表页与详情页读法不同**：列表只做轻量扫描（跳过 `isMeta` / `isCompactSummary` /
   `tool_result`），不重建整段 history（A）。

GA 当前的问题恰好是这四点的反面：见配套文档
`20261025-GA-resume优化设计.md` §2。

## 2. 事件（行）结构

从本机真实会话 JSONL 与反序列化代码（`compact_boundary.txt` 探针）可见的字段：

| 字段 | 含义 | 证据 | 等级 |
| --- | --- | --- | --- |
| `uuid` | 本条事件唯一 id；缺省时反序列化会用 `wo()`（uuid 生成器）补 | 反序列化分支 `uuid:n.uuid??wo()` | S |
| `parentUuid` | 树形父指针（一条回复挂在触发它的 user 消息下） | 真实 jsonl | S |
| `logicalParentUuid` | **逻辑父**，与物理 `parentUuid` 分离：compact 后新头部的逻辑父指向被压缩段的末尾 | `ixn()` 里 `logicalParentUuid:e.logical_parent_uuid` | S |
| `isSidechain` | 子代理/侧链转录标记 | 真实 jsonl | S |
| `origin` | `{kind:'human'}` 等来源标记；非人类输入（tool_result、hook 注入）不显示为“用户说的话” | 反序列化 `origin:s.origin` | S |
| `isMeta` / `isSynthetic` / `isCompactSummary` | 元事件标记：列表扫描、显示都要跳过 | `m0081_0xe583228.js` 跳过 `"isMeta":true`、`"isCompactSummary":true` | S |
| `timestamp` / `cwd` / `version` | 时间、工作目录、写盘时 CC 版本 | 真实 jsonl | S |
| `system` 行 `subtype:"compact_boundary"` | 压缩边界事件（见 §4） | `compact_boundary.txt` | S |
| `last-prompt` 行 | 记录最后一次 prompt（用于列表预览） | 真实 jsonl | S |
| `content-replacement` 类事件 | 大工具结果被替换后的增量记录 | `m0459_0xecff32a.js` | A |
| `cost-state` / `mode` / `api-request` / `progress` / `attachment` 行 | 各类运行时事件各有持久化策略 | `m0459_0xecff32a.js` 策略表 | S |

要点：**一条消息 ≠ 一行**。一次 assistant 回复可能拆成多条（thinking / text / tool_use 分别落盘），
UI 投影时再按 `parentUuid` 链重组。这就是为什么 CC 的 resume 能"显示全部"——
显示层是按 uuid 树重组的，而不是按"某一行里的快照"。

## 3. 持久化策略（按事件类型分流）

`m0459_0xecff32a.js` 里有一张按事件类型分派的持久化策略表（字符串键可直接读出，S 级）：

| 策略 | 适用事件 | 行为 |
| --- | --- | --- |
| transcript | 普通 message / 用户、助手可见消息 | 直接写入会话转录 |
| boundary-cleared | 被 compact 边界清理的事件 | 不重写，靠边界事件的 head/anchor/tail 重定位 |
| accumulate | 内容替换类事件 | 累积写入，读取时叠加 |
| last-wins | `last-prompt`、`mode` 等 | 同 key 只保留最后一条 |
| always | 关键事件 | 无条件写 |
| route-by-agent | 子代理消息 | 按 agent id 路由到 `subagents/agent-<id>.jsonl` |

配套常量（同模块，S）：

- 内容哈希去重：写入前用内容哈希 `W6` 判重，重复内容不重复落盘；
- 去重跳过预算：`Y_s = 5 MiB`（单条）/ `LW = 20 MiB`（累计），超预算则放弃去重直接写；
- `Kro = 0.1`：与降载/抽样相关的比例常量（具体作用未逐行确认，C）。


## 4. 压缩（compact）如何不丢历史

CC 的 `/compact` **不是**把旧行删掉，而是：

1. 追加一条 `system` 行，`subtype: "compact_boundary"`；
2. 该行带 `compact_metadata`：`preTokens` / 触发方式（auto / manual）等；
3. 带 `headUuid` / `anchorUuid` / `tailUuid` 三个坐标：压缩段之后的新事件用
   `parentUuid` 指向头部，`logicalParentUuid` 指向 `anchorUuid`（被压缩段末尾）；
4. 可选 `preservedMessages`：`{anchorUuid, uuids:[...], allUuids:[...]}`——
   **被"压缩掉"但需要保留原样的消息，uuid 清单在这里**，重新 hydrate 时据此还原；
5. 头部本身在 UI 上显示为 `system / "Conversation compacted" / level: info` 一行。

证据：`compact_boundary.txt`（`m0459_0xecff32a.js` 中 `computeEntry` 的
`compact_boundary` 分支 + 反向序列化 `ixn()`），等级 S。

推论（B）：因此 resume 一个被 compact 过的会话时，CC 能完整还原两条视图——
- **API 视图**：从边界头开始，按 metadata 拼接 summary + 保留消息；
- **UI 视图**：边界行前后都能展开（边界行可点开看压缩前内容，依赖 preservedMessages）。

对比 GA：`record_compact` 只存了 `backend_history_after`，**UI 上压缩前的轮次没有任何锚点**，
resume 后自然只剩"压缩后的部分"。

## 5. 两种视图：API 视图与 UI 视图

### 5.1 API 视图（喂给模型的 messages）

`m0459_0xecff32a.js` 中的 `cnn()`（探针 `cnn.txt`，等级 S）：

```js
function cnn(e){
  let n = e.length > Rx,
      r = n ? e.slice(-Rx) : e,
      s = n ? Math.max(r.findIndex(unn), 0) : 0;
  return r.slice(s).map(dnn)
}
function unn(e){
  let {role:n, content:r} = e.message,
      s = Array.isArray(r) && r.some(h => h.type === "tool_result");
  return n === "user" && !s
}
```

含义：

- `Rx` 是消息条数上限（`m0064_0xe564fef.js`：`var Rx=4096, Fje=1e5, dDr=28000, ...`，S）；
- 超限时 `slice(-Rx)` 取尾部，**然后**再往前推到第一条"真正的用户消息"
  （`role==='user'` 且 content 里没有 `tool_result`），
  避免 API 视图以孤立的 tool_result 开头（否则 API 会 400）；
- `dnn` 只取 `{role, content}`，剥掉 uuid 等内部字段。

### 5.2 消息列表构建 `rer()`

`rer()`（探针 `ter2.txt`，S）从后往前遍历：

- 最多收集 `Rx` 条；
- 按 `tool_use_id` 收集 `toolResults`，再让 `toolUses` 经由 `Xhe` 映射——
  即**tool_use 与 tool_result 成对重组**，即使两者落在不同事件行；
- 反向遍历后 `reverse()` 恢复正序。

### 5.3 UI 视图

`ter(e,n)`（S）：`r = await ion(e,n)` 是从磁盘/内存读出的消息，
`s = ...` 是当前内存里的（含正在生成的）消息，合并规则：

```js
let y = new Set(s.map(S => S.uuid));
return [...r.filter(S => !y.has(S.uuid)), ...s]
```

即**以 uuid 为键合并，内存版本优先（last-wins）**——同一个 uuid 不会同时出现两次。
这是 CC 不会出现"重复气泡 / 只显示最后一段"的核心原因之一。


## 6. resume 的完整链路（按源码顺序）

1. **列出会话**（`m0673_0xcf1d63e.js`，A）：扫 `<projectKey>/*.jsonl`；
2. **生成列表预览**（`m0081_0xe583228.js`，S）：从尾部扫描第一条用户消息，
   跳过 `"isMeta":true`、`"isCompactSummary":true` 行与只含 `tool_result` 的行；
   较新的实现还有 `last-prompt` 行可直接取（S）；
3. **恢复会话**：新建/复用进程内 session，把 JSONL 反序列化成事件树；
4. **API 视图**：`cnn()` 裁到 `Rx` 条并前推到真实 user 消息；
5. **UI 视图**：`ter()` 用 uuid 合并磁盘与内存；
6. **SessionStart hook**：`source ∈ {startup, resume, clear, compact, fork}`
   （`m0120_0xe64eaf1.js`，S）；对应的退出原因是
   `SessionEnd.reason ∈ {clear, resume, logout, prompt_input_exit, other}`（S）；
7. **fork**：`--fork-session` / 控制请求 `fork_conversation`——但
   `m0322_0xeb2715c.js` 显示 `fork_conversation` **要求远端 server 可用**（A），
   本地 CLI 以 `--fork-session` 新建文件继承前缀；
8. **空会话占位**：迁移时为空会话写 `00000000-...jsonl`（`m1309_0xd5ade82.js`，A），
   保证列表里"点进去"有东西可读。

> **未定位（C）**：把 API 视图投影成"终端里那一串气泡"的具体函数
> （即从 `cnn/rer` 输出到 Ink 渲染的中间层）没有逐行追到。本文件不对它做断言。

## 7. 对 GA 最值得借的 7 条

1. 显示视图与 API 视图分离；裁 API 视图时从真实 user 消息开始。
2. 每条消息/事件带 `uuid` + `parentUuid`，合并以 uuid 为准，内存优先。
3. 历史改写 = 追加边界事件，而不是覆盖快照字段。
4. compact 边界保留 `preservedMessages`（uuid 清单）以便 UI 还原压缩前内容。
5. 子代理转录独立文件，不进主会话显示。
6. 列表页只做轻量扫描（跳过 meta / compact summary / tool_result），不进详情逻辑。
7. 写入幂等：内容哈希去重 + 跳过预算，避免 resume 重放产生重复。
