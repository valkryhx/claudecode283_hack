## 1. 一句话结论（最终版）

> ⚠️ 本节是 R1 的初版结论，**已被 §73.2.3 的运行时实证订正**。以下为修订后版本，
> 初版原文保留在下面的引用块里，便于对照。

Claude Code 319 的「上下文压缩」是**一套引擎、两个入口、三种变体**：

**一套引擎**：`mfr → Ers → nPe → ayn/vno`。所有压缩（自动/手动/PTL）最终都走 `nPe` 的分轮阶梯，
产出 `vno` 装配的 `boundary + summary + messagesToKeep + attachments`。

**两个入口**：
1. **阈值入口**（每轮请求前）：`hxr()` 用四档水位判定 → `Dno()` 编排 → `mfr()`。
   `trigger` 缺省为 `"auto"`。
2. **PTL 入口**（请求被上游拒绝后）：`isWithheld413` / `lu()` 分支 → 用错误里的
   `actual > limit` 反推该保留多少轮 → `mfr()`。`promptTooLong` 有值时 `nPe` 用 `gap_guided` 步长。

**三种变体**：
- **预计算**（`N8e()` 实验默认关）：idle/stop 时提前算好，到阈值 swap 复用。
- **微型压缩**（不动摘要）：清旧 `tool_result` 正文 + API 级 `clear_tool_uses_20250919`。
- **partial compact**：只压一部分（`direction: "from"|"up_to"`）。

手动 `/compact` **不是独立实现**，走同一条 `mfr` 链路，差异只在
`trigger: "manual"`、跳过水位判定、失败时会提示用户。

**`Ino()` 是第四种情况**：一个独立的简化实现，**只在「反应式不可用」时兜底**
（`!N$()`，即 `CLAUDE_CODE_REMOTE` 且实验 `tengu_reactive_compact_remote` 未开）。
正常 CLI 会话里它不执行——28/28 的真实压缩全部带 `messagesToKeep`，证明走的是 `mfr`。

> **初版原文（R1，已被上述订正）**：
> 「四条并行通道：①前置阈值压缩 ②反应式压缩 ③预计算压缩 ④微型压缩」。
> 问题在于把 ① 与 ② 当成两套实现；实际上它们共用 `nPe`/`vno` 引擎。

### 3.2 querySource 三分：谁能压缩、谁被压缩、谁不许

```js
// m0522:117-127
```

三者的用途完全不同（这是 R1 里最容易被误读的一处）：

- `yXe` → **禁止压缩**：`hxr` 第 2 行直接 `return !1`。理由从集合内容可读：
  这些 querySource 都是「附属/一次性」请求（补全建议、离开摘要、agent 摘要、缓存预热、hook prompt），
  压缩它们没有意义。
- `s7t` → **禁止递归**：压缩请求本身（`querySource: "compact"`）不得再触发压缩。
- `qlo` → **不是禁止，而是走不同的阈值逻辑**：`Ddr()` 里 `if (!qlo(e) || !N$()) return !1;`
  意思是「只有 fork 类 querySource 才允许跳过窗口来源限制」，配合后面
  `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 在 fork 上被忽略的分支（§5.4）。

`m0191:17996-18010` 给出 `querySource` 的三级归类，压缩只认 `main`：

```js

  if (e.startsWith("repl_main_thread") || e === "sdk") return "main";
```

`Rfe`（「是不是主线程」）是压缩路径里出现频率最高的判定，控制：
是否清全局 `readFileState`（`vno:105228`）、是否走 `bde("compact")` UI 事件、
是否 reset autonomous loop preamble（`XMe:117795`）等。

## 7. R1：token 计量（`$f` / `Bh` / `gI` / `xre`）

复刻时最容易做错的地方：CC 有**三套** token 数，混用会得出完全不同的阈值行为。

- 遇到 `Kr(msg)`（compact boundary）→ **立即返回 `{tokens: 0, anchorIndex: n}`**，
  即「边界之后全部重新估」。
- 找到 `pF(msg)`（`msg.message.usage`）且 `!_7e(usage)`（非全零）→ 返回
  `{ tokens: gI(usage), anchorIndex }`；同一 `message.id` 的多条 assistant 会合并到最前一条。


即「实测历史 = 三项 input 之和 + output_tokens」。

`Bh(messages, bytesPerToken)`（`m0591:54554`）是纯本地估算，逐条累加 `PKo`；
`PKo` 对 `assistant|user|api_system` 用 `F9(content)`（按字节/字符估算），

### 18.3 「保留多少轮」的自适应：三种步长模式

```js
// m0591:104228  dot(e /*每轮token*/, n /*要保留的轮数*/, r /*gap*/)
function dot(e, n, r) {
```

三种 `mode`（出现在 `Re.mode` / 遥测 `stepMode`）：

| mode | 何时 | step |
| --- | --- | --- |
| `"seeded"` | 首次即 PTL，但错误里给了 gap | `1 + dot(每轮token, S-1, gap/xe + 摘要prompt − 最后轮)`（`m0591:104431`） |

| `"credits_tenth"` | PTL 来自「额度边界」（`viaCreditsBoundary`）且 `bbr(...) > gap` | `dot(每轮token, Lo, ceil(前Lo轮/10))` |
| `"gap_unparseable"` | gap 无法解析 | `1`（最小步长） |

**这是 CC 反应式压缩的核心价值**：不是「丢掉一半」，而是

## 57. R7：`hOo` 的 6 道复用校验（预计算的核心）

```js
// m0040:2193
function hOo({ coverage, kept, sent, received, instructions, fit }) {
  let a = ({uuid}) => coverage.seenUuids.has(uuid);           // 「该消息是否在预计算覆盖范围内」
  let l = new Set(sent.messages.map(m => m.uuid));            // 「本次要发出去的消息 uuid 集合」

  // ① 覆盖的终点还在
  if (!l.has(coverage.lastUuid)) return { kind:"refuse", reason:"boundary_uuid_missing" };
  // ② 覆盖的每条都还在
  if (!coverage.rowUuids.every(u => l.has(u))) return { kind:"refuse", reason:"covered_messages_changed" };
  // ③ 保留段里「已被覆盖」的消息不能丢
  if (kept.some(m => a(m) && !l.has(m.uuid))) return { kind:"refuse", reason:"kept_message_missing" };
  // ④ 覆盖范围内不能有「模型没见过的回复」
  if (sent.messages.slice(0, sent.messages.findLastIndex(a)).some(m => m.type==="assistant" && !Ub(m) && !a(m)))
    return { kind:"refuse", reason:"unseen_reply" };
  // ⑤ hook 改写校验：指令变了 / 响应里找不到终点 / 前缀不一致
  let f = sent.rowUuids.slice(0, sent.rowUuids.findLastIndex(d => coverage.seenUuids.has(d)) + 1);
  if (instructions || !received.messages.some(({uuid}) => uuid === coverage.lastUuid) || !_e(received.rowUuids, f))
    return { kind:"refuse", reason:"hook_rewrite" };

  // ⑥ 装配 tail，并做「装得下吗」的估算
  let S = received.messages.findLastIndex(a),
      u = received.messages.flatMap((d, index) => d.type === "progress" || a(d) ? [] : [{ message: d, isEarly: index < S }]),
      m = ({message, isEarly}) => isEarly && Ub(message),
      h = new Set(u.filter(m).map(({message}) => message)),          // 早期可丢弃的
      g = u.filter(item => !m(item)),
      tail = g.map(({message}) => message),
      x = fit && Ct(fit, received.messages.filter(item => !h.has(item)), [...kept, ...tail]);
  if (x?.givesWay) return { kind:"refuse", reason:"would_not_fit", sizes: x.sizes };

  return { kind:"reuse", tail, earlyTailCount: U(g, ({isEarly}) => isEarly),
           displayOnlyLeftOutCount: h.size, headReordered: !_e(received.rowUuids, coverage.rowUuids), sizes: x?.sizes };
}
```

`Ct(...)`（`m0040:2275`）— 关掉这块的「装不下」判定：

```js
function Ct({thresholdTokens, windowTokens, liveTokens, madeFromTokens, summary, sizeOf}, receivedMsgs, keptAndTail) {
  let p = new Set(keptAndTail.map(m => m.uuid)),
      f = new Set(receivedMsgs.map(m => m.uuid)),
      S = receivedMsgs.filter(m => !p.has(m.uuid)),       // 会被替换掉的
      u = receivedMsgs.filter(m =>  p.has(m.uuid)),       // 会被保留的
      m = keptAndTail.filter(m => !f.has(m.uuid)),        // 新增的
      postSwapTokens = Math.max(liveTokens - sizeOf(S), sizeOf(u)) + sizeOf([...summary, ...m]);
  return { sizes: {postSwapTokens, thresholdTokens, windowTokens},
           givesWay: postSwapTokens >= thresholdTokens && madeFromTokens < windowTokens };
}
```

→ `givesWay` 的含义：**换完之后仍然超阈值，而且预计算时本来没超** → 换了也白换，拒绝。
（`madeFromTokens < windowTokens` 这个条件排除了「预计算时就已经超窗」的情况——
那种情况换了至少不会更糟。）

**复刻要点**：预计算复用不是「有缓存就用」，而是**六道一致性校验 + 一次容量复核**。
任何一道不过就退回重算。这是「预计算能安全复用」的全部保障。

## 77. R10：复刻蓝图（给自研 agent 的实施顺序）

### 77.1 分阶段（按投入产出比排序）

**P0（必做，2–3 天）** — 有这些就已经比大多数实现好：

   ```
   used = gI(lastUsage) + estimate(messagesAfterAnchor)
   ```
   不要纯估算，也不要纯靠 usage（最后一次请求的 usage 不含新增消息）。
2. **四档水位**（§5.2）：`ok / warn / compact / blocked`，常量 20000/13000/3000。
3. **阈值触发 + 摘要压缩**（§14/§16）：
   - 摘要 prompt 照抄 §16（三套模板选一个，`<analysis>`+`<summary>`）

   - 摘要消息带 `isCompactSummary` 标记 + `Ght` 开场白

5. **压缩后重建**（§23 的 A 类 + B 类）：至少重挂「读过的文件」+「工具/技能列表」。

**P1（推荐，3–5 天）** — 决定「压缩后能不能继续干活」：

6. **PTL 反应式压缩**（§18）：错误信息里的 `actual > limit` 反推保留轮数。
   这是「阈值算错时的兜底」，也是最容易出彩的部分。
7. **分轮阶梯**（§18.3）：`gap_guided` 步长 + 「最后一招」略过 tool_result。
8. **保留尾部**（`messagesToKeep`）+ `Xhn` 前言（§16.6）。

10. **失败熔断**（§6.3）：连续 3 次失败停手；3 轮内回填 3 次报 thrashing。

**P2（加分，2–4 天）**：

11. **微型压缩**（§9.1）：清旧 tool_result（阈值 20000，保留最近 12/5 个）。

14. partial compact（§24）
15. 换大模型压缩（§25）

### 77.2 十四个「不做会踩坑」的细节

1. **`postTokens` ≠ `truePostTokens`**（§14.8）：前者是摘要调用的 output，后者是压缩后整个上下文的估算。
   写进 boundary 的必须是后者。
2. **`<analysis>` 必须丢弃**（§14.5）：只保留 `<summary>` 内容，且 `<summary>` 改写成 `Summary:`。
3. **摘要 prompt 的 `tools` 要最小化**（§15.2）：CC 只给 1 个工具，且 `maxTurns: 1`。
4. **`isVisibleInTranscriptOnly`**（§14.7）：摘要消息要标记，否则 UI 会当成用户消息渲染。
5. **`suppressFollowUpQuestions`**（§16.5）：自动压缩要加「别复述、直接继续」，否则浪费一轮。
6. **kept-tail 前言**（§16.6）：有保留段时必须告诉模型「摘要没看过保留段」。
7. **`preCompactDiscoveredTools`**（§48）：延迟/动态工具的已通告名单要跨压缩继承。
8. **失败静默**（§31/§46）：自动压缩失败不要打扰用户；319 里连「3 次后提示」都被 `zoe()` 关死了。
9. **超时按 token 算**（§70）：`max(10min, tokens × 1.5ms)`，上限 60 分钟。
10. **PTL 归因**（§62.5/§67）：区分「对话太大」与「固定开销太大」，建议完全不同。
11. **PTL 优先撤附件**（§62.3）：PDF/图片比压缩便宜。
