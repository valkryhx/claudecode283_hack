> 目标：回答「CC 压缩时用户看到什么、为什么不会觉得卡死」，

## 0. 结论先行（三个必须先纠正的预期）

### 0.1 CC **没有**百分比进度条

这是本次调研最重要的结论，因为它直接改变复刻方向。

**用户预期**：「CC 有一个压缩的进度条显示」。
**源码实际**：压缩期间**不渲染任何进度条、百分比、剩余时间**。

证据（`m1795:771`，压缩专用渲染分支）：

```js
if (isCompacting_2 && z === null && q) return e(s, {
  ref: I,
  flexDirection: "column",
  marginTop: 1,
  width: "100%",
  children: e(CGt, {
    tone: "dim",
    text: bh(message_2, "…")     // message = "Compacting conversation"
  })
});
```

整个返回体只有**一行动画文字**。没有 `progress`、没有 `%`、没有宽度条。

为什么「进度」本质上做不出来【A】：压缩是**一次 LLM 摘要请求**，服务端不返回
「已完成 N%」。客户端唯一知道的是「发出去了」和「回来了」，中间没有任何
可度量的中间态。所以 CC 只能做「看起来在动」的指示，不能做真进度。

> 这解释了用户的主观印象：CC 那行**在跳动**（spinner 帧 150ms 一换），
> 所以「感觉在推进」；但那是动画，不是进度。

### 0.2 CC 压缩期间**可以**输入，且输入会被排队

**用户预期**：「用户也无法此刻输入【正常】」被当成 CC 的行为来对比。
**源码实际**：CC 压缩期间输入被接受并排队，`canDeliverOverTurn()` 显式
把 `isCompacting` 当作「可以越过回合投递」的条件之一。

证据（`m2159:13419`）：

```js
canDeliverOverTurn() {
  return this.turn.isCompacting || [...zVr(this.transcript.getSnapshot()).keys()].some(this.canMoveCall);
}
```

【A】`isCompacting` 为真时 `canDeliverOverTurn()` 返回真 —— 这是「允许在回合
未结束时投递排队消息」的开关。所以压缩不是「禁止输入」，而是「允许输入、
排队等压缩完」。

### 0.3 「卡住不动」的观感来自**指示缺失**，不是流程错误

GA 现在的形态（用户描述）：压缩开始 → 界面静止 → 压缩完成 → 继续。
这中间既没有动画也没有文案变更，用户唯一能感知的是「时间在流逝」。

CC 做对的最小集是两件事（都不涉及进度条）：
1. **行内动画**（spinner 帧，150ms）；
2. **文案切换**（`Compacting conversation` → 完成后的 `Conversation compacted`）。

## 1. 状态机与文案全表【S】

### 1.1 三个阶段，三套文案

`applyCompactProgress`（`m1007:372`）穷举了 `compact_progress` 事件的处理：

```js

```

| 阶段 | 触发事件 | 显示文案 | 颜色 |
| --- | --- | --- | --- |
| PreCompact hooks 运行中 | `hooks_start` + `hookType: "pre_compact"` | `Running PreCompact hooks…` | `claudeBlue_FOR_SYSTEM_SPINNER` |
| PostCompact hooks 运行中 | `hooks_start` + `hookType: "post_compact"` | `Running PostCompact hooks…` | 同上 |
| session_start hooks | `hooks_start` + 其他 | `Running SessionStart hooks…`（`jQr`，`m0591:231991`） | 同上 |
| **摘要请求中** | `compact_start` | **`Compacting conversation`**（`fc`，`m2064:7486`） | 保持上色 |
| 结束 | `compact_end` | 清空 → 回到普通 spinner | — |

【A】**颜色在这一刻被显式改成蓝色**（`claudeBlue_FOR_SYSTEM_SPINNER`），
而不是默认色。这是「让用户一眼看出这不是普通运行」的手段 —— 比换文案更早被
注意到。

### 1.2 `hintText` 是唯一的「进度」替代品

`compact_start` 可以带 `hintText`（`i.hintText ?? null`）。存进
`compactingHintText`，渲染时**替换**默认文案（`m2064:7531`）：

```js

```

【A】即：**谁发起压缩，谁就可以塞一句话说明当前在做什么**。
这是 CC 里唯一能表达「进度语义」的通道，机制上是个自由文本。

【未验证】319 里 `compact_start` 的实际调用点是否都带了 `hintText` —— 需要
逐个调用点核对；本次未做。

### 1.3 结束后的两条提示

压缩完成写两处（`m2057:9857` 与 `m2079:145`）：

```js

```

`m2079` 的 SDK 适配层也把 `compact_boundary` 帧转成同一条文案：

```js

```

【A】**用户不会只看到「压缩完了」，还会被告知旧消息去哪了**（文件路径 +
文件名）。这消除了「我的历史是不是被删了」的焦虑，是 GA 值得直接照抄的一点。

## 2. 动画机制：150ms 帧 + 减少动效降级【S】

### 2.1 帧间隔与帧表

`CGt`（`m1793:11`）：

```js
var t = 150;
function CGt(M) {
  ...
  const [ref, P] = pl(reducedMotion ? null : t);   // 150ms 一跳
  const frame = Math.floor(P / t);
  return e(HPe, { state: "live", tone, text, linkify: !1, frame, reducedMotion });
}
```

帧表 `tLr`（`m0094:6163`）：

```js
var Kan = "∴",                      // ∴
    gHe = "∷",                      // ∷
    Dy  = "∵",                      // ∵
    tLr = [Kan, gHe, Dy, gHe];           // [∴, ∷, ∵, ∷]
```

`HPe`（`m1789:85`）取帧：

```js

    d.state === "live" && !d.reducedMotion ? tLr[d.frame % tLr.length] : gHe
```

【A】**压缩用的不是普通 spinner 帧表，而是「思考帧」`[∴ ∷ ∵ ∷]`** ——
三角形点阵，来回摆动。这解释了为什么压缩行的动画看起来和普通运行行不同。

【A】`reducedMotion` 时**固定用 `gHe = ∷`**（不跳），且帧间隔传 `null`
（不启动定时器）。这是无障碍降级，GA 应当照做。

### 2.2 与普通运行行的帧间隔对比

`m1795:456`：

```js
let [viewportRef, time] = pl(reducedMotion ? null : mode_2 === "requesting" && !glimmerParked ? 50 : 100)
```

| 场景 | 帧间隔 |
| --- | --- |
| 普通运行 | 100ms |
| `mode === "requesting"`（含压缩请求） | **50ms** |
| 压缩行 `CGt` 自身 | 150ms |

【A】**压缩请求期间普通 spinner 提速到 50ms**（请求态的即时反馈），
而压缩专用行自己用 150ms。两者各自跑。

### 2.3 计时从 `compactingStartTime` 起算，与回合计时分离

`m1795:461`：

```js

  ? Math.max(0, now - compactingStartTime)
  : pauseStartTime !== null
    ? pauseStartTime - loadingStartTime - totalPausedMs
    : now - loadingStartTime - totalPausedMs
```

`setCompacting`（`m1007`）里定锚点：

```js

  g(n, c => {
    if (c.isCompacting === isCompacting && c.compactingHintText === compactingHintText) return c;
```

【A】**压缩有独立的起始时间戳**，且用 `?? u`（幂等：重复调用不会重置起点）。
这让「压缩耗时」与「回合耗时」可以分开显示/上报。

## 3. 输入不被禁用：三条证据【S】

### 3.1 `canDeliverOverTurn` 把压缩当作可投递窗口

见 §0.2。`m2159:13419`。

### 3.2 队列决策里压缩 = `wait`，不是 `cancel`

`m1922:52`（`Aoe` 风格的决策函数）：

```js
if (e.isCompacting) return { action: "wait", reason: "compacting" };
```

【A】注意这里返回的是 **`wait`**，与 `behind_earlier` 同类，而**不是**
`cancel`/`interrupt`。即：压缩期间排队消息**保留在队列里等**，不会被丢弃、
也不会触发中断。

### 3.3 状态帧不阻塞转录写入

`m2159:13477`：

```js
if (e.type === "system" && e.subtype === "status" && e.status !== "requesting")
  this.turn.isCompacting = e.status === "compacting";
```

【A】`status: "compacting"` 只是**一个状态位**，不改变回合的 `isRunning`。
`isRunning` 在 `startTurn` 置真（`m2159:13468`），在回合真正结束时置假
（`m2159:13481`）—— 两者是不同维度。

## 4. 心跳保活：为什么不觉得「断了」【S】

`m0591:103389` 附近，30 秒心跳：

```js
setInterval(qwr, 30000, e)     // 每 30s 重复发 { type:"sdk_status", status:"compacting" }
```

常量 `zwr = 30000`。

【A】长耗时压缩期间，客户端每 30 秒**主动重发一次状态帧**。目的：让上层
（SDK/外部宿主）知道「还活着」，而不是「消息丢了」。

【A】这是**外部宿主通道**的保活，不是终端 UI 的。终端 UI 的「不死感」来自
§2 的动画，两者分工不同 —— 复刻时不要混为一谈。

## 5. 事件契约全表（复刻时照这个实现）【S】

| 事件 | 载荷 | 时机 | UI 反应 |
| --- | --- | --- | --- |
| `compact_progress` | `{type:"hooks_start", hookType:"pre_compact"\|"post_compact"\|"session_start"}` | hook 阶段 | 文案 → `Running X hooks…`，转蓝 |
| `compact_progress` | `{type:"compact_start", hintText?}` | 摘要请求发出 | 文案 → `Compacting conversation`，记起点 |
| `compact_progress` | `{type:"compact_end"}` | 摘要请求结束 | 清空覆盖态 |
| `sdk_status` | `{status:"compacting"}` | 进入压缩 | 状态位 |
| `sdk_status` | `{status:null, metadata:{compactResult, compactError?}}` | 退出 | 状态位清除 |
| `stream_mode` | `{mode:"requesting"}` | 请求态 | spinner 提速到 50ms |
| `compact_progress`（心跳） | 同 `sdk_status compacting` | 每 30s | 外部宿主保活 |

【S】**`compact_end` 在 `.catch()` 之后无条件发出**，位置等价于 `finally`：

```js
let wt = await oes({ ... }).catch((Tn) => { ...; Ze = {reason:"error", detail: vn}; return });
if (gt) Ne.onCompactEvent?.({ type: "stream_mode", mode: "requesting" }), ...;
```

（`m0591:2974683` 附近）

【A】即使摘要请求抛异常，UI 也一定会退出压缩态。这是防「永远卡在
`Compacting conversation`」的关键约束 —— 复刻时**必须**保持这个位置关系，
不能把 `compact_end` 放进 try 分支里。

## 7. 给 GA 的落地建议（按性价比排序）

### P0：一行会动的文字（解决「卡住不动」）

不需要进度条，需要**动画**。最小实现：

1. 压缩开始 → 在 activity 行显示 `Compacting conversation`（dim）；
2. 用一个 150ms 的 tick 循环切换 `∴ ∷ ∵ ∷` 四个字形；
3. 压缩结束 → 清掉这行。

GA 已有 `spinnerFrameAt` / `spinnerTick` 基础设施（本次会话刚接的），
只需要再加一张「思考帧」表和一个独立状态位。

### P1：完成提示带「旧消息去哪了」

照抄 `Earlier messages are saved in <path>`。这一句消除了「我的历史是不是
被删了」的焦虑，成本极低。

### P2：阶段文案

`Running PreCompact hooks…` / `Compacting conversation`。GA 若实现 hooks
（已有），前者几乎零成本。

### P3：`reducedMotion` 降级

固定 `∷`，不启动定时器。无障碍要求，实现成本一个 if。

### 明确不要做

- ❌ **假进度条**。既没有数据源，也会在压缩快结束时显得荒谬（卡在 87%）。
- ❌ **禁用输入**。CC 明确把压缩当作「可投递窗口」（`wait` 而非 `cancel`）。
- ❌ **用百分比估算耗时**。压缩耗时与上下文大小不是线性关系。
