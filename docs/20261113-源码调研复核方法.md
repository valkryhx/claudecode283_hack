# 源码调研的复核方法：为什么第一遍会写错，第二遍能抓到

> 日期：2026-11-13　状态：方法论沉淀（源自 `docs/20261112-CC319记忆系统源码调研.md` 的两轮复核）
> 适用对象：任何「读 minify 后的源码 → 写成结论文档」的活，不限于 CC。

---

## 0. 触发案例

`docs/20261112-CC319记忆系统源码调研.md` 的复核过程反复出现同一个模式：

| 轮次 | 我做了什么 | 结果 |
|---|---|---|
| 第一轮 | `grep` 找关键词 → 读窗口 → 看代码「像什么」→ 写结论 | 写了 4 处订正，但**自己又新增 1 处错** |
| 第二轮 | 建 import 图 → 查 `= "..."` 定义行 → 断言化 → 反向确认 | 抓出第一轮那处错，并又抓出 2 处漏项 |

第一轮那处错是：把 laptop 后端白名单里的 `ze` 当成 **WebFetch**，
实际定义是 `var ze = "Read"`（`m0175_0x1153be5b.js:6`）。
铁证：`m0832` 全文 `WebFetch\|WebSearch` 命中 **0**。

**这不是粗心，是方法本身的缺陷。** 下面把机制说清楚。

---

## 1. 根因一：压缩符号是「局部名」，不是「全局名」

Bun `--compile` 的产物里，**每个模块独立压缩**。同一个两三个字母的符号，
在不同模块里指向完全不同的东西：

| 符号 | m0176 里是 | 别的模块里是 |
|---|---|---|
| `dt` | `"Edit"`（`m0176:6`） | `m0293` 里是别的变量 |
| `as` | — | `m0292:5` 是 `"ToolSearch"`；`m0126:1777` 是一串 PowerShell 路径 |
| `yg` | — | `m0290:6` 是 `"memory_read"`；`m0094:237` 是正则；`m0165:2860` 是 OTel 属性名 |
| `ze` | — | `m0175:6` 是 `"Read"` |

所以 **`grep -rn 'dt = "'` 这种全仓搜索，拿到的是「某个模块里的 dt」，不是「目标模块里的 dt」**。

**正确姿势：先确定目标模块 import 的 chunk 对应哪个源模块，再在那个模块里查定义。**

```bash
# ❌ 错误：全仓搜，撞名
grep -rn 'ze = "' reconstructed319/deminified/

# ✅ 正确：先解析 import 图
python docs/probes/20261113-319-chunk映射核验.py m0191_0x1155a4cc.js chunk-xwzn0yxv
#   -> [完全覆盖] m0175_0x1153be5b.js
python docs/probes/20261113-319-符号定义定位.py m0175_0x1153be5b.js ze
#   -> var ze = "Read",
```

### 1.1 chunk → 源模块 怎么唯一确定

Bun 里一个 m 模块编译成一个 chunk，所以：

1. 解析所有 `m*.js` 的 `export { ... }`，建「符号 → 文件」反查表；
2. 对目标模块的每条 `import { A, B } from "chunk-X.js"`，
   求「export 集合**完全覆盖** `{A, B}`」的文件。

完全覆盖通常唯一。若多个文件都覆盖，说明符号太通用（如 `a`、`b`），
此时退回「部分覆盖 + 使用点交叉」人工判定。

脚本：`docs/probes/20261113-319-chunk映射核验.py`

## 2. 根因二：单点确认 —— 找到第一个就停手

第二个真实失误：`dc("nested_memory", ...)` 我第一轮只记了 `:151783`，
漏掉了 `:151746` 的第二处注册（`inputMentionsOnly` 短路分支）。

原因：grep 返回第一处命中时，代码「看起来」就是我要找的那段，于是停止搜索。

**规则：凡是「某某是怎么注册 / 怎么触发 / 谁调用」的问题，
必须用 `grep -c` 统计出现次数，再逐个数完。**

```bash
# ❌ 只取第一处
grep -n 'dc("nested_memory"' m0591.js | head -1

# ✅ 先数总数，再逐个看
grep -c 'dc("nested_memory"' m0591.js     # -> 2
grep -n 'dc("nested_memory"' m0591.js     # -> 两个都要看
```

同源失误：`:76049` / `:76063` / `:76090` 我第一轮当成「同一段逻辑的三个分支」，
实际前两个在 `B9e()`（`:76043`）、第三个在 `_rn()`（`:76088`），是两个不同函数。
**并列列举的位置相近，不等于同一个函数。**

## 3. 根因三：把「看起来像」当成「已证明」

第一轮的表述是「这个符号大概是 WebFetch」——用词就暴露了问题：
**身份（identity）是事实，不是印象。**

只要结论依赖某个压缩符号的取值，就必须拿到 `= "..."` 那行作为证据。
拿不到就不能写名字，只能写符号本身（这也是 `AGENTS.md` §0 铁律 4 的要求：
「没证据就不改名」）。

## 4. 强方法：把结论变成可执行断言

读完源码写结论，本质上是一次「人工编译」。人工编译必然有漏，
所以要再写一遍「机器可复算」的版本。

### 4.1 断言三要素

每条事实写成 `(模块, 精确片段, 期望行号)`：

```python
check("ze = Read（不是 WebFetch）", M0175, 'var ze = "Read"', expect_line=6)
check("mcp 门禁挡非白名单工具", M0832, "if (!XIs.has(o.name))", expect_line=730)
```

- **精确片段**：不用正则模糊匹配，直接抄源码原文（避免「大概在附近」）；
- **期望行号**：坐标漂移立刻暴露；
- **模块名显式**：避免跨模块撞名（根因一）。

### 4.2 否定事实要用 `must_not`

「没有向量库」「不碰网络工具」这类结论，同样需要可执行证据：

```python
check("m0832 绝不含 WebFetch / WebSearch", M0832, "WebFetch", must_not=True)
for fn in (M0832, M0191, M0452, M0290):
    check(f"{fn} 无 embedding", fn, "embedding", must_not=True)
```

**否定结论最容易被想当然**——因为「我没搜到」和「它不存在」是两件事，
必须让机器在每次复核时重新搜一遍。

### 4.3 一次跑全量

125 条断言一次跑完，失败项直接打印「期望 X±0，实际 Y」。
改源码或改文档后重跑，就知道哪些坐标失效。

脚本：`docs/probes/20261113-记忆调研断言核验.py`

## 5. 关键一步：反向确认（文档版 TDD）

**断言全绿不能证明断言有效。** 这是 `AGENTS.md` §8.5 的核心教训，
在「文档复核」场景同样成立，而且**更隐蔽**——因为文档没有编译器帮你兜底。

做法：故意写错几条断言，要求引擎必须报 FAIL。

```python
# A: 错误行号必须 FAIL
check("A. 错误行号应 FAIL", M0832, 'querySource: "extract_memories_first_look"', expect_line=9999)

# B: 不存在的字符串必须 FAIL
check("B. 不存在的字符串应 FAIL", M0832, "THIS_STRING_DOES_NOT_EXIST_XYZ", expect_line=461)

# C: must_not 撞到真实存在的串必须 FAIL
check("C. must_not 撞真实存在的串应 FAIL", M0832, "extractMemories", must_not=True)

# D: 正确行号必须 PASS（防止「无脑全红」伪装成严格）
check("D. 正确行号应 PASS", M0832, 'querySource: "extract_memories_first_look"', expect_line=461)
```

**D 这一步不能省**：如果引擎只会返回 FAIL，那它和「什么都查不到」没区别，
全绿/全红都不携带信息。

### 5.1 反向确认实际抓到了什么

跑反向确认时，当场暴露出**我自己写的断言有问题**：

| 断言 | 问题 |
|---|---|
| `requireReadBeforeWrite: !0` 期望 `:62` | 实际 `:63`（`:62` 是外层 `let u = await nZt(...)`） |
| `if (b === "") return w("empty")` | 源码实际是 `if (b = T.text, userTurns_2 = T.userTurns, b === "") ...`，串不匹配 |
| `the pass is not skipped` 期望 1 处 | 实际 **4 处**（`:423`/`:424`/`:467`/`:470`），全是否决路径 |

这三处的共同点：**断言写得太「像我以为的样子」，而不是源码原文**。
反向确认把它们逼出来了。

## 6. 为什么第二遍能发现第一遍发现不了的

一句话：**第一遍在做「理解」，第二遍在做「证明」。**

| | 第一遍（理解） | 第二遍（证明） |
|---|---|---|
| 目标 | 把代码看明白，写出机制 | 把每条结论钉到一个可复算的点上 |
| 成功标准 | 「读通了，能自洽解释」 | 「机器跑一遍全绿，且引擎被证明会变红」 |
| 失败模式 | 撞名、单点确认、把像当成是 | 断言写得太像自己的理解 |
| 产出 | 叙述 | 叙述 + 断言 + 反向确认 |

**关键认知：自洽 ≠ 正确。** 第一遍写出来的东西是自洽的
（「记忆不走 hook 走 attachment」这个主线完全对，错的只是白名单那一格的细节），
正因为主线对，细节错的地方不会被「读起来别扭」暴露出来。
**只有强制取证据才会暴露。**

## 7. 可复用 SOP

写任何「源码调研文档」时：

```
① 定位         grep -n 找关键词，先用 grep -c 看总数
② 取窗口       awk 'NR>=..&&NR<=..' 只读命中段（大模块禁止整读，见 AGENTS.md §10）
③ 查身份       凡依赖压缩符号，先解析 chunk→模块，再查 '= "..."' 定义行
④ 写文档       结论 + 模块:行号 + 证据片段
⑤ 断言化       把每条「结论」翻译成 (模块, 精确片段, 期望行号)
⑥ 反向确认     故意注入 3-4 条错误断言，证明引擎会变红；再放 1 条正确断言证明不会全红
⑦ 记录修订     文档头部写清「哪些是订正、哪些是补漏、哪些是我自己第一轮写错的」
```

第 ⑦ 步不是自我批评，是给下一个人的信息：
**错误模式比正确结论更有复用价值**。

## 8. 反模式对照表

| 反模式 | 为什么会错 | 正确做法 |
|---|---|---|
| 全仓 `grep 'X = "'` 找符号定义 | 压缩符号是局部名，跨模块撞名 | 先解析 chunk→模块 |
| grep 第一处命中就写结论 | 同一模式常有多处注册 | 先 `grep -c` 数总数 |
| 「这个符号大概是 XX」 | 身份是事实不是印象 | 必须拿到 `= "..."` 行 |
| 位置相近就当成同一函数 | `:76049`/`:76090` 分属 `B9e`/`_rn` | 往上找最近的 `function` 行 |
| 否定结论靠「我没搜到」 | 搜漏了也是「没搜到」 | `must_not` 断言，每次重跑 |
| 断言全绿就交付 | 可能是断言写得太松 | 反向确认：必须能变红 |
| 断言写「我以为的样子」 | 与源码原文不符，误报/漏报 | 直接抄源码原文片段 |
| 只做一遍 | 自洽掩盖细节错 | 理解一遍 + 证明一遍 |

## 10. 元教训：我自己在写这份文档时也犯了同一个错

记录一个当场发生的实例，因为它比任何抽象总结都有说服力：

写 §9 时我想跑个小脚本验证一件事，顺手写了 `python - <<'PY' ... PY`。
结果 heredoc 正文没写进去，`python -` 读到**空 stdin 直接进了 REPL**，
表面没报错，实际什么都没验证——这正是 `AGENTS.md` §9 明令禁止的用法。

教训有两层：
1. **规则不是读过就算**，手会不听话。所以规则要写成「必须跑的命令」，
   而不是「要注意的事项」。
2. **「没报错」和「做成了」是两件事**。REPL 里没报错，但也没干活。
   这和 §5 的反向确认是同一个道理：全绿 / 静默都不携带信息，
   必须有一个**明确的成功信号**（这里是：脚本自己打印「全部通过」）。

所以本文 §7 SOP 的第 ⑥ 步才要求反向确认，第 ⑦ 步才要求记录修订：
**能被验证的才叫结论，其余都只是印象。**

### 10.1 同日第二个实例：`grep -c $'\r'` 的假信号

同一轮里还踩了一次：用 `grep -c $'\r' file` 检查行尾，输出**等于文件总行数**，
看起来像「每一行都是 CRLF」。实际字节级是 `CR=0`。

原因：payload 穿过 PowerShell here-string 后 `$'\r'` 没有做 ANSI-C 展开，
退化成 `grep -c ''`（空模式），于是匹配了全部行。

**结论：行尾/编码一律用字节级检查裁决，不用 grep。**
脚本：`docs/probes/20261113-文本字节校验.py`（CR 数 / BOM / UTF-8 / 结尾完整性，一次说清）。

这类假信号的共同结构是：**工具没报错，但给出的数字毫无意义**。
和 §10 的 REPL 空 stdin 是同一族问题——
判定「有没有问题」时，先确认「这个信号本身是不是有效信号」。
