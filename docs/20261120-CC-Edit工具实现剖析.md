# CC319 的 Edit 工具：为什么「只发 diff」能可靠工作

日期：2026-11-20
源码：`reconstructed319/deminified/m0591_0x11be624e.js`（工具本体）
+ `m0520_0x11b936b1.js`（匹配器 `hWe`）
可复算：`docs/probes/20261120-CC-Edit机制核验.py`

## 0. 一句话结论

**Edit 的难点不是「只发 diff」，而是「让模型少发的那部分仍然能精确命中」。**

模型只发 `old_string`（通常 1–3 行）+ `new_string`。风险是：
它手抄的 `old_string` 与文件实际内容有细微差异（智能引号、`\uXXXX` 转义、
行尾空白），于是「找不到要替换的字符串」，模型陷入「重读 → 再错」的循环。

CC 用 **四级降级匹配** + **明确的失败文案** 解决这个问题。
这正是 Hlaudz 的 `file_patch` 缺的东西。

## 1. 工具契约

`m0591:73496-73498`：

```js
old_string: "The text to replace"
new_string: "The text to replace it with (must be different from old_string)"
replace_all: "Replace all occurrences of old_string (default false)"
```

三个参数的语义，与 Hlaudz 的 `file_patch(old_content, new_content)` 相比，
**只多一个 `replace_all`**。

## 2. ★ 核心：四级降级匹配（`hWe`）

`m0520:215-232`：

```js
function hWe(e, n) {              // e = 文件全文, n = old_string
  if (e.includes(n)) return n;                       // ① 精确
  let r = b(n),                                      // ② 引号归一化
    o = b(e).indexOf(r);
  if (o !== -1) return e.substring(o, o + n.length);
  if (R.test(n)) {                                   // ③ \uXXXX → 字符
    let l = F(n);
    if (l !== n && e.includes(l)) return l;
  }
  if (w.test(n)) {                                   // ④ 字符 → \uXXXX
    if (L(n) > e.length || !e.includes("\\u")) return null;
    return N(e, n);
  }
  return null;
}
```

**返回值是「文件里真实存在的那段文本」**，不是布尔值。
所以后续 `replace(gt, w)` 用的是**原文**，而不是模型抄错的那份。

### 2.1 ① 精确匹配

最常见的路径，零成本。

### 2.2 ② 引号归一化（`b`，`m0520:139-141`）

```js
var A = "‘", m = "’",     // ‘ ’
    y = "“", T = "”";     // “ ”
function b(e) {
  return e.replaceAll(A, "'").replaceAll(m, "'")
          .replaceAll(y, '"').replaceAll(T, '"');
}
```

**为什么这很重要**：模型（尤其从网页/文档里读到的内容）经常把
`"` 输出成 `“`/`”`，把 `'` 输出成 `‘`/`’`。文件里是 ASCII 引号时，
精确匹配会失败，但语义其实完全相同。

注意 `hWe` 的写法：**两边都归一化**（`b(n)` 与 `b(e)`），
然后取 `e.substring(o, o + n.length)` —— 在**原文**里截取等长片段。
这是因为归一化保持长度不变（1 字符换 1 字符）。

### 2.3 ③ `\uXXXX` 转义 → 实际字符（`F`，`m0520:144-146`）

```js
function F(e) {
  return e.replace(/(\\\\)|\\u([0-9a-fA-F]{4})/g,
    (n, r, s) => r !== void 0 ? n : String.fromCharCode(parseInt(s, 16)));
}
```

模型有时会把中文写成 `你好`（源码字符串里的转义形式），
而文件里是「你好」。这级把转义还原后再试。

注意 `(\\\\)` 分支：`\\u4f60`（转义了的反斜杠）要保持原样，不转换 ——
这是防「双重转义」误伤。

### 2.4 ④ 实际字符 → `\uXXXX`（`N`，`m0520:168-190`）

反向：模型发「你好」，但文件里存的是 `你好`（例如 JSON 源码）。

这一级最复杂，因为它用**正则**匹配，必须处理「合法转义 vs 偶然出现的反斜杠」：

```js
function N(e, n) {
  if (C(e, e.length) % 2 === 1) return null;      // 末尾反斜杠数为奇数 → 放弃
  let r = e[0] === "\\" ? [0] : [], s = 0;
  for (let l = 0; l < e.length; l++)
    if (e.charCodeAt(l) >= 128) r.push(s), s += 6; else s += 1;
  let o = X(e);                                    // 构造正则
  try {
    let regExp = new RegExp(o, "g");
    for (let c = regExp.exec(n); c !== null; c = regExp.exec(n)) {
      let index = c.index;
      // 命中的位置前面，反斜杠计数必须为偶数（否则是被转义的）
      if (r.every(item => C(n, index + item) % 2 === 0))
        return n.indexOf(c[0]) === index ? c[0] : null;
      regExp.lastIndex = index + 1;
    }
    return null;
  } catch (error) { /* 正则拒绝 → 记日志返回 null */ }
}
```

**三个细节值得学**：

1. **反斜杠奇偶校验**（`C`）：位置前面有 1 个反斜杠 ⇒ 它是 `\u` 的一部分；
   有 2 个 ⇒ 是被转义的 `\\` + `u`，不该当转义看。
2. **要求唯一命中**（`n.indexOf(c[0]) === index`）：多处命中时返回 `null`，
   让上层报「不唯一」而不是猜一个。
3. **正则失败要吞掉**：模型可能发出让 `new RegExp` 抛错的字符串，
   这时记一条日志返回 `null`，不能让整个工具崩。

### 2.5 大小写风格继承（`Mmr`，`m0520:189-209`）

第 ④ 级还原出原文后，写回时还要**保持原文件的 hex 大小写风格**：

```js
if (w.test(e) && L(e) === n.length && N(e, n) !== null) {
  // 统计原文里 hex 字母的大写/小写各多少
  for (...) if (p >= "a" && p <= "f") l++; else if (p >= "A" && p <= "F") o++;
  return r.replace(/[\u0080-￿]/g, c => {
    ...
    return "\\u" + (o > l ? f.toUpperCase() : f);   // 跟随原文多数风格
  });
}
```

**这是「不产生无关 diff」的关键**：不做这层，
一次编辑会把文件里所有 `你` 变成 `你`，diff 从 3 行变成几百行。

## 3. 失败时的文案（这比机制本身更重要）

模型是「按错误信息行动」的。CC 的每条失败文案都告诉模型下一步做什么：

| 情况 | 文案（`m0591`） | 教模型做什么 |
| --- | --- | --- |
| 找不到（`:212865`） | `String to replace not found in file.` + 转义形态时附加「也试过 \uXXXX 互换，所以问题在别处，重读文件抄准确文本」 | **重读文件** |
| 多处命中（`:212877`） | `Found N matches ... but replace_all is false. To replace only one, provide more context` | 加更多上下文，或开 `replace_all` |
| 新旧相同（`:212711`） | `No changes to make: old_string and new_string are exactly the same.` | 无需重试 |
| 文件太大（`:212744`） | `File is too large to edit (X). Maximum editable file size is Y.` | 换工具 |

`kso = 1073741824`（`m0591:212505`）—— **1 GiB** 上限。

> Hlaudz 的 `file_patch` 现在只返回「未找到匹配的旧文本块。请先用 file_read
> 确认当前内容，再分小段 patch。」—— 意思对，但没有降级匹配兜底，
> 模型抄错一个引号就会卡在这一步反复重读。

## 4. 与 Hlaudz `file_patch` 的逐项对比

| 项 | CC Edit | Hlaudz file_patch | 差距 |
| --- | --- | --- | --- |
| 只发 diff | ✅ | ✅ | — |
| 唯一性检查 | ✅ | ✅ | — |
| `replace_all` | ✅ | ❌ | **缺** |
| 引号归一化 | ✅ | ❌ | **缺（最常见失败）** |
| `\uXXXX` 双向匹配 | ✅ | ❌ | **缺** |
| 转义大小写保持 | ✅ | ❌ | **缺** |
| 返回实际匹配原文 | ✅ | ❌ | **缺（诊断能力）** |
| 文件大小上限 | ✅ 1 GiB | ❌ | 可选 |
| 陈旧读检测 | ✅ (mtime) | ❌ | 见 §5 |

## 5. CC 还有一层：陈旧读检测

`m0591:212848-212851`：

```js
if (Xe) {
  if (Cso(Xe) && !pt(b("refreshed"))) return ot();
  if (await cP(ke) > Xe.timestamp) {              // 文件 mtime > 读取时间
    if (!(PL(Xe) && f3(Xe, Ne)) && !pt(b("mtime"))) return ot()   // 报「文件已变」
  }
}
```

即：**如果文件在你读过之后被别人改过，编辑会被拒绝**，让你重读。
这是防「用陈旧内容做替换导致误删」。

> Hlaudz 的读前置门禁已按用户要求删除（见
> `docs/20261120-删除写前必读门禁.md`）。**所以这层不能照搬** ——
> 没有读前置就没有 `readFileState`。若将来要加，应该独立设计
> （例如只对「本次会话读过的文件」做 mtime 校验）。
