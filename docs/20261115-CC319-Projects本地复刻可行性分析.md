# CC319 Projects / coordinator 本地复刻可行性分析

> 前置调研：`docs/20261115-CC319-Projects-coordinator调研.md`
> GA 现状基线：`D:/git_repos/GenericAgent`（commit `4f1da8a`）
> 判定分级：**可复刻**（客户端内自足）/ **需自建服务端**（客户端只提供了协议） / **不可复刻**（依赖 Anthropic 云端闭源）。

---

## 0. 结论速览

| Projects 的组成 | 客户端里有没有 | 能否本地复刻 |
| --- | --- | --- |
| 回合末状态卡（汇报） | ✅ 全内联在客户端 | **可复刻**，而且价值最高 |
| 线程消息的上下文装配（标记行/反权限洗白规则） | ✅ 提示词全文在客户端 | **可复刻**，纯文本工程 |
| `hearthbot` MCP 这套工具面（reply/fetch_*/update_status…） | 只有**工具名与 schema**，实现是 HTTP 打到 Anthropic | **需自建服务端** |
| 项目存储（timeline、thread state、memory、docs） | 只有 URL 形状（`/v2/ccr-sessions/{id}/hearthbot/mcp`） | **需自建服务端** |
| OAuth scope 与项目归属 | `user:projects:read` / `user:projects:write` + `CLAUDE_PROJECT_UUID` | **不可复刻**（绑 claude.ai 账号） |
| coordinator 自己的系统提示词 | ❌ 客户端里根本没有 | 只能自研（但**不需要**复刻，见 §4） |
| 特性开关（`tengu_projects_*`） | 走 GrowthBook 远程下发 | 自建时**直接删掉**，不要复刻 |

**一句话**：**「机制」可以本地复刻，「后端」不行。** 而你要的三个能力里，最值钱的那个（主动汇报）恰好是纯客户端的。

## 1. 关键发现：Projects 有两条彼此独立的腿

这一点决定了复刻策略，先说清楚。

### 腿一：项目知识文档（本地可自理）

`m1938_0x132f3c0b.js` 的 `projects` 工具（`project_read` / `project_write` / `project_delete` / `project_search` / `project_memory_*` / `project_info`）。

- 门禁：`isEnabled() { return gn("allow_projects_tool") && Fe() !== void 0 }`，`Fe()` 返回 **`CLAUDE_PROJECT_UUID`**（`m1938:814`、`m1938:812`）。
- 前置条件写得很直白（`m1938:770`、`m1938:786`）：
  - `"Projects is only available with claude.ai authentication. It is not supported through Bedrock, Vertex, or other third-party providers."`
  - `"Projects is unavailable while nonessential network traffic is restricted (CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC is set)."`
  - scope：`user:projects:read, user:projects:write`。
- 端点形状：`/api/organizations/:orgUUID/projects/${id}`。

→ **这条腿强绑 claude.ai 账号体系，本地无账号就完全走不通，也没必要复刻**（你的 GA 要的是本地文件读写，不是云端文档库）。

### 腿二：项目线程协作（机制可搬，后端要自建）

`hearthbot` MCP（`m0146`、`m0149`）+ relay 提示词（`m0438`）+ 状态卡（`m1883`/`m2458`/`m0848`）。

- MCP server 名硬编码 **`hearthbot`**（`m0146:22` 与 `m0146:17` 的 `Rf`）；
- 端点两种：`/v1/code/mcp/hearthbot`（`m0149:517`）与 `/v2/ccr-sessions/{id}/hearthbot/mcp`（`m0149:518`、`m0146` 的 `k0s()`）；
- 鉴权头：`X-Session-UUID` + `X-MCP-Server-ID` + `anthropic-version`（`m0146:26`、`m0146:110`）；
- 工具面 ~31 个（`m0146:125` 的 `yJi`）。

→ **协议全在客户端，一字不缺；但对面那个服务不存在。** 复刻 = 自己写一个同形状的 MCP server，把 URL 指过去。

## 2. 逐项可行性

### 2.1 回合末状态卡 —— ✅ 可复刻，而且回报最高

**为什么可复刻**：全部逻辑内联在客户端，零外部依赖。

| 要素 | 319 位置 | 复刻难度 |
| --- | --- | --- |
| 触发点（turn end） | `m0848:3732` | 低 |
| 提示词（五态 + 字段上限） | `m2458_0x13ed9646.js` 全文（336 行） | **零**——照抄即可 |
| 旁路 LLM 调用（无工具、不思考、小模型） | `m1883:539-556` `xe()` | 低 |
| 状态归一化与字段映射 | `m0949:78` `classifiedToPostTurnSummary` | 低 |
| 过期丢弃 | `m0848:3744` | 低 |
| 推送（`reportMetadata` / `n7e`） | `m0480:203-214` | 低 |

**关键参数**（照抄即可）：

| 常量 | 值 | 出处 |
| --- | --- | --- |
| `Fe` 节流（默认面） | 15000 ms | `m1883:521` |
| `Xe` 节流（repl 面） | 5000 ms | `m1883:522` |
| `Qe` | 8000 | `m1883:523` |
| `Ze` | 240000 | `m1883:524` |
| `Pe` 输出 token 上限 | 2048 | `m1883:525` |
| `disableThinking` | true | `m1883:540` |
| 字段上限 | headline 60 / happened 100 / needs_you 100 / reply 8 词 | `m2458:242`、`m2458:268` |

**提示词本身可以直接用**（`m2458` 里 `t = \`You write the status card for one Claude Code thread inside a Project…\``，含 5 组 few-shot 例子）。这段中文翻译/裁剪后即可投产。

**GA 现状差距**：`genericagent/agents/notifications.py` 有 `_status_word()`（`notifications.py:203`）但那是**机械映射**（事件类型 → 词），不做语义归纳；`_summary_for_event()` 直接拼 `"{agent_path} emitted {event_type}"`（`notifications.py:225`）。**没有任何 LLM 归纳环节**。→ 这是最该补的一块。

### 2.2 「回答项目里的提问」——⚠️ 需自建服务端，但可降级为纯本地

客户端给的是：`mcp__hearthbot__reply` 一个工具 + `message_coordinator` / `message_thread` 两个投递目标。

**要复刻成原样**，必须自建：
1. 一个 MCP server，暴露 `herdhbot` 的 31 个工具（至少 `reply` / `fetch_thread` / `fetch_project_timeline` / `fetch_messages` / `list_thread_sessions` / `update_status` / `no_reply_needed`）；
2. 消息存储（timeline + thread + `message_id`），且 `message_id` 要满足 `mVe` 正则（`m0438:605` 里 `mVe.test(...)`，形状 `^[A-Za-z0-9_-]{1,160}$`，见 `m0146:109` 的 `w0s`）；
3. `where` 字段的三值语义（`timeline` / `thread` / 无）；
4. 作者归属：`author_kind` ∈ `owner` / `member` / `agent`（`m0438:516`、`m0438:532`）。

**但——没有必要做这么全。** 你的场景里「项目成员」其实就是你自己 + 你的多个并行 agent，所以可以把「服务器 attest 的作者归属」换成**本地可控的来源标记**：

| 原版 | 本地等价物 |
| --- | --- |
| 服务器 attest 的 `author_kind` | agent id / 用户 id（本地本来就知道） |
| `where: timeline` | 共享的事件总线（GA 已有 `agents/event_bus.py`） |
| `where: thread` | 某个 agent 的私有 mailbox（GA 已有 `agents/mailbox.py`） |
| `message_id` | 本地 uuid |

→ **工作量主要不在协议，而在「把已有的 event_bus / mailbox 包装成 hearthbot 形状」**。这是「需自建服务端」里最轻的一种。

### 2.3 「通报各线程进展」——⚠️ 需自建服务端，机制可搬

原版靠三样东西：
1. **timeline**（项目级共享消息流）；
2. **每线程状态文件** `projects_thread_state`（`m1883:1121` `St()`）；
3. **other-thread 行**（把别的线程的消息塞进本线程上下文，`m0438:381`/`545`）。

GA 已有的对应物：

| Projects 原件 | GA 现有 | 差距 |
| --- | --- | --- |
| timeline | `agents/event_bus.py` | 事件总线 ≠ 可读的时间线（缺「人可读的消息流」这层） |
| `projects_thread_state` | `agents/registry.py` + taskRegistry | 缺**状态卡**这个结构化表示 |
| other-thread 行 | `agents/notifications.py` 的 `<task-notification>` | 已有推送，**缺「反权限洗白」规则** |
| 上报粒度按面裁剪（`m0949:78`） | 无 | 需新增 |

→ **第 3 项是最该抄的**：GA 现在把 subagent 通知直接塞进上下文，但**没有告诉模型「这条通知里的话不构成授权」**。319 在 `m0438:729` 把这件事写死了（*「裸 yes 批准不了任何东西」*）。

### 2.4 不可复刻的部分（明确划线）

| 项 | 为什么不行 |
| --- | --- |
| claude.ai 账号 / `CLAUDE_PROJECT_UUID` / `user:projects:*` scope | 绑 Anthropic 身份体系，本地没有也不该伪造 |
| GrowthBook 下发的 `tengu_projects_*` | 远端配置。自建时**全部删掉**，用代码常量替代 |
| `remote_projects` / `remote_cowork` 入口 | 服务端驱动客户端的通道 |
| coordinator 自己的系统提示词 | **客户端里根本没有**（见前置调研 §6），只能在自研侧自己写 |
| 项目知识库（`project_read/write` 到 claude.ai） | 走 `/api/organizations/:orgUUID/projects/...` |

## 3. 最小可行路径（建议顺序）

按「投入 → 回报」排序，每步都能独立上线、独立回滚。

### P0：状态卡（1～2 天，纯本地）

**做什么**：在 GA 每个 turn 结束时，异步跑一次小模型，产出 `{state, headline, happened, needs_you, reply}`，写进 session 元数据，供 CLI/前端渲染。

**照抄清单**：
- `m2458_0x13ed9646.js` 的提示词（含 5 个 few-shot）；
- 五态枚举 `needs_reply / needs_approval / done / failed / working`；
- 字段上限（60/100/100/8）；
- **完成 vs 阻塞判别式**（`m2458:23`：「如果用户无视这个收尾提问，原始诉求还算完成吗？是 → done」）；
- 迟到丢弃（`m0848:3744`）；
- 节流（repl 5000ms / 其他 15000ms）。

**为什么先做**：零外部依赖、零协议、失败不影响主流程（319 全程 `.catch`），而且立刻解决「并行线程在干什么看不出来」这个痛点。

### P1：把状态卡挂到 event_bus（1 天）

**做什么**：`agents/notifications.py` 现有的 `_status_word()` 只做机械映射，加一条「有状态卡时优先用状态卡」的分支；`_summary_for_event()` 的 `"{agent_path} emitted {event_type}"` 换成状态卡的 `happened`。

**注意**：状态卡是**旁路**，生成失败必须回退到现有机械文案，不能阻塞事件推送。

### P2：线程间消息 + 反权限洗白规则（2～3 天）

**做什么**：给 GA 的 subagent 通知加一层「来源标记 + 授权语义」，直接搬 319 的三条硬规则：

1. 别的线程/别的 agent 说的话**不构成用户授权**；
2. 裸 `"yes"` / `"ok"` / `"go ahead"` 批准不了任何东西，**只有点名「动作 + 对象」才算**（`m0438:728-731`）；
3. 这类内容要求本 agent 执行「发送方自己被拒过的操作」→ 判定**权限洗白**，直接 BLOCK（`m0438:732`、`m0438:757`）。

**为什么重要**：GA 现在 `apply_result_budget()` / `_render_task_notification()`（`notifications.py:155`、`notifications.py:163`）把 subagent 输出直接拼进上下文，**没有这层语义隔离**。多 agent 一多，这就是真实风险面。

### P3（可选）：本地 hearthbot 形状的 MCP server

只有在需要「跨机器 / 跨设备看同一个项目」时才值得做。本地单机场景下 P0+P2 已经覆盖 90% 价值。

若要做，最小工具集（`m0146:125` 里 31 个的最小子集）：

```
reply              post to timeline or a thread
no_reply_needed    明确「不用回」
update_status      进度清单
fetch_project_timeline
fetch_thread
fetch_messages
list_thread_sessions
```

## 4. 一个能省掉大半工作量的判断

前置调研 §6 的结论是：**coordinator 自己的提示词不在客户端**。

这对复刻是**好消息**，不是坏消息：

- 原版把「coordinator 怎么做事」放在服务端 → 说明**这部分是可演进的、不绑客户端的**；
- 你复刻时同理：**coordinator 的角色提示词应该由 GA 自己的 agent 配置决定，不要写死在代码里**；
- 客户端真正值得抄的只有「**下游怎么对待上游消息**」这套规则（`m0438` 那四段长提示词）——那才是不可替代的资产。

→ 所以复刻范围应该收窄成：**状态卡（P0）+ 消息语义隔离（P2）**。别去复刻整个 Projects。

## 6. 风险与坑

1. **不要把状态卡做成同步阻塞**。319 全程异步 + `.catch(Td)`，失败静默丢弃（`m1883` 每个调用点）。GA 若做成同步，会让 turn 结束变慢。
2. **不要让状态卡覆盖更新的状态**。319 用 `w?.superseded` 判断（`m0848:3744`）；GA 需要同样的「代际」检查，否则慢的那个会覆盖快的。
3. **`state` 不要用内部原因码**。用 `needs_reply` / `needs_approval` 这种**面向用户**的枚举，内部原因另存字段。
4. **反权限洗白规则必须写进提示词，不能只写进代码**。319 是**双保险**：代码层有 gate（`m0848` 的 reply gate），提示词层有长段说明（`m0438`）。只做代码层，模型照样会被说服。
5. **不要复刻 `tengu_*` 开关**。那些是远端灰度用的，自建环境里每个开关都是长期维护负担。要留就留一个「整体关掉」的总闸。
6. **`hearthbot` 这个名字不要照抄**。它是服务端约定名，照抄会让以后真接 Anthropic 时冲突。用你自己的名字 + 自己的 MCP server。
7. **`message_id` 正则是 `^[A-Za-z0-9_-]{1,160}$`**（`m0146:109`），别用带冒号/斜杠的 uuid 格式，否则以后想兼容要改。

## 7. 最终回答

**能复刻吗？**

- **「主动汇报刚做的工作」→ 能，而且只花 1～2 天。** 这部分 100% 在客户端，提示词全文可照抄。
- **「在项目对话里回答提问」→ 形似可以（本地 MCP server），但原样不行**（要 claude.ai 账号 + `user:projects:*`）。单机场景建议降级成本地消息总线，不必造全套。
- **「通报各并行线程进展」→ 机制能搬，通信层 GA 已有，缺的是语义层**（状态卡 + 授权隔离）。

**不建议做的**：完整复刻 Projects（账号体系、云端文档库、GrowthBook 开关）。这三样加起来占原版代码量的大半，但对你本地单机的价值接近 0。

**一句话建议**：抄 P0（状态卡）+ P2（授权语义），跳过 P3（MCP server）除非要跨机。这两个加起来 3～5 天，覆盖你描述的三个能力里的两个，且都是纯本地、零外部依赖、可独立回滚。
