## 0. 证据等级与文档边界

本文使用四级证据：

- **S**：源码字面量、字符串、对象字段直接可见，能直接确认。
- **A**：控制流、分支、调用关系直接可见，能确认“发生了什么”。
- **B**：由多处源码交叉推断出的工程意图或生命周期；会标明是推断。
- **C**：仅作为待验证假设，不进入本文结论。

本文区分三个层次：

1. **canonical transcript**：磁盘上的 JSONL 事件流，是会话恢复的事实源。
2. **API projection**：从 canonical transcript 生成、准备发给模型的 messages 视图。
3. **UI projection**：从 canonical transcript 生成、供用户查看的显示行。

这三层不能混为一谈。旧文档里把“显示行”“API messages”“磁盘历史快照”混在一起描述，正是 GA 当前设计容易走偏的地方。

## 1. 先纠正旧调研中的过时点

`docs/20261025-CC-resume机制调研.md` 和 `docs/20261025-GA-resume优化设计.md` 仍有参考价值，但不能直接当作 303 当前源码事实使用：

1. 旧文档中的部分模块名已经与当前 303 模块不一致。例如旧文档写 `m0167_0xc2bf61d.js`，当前实际为 `m0167_0xe836295.js`；旧文档写 `m0673_0xcf1d63e.js`，当前实际为 `m0673_0xf5706ad.js`；旧文档写 `m1309_0xd5ade82.js`，当前实际为 `m1309_0xfc60202.js`。旧模块名只能作为“曾经存在过的线索”，不能作为本轮证据坐标。
2. 旧文档中的“append-only”表述不够精确。更准确的表述是：**在线写入阶段是增量事件追加；compact 之后存在受控的 transcript 物理压缩，会删除 boundary 之前未被保留的行。**
3. 旧文档把 compact 描述成“保留消息快照”也不够精确。303 的 boundary 主要保存 UUID、锚点、保留段信息；真正保留哪些消息，要通过这些 UUID 和 parent 链回到事件流里解析。

因此，本文所有新结论都以当前 `claudecode303/modules/INDEX.tsv`、实际模块文件和字节坐标为证据。

## 2. 结论先行

CC 303 的会话设计不是“每轮保存一份完整 backend history”，而是：

1. **每行一个事件**：user、assistant、system、attachment、progress、summary、mode 等事件分别写进 JSONL。
2. **消息有稳定身份**：普通消息带 `uuid`、`parentUuid`；compact boundary 还会带 `logicalParentUuid`。
3. **写入前按 UUID 去重**：`appendEntry()` 通过 session messages 集合判断该 UUID 是否已经存在。
4. **compact 先追加 boundary 和 summary**：boundary 是事件流中的一个 system 事件，不是把旧历史复制一份另存。
5. **boundary 记录保留范围**：`preservedMessages` / `preservedSegment` 记录 UUID 集合或 head/anchor/tail 锚点，而不是完整消息副本。
6. **之后按 boundary 做物理压缩**：扫描最后 boundary，保留 boundary 后的 transcript、preserved UUID、parent 链和必要的文件历史事件，原子替换文件。
7. **读取时做投影**：API messages 和 UI rows 都是 canonical transcript 的派生视图，不是直接回放“某一轮的完整 history 快照”。
8. **resume 从最后一个 compact boundary 之后重建**：`ni()` 用 `sdt()` 找到最后 boundary，再做切片；summary 与保留段负责承接 compact 前语义。

一句话：**CC 的稳定恢复能力来自“事件身份 + 边界锚点 + 投影”，不是来自“整份 history 反复复制”。**

## 4. 存储模型：一行一个事件

### 4.1 事件写入链路

`insertMessageChain()` 在一次写入中维护消息链的父指针：

```js
let rt = {
  parentUuid: et ? null : kt,
  logicalParentUuid: et ? be : void 0,
  isSidechain: n,
  ...
};
```

其中：

- `et` 表示当前条目是 compact boundary（`Do(Xe)`）。
- 普通条目的 `parentUuid` 指向前一条链尾 `kt`。
- compact boundary 的物理 `parentUuid` 被置为 `null`。
- compact boundary 的 `logicalParentUuid` 指向 compact 前的链尾 `be`。
- 这使“物理新根”和“逻辑上仍接在旧历史尾部”可以同时成立。

证据：`m0459_0xecff32a.js:374565` 起，`rt={parentUuid:et?null:kt,logicalParentUuid:et?be:void 0,...}`。等级 S/A。

### 4.2 单事件追加

`appendEntry()` 负责把单条事件路由到目标 transcript：

- 当前 session 文件存在时直接写；
- 其他 session 先解析已有文件；
- 根据 `tXs[e.type]` 做 `always` / `route-by-agent` / `dedup-transcript` 分派；
- `dedup-transcript` 分支读取 `this.store.sessionMessages(...)`，判断 `q.has(e.uuid)`；
- 未出现过的 UUID 才进入写入队列。

关键片段：

```js
let q = await this.store.sessionMessages(n, s)
...
let Se = !q.has(e.uuid);
if (V || Se) {
  this.enqueueWrite(...);
  q.add(e.uuid);
}
```

证据：字节 `379742` 起的 `appendEntry()`，以及字节 `381508` 附近。等级 S/A。

结论：普通消息不是每轮重写全部历史，而是**以 UUID 为身份的增量写入**。

### 4.3 写入队列不是“同步写一行”

`class uEt` 的字段直接给出批处理参数：

```js
FLUSH_INTERVAL_MS = 100;
MAX_CHUNK_BYTES = 104857600;
```

证据：字节 `347846` 起的类字段，字节 `349651` 附近。等级 S。

工程含义：

- 事件先进入 per-file `writeQueues`；
- 每 100ms drain；
- 按 chunk 批量写；
- 有 `tornTailToSeal` / `tornTail` 修复路径；
- 有多个 session 的写入队列和 mirror 机制；
- 未找到明确 `fsync` 证据，本文不声称 CC 每次 append 都调用了 `fsync`。

这是 B 级工程推断：上述字段和控制流说明有批量队列和尾部修复，但不能外推为“每条消息都持久化落盘后才返回”。

## 5. 事件持久化策略：不同事件不是同一种写盘语义

`var Coo=` 直接列出事件类型到策略的映射（字节 `279412`，等级 S）：

```js
user: "transcript",
assistant: "transcript",
system: "transcript",
attachment: "transcript",
progress: "boundary-cleared",
"file-history-snapshot": "boundary-cleared",
"file-history-delta": "boundary-cleared",
"last-prompt": "boundary-cleared",
"continued-in": "boundary-cleared",
"content-replacement": "accumulate",
"fork-context-ref": "accumulate",
"frame-link": "accumulate",
summary: "last-wins",
"custom-title": "last-wins",
"mode": "last-wins",
"permission-mode": "last-wins",
...
```

`function xoo(e){return Coo[e]??"accumulate"}` 表明未列出类型默认按 `accumulate` 处理（字节约 `280567`，等级 S）。

需要准确理解这些策略：

- `transcript`：普通消息链事件，是 canonical conversation 的主体。
- `boundary-cleared`：与 compact 边界相关，物理压缩时可以按 boundary 规则清理。
- `accumulate`：读取时需要累积/合并，不能简单只保留最后一行；`content-replacement` 属于此类。
- `last-wins`：同一逻辑 key 后续覆盖前面；`summary`、`mode` 等属于此类。

这不是“所有行都同权重 append-only”。CC 对事件有明确的持久化语义和生命周期分类。

## 6. canonical transcript 读取

### 6.1 读取入口

`function yFe()`（字节 `492030`）负责从 session id / 路径解析出目标 transcript，再调用 `MZ()`：

```js
let w = await MZ(n, {storageV5: S, precedingEntries: s});
```

`async function MZ()`（字节 `488607`）是核心 canonical loader。它不只是 `JSON.parse` 整个文件，而会根据文件大小和存储后端分流：

- v5 storage 后端读取；
- 大文件使用流式/裁剪扫描；
- 小文件走普通读取后逐条处理；
- 处理 torn tail；
- 折叠 `content-replacement`；
- 处理 `last-wins` 元事件；
- 维护 session messages 集合和 session metadata；
- 最终返回消息 map 及元信息。

证据：`yFe` 字节 `492030`，`MZ` 字节 `488607`。等级 S/A。

### 6.2 小文件路径和大文件路径

`MZ()` 里可以看到两条路径（字节 `488607` 附近）：

- `q.size > Fne` 时走分页/扫描路径，调用 `Fso(...)`、`DEt(...)` 等；
- 否则读取完整内容后按 `DTt()`、`Hle()` 等处理。

这说明 CC 对长 transcript 的读取本身也有性能分层，不是“每次 resume 都把整个文件映射成一个完整数组再重放”。

具体阈值 `Fne` 和读法属于实现细节，本文不把它外推成固定产品承诺；从控制流可以确认存在“大文件走不同读取路径”的设计（A）。

### 6.3 last-wins 与内容替换

`MZ()` 的 `processEntry` 会把不同类型分到不同容器：

- 普通消息进入 `messages`；
- `content-replacement` 进入 replacement 容器；
- `fork-context-ref` 进入单独引用容器；
- `summary` 等 last-wins 类型在 fold 阶段处理。

这与 §5 的策略表一致。关键工程含义是：

> canonical transcript 不是“原样把所有行交给模型”，而是先经过 fold/merge，再生成 API 视图。

### 7.2 compact 主流程

`async function hbr()`（字节 `3182263`，行 2972）是 compact 主流程。直接可见的步骤包括：

1. 执行 PreCompact hooks；
2. 通过 `Xwn(...)` 生成 summary；
3. 通过 `MV(...)` 生成 boundary；
4. 生成 summary message；
5. 生成附件/hook 结果；
6. 组装 compact result；
7. 返回 boundary、summaryMessages、messagesToKeep、attachments、hookResults 等。

关键片段：

```js
let Gn = MV(S ? "auto" : "manual", Te ?? 0, e.at(-1)?.uuid);
...
let dn = [Re({
  ...GZ(Lt, {...}),
  isCompactSummary: true,
  isVisibleInTranscriptOnly: true

...
Gn.compactMetadata.postTokens = qn;
Gn.compactMetadata.durationMs = tn;
```

证据：`hbr` 字节 `3182263` 起；summary 的 `isCompactSummary:true` / `isVisibleInTranscriptOnly:true` 同段可见。等级 S/A。

这里必须注意：

- compact 生成的 summary 是一条 user 形态的摘要消息，不是“把完整旧历史写进 summary”。
- summary 带 `isCompactSummary:true` 和 `isVisibleInTranscriptOnly:true`，用于 API/UI 投影区分。
- boundary 和 summary 是后续重建会话的锚点。

### 7.3 compact 结果如何组合

`function fU()` 的完整版本由调用点可见：

```js
[
  boundaryMarker,
  ...summaryMessages,
  ...replacement,
  ...messagesToKeep,
  ...attachments,
  ...hookResults
]
```

而磁盘最小版本 `Tuo()` 只包含：

```js

  ...summaryMessages,
  ...replacement,
  ...attachments,

```

证据：`Tuo()` 在字节 `3181165`，`fU()` 的调用点在字节 `3133833`、`3140289`、`3143785`。等级 S/A。

这是一个非常重要的设计点：

- **发给模型的 compact result** 可能需要 `messagesToKeep`；
- **刚落盘的 compact 最小记录** 不一定包含所有保留消息，因为保留消息仍可从原 transcript 的 UUID 读取；
- boundary 负责“指路”，不是负责“复制整段内容”。

换句话说，`messagesToKeep` 是 compact 计算过程的产物，不等于要新建一份完整 history 快照。

## 8. preservedMessages 与 preservedSegment

### 8.1 直接字段

`function xet()`（字节约 `3181400`，行 2970）返回：

```js
{
  ...e,
  compactMetadata: {
    ...e.compactMetadata,
    ...y.length > 0 && {
      preservedSegment: {
        headUuid: y[0],
        anchorUuid: n,
        tailUuid: y.at(-1)
      }
    },
    preservedMessages: {
      anchorUuid: n,
      uuids: y,
      allUuids: h
    }
  }
}
```

其中：

```js
let h = r.map((S) => S.uuid);
let y = Fxe([...r], s).map((S) => S.uuid);
```

证据：字节 `3181400` 附近；字段名和赋值均为 S 级。

### 8.2 两个 UUID 集合的区别

- `allUuids = h`：compact 前输入候选消息的原始 UUID 全集。
- `uuids = y`：经过 `Fxe(...)` 过滤后，仍应保留在恢复视图中的 UUID。
- `anchorUuid = n`：preserved 段的锚点（通常与 summary 或 boundary 的上下文关联）。
- `preservedSegment`：当 `y` 非空时，记录 head/anchor/tail 三个端点，便于按 parent 链走段。

关键结论：

> `preservedMessages` 是 UUID 索引，不是把消息正文复制到 compact boundary 中。

这正是与 GA 当前 `backend_history_after` 完整快照的根本差异。

### 8.3 物理压缩如何使用这些 UUID

`function kLe()`（字节 `283298`）扫描 transcript，找到最后一个 compact boundary：

```js
if (Roo(ot)) {
  if (r = n, s = ot.compactMetadata, !ot.compactMetadata?.preservedSegment && !ot.compactMetadata?.preservedMessages) {
    h = n;
  }
}
```

然后：

- 如果存在 `preservedMessages`，逐个 UUID 查找 `y.get(ze)`；
- 找不到时返回 `{kind:"abort", reason:"preserved_uuid_missing"}`；
- 如果存在 `preservedSegment`，从 `tailUuid` 沿 `parent` 链向上走到 `headUuid`；
- 走链失败时返回 `{kind:"abort", reason:"preserved_walk_broken"}`；
- 保留 boundary 之后的所有 transcript；
- 保留被标记的 file-history snapshot/delta；
- 对 last-wins 元事件只保留最终有效行；
- 计算可回收字节数；
- 输出删除索引集合。

证据：`kLe()` 字节 `283298`；`preserved_uuid_missing` / `preserved_walk_broken` 字符串直接可见。等级 S/A。

### 8.4 物理压缩执行

`async performCompactTranscript()`（字节 `368246`，行 215）确认了真正的文件级压缩：

1. 读取源文件 size；
2. 取头部、中部、尾部快照，用于检测并发修改；
3. 检查尾部是否完整（`snapshot_mid_line`）；
4. 调用 `kLe()` 生成保留计划；
5. 写临时文件 `${file}.compact.tmp.<random>`；
6. 只输出 `SLe(plan)` 允许保留的行；
7. 校验源 inode/size 未变化；
8. `await Oe.sync()`；
9. 再次校验源文件；
10. 原子 rename 替换；
11. 记录 `bytesBefore` / `bytesAfter`。

证据：`performCompactTranscript()` 字节 `368246` 起；`snapshot_mid_line`、`source_changed`、`rename` 附近控制流均为 A/S 级。

因此，准确说法是：

> CC 303 的在线写入是增量事件流；compact 后会在满足条件时对 transcript 做受控物理压缩，删除 boundary 前未被保留的行。它不是“永远 append-only”，也不是“每轮复制完整 history”。

```js
  this.store.localGcEnabled &&
  this.sessionFile &&
  this.storeFence === void 0 &&
  this.compactAwaitingSummary === void 0 &&
```

证据：字节约 `355370`。等级 S/A。

工程含义（B）：物理压缩不是每次 compact 都立即发生，而是由 local GC 开关、待摘要状态、累计字节数等条件控制；compact 生成 boundary/summary 是主路径，物理压缩是后续维护路径。

## 9. API projection：`cnn()`

### 9.1 代码

`function cnn()`（字节 `2240601`，行 1952）：

```js
function cnn(e) {
  let n = e.length > Rx,
      r = n ? e.slice(-Rx) : e,
      s = n ? Math.max(r.findIndex(unn), 0) : 0;
  return r.slice(s).map(dnn);
}
```

`Rx=4096`，来自 `m0064_0xe564fef.js`。

`unn()` 的定义：

```js
function unn(e) {
  let { role: n, content: r } = e.message;
  let s = Array.isArray(r) && r.some((h) => h.type === "tool_result");
  return n === "user" && !s;
}
```

`dnn()` 只保留：

```js
{
  role: e.message.role,
  content: clone(e.message.content)
}
```

证据：`unn` 字节 `2240475`，`cnn` 字节 `2240601`。等级 S。

### 9.2 行为

1. 先取最后 `Rx=4096` 条内部消息。
2. 如果被裁剪，则从窗口内找第一个“真正的 user 消息”（不是 tool_result 包装的 user 行）。
3. 从该 user 消息开始切片。
4. 把内部消息压成 `{role, content}`。
5. 后续才进入 API 请求构造。

注意：`cnn()` 是**只读投影**，`e.slice()` / `r.slice()` 都是新数组或浅切片；没有原地 `pop()`。

### 9.3 与工具配对的关系

`Yhe()` 和 `rer()` 负责 UI 侧工具行；API 侧 `cnn()` 只负责消息投影。工具请求结果的配对、补齐、去孤立结果，在 `requestMessages` 和请求前处理链路中完成；本文没有把 `cnn()` 误写成完整工具修复器。

证据：`requestMessages` 的调用点在字节 `2256211` 附近；`cnn(r.requestMessages(y))` 是 API 路径。实现绑定见 `m1635_0x101da730.js` 字节 `180019`：`requestMessages:(R)=>Myn(R,this.computeTools())`；`m1596_0x1017d8fa.js` 字节 `133556` 定义 `var Myn=(e,n)=>bC(ni([...e]),n)`，即先做 boundary 切片，再进入请求消息构造。等级 A。

## 10. UI projection：`rer()` 与工具行重建

`function rer()`（字节 `2255486`，行 1953）：

```js
function rer(e, n) {
  let r = [], s = new Map(), h = Xhe(s, n);
  for (let y of e.toReversed()) {
    if (r.length === Rx) break;
    let S = Yhe(y);
    if (!S) continue;
    for (let w of S.toolResults ?? []) s.set(w.tool_use_id, w);
    r.push({...S, toolUses: S.toolUses.map(h)});
  }
  return r.reverse();
}
```

### 10.1 `Yhe()` 做什么

`function Yhe()`（字节 `1406245`，行 860）：

- assistant：提取 text 和 tool_use；
- user：
  - 跳过 `isMeta === true`；
  - 跳过 `isVirtual === true`；
  - 提取 text 和 tool_result；
  - tool_result 保留 `tool_use_id`、错误状态、可选 meta。

### 10.2 `rer()` 做什么

1. 从后向前遍历最多 `Rx=4096` 条消息。
2. `Yhe()` 把内部消息变成 UI 行。
3. 先把 tool_result 放进 map。
4. 再回溯给前面的 tool_use 补上 result。
5. 最后 reverse，恢复时间顺序。

关键结论：

- UI 视图和 API 视图不是同一份数据；
- UI 工具行是“tool_use + tool_result”配对后的合成行；
- UI 投影最多看 4096 条内部消息，不代表 canonical transcript 只有 4096 条；
- UI 视图不使用 `backend_history_after` 这种整段快照。

证据：`Yhe` 字节 `1406245`，`rer` 字节 `2255486`。等级 S/A。

### 11.1 找最后一个 compact boundary

`function Uxe()`：

含义：恢复时从最后一个 compact boundary 开始截取，boundary 之前的历史由 summary 和 preserved UUID 负责承接。

### 11.3 `mwr()` 的补充判断


## 12. UUID 去重、分支与 fork

### 12.1 UUID 去重

`appendEntry()` 的 `dedup-transcript` 分支以 `q.has(e.uuid)` 判断是否已存在；只有不存在才 `enqueueWrite` 并 `q.add(e.uuid)`。

`async function ter()`（字节 `2255058`）则负责把磁盘 transcript 与内存 / held transcript 合并：

```js
let y = new Set(h.map((S) => S.uuid));
return [...r.filter((S) => !y.has(S.uuid)), ...h];
```

其中 `r` 是读取到的磁盘消息，`h` 是当前内存/held 消息；以 UUID 去重，内存优先。

证据：`ter` 字节 `2255058`。等级 S/A。

### 12.2 rewind 不是用 history 深度相等推断

CC 的 resume/rewind 相关逻辑依赖：

- `uuid`；
- `parentUuid`；
- `logicalParentUuid`；
- `leafUuid`；
- `last-prompt` 的 `leafUuid`；
- 必要时重写/追加分支 meta 事件。

`TOt()` 直接构造 `last-prompt` 事件：

```js

  lastPrompt: ...,

  explicit: true,
  ...n?.rewound && {rewound: true},

```

证据：字节 `388847` 附近。等级 S。

这里不把 CC 的具体 UI rewind 反馈链路外推为 GA 的实现细节；能确认的是：**它使用事件身份和 leaf 指针，而不是比较两份完整 history 是否深度相等。**

### 12.3 fork/branch

`m1103_0xfa5da58.js` 中可见与 `content-replacement` 复制相关的逻辑，说明 fork/branch 不是简单复制一份“最终 UI 消息列表”，而是按事件身份复制/引用内容替换记录。该模块不是主 compact 模块，本文只把它作为“content-replacement 有独立生命周期”的辅助证据（A/B）。

## 13. 为什么 CC 能做到稳定 resume

把前面的机制合起来：

1. **canonical 事件有唯一身份**：UUID 能避免重复写入，也能把工具调用和结果重新关联。
2. **parent/logical parent 分离**：compact 产生物理新根，但逻辑上仍能追溯到旧链尾。
3. **boundary 记录保留范围**：preserved UUID/anchor/head/tail 是恢复的索引。
4. **物理压缩有前置校验**：源文件变化、尾部半行、preserved UUID 缺失都会 abort，不会悄悄写出错误文件。
5. **API/UI 是投影**：4096 条窗口、真实 user 起点、工具行配对都可以独立演进，不会反过来篡改 canonical 事件。
6. **列表页和详情页分离**：列表只需要 preview/rounds/metadata，不需要重建完整历史。

## 16. 对 GA 的直接启示

GA 不需要、也不应该照搬 CC 的全部内部复杂性。但至少应采用以下不可替代的原则：

1. canonical transcript 只追加事件，不在每个 turn 里复制整份 backend history。
2. 每条消息有 UUID，至少要有稳定的事件序号和 turn 关系。
3. compact 保存 boundary + summary + preserved UUID/锚点，而不是完整 `backend_history_after`。
4. API history 从 canonical entries 投影生成，硬裁剪只作用于请求副本。
5. UI 显示从 canonical entries 或 UI 事件投影，不把 `turns` 的完整快照当显示源。
6. rewind 用显式事件和锚点，不用“前后 history 深度相等”推断。
7. 恢复要同时恢复工作记忆和 handler 状态，而不是只替换 backend.history。
