## 0. 先回答你的两个问题

### 问题一：CC 源码里有没有比 Docker 容器更轻量的沙箱？

**有，而且它用的不是"轻量容器"，是另一个维度：OS 级的「单进程/单命令」沙箱。**

| 维度 | 你同事那套（Docker 容器） | CC 这套（bwrap / Seatbelt / srt-win） |
| --- | --- | --- |
| 隔离单位 | 一个用户一个容器，容器活得久 | **一条命令一次 fork+exec**，命令结束即消失 |
| 启动成本 | 秒级（起容器） | **毫秒级**（只是多一层 exec，无 init、无镜像层） |
| 隔离手段 | namespace + cgroup + 独立网络栈 + 独立 rootfs | mount namespace + 文件挂载遮罩 + seccomp + 代理 |
| 有没有"镜像" | 有 | **没有**（直接复用宿主 rootfs，用 `--ro-bind / /` + 遮罩改写视图） |
| 有没有独立 IP | 有 | **没有**（`--unshare-net` 直接断网，要网络就塞代理） |
| 资源上限 | cgroup（CPU/内存/pids） | **完全没有**（本地沙箱里 0 处 cgroup/rlimit，见 §5.4） |
| 跨用户隔离 | 是（本来的目的） | **不是**（Linux 下 uid 不换，见 §4.1.1） |

一句话：**CC 的沙箱解决的是"同一个用户，别让 agent 把机器搞坏/把密钥读走"；不是"用户 A 别碰用户 B"。**
这两件事需要的能力不一样，所以**它不是你那套方案的替代品，但可以叠在它里面**（§8/§9 给具体做法）。

### 问题二：你那边应该"一个沙箱 for all users"还是"一个用户一个沙箱"？

**必须一个用户一个**（你同事当初也这么做，只是他那句"一个沙箱 for all users"如果指的是容器，那就有问题）。
CC 的源码恰好从反向证明了这一点：CC 的沙箱之所以敢"一条命令一个、随便起"，是因为**它默认整个进程只有一个人用**。
一旦你把 CC 这套沙箱拿去服务多个用户，**它挡不住跨用户读取**——因为：

- Linux 下 `--unshare-user` **没有 `--uid`**，映射进去还是当前 euid（`m0302:33920`，全模块 `--uid` 0 处命中）；
- 它靠的是"路径遮罩"（`--tmpfs` 挖洞 + `--ro-bind` 回填），**不是权限位**——同 uid 的另一个进程完全可以绕开你的挂载视图。

所以正确的关系是：

```
你的容器（用户隔离，uid/网络/资源/持久化边界）
   └─ 容器内 CC 式 per-command OS 沙箱（纵深防御：就算 prompt 注入成功，
        单条命令也只能碰 allowWrite 里的路径、只能访问 allowlist 里的域名）
```

## 0.5 一句话结论：选什么

**底座选容器，一个用户一个容器。运行时不要用裸 `runc`/Docker 默认，按优先级：gVisor（runsc）→ Firecracker → 加固后的 runc。**

> ⚠️ 两个前提先摆出来，别被"gVisor"这个词误导：
> 1. **gVisor 只能在 Linux 宿主上跑**，没有 Windows 原生版本（见"平台"一节）。
> 2. **它不比 Docker 轻，比 Docker 默认的 `runc` 重**——换来的是隔离强度，不是性能（见下一节）。

这个结论由**威胁模型**决定，不是因为"CC 没做所以不能做"：

> 你的工具里有 **Python Code Run 和 Shell**，执行的是**不可信的用户代码**。
> 裸 `runc` 与宿主**共享内核**——一次容器逃逸就是**全租户沦陷**，比跨用户读文件严重一个量级。

三个必须由容器（而且是换内核的容器）来提供、CC 那套一个都给不了的能力：

| 必需能力 | 为什么必需 | 裸 runc | gVisor | CC 的 bwrap/Seatbelt |
| --- | --- | --- | --- | --- |
| **独立内核攻击面** | 用户代码可能带内核 exploit | ❌ 共享宿主内核 | ✅ 用户态内核（Sentry）拦截 syscall | ❌ 共享宿主内核 |
| **uid / user ns 真正切换** | 跨租户文件权限边界 | ✅ | ✅ | ❌ `--unshare-user` 不带 `--uid`（§4.1.1） |
| **cgroup 资源上限** | 一条死循环变量拖垮全机器 | ✅ | ✅ | ❌ 0 处命中（§5.5） |
| **独立 rootfs** | 不共享宿主 inode | ✅ | ✅ | ❌ `--ro-bind / /`（§4.1.2） |
| **独立 netns** | 跨租户网络不可达 | ✅ | ✅ | ✅（唯一对等的一项） |

### 运行时怎么选

| 选项 | 隔离强度 | 运维成本 | 何时选 |
| --- | --- | --- | --- |
| **gVisor（`--runtime=runsc`）** | 高（用户态内核） | **架构改动低**（换个 runtime 名），**运行开销高于 runc**（见下节） | **首选**，前提是宿主是 Linux 且接受性能代价 |
| Firecracker / microVM | 最高（硬件虚拟化） | 中——要自己管 VM 生命周期 | 有多租户强合规要求、或要高密部署时 |
| 加固后的 runc | 中 | 低 | **只在"用户是你信任的同事"时**够用；对不可信代码不够 |
| 不用容器（共享进程 + bwrap） | 低 | 极低 | ❌ **不适用于你**（见下） |

### gVisor 不是「更轻的 Docker」，它更重

**先把范畴说清**：gVisor 不是 Docker 的替代品，它是 **Docker 的一个 OCI runtime**，和 `runc` 平级。
所以「gVisor vs Docker」不成立，能比的只有「gVisor vs runc」。

| 对比 | 谁更轻 | 差在哪 |
| --- | --- | --- |
| gVisor vs **runc**（Docker 默认） | **runc 更轻** | gVisor 多一个用户态内核进程（Sentry + Gofer），应用的每次 syscall 都要被拦截再转发；启动更慢、常驻内存更多、**syscall 密集的 workload 明显变慢** |
| gVisor vs **Firecracker** | gVisor 更轻 | 不用起 VM、不用管内核镜像和引导流程 |
| gVisor vs **CC 的 bwrap**（§4.1） | bwrap 轻得多 | bwrap 只是一层 exec 包装，零常驻进程；gVisor 是一整套用户态内核 |

**它换来的是隔离强度**：应用的 syscall 由用户态内核实现，不直接落到宿主内核上，
所以内核 exploit 打不到宿主。**这是 runc 给不了的，也是你跑不可信用户代码时真正需要的那一项。**

**但代价是真金白银的性能开销**，而且——

> **具体倍数必须你自己在同一台机器、同一份 workload 上压测。**
> 本文是纯静态源码调研（§10.1：L0，无运行时数据），**不替你给性能数字**。
> 谁给你一个"gVisor 只慢 5%"的通用结论，都不要信——它高度依赖 workload 的 syscall 密度。

**所以取舍是明确的**：

- 跑**不可信用户代码**（你的情况）→ 接受性能代价，换内核隔离。**值得。**
- 跑**可信的自家任务**（批处理、CI）→ 用 runc，速度优先。

### 平台：gVisor 只在 Linux 上跑

`runsc` 是 Linux syscall 的用户态实现，**没有 Windows 原生版本**，也不能充当 Windows 容器的 runtime。

- **你的部署目标本来就是 Linux Host**（你自己的方案文档里画的就是 `Linux Host` + `Docker Engine`），
  所以**生产环境不受影响**。
- **Windows 只影响本地开发**。三个可行办法：
  1. **在 WSL2 的 Linux 发行版里自己装 Docker + runsc**（WSL2 是 Linux 内核，能装）。
     注意：**Docker Desktop 自带的 daemon 加不了自定义 runtime**，要用 distro 内独立安装的 engine。
  2. **本地用普通 runc 开发**，把隔离相关的验证放到 Linux CI / 预发环境。
  3. **本地直接开一台 Linux VM**（Hyper-V / VirtualBox）当开发环境。
- **Windows 容器（process / Hyper-V isolation）与 gVisor 无关**：那是 Windows 自己的容器模型；
  其中 **Hyper-V isolation 本身就是 VM 边界**，隔离强度不低于 gVisor，但只能在 Windows 宿主上跑 Linux 无关的工作负载。

**部署时两个必须提前确认的坑**（不确认就会退化到最慢路径）：

| 坑 | 症状 | 怎么办 |
| --- | --- | --- |
| `runsc` 的 **KVM platform 要 `/dev/kvm`** | 跑在 VM 里又没开嵌套虚拟化 → 退到 **ptrace platform**，性能差距进一步拉大 | 宿主开嵌套虚拟化并暴露 `/dev/kvm`；用 `runsc --platform=kvm` 验证 |
| **不实现全部 syscall** | 某些 ioctl / `/proc` 读取 / GPU 相关调用直接失败 | Python + shell 一般没问题；以后要加 GPU 或特殊调用，先验证再上 |

### 容器里还要不要 CC 那套？

**可选，而且不是隔离需求，是"体验 + 防误伤"需求。** 优先级（§8.2 有详细论证）：

1. `--unshare-net` + 域名白名单代理 —— 容器已经有 netns，这层是"在容器内再防 SSRF/内网扫描"
2. 凭据 mask（§5.1）—— 防 token 进日志/进公网，与容器正交
3. `<sandbox_violations>` 结构化上报（§5.2）—— 让"被挡了"变成可解释反馈

**不要**在容器里再套 bwrap 的挂载遮罩那套（§4.1.2）——你的 rootfs 已经是隔离的，收益很小、复杂度很高。

### 唯一能推翻"一用户一容器"的情况

只有当**每次执行都是短时、无状态、且用户之间不需要持久工作区**时，才可以改成
"共享沙箱池 + 每次执行后销毁"。但你的方案里有 `/workspace` 持久化、有 shell 会话、有 MinIO 同步——
**这些前提不成立**，所以必须一用户一容器（§7.1 用 CC 的源码反证了"一个沙箱 for all users"为什么不安全）。

## 2. 沙箱包住了什么、没包住什么（这是最关键的一节）

**沙箱只包 Bash / PowerShell 这两条"命令执行"通道。**

| 通道 | 走沙箱？ | 证据 |
| --- | --- | --- |
| Bash 工具 | ✅ 默认进沙箱 | `m0591:143767` / `m0591:143772` 两个 wrap 调用点 |
| PowerShell（Windows） | ✅ | 同上；PowerShell 分支见 `m0591:143754`（`if (r === "powershell")` → `a2t` 重写命令） |
| Read / Write / Edit / Glob / Grep | ❌ **不走** | 文件工具模块 `sandbox` 计数 0（见 §11 错误 6） |
| WebFetch / WebSearch | ❌ 不走 | 设置文档原文：`strictAllowlist` "Enforced for sandboxed commands only — in-process tools such as WebFetch are not gated by this setting"（`m0094:4665`） |
| 本地 hooks | ❌ 不走 | hook 命令是 `shell: true` 直接 spawn（`m0591:159300`），`C1()`（`m0591:159036`–`159606`，内含 4 处 `AIe(` 直接 spawn）内 0 处 `wrapWithSandbox` |
| plugin monitors | ❌（明确写了） | `m0094:3531`：`persistent Monitor tasks (unsandboxed, same trust tier as hooks)` |
| MCP server 子进程 | ❌ 不走（与 hooks 同信任层） | `m0302`（沙箱实现模块）内 `StdioClientTransport` / `StdioServerParameters` 计数 **0** |
| **云端会话里代跑的项目 hook** | ✅（这是唯一给 hook 上沙箱的场景） | `m0591:50843` `if (h.mode === "locked") y = await Ge.wrapWithSandbox(...)` |
| 沙箱内 git 写（供 agent 用的内部 git） | ✅ | `m1688:298`、`m0591:219565` 两个额外 wrap 点 |
| 沙箱本体的 CLI 子命令 | — | `claude sandbox install/status/uninstall`（`m0975:1405`、`m0975:1410`） |

**推论**：在你自己那套多租户里，如果照搬 CC 的边界，**Read/Write 工具必须自己再做一层路径校验**。
CC 之所以敢让 Read/Write 裸奔，是因为它还有权限系统（permission rules）单独管这两条，两条线是互补的：
沙箱管"命令里能碰到什么"，permission 管"工具调用本身批不批"。

## 4. 三套平台实现逐条拆解

### 4.1 Linux：bubblewrap + seccomp + socat 代理（最值得抄的一套）

#### 4.1.1 bwrap 命令行：只用 3 种 namespace，不换 uid

`wrapWithSandbox` 的 Linux 分支从一条基线开始：

```js
Et = ["--new-session", "--die-with-parent"],     // m0302:33858
```

随后按需追加（`m0302:33858`–`33956`）：

| 开关 | 行号 | 作用 | 备注 |
| --- | --- | --- | --- |
| `--new-session` | 33858 | 脱离控制终端，防 TIOCSTI 注入 | 总是加 |
| `--die-with-parent` | 33858 | 父进程死则子进程死 | 总是加 |
| `--unshare-net` | 33883 | **直接断网**，要网络只能走代理 | 需要网络限制时才加 |
| `--bind <sock> <sock>` ×2 | 33886 | 把 HTTP/SOCKS 代理的 unix socket 塞进去 | 与 `--unshare-net` 配套 |
| `--setenv http_proxy=...` | 33887–33898 | 让子进程以为有网 | `Opt(3128, 1080, ...)` 生成后逐个 `--setenv` |
| `--dev /dev` | 33914 | 挂 devtmpfs | |
| `--unshare-pid` | 33914 | 独立 PID ns | |
| `--unshare-user` + `--cap-drop ALL` | 33920 + 32860 | 用户 ns + **丢掉所有 capability** | 见下 |
| `--proc /proc` | 33924 | 新 /proc（可关，见 `enableWeakerNestedSandbox`） | |
| `--disable-userns` | 33929 | 禁止子进程自己再建 user ns | 需要 bwrap ≥0.8.0 且非 setuid |

**关键：`--unshare-user` 后面只跟 capability 开关，没有 `--uid`。**
`zgs()`（`m0302:32855`）整个函数体只返回 `["--cap-drop","ALL"]`，唯一例外是
"以 root 运行且有 CAP_SETFCAP 且用了 seccomp helper"时追加 `--cap-add CAP_SETFCAP`（`m0302:32863`）。
全模块 `--uid` 命中 **0** 次。

> **这就是它不能做多租户隔离的根本原因**：user namespace 只是让你能"看起来是 root"，
> 实际文件权限检查用的还是**宿主 uid**。两个同 uid 的沙箱进程，靠的是各自的 mount 视图互不可见；
> 一旦某个进程能绕过挂载（比如你容器里给了它别的能力、或者它进了宿主 mount ns），遮罩就失效了。
> 而 Docker 容器是**换 uid + 换 user ns + 换 net ns**，那是另一回事。

`/proc/self/status` 还会被读来判断当前进程有没有 capability（`m0302:32840`），
以 root 跑又没 CAP_SETFCAP 时给出一条明确的失败原因（`m0302:32867`："every sandboxed command fails while writing a uid map"）——
**这正说明它确实在写 uid map（user ns），只是不改 uid**。

#### 4.1.2 文件可见性：`--ro-bind / /` + `--tmpfs` 挖洞 + `--ro-bind` 回填

这是整套里最巧的部分。**没有独立 rootfs，直接把宿主根以只读方式整体挂进来**，然后：

1. 需要写的路径 → `--bind`（可写绑定，`m0302:33282` 的 `S.flatMap((w) => ["--bind", w, w])`）
2. 需要隐藏的目录 → `--tmpfs`（挖空，`m0302:33291` / `33809`）
3. 挖空后又要保留的 → `--ro-bind` 回填（`m0302:33329` / `33810` / `33814`）
4. 单个文件要挡 → `--ro-bind /dev/null <path>`（`m0302:33644` / `33758`），注释原文是
   `Mounted /dev/null at symlink ... to prevent symlink replacement attack`（防符号链接替换攻击）
5. 根目录被整体 deny 时 → 先把 `/` 只读绑进来再逐个处理（`m0302:33472` `A.push("--ro-bind", "/", "/")`）

**为什么这比容器轻**：不需要准备镜像、不需要 chroot、不需要 pivot_root，所有内容都是宿主现成的 inode。

**代价（你在多租户里要特别注意）**：`--ro-bind / /` 意味着**宿主的整个文件系统对沙箱可见**，
安全全靠"遮罩列表对不对"。这在一个用户一台机器上没问题，**在多租户共享宿主上完全不可接受**——
因为遮罩表是 Claude Code 按"当前用户的 home/cwd"算出来的，它不知道别人的目录在哪。

配套的复杂度控制：

| 常量 | 值 | 位置 | 含义 |
| --- | --- | --- | --- |
| `e1` | 4096 | `m0302:32888` | 单个参数超过 4 KiB 就改走匿名文件（`/proc/self/fd/N`） |
| `Hf` | 9000 | `m0302:32889` | bwrap 参数个数硬上限（约 3000 个挂载） |
| `m1` | 256 | `m0302:33956` | denyRead glob 展开后超过 256 个挂载就告警（每个挂载都是一次 bwrap mount） |
| `YE` | 3 | `m0302:32590` | `mandatoryDenySearchDepth` 默认 3 —— 内置写保护向上搜几层 |

`I8()`（`m0302:32948`）就是那个"参数太长改用文件"的实现：超限时用
`/bin/sh -c 'exec N<"$1" && shift && exec "$@"' srt-args <fd> bwrap ...` 的方式把参数表从一个 fd 读进去
（`m0302:32965`）。

#### 4.1.3 seccomp：只挡 AF_UNIX socket，而且默认是关的

- 内嵌 helper 的路径是 `/proc/self/fd/3`，argv0 固定 `apply-seccomp`（`m0302:39818`–`39821`，`Kce = 3` 在 `39802`）。
- **但内嵌开关 `T4()` 直接 `return !1`（`m0302:39805`–`39806`）** —— 也就是说是死代码，永不启用内嵌。
- 实际走 `cwr()` → `{ applyPath: '/proc/self/fd/3', argv0: 'apply-seccomp' }`，再由
  `F8()`（`m0302:33216`）检查 `nwr()` 找不找得到这个二进制；找不到就**只告警、继续跑**：
  `seccomp not available - unix socket access not restricted`（`m0302:33039`）。
- 只在 `allowAllUnixSockets` 为假时应用（`m0302:33866`），日志 `Applying seccomp filter for Unix socket blocking`（`m0302:33865`）。
- 能力很窄：注释写得很直白 —— 只 block `socket(AF_UNIX, ...)`，**32 位 x86 不支持**，因为
  `socketcall()` 能绕过（`m0302:32491`）。
- 二进制的解析顺序：显式路径 → 包内 `vendor/seccomp/<arch>/apply-seccomp` → 全局
  `@anthropic-ai/sandbox-runtime` 安装位置（`m0302:32481`）。
- **注意 seccomp 还被用来做违规监控的通知通道**：`SRT_OBSERVE_SOCK` 环境变量 + 一个 unix socket
  （`m0302:33868`），由 `k1()`（`m0302:34617`）起的 net server 收 JSON 行，
  把 `{path, syscall}` 转成"违规记录"。

#### 4.1.4 网络：断网 + socat 双层代理 + 每命令域名清单

```
子进程 --unshare-net（真断网，m0302:33883）
   ↓ --bind 把宿主侧 unix socket 塞进沙箱 + --setenv http_proxy/https_proxy（m0302:33886–33898）
socat（宿主侧进程，m0302:33226 的 $8() 组装：TCP6/TCP4-LISTEN:3128 / :1080 → UNIX-CONNECT:<sock>）
   ↓
Mux proxy（HTTP + SOCKS 同端口，m0302:36588 "Mux proxy (HTTP+SOCKS) listening on localhost:"）
   ↓ 按 allowedDomains / deniedDomains 判定（`_I()` = `m0302:36402`，判定顺序见下）
公网
```

`_I()`（`m0302:36402`）的判定顺序是硬编码的六步，源码里每步都有日志：

1. `Ve.network.deniedDomains` 命中 → 拒（`m0302:36409`）
2. 开了 `tlsTerminate` 且不在 `excludeDomains` → 走 SOCKS 隧道判定，refuse 则拒（`m0302:36411`）
3. `Ve.network.allowedDomains` 命中 → 放（`m0302:36415`）
4. `strictAllowlist` 开 → 直接拒（"host is not on the allow list"，`m0302:36417`）
5. **该命令自己的** `allowedDomains` 命中 → 放（"Allowed by per-command rule"，`m0302:36419`）
6. 都不中 → 交给 `askCallback` 问用户（`m0302:36422` 起），答非布尔也按拒绝处理

**「per-command 规则」就是 §4.1.4 那个 `allowed_domains` 参数**——它在第 5 步才被考虑，
所以只能"在配置的 allowlist 之外再放宽一点点"，不能绕过 `deniedDomains` 和 `strictAllowlist`。

`$8()`（`m0302:33226`）原文细节：分别起 3128（HTTP）和 1080（SOCKS）两个 socat 监听，
`fork,reuseaddr,backlog=4096`，先试 `TCP6-LISTEN` 失败再退 `TCP4-LISTEN`；起完再 exec 真正要跑的命令，`trap` 里 kill 两个 socat。
也就是说**代理是命令的兄弟进程，命令退出代理就死**——没有常驻守护。

- 代理端口范围默认 `[60080, 60089]`（`m0302:34712` 的 `var zf = [60080, 60089]`）。
- 被挡住的响应带固定标记 `blocked-by-sandbox-runtime`（`m0302:29780`），并且会给模型写一段"别重试"的理由。
- 可选 **MITM**：`tlsTerminate`（`m0094:4678`）—— 进程内 TLS 终止，让代理能看到 HTTPS body；
  macOS 用临时 CA，Windows 用持久 CA（因为临时 CA 过不了 sandbox 的信任检查）。
- **每命令粒度**：Bash 工具可以带一个 `allowed_domains` 参数（`m0591:57039`–`57043`，上限 100 条、每条 260 字符），
  用于"这一条命令临时需要访问某域名"。校验很严：不许 loopback/映射地址、
  必须与沙箱实际 dial 的规范形式一致（`m0591:57066` 起的三段错误文案）。这个能力**只在真进沙箱时生效**，
  否则报错 `allowed_domains applies only to a command that runs in the sandbox`（`m0591:57066`）。

#### 4.1.5 违规上报：`<sandbox_violations>` 块

`ej()`（`m0302:37495`）把本命令的违规记录拼成一段 XML 追加到 stderr 后面：

```js
s += bx + "<sandbox_violations>" + bx;
for (let h of r) s += h.line + bx;
s += "</sandbox_violations>";
```
（`m0302:37500`–`37502`）

存储是 `Sc = new Im`（`m0302:36274`），`getViolationsForCommand(e)`（`m0302:29363`）按命令查。
注意 `bx` 是换行，这是个**能被模型读到的结构化信号**——CC 用这个通道告诉模型"你被挡了什么、为什么"。

> 这个通道也被写进了 `m0051:120` 的"标签白名单"，说明它不是随手拼的字符串，是协议的一部分。

#### 4.1.6 Ubuntu AppArmor 的坑

`N4()`（`m0302:39861` 附近）会读 `/proc/sys/kernel/apparmor_restrict_unprivileged_userns`，
如果是 `1` 且 bwrap 试验失败、stderr 命中
`/setting up uid map: Permission denied|Failed RTM_NEWADDR/`，就给出一条可执行建议
（`m0302:39877`）：装 bubblewrap 的 AppArmor profile，或 `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`。
**这条对你在容器里部署很关键**：Ubuntu 24.04+ 的容器默认可能就带这个限制。

### 4.2 macOS：Seatbelt（SBPL 策略文本 + `sandbox-exec`）

**没有守护进程、没有内核模块，就是拼一段 S 表达式策略文本，交给系统自带的 `/usr/bin/sandbox-exec`。**

`a9()`（`m0302:34431`）生成策略，`Euo()`（`m0302:34481`）拼最终命令：

```js
gt = $oe(["env", ...Sn, ...kt, ...Vt, "/usr/bin/sandbox-exec", "-p", He, bn, "-c", n]);
```
（`m0302:34555`——`He` 是策略文本，`bn` 是 shell 路径，`n` 是原命令）

策略的第一行和总纲（`m0302:34448`）：

```
(version 1)
(deny default (with message "<LogTag>"))
```

**`(deny default)` 是白名单模式**——所有操作默认拒绝，靠后面的 `(allow ...)` 一条条开。
注释里明写 `Essential permissions - based on Chrome sandbox policy`，逐项开：`process-exec`、`process-fork`、
`signal (target same-sandbox)`、特定 Mach 服务（字体、日志、`securityd`、`launchservicesd` 等）、
`ipc-posix-shm`、`ipc-posix-sem`（注释点明是给 Python multiprocessing 用）、特定 IOKit 类、
一长串 sysctl（`hw.*` / `kern.*`，注释点明 `V8 thread calculations` 需要 `kern.tcsm_enable` 可写）等。

由此派生的几个开关都是"再开一条洞"：

| 设置 | 行号 | 具体动作 |
| --- | --- | --- |
| `allowPty` | `m0302:34472` | `(allow pseudo-tty)` + `/dev/ptmx` + `^/dev/ttys` + file-ioctl |
| `enableWeakerNetworkIsolation` | `m0302:34448` 段内 | `(allow mach-lookup (global-name "com.apple.trustd.agent"))`（Go 系工具验 TLS 用） |
| `allowAppleEvents` | `m0302:34448` 段内 | `(allow appleevent-send)` + `lsopen` + coreservicesd/quarantine-resolver |
| `allowLocalBinding` | `m0302:34451` | `(allow network-bind (local ip "*:*"))` 等 |
| `allowUnixSockets` | `m0302:34454`–`34457` | `(allow system-socket (socket-domain AF_UNIX))` + 按路径 subpath |
| `allowMachLookup` | `m0302:34448` 段内 | 用户追加的 XPC 服务名，支持尾部 `*` |

文件读写是**另一套函数**拼的：读用 `Z8()`（`m0302:34175`，生成 `{denyOnly, allowWithinDeny}` 结构）
→ `s9()`（`m0302:34377`，`if (!e) return ["(allow file-read*)"]` 起步，否则 `m0302:34380` 先
`(allow file-read*)` 再 `m0302:34387` 逐条 `(deny file-read*)`，最后 `m0302:34388` 用
`(allow file-read-metadata (vnode-type DIRECTORY))` 让目录能被列）；
写用 `o9()`（`m0302:34398`）——**写 deny 是在写 allow 之内再 deny**：先
`h.push(...ao("allow", ["file-write*"], y, n))` 列允许，再 `h.push(...ao("deny", ["file-write*"], N, n))` 减掉不允许的，
最后 `(deny file-write-unlink file-write-create)` 挡 unlink/创建。

**已知降级**（源码自己写在日志里）：
`[Sandbox macOS] file mask degrades to deny on macOS until the interposer lands`（`m0302:34508`）。
也就是**凭据 `mask` 模式在 macOS 上目前等于 `deny`**——没有"给假值、出网换真值"那套。Windows 也一样
（`m0094:4735` 的 describe 原文含 `` `mask` currently degrades to `deny`. ``）。

> 这条对复刻很重要：**凭据"假值替换"只在 Linux 上真的实现了**。

### 4.3 Windows：唯一"真换了账户"的一套（但它是一个机器一个账户）

Windows 上 CC 不用 namespace（Windows 没有对等的轻量机制），它用的是：

1. **一个专用本地账户**，默认名 `ClaudeCodeSandbox`（`m0302:37918` `var kpt = "ClaudeCodeSandbox";`，`m0302:43423` 塞进 config）
   —— 注意另一处文案里出现的是 `srt-sandbox`（`m0302:36085`），**两个名字并存**，前者是传给 `srt-win install`
   的 `--sandbox-user` 默认值的比较基准（`m0302:35051`），后者是 WFP 过滤器文案里的旧名。
2. **一次 UAC 安装**：`npx sandbox-runtime windows-install` / `claude sandbox install` / `/sandbox install`，
   三处入口同一实现（`m0302:36082` 的文案里三选一）。装的是：账户 + WFP 过滤器 + 持久 CA。
3. **每条命令用 `CreateProcessWithLogonW` 以该账户身份启动**（`m0302:37930` 的正则里能看到这个 API 名），
   依赖 `seclogon`（Secondary Logon）服务；服务缺失/被禁会报 `m0302:35017` 那句明确提示。
4. **文件权限靠 ACL 授予，不是挂载**：`srt-win acl grant --holder-pid <pid> --sandbox-user-sid <sid>`（`m0302:35649`），
   撤销是 `acl revoke`（`m0302:35661`），进程退出后 `acl restore`（`m0302:35622`）。
   **`--holder-pid` 是关键设计**：授权绑定到持有它的进程，进程死了权限就该回收。
5. **网络靠 WFP（Windows Filtering Platform）**：装一组过滤器，只允许走代理端口段，
   校验用 `srt-win wfp verify` 真去连一次看会不会被挡（`m0302:35148`、`m0302:36133` 的
   `WFP installed: N filters, proxy port range a-b, loopback ...`）。
6. **每条命令加 `--write-restricted-token`**（`m0302:36009`）—— 即使是沙箱账户，token 也再降权一层写权限；
   配合 `--write-root` 逐个授权写根。

**这台的限制（源码明确写了的）**：

| 限制 | 证据 |
| --- | --- |
| 每条命令只能加 deny，不能加 allow | `m0302:37309`：`Per-exec filesystem.allowRead/allowWrite is not supported on Windows — srt-win exec only exposes per-exec denies` |
| 文件访问集合是 session 级，改了要 reset+initialize | `m0302:37371`：`the resolved file-access set ... changed but the ACL stamp/grant is session-wide` |
| 无 loopback 时沙箱内连不上 localhost | `m0591:148670` 段（`On Windows, sandboxed commands cannot connect directly to localhost`） |
| 用 Windows 原生 TLS（Schannel）的程序在沙箱里发不出 HTTPS | `m0591:148675`：`Windows' curl.exe ... PowerShell's Invoke-WebRequest ... .NET's HttpClient ... cannot make HTTPS connections inside the sandbox` |
| 沙箱内创建的文件属于沙箱账户，用户自己的 git 会报 dubious ownership | `m0591:148684`–`148687`（明确写了不要 `git init`/`git worktree add`） |
| 命令行走 `CreateProcessW` 上限，太长就拒 | `m0302:45784`/`45785`（`windows_argv_too_long` / `windows_child_env_too_long`） |

**这就是"比 Docker 轻"的代价**：Windows 这条路把"一个账户 + ACL + WFP"做成机器级的，
所以**一台机器上所有 CC 会话共用同一个沙箱账户**。对你多租户来说这是一个**反例警示**：
一旦共用账户，跨用户隔离就完全不存在了。

## 5. 五个"轻量但很有效"的附加机制

这五条跟"隔离"不是直接相关，但它们才是 CC 敢在宿主机上直接跑 agent 命令的真正原因，**你复刻时最值得抄**。

### 5.1 凭据 mask：给命令一个假值，出网时由代理换回真值

只有 Linux 真的实现了。机制：

1. 配置 `credentials.files[]` / `credentials.envVars[]`，`mode` 二选一：`deny`（直接不给）或 `mask`（给假值）。
2. `mask` 生成一个**与真值等长**的哨兵串：`var Vf = "fake_value_"`（`m0302:31842`），
   `KH()` 会补齐到原值长度、字符集限制在 `abcdefghijklmnopqrstuvwxyz0123456789_-`
   ——**等长是为了让依赖长度的解析器（JWT 分段、固定宽度字段）不炸**。
3. `extract` 正则支持**局部**替换（只替换 capture group 1），注释特意举了 `DATABASE_URL` / `KEY:SECRET`
   这种复合值（`m0094:4755`）。
4. `decode: "jwt"` 时先验真是 JWT 再替换，且**生成的假 JWT 结构仍然合法**，让客户端侧的 token 解析不崩（`m0094:4738`）。
5. 出网时由宿主代理把哨兵换回真值，且只在 `injectHosts` 指定的 host 上换（默认等于 `network.allowedDomains`）。
6. AWS 特例：`accessKeyIdVar` 和 `secretAccessKeyVar` **必须成对配**，否则代理无法重签 SigV4，
   会明确告警"两个都 mask 才启用重签"（`m0302:32245`）。
7. `onExtractNoMatch` 决定匹配不到时的行为：`warn`（默认，fail-open 保持可读）/ `deny`（降级为拒绝）/ `error`（安装期就中止）。

**对你的价值**：这套东西跟你"每用户一个容器"是**正交**的——容器解决了"别碰别人文件"，
mask 解决"别把用户的 token 打到日志/公网"。**强烈建议照抄。**

### 5.2 违规上报 `<sandbox_violations>`

见 §4.1.5。要点是它**是给模型看的**，不是给人看的：格式固定、放在命令输出尾部、
带"哪一条被挡、为什么"。这是"沙箱失败要变成可解释的反馈，而不是无声拒绝"的具体实现。

配套还有 `ignoreViolations`（`m0094:4836`）：按"命令模式 → 路径列表"配置哪些违规不报。

### 5.3 沙箱规则与权限规则是**两套**，但会合流

`allowWrite` / `denyRead` / `denyWrite` 的 describe 都写着
"Merged with paths from `Edit(...)` allow permission rules"（`m0094:4681`–`4683`）。
合流方向是**并集**，但有一层"信任分级"：managed / `--settings` / user 能开洞，
**项目级 settings（`.claude/settings.json`）被明确忽略**（`m0094:4651`–`4653` 那一组 `describe` 的前缀常量）。

> 这一条对多租户极重要：**用户自己的项目配置文件不能放宽沙箱**。CC 已经替你把这个决定做对了。

### 5.4 生命周期：懒初始化 + 一次失败就整会话关闭

`class eV`（`m0302:43504`）就是状态机，字段名直接暴露设计：

| 字段 | 含义 |
| --- | --- |
| `initializationPromise` | 懒初始化（`m0302:45746` `sandbox_exec_lazy_init`） |
| `sandboxDisabledThisSession` | **一次初始化失败，本会话剩下全关**（`m0302:45733` 那句文案） |
| `startsFailed` / `initFailureCode` / `initFailureReason` | 失败诊断 |
| `refusedOverWorkingFolder` / `hardLinkedDenyTargets` | 两种"拒绝运行"的特例（后者文案在 `m0302:45729`） |
| `realPathTwins` | `listed`/`off`/`unlisted` 三态，真路径解析失败时自动退化（`m0302:45758`） |
| `installedFilterRequestEnforcesAllowlist` | Windows WFP 是否真的在生效（不能只看"装了"） |

`ensureInitializedForWrap()`（`m0302:46493` 导出，实现 `Mw` 在 `m0302:45743`）就是那条"懒初始化 + 失败策略"的入口。

**没有常驻守护进程**：Linux 是每条命令 fork bwrap，macOS 是每条命令 exec sandbox-exec，
Windows 是每条命令 CreateProcessWithLogonW。唯一常驻的是网络代理（要接连接）和 Linux 的违规监听 socket。

### 5.5 **它没有任何资源限制**（这是与容器最大的能力差）

| 机制 | 本机/容器侧 | 在 `m0302` 里的命中数 |
| --- | --- | --- |
| cgroup（cpu/memory/pids） | Docker 标配 | **0** |
| `setrlimit` / `RLIMIT_*` | 进程级 | **0** |
| pids 上限 | Docker `--pids-limit` | **0** |
| 内存上限 | Docker `--memory` | **0** |

（以上四条已写成 MUST_NOT 断言，每次复核重跑，见探针。）

它有的是：

- **CPU 时间窗看门狗**，但**只在云端会话**（`CLAUDE_CODE_REMOTE`）启用：读
  `/proc/self/cgroup` → `cpuacct.usage`（`m2159:26424`–`26434`），
  超过 90% CPU 持续一段时间就停掉本会话的 shell 命令及其进程，并给模型一条 `task-notification`
  （`m2159:25999`）。文案里明写 "The limit is ..."，说明**上限是执行环境给的，不是 CC 给的**。
- **超时**（Bash 工具层，不属于沙箱）。

> **对你多租户的直接结论**：资源限制必须由**外层容器**（cgroup）提供，
> 别指望把 CC 的沙箱当资源边界用。这也是"容器 + 进程内沙箱"两层叠起来的另一个理由。

## 6. 模型侧怎么被说服"待在沙箱里"

CC 不靠一句"请勿越界"，它把**沙箱的当前实际边界**渲染成一段附件注入上下文：

- 附件类型 `sandbox_instructions`（`m0591:151759` 的 producer 注册，`m0591:152397` 的构造）
- 生成器 `RAn()`（`m0591:152386`）→ `LFn()`（`m0591:148599`，`if (!Ge.isSandboxingEnabled()) return ""`）
- 平台标签：`_1r()`（`m0591:148592`）返回 `" (macOS Seatbelt)"` / `" (Linux bubblewrap)"` / `""`
  —— **Windows 没有标签**（这是可回查的不对称）
- 边界总纲 `g1r`（`m0591:148583`）：

  > "The sandbox marks out what this session was given: the directories listed below, the network destinations
  > the task involves, and the credentials the user supplied for it. Treat that as the boundary even where a limit
  > below is not enforced. Commands can reach more than that — credentials and keys elsewhere on this machine,
  > the user's other projects and configuration, sockets that control this machine or other workloads,
  > cloud metadata endpoints — but being reachable does not make them provided..."

  **这段话承认了"能碰到的比允许的多"**——它承认沙箱不是完备的，所以补一层"提示词层的边界"。

### 7.1 你同事"一个沙箱 for all users"的问题在哪（用 CC 的代码反推）

CC 的 Linux 沙箱**建立在"宿主文件系统对沙箱可见"的前提上**（`--ro-bind / /`，`m0302:33472`），
安全性完全由"遮罩表算得对不对"承担。而遮罩表是这样算出来的：

- `denyRead` = 配置的 deny + **凭据目录**（`m0302:35570`）
- `allowWrite` = 配置 + 项目根 + 工作区

**这些输入全都隐含"只有一个用户"**：`home` 就是当前进程的 home，`cwd` 就是当前项目。
如果多个用户共享一个容器，A 的沙箱遮罩里根本不会出现 B 的目录 —— 因为程序不知道 B 存在。
于是 `--ro-bind / /` 会把 B 的目录**以只读方式暴露给 A**（至少可读！）。

Windows 那条路更直接：**一台机器一个 `ClaudeCodeSandbox` 账户**（`m0302:37918`），
所有会话共用。ACL 是按"该账户 + 命令持有者 pid"授的，共用账户意味着**权限在会话之间是共享池**。

所以：**"一个沙箱 for all users"在 CC 这套机制下是明确不安全的**，你判断"应该一个用户一个"是对的。

## 8. 建议：把你的方案改成两层

```
┌─ 你的 Sandbox Manager（唯一能碰 Docker）
│
├─ 每用户一个容器（C 层：既有的那套，别改）
│     ├─ uid / user ns / net ns 隔离     ← 跨用户边界，CC 给不了
│     ├─ cgroup: cpu / memory / pids     ← 资源边界，CC 给不了
│     ├─ 独立 rootfs（镜像）              ← 不共享宿主 inode
│     ├─ 独立持久卷 / MinIO 同步
│     └─ 默认 network=none + 受控出口
│
└─ 容器内的 Tool Worker（D 层：新增，抄 CC）
      ├─ Bash 类工具 → per-command bwrap（Linux）:
      │     --unshare-net --unshare-pid --unshare-user --cap-drop ALL
      │     --die-with-parent --new-session --disable-userns
      │     + --ro-bind / / + 挂载遮罩（只暴露本用户工作区）
      │     + seccomp: 挡 AF_UNIX socket
      │     + socat/mux 代理 + allowedDomains 白名单
      ├─ 凭据 mask: 假值注入 + 出网换真值（§5.1）
      ├─ 违规上报 <sandbox_violations>（§5.2）
      └─ **Read/Write 等文件工具也要过同一套路径判定**
            （CC 这层靠权限系统，你必须自己补，见 §2）
```

### 8.1 D 层值不值得做（成本/收益）

| | 只有容器（C 层） | 容器 + per-command 沙箱（C+D） |
| --- | --- | --- |
| 挡住"agent 读 ~/.ssh 再 POST 出去" | 部分（容器里可能也有密钥/配置） | ✅ 两层都挡 |
| 挡住"一条命令 `rm -rf` 掉整个工作区" | ❌ 容器内可写 | ✅ 只有 allowWrite 可写 |
| 挡住"通过 unix socket 控制别的服务" | ❌ | ✅ seccomp |
| 挡住"curl 内网管理接口" | 靠 netns | ✅ 再加域名白名单（更细） |
| 挡住"用户 A 读用户 B" | ✅ | （D 层不负责，也不需要） |
| 拦住耗 CPU 的死循环 | ✅ cgroup | （D 层不负责） |
| 实现成本 | — | **中**：bwrap 参数组装 + 遮罩表 + 代理，都是可移植的纯逻辑 |
| 运行时开销 | — | **极低**：多一次 exec，毫秒级 |

**结论：D 层值得做，而且不该做成"又一个容器"。** 它解决的是"容器内部再收一层"，
跟你"每用户一个容器"是嵌套关系，不是替代关系。

### 8.2 如果只做一件，做哪件

按性价比排序（依据 CC 的实现复杂度 + 防御收益）：

1. **`--unshare-net` + 域名白名单代理**（§4.1.4）。CC 里这块代码量最大但收益最高：
   数据外泄、内网扫描、云 metadata 探测**全靠这一层挡**。哪怕不用 bwrap，只在容器内断网 + 强制走代理也值得。
2. **凭据 mask**（§5.1）。改动小、对"token 进日志/进公网"直接生效。
3. **`<sandbox_violations>` 结构化上报**（§5.2）。让"被挡了"变成可解释反馈，而不是用户看到莫名失败。
4. 最后才是完整的 bwrap 挂载遮罩——因为它复杂（§4.1.2 那套 `--tmpfs` 挖洞 + 回填），
   而且在容器里你的 rootfs 已经是隔离的，收益比在宿主上小。

### 8.3 三条**不要照抄**的地方

1. **`enableWeakerNestedSandbox`**（`m0094:4837`）：为"非特权 Docker 容器里跑不了 /proc 挂载"准备的后门，
   会**保留宿主 /proc 可读**。你在容器里部署可能正好撞上这个需求，**但它会削弱隔离**——
   宁可给容器 `--privileged` 级的 user ns 权限，也不要用这个开关。
2. **`dangerouslyDisableSandbox` 这个参数本身**：CC 里它是**模型可以传的**（`m0591:66437`），
   靠 `allowUnsandboxedCommands` / strict mode / 权限提示来兜。**你这样是绝对不能有的**——
   用户身份和执行边界不能由模型决定。CC 自己也知道有问题，所以有 strict mode（`m0591:66396`）把它彻底关死。
3. **`--ro-bind / /` 复用宿主 rootfs**：单用户机器上很聪明（省镜像、省空间、启动快），
   **多租户上不能做**（§7.1）。容器里你已经有独立 rootfs 了，直接在容器内做遮罩即可。

### 8.4 一个容易忽略的点：`allowed_domains` 的层层收紧

CC 给模型一个"这条命令临时需要访问某域名"的能力（§4.1.4），但做了三层限制：
数量上限 100（`m0591:57043` 的 `.max(cVo)`，`cVo = 100` 在 `m0591:57029`）、
不许 loopback/映射地址、**必须在配置的 allowlist 之内再放宽**（`m0302:36419` 是第 5 步，
排在 `deniedDomains` 和 `strictAllowlist` 之后）。

**如果你的方案要给模型类似的"临时开口"能力，务必照抄这个"只能收紧不能突破"的次序**——
否则模型一句"我需要访问 internal-admin.corp"就把你整个白名单绕过去了。

## 13. 一句话总结

**CC 有一套比 Docker 轻两三个数量级的沙箱：Linux 是 per-command 的 `bubblewrap`（3 种 namespace + 挂载遮罩 + 外部 seccomp + socat 代理），
macOS 是 per-command 的 `sandbox-exec` + 一段 `(deny default)` 的 SBPL 文本，Windows 是 per-command 的
`CreateProcessWithLogonW` 换专用账户 + ACL + WFP。
它没有容器、没有 cgroup、不换 uid、连镜像都不需要——代价是它只做"单用户纵深防御"，
不做"跨用户隔离"。**
所以对你的方案：**容器层照旧（跨用户 + 资源边界必须靠它），把 CC 这套作为容器内的第二层收口（网络白名单、凭据 mask、违规上报优先）。**

## 14. 附：Windows 上能不能拿 bwrap 做 code runner

> 这一节回答一个具体的追问：**"我们就在 Windows 上和 CC 对话，CC 能跑，那是不是说明 bwrap 在 Windows 能用？"**
> 答案：**不能，而且现在的 CC 在 Windows 上根本没在用 bwrap。** 下面给证据。

### 14.1 直接的答案

**不能。`bubblewrap` 到目前为止没有可用的 Windows 版本，CC 在 Windows 上也不调用它。**

CC 的 `bwrap` 依赖的原语全部是 Linux 内核专有的：

| bwrap 参数 | 依赖的 Linux 机制 | Windows 有吗 |
| --- | --- | --- |
| `--unshare-user` / `--unshare-pid` / `--unshare-net` | user / PID / network namespace | ❌ 无对等物 |
| `--cap-drop ALL` | POSIX capability | ❌ 无对等物 |
| `--ro-bind` / `--bind` / `--tmpfs` | mount namespace + bind mount | ❌ 无对等物 |
| `--die-with-parent` | `PR_SET_PDEATHSIG` | ❌ 无对等物 |

CC 源码里 `bwrap` 的所有使用点都在 **Linux 分支**（`m0302:33035` 的依赖检查、`m0302:33927` 的实际取用），
**`bwrap.exe` / `bubblewrap.exe` / `bwrap.*win32` 在 `m0302` 内 0 命中**，也没有 vendor 进来——
`vendor/` 下只有三样：`java-proxy-agent`、`seccomp`、`srt-win`（`m0302:32503` / `32539` / `34771`）。

### 14.2 那"我们在 Windows 上用 CC，CC 能跑"是怎么回事

**因为 Windows 上走的是完全另一套：`srt-win.exe`，不是 bwrap。**

平台分派是一行 `if` 就分开的（`PI()`，`m0302:36766`）：

- `s === "linux"` → 检查 `bwrap` + `socat`（`m0302:36776`、`m0302:36781`）
- `s === "windows"` → 检查 `srt-win`（`m0302:36787`、`m0302:36790`）

`wrapWithSandboxArgv` 的入口第一句就是平台判断（`m0302:37298` `if (JE() === "windows") {`），
Windows 分支里所有调用都指向 `srt-win`（`m0302:37334`、`m0302:37355`），**一条路都通不到 bwrap**。

而且 Windows 那套**必须做过一次性安装**（专用账户 + ACL + WFP 过滤器，§4.3），
没装就是"沙箱不可用"，不是"降级用 bwrap"。

### 14.3 运行时实测：本机这个 CC 的 Windows 沙箱是关的

这一条是**实测**，不是读源码推的：

```console
$ claude sandbox status
{"statusVersion":3,"available":false,"installed":false,"policyLocked":false,
 "reasons":["The Windows sandbox is not enabled on this build."],
 "supported":false,"enabled":false,"enabledSource":"off", ...}
```

`"enabled":false` / `"installed":false` —— **本机根本没有启用沙箱**。
而且 `sandbox.enabled` 的默认值就是 `false`（`m0094:4829`：`Run Bash commands inside the sandbox. Default: false.`），
本机 `~/.claude/settings.json` 里 `sandbox` 键 0 命中，即**从未打开过**。

那句 `"not enabled on this build"` 出自 `m1737:523` → `K6()`（`m0302:37908`）：
Windows 沙箱还挂在一个特性开关后面（`tengu_nankeen_kestrel` / `CLAUDE_CODE_NANKEEN_KESTREL`，`m0302:37910`–`37911`）。

> **换句话说**：你和我现在在 Windows 上对话、CC 能跑 Bash，
> **不是因为 bwrap 在 Windows 上能工作，而是因为沙箱压根没开**——命令就是在宿主上直接跑的。

**这一点对你要做的事至关重要**（见 14.5）。

### 14.4 那 Windows 上想"以 bwrap 为基础"有没有别的路

三条路，按可行性排：

| 方案 | 可行性 | 说明 |
| --- | --- | --- |
| **WSL2 里用 bwrap** | ✅ 可行 | WSL2 是真 Linux 内核，`apt install bubblewrap` 就能用。但**你没法拿它约束 Windows 侧的可执行文件**——它只能管 WSL 里的进程 |
| 自己写 Windows 原生沙箱 | ⚠️ 成本极高 | 要对等 bwrap 的能力得用 Job Object（资源）+ AppContainer / restricted token（权限）+ ACL（文件）——CC 的 `srt-win` 走的就是这条路，且它是个独立二进制（`vendor/srt-win/x64/srt-win.exe`），不是几行 JS |
| 直接抄 `srt-win` 的思路 | ⚠️ 只能抄设计 | 二进制本身没开源在我们的分析面上（§10.1 已声明未逆向）；CC 侧只覆盖"怎么调它" |

**注意 CC 也没能"用 JS 实现 Windows 沙箱"**：它把这件事交给了外面的 `srt-win.exe`。
这本身就说明**在 Windows 上做原生进程沙箱不是一个小工程**。

### 14.5 对"code runner runtime"的结论

**如果你的目标平台是 Windows，别以 bwrap 为基础。** 分三种情况：

1. **code runner 跑在 Linux（容器里）** —— 这是**正路**，也是你原方案的设计。
   容器内用 bwrap 做 per-command 收口完全可行（§8 的 D 层），因为容器里就是 Linux。
   **bwrap 该待的地方是容器里面，不是 Windows 宿主上。**

2. **code runner 必须跑在 Windows 宿主上** —— 那就：
   - 要么抄 `srt-win` 的三件套（专用账户 + ACL + WFP），成本高、需要一次 UAC 安装；
   - 要么降级到 **Job Object + restricted token + 只读目录**（能挡资源和大部分写操作，**挡不住同用户读取**）；
   - 要么把执行环境放到一个 Linux VM / WSL2 里，Windows 侧只做客户端。

3. **只是想"在本地 Windows 上有个轻量沙箱做开发验证"** —— WSL2 + bwrap 最省事，
   但它和生产环境的边界不是一回事，**别把本地验证结论当成生产可用的证据**。

> ⚠️ **别被"我现在就在 Windows 上用 CC"误导**：14.3 已经实测了，
> 这台机器上 CC 的沙箱是**关着的**，Bash 直接跑在宿主上。
> "CC 能用" 和 "CC 的沙箱在 Windows 能用" 是两件完全不同的事。
