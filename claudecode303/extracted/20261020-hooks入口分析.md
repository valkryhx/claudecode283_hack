## 0. 一句话结论

## 3. 五种用户可见 hook 类型

`m0062_0xe4ee087.js:2636` 的 `dh()` 返回五个 schema：

| 类型 | 核心字段 | 说明 |
| --- | --- | --- |
| `command` | `command`、`args?`、`shell?`、`timeout?`、`onFailure?`、`async?`、`asyncRewake?` | 最常用；有 shell 形式和 exec 形式 |
| `prompt` | `prompt`、`model?`、`timeout?`、`continueOnBlock?` | 用小模型评估 hook 输入 |
| `mcp_tool` | `server`、`tool`、`input?`、`timeout?` | 调用已配置的 MCP 工具 |
| `http` | `url`、`headers?`、`allowedEnvVars?`、`timeout?`、`onFailure?` | POST hook 输入 JSON |
| `agent` | `prompt`、`model?`、`timeout?` | Agentic verifier，默认 60 秒、默认 Haiku |

### 3.1 command（`m0062:2637-2652`）

| 字段 | 要求 / 语义 |
| --- | --- |
| `command` | 必填；shell 命令或 exec form 的可执行文件 |
| `args?` | 存在时是 **exec form**：`command` 当可执行文件，`args` 逐元素替换占位符，不经过 shell |
| `if?` | handler 级 permission-rule 过滤（例：`Bash(git *)`） |
| `shell?` | `bash | powershell`；无 Git Bash 的 Windows 默认 PowerShell |
| `timeout?` | 正数秒；仅此 command |
| `onFailure?` | `continue | block`。启动失败、超时、非 0/2、无效 JSON 等可被提升为阻塞 |
| `statusMessage?` | spinner 自定义状态文案 |
| `once?` | 执行后移除 |
| `async?` | 后台运行，不阻塞当前动作 |
| `asyncRewake?` | 后台运行，exit code 2 唤醒模型；schema 写明 **Implies async** |
| `rewakeMessage?` | `@internal`；唤醒模型时的系统提醒前缀 |
| `rewakeSummary?` | `@internal`；终端的一行摘要，默认 “Stop hook feedback” |
| `cloud?` | `device | skip`；cloud/device 转发**不在本阶段 GA 必做范围** |

`onFailure:"block"` 只对 command 的非 async、http 生效；`Stop`、`SubagentStop`、`TaskCompleted`、`TeammateIdle` 忽略该提升（`m0459:57372-57435`）。

### 3.2 prompt（`m0062:2653-2662`）

| 字段 | 要求 / 语义 |
| --- | --- |
| `prompt` | 必填；`$ARGUMENTS` 接收 hook input JSON |
| `if?` | handler 级 permission-rule |
| `timeout?` | 正数秒 |
| `model?` | 不填时使用默认 small fast model |
| `continueOnBlock?` | 只影响 `decision:"block"` 时的 `continue`；不改变事件硬门禁 |
| `statusMessage?` | spinner 文案 |
| `once?` | 执行后移除 |

### 3.3 mcp_tool（`m0062:2663-2672`）

| 字段 | 要求 / 语义 |
| --- | --- |
| `server` | 已配置 MCP server 名 |
| `tool` | 该 server 的工具名 |
| `input?` | 字符串值支持 `${path}` 从 hook input 插值，例如 `${tool_input.file_path}` |
| `if?` / `timeout?` / `statusMessage?` / `once?` | 同前述 handler 级过滤、超时、文案、移除语义 |

### 3.4 http（`m0062:2673-2684`）

| 字段 | 要求 / 语义 |
| --- | --- |
| `url` | 必填；POST hook input JSON |
| `if?` / `timeout?` | handler 级 permission-rule / 正数秒超时 |
| `onFailure?` | `continue | block` |
| `headers?` | 可插值 `$VAR_NAME` / `${VAR_NAME}` |
| `allowedEnvVars?` | 允许插值的变量；与全局 `httpHookAllowedEnvVars` 取交集 |
| `statusMessage?` / `once?` | spinner 文案 / 执行后移除 |
| `cloud?` | `device | skip`；cloud/device 转发不在本阶段 GA 范围 |

### 3.5 agent（`m0062:2685-2693`）

| 字段 | 要求 / 语义 |
| --- | --- |
| `prompt` | 必填；`$ARGUMENTS` 接收 hook input JSON |
| `if?` | handler 级 permission-rule |
| `timeout?` | 默认 **60 秒**；运行时 `e.timeout ? e.timeout*1000 : 60000`（`m0459:154757`） |
| `model?` | 不填时使用 Haiku |
| `statusMessage?` / `once?` | spinner 文案 / 执行后移除 |

### 3.6 `script` / `callback` / `function` 的边界

- **`script` 不是用户 settings 的五种类型**。本 build 明确 `script hooks are not available in this build`（`m0353:13676-13677`）；运行时类型表和路径校验仍有 `script` 符号，但用户无法用本 build 正常运行它；
- `callback`（`m0459:160269`）和 `function`（`m0459:160334`）是 SDK / REPL / 进程内通道，不是 settings 的五种 handler；
- `SessionStart` / `Setup` 会跳过 HTTP hook（`m0459:159725-159727`）。

## 4. 配置结构、matcher 与 `if`

`m0062:2713` 的 entry：

```js
{
  matcher: "Write|Edit",       // 可选，entry 级
  hooks: [ /* Handler[] */ ]
}
```

外层：

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash", "hooks": [{ "type": "command", "command": "..." }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command", "command": "..." }] }
    ]
  }
}
```

### 4.1 matcher（先决定整个 entry 是否参与）

- matcher 是字符串；空或 `*` 匹配全部（`m0459:158589-158590`）；
- 简单 token 走精确 token 路径，复杂模式走正则路径（`m0459:158591-158607`）；
- `mcp__server` 若没有第二个 `__`，本 build 会警告它按精确字符串比较、**不会**匹配这个 server 的全部工具；应写 `mcp__server__.*`（`m0459:158553-158565`）；
- stderr 中有提示：`matches no tool (it is compared as an exact string)`。

匹配对象由 `vnt()`（`m0459:158496-158550`）选择：

| 事件 | matcher 对象 |
| --- | --- |
| tool 事件（`PreToolUse` / `PostToolUse` / `PostToolUseFailure` / `PermissionRequest` / `PermissionDenied`） | `tool_name` |
| `UserPromptExpansion` | `command_name` |
| `SessionStart` | `source` |
| `Setup` / `PreCompact` / `PostCompact` | `trigger` |
| `PreModelSwitch` / `PostModelSwitch` | 目标模型（去 ANSI 后） |
| `Notification` | `notification_type` |
| `SessionEnd` | `reason` |
| `StopFailure` | `error` |
| `SubagentStart` / `SubagentStop` | `agent_type` |
| `Elicitation` / `ElicitationResult` | `mcp_server_name` |
| `ConfigChange` | `source` |
| `DirectoryAdded` | `source` |
| `InstructionsLoaded` | `load_reason` |
| `FileChanged` | 文件名 |
| `TeammateIdle` / `TaskCreated` / `TaskCompleted` | 无单独匹配对象 |

### 4.2 `if`（再决定单个 handler 是否 spawn）

`if` 是 handler 级的 permission-rule 语法，例如 `Bash(git *)`；目的是避免为不匹配的命令 spawn hook（`m0062:2634`）。

- `if` 在 matcher 之后执行，位于生成执行项之前（`m0459:159676-159724`）；
- 只在 tool 类事件可求值：`PreToolUse`、`PostToolUse`、`PostToolUseFailure`、`PermissionRequest`、`PermissionDenied`（`m0459:158629-158641`）；
- 对非 tool 事件写了 `if`，会记 `cannot be evaluated for non-tool event`，该 handler 不跑（`m0459:159711`）；
- 不匹配时记 `Skipping hook due to if condition ... not matching` 并排除（`m0459:159723`）；
- `PreToolUse` / `PermissionRequest` 的配置错误是 fail-closed：坏守卫可能正是权限门，不能静默放行（`m0062:2815`、`m0062:2893`；`m0459:55453-55475`）。

### 4.3 配置错误与来源

- 用户 settings 只接受上述五种 handler；`script` 是会报错的运行时类型，不是用户可见 handler；
- `hooks` 字段既可以是 entry 数组，也可以来自 hooks module；`m0062:3675` 的报错写明 `hooks.json must have hooks ... or modules ... or both`；
- 来源合并不是“后写覆盖”：实际收集是 union；展示顺序与具体事件的合并语义是两件事（见 §8）。

### 5.3 输入序列化与大小

`m0459:160149-160175` 的 `qo()`：

- 把输入序列化为 JSON；
- 大小检查 `KCn()`（`m0459:157689-157690`）只在 `I$(event)` 为真时生效；
- `I$()` = event 属于 `PreToolUse` / `PermissionRequest` 且 `T8()` 特性开关为真（`m0459:55426-55446`）；
- 上限 `SBt()` = `Math.floor(buffer.constants.MAX_STRING_LENGTH / 2)`（`m0459:55449-55450`）；本机 Node 值 `536870888 / 2 = 268435444` 个 UTF-16 单元；
- 超出时报 `RangeError("Hook input is over the size limit")`，分类 `hook_input_too_large`；其它序列化失败为 `hook_input_stringify_failed`（`m0459:160160-160168`）；
- 对受保护事件，这类失败是 **fail-closed**：`Xfe()` 构造 `blockingError`，`PermissionRequest` 同时返回 deny（`m0459:55453-55467`）。

- `callback` 在 `m0459:160269` 起处理；适合 SDK host 提供的回调。

- 它们不是用户 settings 的 5 种类型之一；属于内置/SDK 通道。复刻时可以先把它们视为“进程内 handler”。

### 7.5 workspace trust、kill switch 与 cloud

- `m0459:159965`：未接受 workspace trust 时直接跳过 hook，并打印 `Skipping ... hook execution - workspace trust not accepted`；

### 9.2 HTTP allowlist 的精确默认值（补充核验）

`m0062:8024` 的 schema 描述是权威边界：

- `allowedHttpHookUrls` **undefined**：所有 URL 都允许；
- `allowedHttpHookUrls: []`：所有 HTTP hook 都禁止；
- 非空数组：只允许匹配项，`*` 可作通配符，例如 `https://hooks.example.com/*`；
- 多个 settings source 的该数组按并集合并；
- `httpHookAllowedEnvVars` 同理，是 **全局 ∩ handler.allowedEnvVars** 的交集语义；
- HTTP hook 不应跟随重定向（CC 侧证据为 `maxRedirects: 0`）。

GA 的实现顺序必须是：先做 URL policy 判定，再创建请求；不能用“请求失败后再说没权限”，否则 DNS/代理侧已经发生了外联侧信道。空数组必须 fail-closed。

### 9.1 输出大小：不要把常量当结论

`m0062:2702` 的 `var Yqs = 24576` 与 `m0353:13661` 的 `uue = Yqs * 3` 是源码事实，但**尚没有**`Yqs` 被 hook stdout 输出路径实际消费的可靠证据。当前 deminified 源码中它只在定义/export 与该乘法出现；`uue` 又与其他模块同名变量冲突。因此：

- **不能说“所有 hook 输出都有 24 KB 上限”；**
- **不能把 `Yqs` 当成 GA 的输出预算去抄；**
- GA 应设置自己的、可配置的 `maxOutputChars`，超限持久化并返回 preview；
- 仍需专项动态验证 `Yqs` 是否属于 script hook 的另一条预算。

## 10. async 与 worker

### 10.1 async 的两条触发路径

**配置型**：

- `async: true`：后台运行，不阻塞当前动作；
- `asyncRewake: true`：后台运行，exit code 2 唤醒模型；schema 明文“Implies async”（`m0062:2647-2648`）；
- 配置型注册点在 `m0459:157971-157975`；`jH()` 决定何时 background（`m0459:157699-157701`）。

**协议型**：

- 脚本首行返回 `{"async":true}` 时，CLI 会 background 该进程（`m0459:158036-158059`）；
- 初始 async JSON 还可带 `asyncTimeout`（`m0353:10984-10989`、`m0120:7068-7071`）；
- `forceSyncExecution` 为 true 时，即使出现 async 协议也等它完成（`m0459:158059`）。

超时值需要分开说：

- 注册器 `Kjt()` 的回退是 **15000 ms**（`m0459:58014`）；
- 配置型 async 的 timeout 会写为 `e.timeout ? e.timeout*1000 : fu`（`m0459:157745`），其中 `fu = 600000`；
- 所以**不能**写成“所有 async 一律 15 秒”。

### 10.2 async 结果协议

- async hook 结束后按行解析 stdout；每行可以是一个 JSON 对象；
- 首个 `{"async":true}` 只是后台 marker，不是最终结果；
- 之后若出现以 `{` 开头但无法解析的行，会记录：`After any {"async":true} line, print one JSON object and nothing else, or put the object on one line.`（`m0459:58083`）；
- 无效 async JSON 不会当成有效 verdict；只交付可识别的 `systemMessage` / `metrics` / `hookSpecificOutput` 子集（`m0459:57882-57911`）；
- 收尾有 pending async 的 grace / drain（`m0459:58148-58169`）；会话退出会 kill 尚未完成的 async（`m0459:58171-58179`）；
- UI 侧走 `async_hook_response` / `async_hook_response_batch`（`m0671:662`、`m1556:7157`）。

### 10.3 asyncRewake 的精确消费语义（补充核验）

源码坐标：`m0459:157142-157221`（后台完成器 `ynt()`）、`m0062:2647-2650`（字段 schema）、`m0120:7068-7071`（协议型 async marker）。

已确认的事实：

1. `asyncRewake` 只适用于 `command`，且 schema 明文 `Implies async`；`prompt` / `agent` / `http` / `mcp_tool` 没有这个字段。
2. 后台进程结束时，只有 **exit code 2** 才会唤醒模型；exit 0 仅记录 `hook_response`，exit 其他非零码只按错误记录，不产生 wake。
3. 唤醒正文的优先级是：
   ```text
   rewakeMessage（配置）
   否则 "Stop hook blocking error from command "<hook name>":"
   ```
   正文内容优先 `stderr`，为空时再取 `stdout`。这解释了“验证脚本把原因写到 stderr”为什么能被模型看到。
4. 用户侧一行摘要优先级是：
   ```text
   输出 JSON 的 rewakeSummary（部分 plugin 路径）
   -> 配置的 rewakeSummary
   -> "Stop hook feedback"
   ```
   摘要会 trim、压缩连续空白并截到 **300 字符**（`W4r=300`）。
5. 唤醒不是普通日志：它通过内部队列（`h9t`）以 `priority:"next"`、`stopHookActive:true` 注入下一轮；模型看到的是自动化 hook feedback，不应误认成用户回复。
6. async 完成后的 stdout 不是任意 JSON 串：首个 `{"async":true}` 只是 marker；最终结果需是单行/可整体解析的 JSON 对象，无法解析的行只记录诊断且不会成为 verdict（`m0459:57882-58091`）。
7. 进程退出/会话结束会 drain 已完成的 async，尚未完成的会被 kill（`m0459:58148-58179`）。GA 复刻至少要做到：后台完成统一回收、会话切换时不把旧 session 的 wake 注入新 session。

### 10.4 GA 的最小 async 实现边界

GA 不照抄 CC 的 cloud/device 路径，只复刻本地语义：

```text
command + async=true
  -> run_event 立即返回，aggregate 不阻塞当前工具/回合
  -> 后台线程执行 command
  -> 完成后写 audit + 发 async_hook_response / hook_error

command + asyncRewake=true
  -> 同上，并且仅 exit=2 时调度一次 hook wake
  -> wake 走 GA 的“后续用户回合队列”，但 prompt 必须带
     [SYSTEM NOTIFICATION - NOT USER INPUT] 防伪前缀
  -> 若主 agent 忙则排队；空闲且旧 session 仍有效时再提交
```

刻意不做的部分：cloud hook、device forwarding、跨机器 wake、plugin 远端运行。

### 12.0 PermissionRequest 的精确输出与 GA 接入（补充核验）

源码事实：

- 输出结构定义在 `m0120:7156-7167`：`hookSpecificOutput.hookEventName` 必须为 `PermissionRequest`，`decision` 是 union：
  - `{"behavior":"allow","updatedInput?":object,"updatedPermissions?":array}`
  - `{"behavior":"deny","message?":string,"interrupt?":boolean}`
- 校验说明在 `m0459:155550`：`PermissionRequest.decision` 必须是上述 allow/deny 对象；顶层 `decision` 不是这里的替代字段。
- 结果归一化在 `m0459:157547` 与 `m0459:159281-159335`：CC 将其转成 `permissionRequestResult`、`permissionBehavior` 和 `updatedInput`。`allow` 的 `updatedInput` 也位于 `decision` 内，不是 `hookSpecificOutput.updatedInput`。
- 执行入口 `m0459:110136-110153`：`xYe()` 发送 `hook_event_name: "PermissionRequest"`、`tool_name`、`tool_input`、`permission_suggestions`，并带 MCP server 信息（`m0120:6815-6819`）。
- `agent` 类型 handler 明确不支持此事件：`m0459:160438`，因为它只能回答 ok/not ok，不能给出 allow/deny 决策；GA 用户配置应优先使用 `command` / `http` / `mcp_tool`。
- 自动化审批路径 `m0459:163225-163320`：当 PermissionRequest allow 时，CC 仍会检查已有 deny/ask 规则、工具输入 schema、requiresUserInteraction 等；“hook allow”不是硬安全边界的放大器。deny 则返回带 `decisionReason.type="hook"` 的拒绝。

GA 映射：

```text
mode_policy.evaluate() == ask
  -> run_event("PermissionRequest")
     -> decision.behavior == allow:
          merge decision.updatedInput
          re-run PathACL
          mark decision allow, skip PermissionRuntime user prompt
     -> decision.behavior == deny:
          emit PermissionDenied
          return tool error; never execute
     -> no decision:
          continue existing PermissionRuntime approval flow
```

边界：当前复刻的是本地会话、本地 handler 和本地 user approval；不实现 cloud `setMode`、device forwarding 或云端会话中的 hook 转发。**复刻 hooks 时暂时不需要参考 Claude Code 云端会话的实现。**

### 12.1 事件映射

| CC hook 事件 | GA 接入点 | 说明 |
| --- | --- | --- |
| `PreToolUse` | 工具执行前统一 guard | 对应 `permissionDecision`；deny 必须 fail-closed |
| `PermissionRequest` | 权限询问 / 自动审批层 | 第一版先做 allow/deny；`updatedPermissions` 后做 |
| `PostToolUse` / `PostToolUseFailure` | 单工具结果归一化之后 | 支持 `additionalContext`；改写输出晚做 |
| `PostToolBatch` | 并行工具批结束 | GA 并行工具与 workflow 工具批非常适配 |

| `SessionEnd` | GA 退出 / 会话关闭 | async 清理、flush 指标 |

| `WorktreeCreate` / `WorktreeRemove` | subagent worktree | 先接观测事件，不接管清理 |

### 12.2 实施原则

- **先 command，后 prompt/agent/http/mcp_tool**：command 协议最容易先验证 matcher/`if`/超时/exit code；
- **fail-closed 只限守卫类**：`PreToolUse` / `PermissionRequest`；其它事件失败一律 non-blocking，避免一个日志 hook 拖死 agent；
- **并发上限 12，prompt/agent 串行**：按完成顺序聚合，不要照抄成“所有 handler 并行”；
- **`if` 前置于 spawn**：GA 已有 permission rule，可在 handler 启动前做一次匹配，显著减少 shell 进程；
- **时间预算分开**：command 默认 600 秒；agent 默认 60 秒；HTTP 独立配置；async 注册器回退 15 秒；
- **输出预算自建**：GA 用可配置 `maxOutputChars` + 持久化 preview；**不要照抄未证实的 `Yqs=24576`**；
- **UI 统一状态机**：queued → running → stdout/stderr → done/error/cancelled；使用 `statusMessage` 与 `hook_progress`，async 结果批处理，避免逐行重绘；
- **安全默认值**：第一版不执行用户 `script`；HTTP 不跟随 redirect；URL allowlist；headers 环境变量只允许交集白名单；
- **不做**：cloud / device forwarding、cloud `setMode`、CC cloud 会话策略。

### 12.3 推荐的最小落地顺序

1. 定义 event entry 与五种 handler 类型（先只允许 command）；
2. 实现公共输入字段 + tool 类事件专属字段；
3. 实现 matcher → `if` → spawn → exit code → JSON 校验；
4. 接入 `PreToolUse` guard 与 `PostToolUse` 上下文；
5. 加 hub 并发 12、prompt/agent 串行、最严格权限聚合；
6. 加 progress 事件与 UI 状态机；
7. 再扩 `UserPromptSubmit` / `SessionStart` / `Stop` / `SubagentStop`；
8. 最后做 async、HTTP、MCP、hooks module。

### 15.3 `Stop` 的准确语义（本实例最关键的边界）

- `Stop` 对应的是**主 agent 一轮面向用户的停止点**，不是每次工具调用。
- `PostToolUse` 是单个工具成功后的 hook；把 beep 配在这里会在每个工具 step 响一次，不符合本需求。
- `SubagentStop` 是子 agent 停止；主会话的 beep 不应绑定它，否则 fan-out workflow 会响多次。
- `Stop` 的输入含 `stop_hook_active`。如果 Stop hook 返回 blocking，后续续跑再触发 Stop 时该字段为 true；hook 应据此避免无限阻断。源码在 `m0671:8983-8998` 还提供默认 `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP=8` 的兜底。
- `StopFailure` 是另一事件，不应把 API/执行失败伪装成普通 `Stop`。
- `Stop` 的 stdout 是协议通道，不是日志通道。beep 脚本保持 stdout 完全静默，避免被当作 JSON 控制输出解析；需要调试信息时写 stderr 或临时文件。

### 15.4 “turn” 术语警告

Claude Code 的 `Stop` 不能被机械映射成 GA `agent_runner_loop` 每次 `Turn N` 的结束：

```text
CC Stop
  = 一个用户请求的主 agent 回复结束，控制权交回用户

GA agent_runner_loop turn
  = 一个用户请求内部的一次 LLM 调用 / 工具迭代
```

因此 GA 若要在“每次回复结束响一声”，应当在外层 `GenericAgent.run()` 的任务终态派发 `Stop`，而不是在 `handler.turn_end_callback()` 里派发。这个结论直接约束 GA hooks 的实现落点，详见：

```text
D:/git_codes/GenericAgent/docs/20261020-GA-hooks设计与实现方案.md
```

### 15.5 与旧 beep 记录的差异说明

早期曾尝试：
