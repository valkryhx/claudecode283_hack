# Claude Code 2.1.303 mods 入口分析

> 日期：2026-10-20  
> 基准：`reconstructed303/deminified/` 当前行号；`m0459` 为共享大模块，符号仍为压缩名。  
> 目标：解释 303 的 `mods` 产品层是什么、从哪里加载、如何排序和隔离，给出可复刻入口。

## 0. 一句话结论

303 的 `mods` **不是独立的 `mods/` 目录 API**。它是产品层对以下三类的称呼：

1. 用户安装的 plugin；
2. plugin 提供的 function hooks / hooks module；
3. 内置安全 plugin（`cc-plugin-sec-default@builtin`）。

代码内部仍大量使用 `plugin`、`plugins`、`hooks module`、`builtinPlugins`。复刻时不要把 `mods` 当成与 plugin 平行的第二套插件系统。

更准确的实现关系是：

```text
plugin = 可分发单元（manifest + hooks 配置 + 可选 hooks module）
hooks = 事件契约与执行面
hooks module = 在进程内/plugin sandbox 中执行的原生 JS 扩展面
mods = 产品层称呼，不是第四套运行时
```

**不能“一次做完 mods 就白拿 hooks”。** `hooks.json` 的 matcher、五种 handler、输入/输出 schema、权限语义和生命周期，仍必须单独实现；mods 让这些能力可打包、可分发、可动态加载，但不会代替 hook 协议本身。

**也不能只做 `hooks.json` 就宣称完成 mods。** manifest、来源与启用状态、managed 优先级、plugin 沙箱、hooks module 生命周期、热重载与 worker 恢复，都属于 mods 层。

## 3. 总体架构

```text
managed settings / user settings / installed plugin dirs
  ├─ enabledPlugins
  ├─ prependPlugins / appendPlugins
  └─ builtinPlugins
        ├─ plugin manifest
        ├─ hooks.json
        └─ hooksModule (scan / shipped)
                ├─ bundle-builtin-hooks-module.ts
                ├─ hooks/register.ts
                └─ mods/ 虚拟 import
        ↓
plugin / hooks module loader
        ├─ m0459 Q9e() 初始化
        ├─ m0249 调度 / matcher / reentry / worker
        └─ m0459 worker / respawn / telemetry
```

这里要区分两条扩展面：

| 扩展面 | 声明方式 | 执行方式 | 适合什么 |
| --- | --- | --- | --- |
| 文件型 hooks | `hooks/hooks.json` 的 `hooks` | `command` / `prompt` / `http` / `agent` / `mcp_tool` | 配置化、跨语言、最小权限 |
| hooks module | `hooks/hooks.json` 的 `modules` | `register(on)` 的进程内 JS / plugin sandbox | 新接口、新命令、UI 组件、复杂状态与事件组合 |

两者可以同时存在；`m0062:3674-3675` 要求 `hooks` 或 `modules` 至少一个存在。

### 3.0 hooks.json 与 plugin manifest

`m0062:3664-3675` 的 hooks 文件 schema：

```js
u({
  description: string.optional(),
  hooks: hooksSchema.optional(),
  modules: array(string).max(1).optional(),
  surface: deprecated.optional()
}).refine(e => e.hooks !== undefined || (e.modules?.length ?? 0) > 0)
```

源码事实：

- 一个 plugin 最多声明**一个** hooks module；第二个 entry 明确拒绝；
- 错误文案：`hooks.json \`modules\` names one hooks module per plugin; a second entry is refused`（`m0062:3668-3670`）；
- `hooks` 与 `modules` 可同时存在，但至少有一个；
- `modules` 是**相对本 hooks.json 的路径**；
- module 及相对 import 的文件必须“named like code”，无论扩展名都按 ES module 处理；
- 加载前先读源码，得到 hook 什么、调用什么；`claude plugin validate` 可展示 scan 结果；
- `surface` 已废弃，错误文案要求用 `Client({ module: "./board.tsx", key })`（`m0062:3671-3673`）。

plugin manifest 的 `hooks` 字段可追加 hooks 文件路径或内联 hooks（`m0062:3677-3679`）；标准 `hooks/hooks.json` 会自动加载，manifest 重复指向会被去重（`m0459:194762-194781`）。

### 3.2 hooks module 的 register 入口与静态 scan

`m0062:3670` 明确 module 导出 `register(on)`。scan 可读出的面包括：

- `hooks`：`on(event, matcher?, handler)`；
- `calls`：`$.noun.method(...)`；
- `nextTo`：`next.to(e, "append" | "builtin" | "core")`；
- `clients`：`Client({ module: "...", key })`；
- env / state / command / agent / MCP / UI / tool / session / config 等显式接口。

`m0103:87-88` 列出 `$.model.*`、`$.mcp.*`、`$.tool.*`、`$.command.*`、`$.agent.*`、`$.ui.*`、`$.fs.*`、`$.process.*`、`$.settings.*`、`$.session.*`、`$.turn.*`、`$.engine.create`，以及 `tool.call`、`ui.render`、`ui.press`、`agent.spawn`、`prompt.submit`、`command.run`、`plugin.register`、`engine.create` 等事件。

**scan 是权限上限，不是文档提示。** `m0459:106826-106883` 的 host gate 会核对 module 已加载、调用 spelling 在 scan 内、noun 未被 withhold、policy 仍允许、set 已完成 admission；越出 scan 的调用会被拒绝。

### 4.5 `engine.create` 与 `$` 接口折叠

hooks module 添加新接口不是随意改全局对象，而是通过 `engine.create` 按顺序折叠：

- `m0459:130076-130250` 构造 `$` 接口表；
- 每个 `engine.create` handler 可以返回新增 noun，后一个模块能看到前面的结果；
- 同名 noun 冲突不能静默覆盖：源码要求“要改方法就 hook 方法”，不能替换别家 noun；
- 某个模块在 `engine.create` 失败，会被卸载，整组重新折叠，而不是留下半成品；
- user tier plugin 若试图 withhold 别家 noun，会被明确拒绝。

这个设计比“大家都往一个全局对象 assign”稳健，因为冲突会显式失败，失败可回滚。

### 4.6 调度、重入与 `.catch`

`m0249` 是 hooks module 的运行面：

- `m0249:1299` 起构造 dispatch；
- `m0249:1339-1363` 过滤 re-entry，生成 `leftOut`；
- `m0249:1385-1440` worker 被替换后，由 `.catch` 接管；
- `m0249:1706-1720` 选模块、匹配 event、应用 pinned matcher；
- `m0249:1759-1765` worker respawn 等待；
- `m0249:1815-1853` 单个 module 的 `run` / `hop`。

### 4.7 生命周期、热重载与回滚

`m0459:130340-130720` 展示了完整的热重载路径：

- 文件变化/插件启用变化会触发 `state.queue(...)`，重载串行化；
- 扫描得到新 module 集合后，未变的 module 可保留为 loaded；
- 失败的 reload 默认保留旧版本；只有整个 set 需要 refold 时才整体切换；
- 成功后才 `Swe(qt)` 同步 `loadedModules`、通知 worker、发遥测；
- 旧 module 调用 `retire()`，正在执行的请求等计数归零后 unload；
- `m0249:1366-1384` 在 worker 替换时等待并重新绑定 environment，拿不到新 module 就丢弃。

**核心思想：动态可变 ≠ 每次全量重启。** CC 做的是“可回滚、按 generation 更新、正在执行的操作安全退场”的热重载。

## 5. 来源、排序与冲突

### 5.1 mod 来源

`m0459:106155`：

```js
Qbe = Object.freeze(["installed", "plugin_dir", "dev_mods", "managed"])
```

遥测 `tengu_plugin_function_hooks_mod_load` 会带：

- `provenance`；
- `plugin_id_hash`；
- `tier`；
- `is_hosted`；
- `outcome`（loaded / failed）；
- `hook_patterns` 数量。

`m0459:106198-106213` 的首轮汇总带 `loaded_mods`、`failed_mods`、`mod_dispatches`，并按 provenance 分桶。

### 5.2 同名 plugin 与 managed 优先

`m0459:134741-134786` 的同名选择规则：

- 先按 managed / 来源优先级选一个；
- 同名 plugin 中先被选中的 module 进入加载集；
- 其余进入 `hooks-module-left-out-by-name`，错误文案为 `another plugin of that name loads first (a managed one, or an earlier source)`；
- plugin 自己的普通 hooks 与它的 hooks module 不是同一个命名空间：前者按 event 聚合，后者按 module name 分座。

### 5.3 managed plugin 顺序

从 `m0250` 与既有复刻清单可核对的事实：

- `prependPlugins`：managed plugin 的 hooks 最先、最外层；
- `appendPlugins`：managed plugin 的 hooks 最后、最内层；
- 未列出的 managed plugin 排在列出的 managed plugin 之后；
- user/project/marketplace plugins 再之后；
- 最后是 builtin plugins；
- managed plugin 冲突时显式报错，不做 last-write-wins（`m0459:134692-134730`）。

### 5.4 默认安全 plugin seat

`m0250:28-54`、`:708-777` 描述 `cc-plugin-sec-default@builtin` 的默认安全位置；若设置了 `prependPlugins`，需要组织显式列出它，不能用“用户 plugin 先跑”替代安全层。

### 6.3 host gate 是总闸

`m0459:106826-106883` 的调用路径必须过五道检查：

1. module 已加载；
2. 调用 spelling 在它的 scan 内；
3. 目标 noun/method 没有被 withhold 或被崩溃 module 牵连；
4. module 当前 policy 仍允许；

即使通过 scan，也要在调用时检查 `generation` / environment；module 被替换后，旧 `$` 不能继续借用旧权限。

## 10. GA 的复刻策略：hooks 与 mods 怎么排

### 10.1 结论：不是二选一，也不是“一次做完 mods 自动有 hooks”

推荐拆成三个里程碑，但共用同一套插件目录与安全元数据：

```text
M1：本地文件型 hooks
    manifest → hooks/hooks.json → event/matcher → handler → 聚合/权限

M2：本地 hooks module
    hooks.json.modules → 静态 scan → sandbox worker → register(on) → $
    → command / tool / session / UI 等扩展面 → reload

M3：本地 mods 产品层
    plugin 来源 / 启用 / managed 顺序 / 安全 seat / UI / 诊断 / 版本
```

M1 是 hooks 的核心；M2 才让“新特性可插拔”；M3 是分发与管理体验。

### 10.2 必须复用同一套事件协议

mods 的 `on("PreToolUse", ...)` 和 `hooks.json` 的 `PreToolUse` **必须落到同一个 hook dispatcher**。不要为 hooks module 新建一套与现有 agent loop 割裂的事件系统。

GA 建议的边界：

| CC 概念 | GA 本地映射 | 注意 |
| --- | --- | --- |
| `hooks/hooks.json` | `plugins/<id>/hooks.json` | GA 可兼容 CC 的文件名，但内部用 GA 命名 |
| hooks module | `plugins/<id>/<module>.ts` / `.js` | 先支持 TS/JS，之后按需扩 |
| `register(on)` | 同一注册 API | `on` 只允许声明式事件 |
| `$.noun.method()` | GA capability interface | 必须声明 + host gate，不允许任意 import 内部模块 |
| `engine.create` | capability fold | 冲突显式失败、失败可回滚 |
| `Client` | Ink/React surface 或保留未来接口 | 第一版不要急着做任意 UI module |
| `next.to` | hook chain skip | 仅服务端/受信 plugin 可开放 |
| builtin plugin | GA 内置安全 plugin | 走 native，不进普通 sandbox |

### 10.3 hooks 与 mods 的先后关系

**先做 M1，不等于要重写两次。** 第一版就应预埋：

- plugin manifest 与 source / enabled 字段；
- `hooks.json` 的 `hooks` 与 `modules` 两个字段；
- 统一 event envelope；
- 统一 scan 结果结构；
- 统一 matcher、handler 结果与聚合器；
- 统一 worker / sandbox 接口。

这样 M2 只需新增 module loader、scan、capability gate 与 `engine.create`，不会把 M1 的 handler 协议推翻。

**只做 M2 不够。** 没有 `hooks.json` 的文件型 hooks，就无法用最简单的方式接入外部脚本；而且 command hook 是最稳定的最小权限扩展面。

### 10.4 GA 第一版不需要抄的部分

- `claude-code-server tenant`、cloud session、device forwarding；
- MCP cgroup / 企业 rollout 服务端字段；
- 任意 UI module 的完整组件树；
- `registerScan` 这种 builtin 内部打包捷径；
- 旧 build 的 `script` hook（303 已明确本 build 不可用）。

### 10.5 与 hooks 文档的分工

- 事件、输入/输出 schema、5 种 handler、exit code、并发与聚合：见 `claudecode303/extracted/20261020-hooks入口分析.md`；
- 本文只负责 plugin / hooks module / mods 的产品层与动态加载边界。

## 10.6 设计思想提炼：为什么它比“全局插件对象”稳

从源码可以提炼出六条可迁移原则：

1. **声明先于执行**：先 scan 出 module 会注册什么、调用什么，再允许它加载；
2. **能力不是全局命名空间**：`$` 是显式 capability 表，不是任意 import 和 monkey patch；
3. **冲突显式失败**：同名 noun 或同名 command 不静默 last-write-wins；
4. **折叠可回滚**：`engine.create` 失败时卸掉 module、重新折叠整个 set；
5. **线程边界随来源变化**：builtin 可 native link，普通 plugin 必须走 sandbox/hop；
6. **动态更新有 generation**：旧 module 先 retire，执行中的调用安全退场，新 module 才接管。

这六条比某个具体 API 更值得 GA 抄；即使 GA 第一版只做少量事件和少量 capability，也应按这个骨架设计。

## 11. 复刻清单（按依赖排序）

### 必做：先打通文件型 hooks（M1）

1. 把 mods 建模为 **plugin**，不要另起一套平行 API。
2. plugin manifest 至少包含 `name`、`version`、`enabled`、`hooks`、可选 `modules`。
3. 支持 `hooks/hooks.json` 的 `hooks` 与 `modules`；一个 plugin 最多一个 module。
4. `hooks` 与 `modules` 至少有一个存在；路径必须留在 plugin 根目录内。
5. 静态 scan 文件型 hooks 的事件、matcher、handler 与占位符；解析失败时 fail-closed。
6. 统一接入 CC 的 33 个事件与 5 种 handler，复用 `hooks入口分析.md` 的 schema。
7. 实现来源分层、启用状态、managed 优先与同名冲突显式报错。
8. managed-only / disable-all / workspace trust 三类门禁先做；cloud 分支不做。
9. 默认安全 plugin 放在最外层；deny rule 不能被普通 plugin 覆盖。
10. 文件型 hooks 的 progress、超时、abort、exit code 与错误信息接入 GA 的 UI。

### 必做：再接 hooks module（M2）

11. `hooks.json.modules` 只允许相对路径，限制文件大小、文件类型与 import 边界。
12. 对 module 及相对 import 做 AST / 语义扫描，生成 `hooks`、`calls`、`clients`、`nextTo`、环境/状态访问声明。
13. 运行时校验“实际注册项 ⊆ scan 结果”；越界就拒绝整个 module，而不是悄悄放行。
14. module 在独立 worker / sandbox 中运行；builtin 才允许 native link。
15. 提供受控 `$` capability 接口与 `engine.create` 折叠；noun 冲突显式失败。
16. 支持 `leftOut` 重入过滤、pinned matcher、`.catch` 与 worker respawn。
17. 支持 generation、retire、热重载、失败保留旧版本、整组 refold 回滚。
18. 记录 loaded / failed / dispatch / respawn / reload 的本地诊断数据，UI 能解释“为何没加载”。

### 推荐：mods 产品化（M3）

19. 支持 installed / plugin_dir / dev_mods / managed 四类来源，但只记录本地 provenance，不接远程 rollout。
20. 做 `/plugins` 或等价诊断：每个 plugin 的 manifest、hooks、module scan、状态、错误、版本、来源。
21. 支持 disable / enable / reload / validate；reload 必须走串行队列，不能并发改写 loaded set。
22. 支持受信 plugin 的 `next.to`；普通 plugin 默认禁止。
23. 支持本地 plugin 依赖与版本约束；依赖缺失时给出明确诊断。
24. 为 module author 提供最小 SDK、类型定义、示例与 `validate` 命令。

### 可延后

25. 任意 Ink/React UI surface module。
26. cloud / remote rollout / multi-tenant server。
27. MCP cgroup、企业级策略分发、跨机器同步。

## 14. 一句话复刻原则

**先把 plugin 系统做对，再把 hooks module 当作 plugin 的一种可执行扩展；`mods` 只是产品层名字，不是新的权限边界。**

面向 GA 的落地顺序：

```text
plugin 目录 / manifest
  -> 文件型 hooks（M1：先把 hook 协议、权限和 UI 状态做稳）
  -> hooks module + scan + sandbox（M2：获得可插拔的新命令、工具、UI、状态）
  -> mods 管理 / 诊断 / 热重载（M3：形成产品能力）
```

**复刻 hooks / mods 时暂时不需要参考 Claude Code 云端会话实现。**
