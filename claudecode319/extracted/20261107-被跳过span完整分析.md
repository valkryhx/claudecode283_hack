## 1. 为什么会有"跳过"

`tools/extract_bun_modules.py` 按 `// @bun @bytecode` 标记把 `.bun` 载荷切成每标记一段。
它用两条规则跳过不适合当"一个源码模块"的段：

| 规则 | 判据 | 触发者 |
| --- | --- | --- |
| 大小上限 | `size > --max-size`（319 用 6 MiB） | marker 1（141 MB） |
| 非模块尾部 | 段内出现 NUL 且其后 1 MiB 以外可打印率 < 0.85 | marker 2882 |

这两条规则本身是对的 —— 硬把 141 MB 写成"一个模块"会污染索引。
但"跳过"不等于"不重要"，`AGENTS.md` §0 要求全部字节有交代，所以本轮把它们补齐。

## 2. marker 计数的一个陷阱

全盘扫 `// @bun` 前缀，得到 4 种变体：

| 出现次数 | 文本 |
| ---: | --- |
| 2,882 | `// @bun @bytecode` |
| 5 | `// @bun` |
| 1 | `// @bun @bun-cjs` |
| 1 | `// @bun @bytecode @bun-cjs` |

但真正的模块切分标记（`// @bun @bytecode`，严格子串）是 **2,883 个**。
其中 **只有 2,881 个落在 `.bun` 段**，另外 2 个落在 `.rdata`。

### marker 0 / 1 是伪标记

```
marker 0  off=0x84910b4  section=.rdata  -> next 0x84910c6   span = 18 B
marker 1  off=0x84910c6  section=.rdata  -> next 0x1120cbb8  span = 141 MB
```

marker 0 的 18 字节内容就是 `// @bun @bytecode\n` —— 那是 marker 1 那行的**前缀被单独匹配到**，
不是独立模块（已提取为 `m0000_0x84910b4.js`，18 B，内容就是这个字符串）。
marker 1 才是真起点，它带 `@bun-cjs` 后缀，全盘唯一一处。

所以：**marker 数 2,883 ≠ 模块数 2,881**，与 303 的 2,433 marker / 2,431 模块是同一类现象。

### 4.4 为什么会被截断

第 422 字节处有一个孤立 NUL：

```
...export{...jwtVerify};\n\x00// atom-brand/atom-brand.js
```

其后紧接着仍是正常源码（`atom-brand` 一直延续到 4,482 B）。从这个位置之后
二进制数据开始（printable 由 1.000 掉到 0.68 → 0.32）：

```
};                     <- 模块最后一个 token
\x00(\xb5/\xfd\xa0\x04  <- NUL + 压缩流魔数（Bun 的 zstd 字节码块）
```

**关键：那个 NUL 不是模块结束标志。** 早期实现把"第一个 NUL"当结尾，切出 4,485 B，
末字符是一个孤立的 `(`，js-beautify 直接报 `Unexpected token`。修正后的规则是：

> NUL 只有在其后 64 字节可打印率 < 0.95 时才算模块结束；否则视为头部内的游离 NUL，继续往后。

按此规则切得 **4,482 B**，末字符是 `};`，语义完整。

后面的 3.86 MB 里：`B:/~BUN/root/` 出现 **6,008 次**、`chunk-*` 名下 **5,756 个**、
模块标记 **0 次** —— 这不是一张表，而是**三段不同的数据**。
当时的判断是「chunk 路径 / 字节码偏移索引表」，**该判断已被 §8 修正**：

- 90.4% 是 **141 帧 zstd 压缩的内嵌文档与第三方 bundle**（解压 7.74 MB）；
- 4.4% 才是 chunk 名表（**2,878 个唯一名，每条重复两次** = 5,756 条目）；
- 5.2% 是 `B:/~BUN/root/` 资源名索引（247 条）。

「5,756 个 chunk 名」实为 **2,878 × 2 的条目数**；真正从未被任何 import 引用的只有 **7 个**。
详见 §8。

### 4.5 判定与处置

**span 2 = 一个真实模块（4,482 B）+ 紧邻的 Bun 内嵌资源与 chunk 清单（3.86 MB）。**
模块本身不在任何已提取模块里，属于**本轮新发现的独有源码**。

处置：给 `extract_bun_modules.py` 增加 `--carve-head` 选项，让它在
"真模块 + 二进制尾"的 span 里只保留模块头。319 重跑后得到 **2,882** 个模块
（原 2,881 + 这 1 个），该模块已走完线 A / 线 B，改名 2 处（`one` → `item`，C 级）。

**283 / 303 不受影响**：默认不开 `--carve-head`，模块数仍是 2,135 / 2,431
（实测 303 若开启会多切出 6,876 B，但那会改变已发布口径，故不启用）。

## 8. 【补充】marker 2882 二进制尾的完整解剖（2026-11-08）

§4.4 当时只给了三个数：`B:/~BUN/root/` 6,008 次、`chunk-*` 5,756 个、模块标记 0 次，
并断定"这是一张 chunk 路径 / 字节码偏移索引表"。
本节把它拆到底，并**修正两个流传中的数字**。

### 8.1 先纠正两个数

前一版流传的说法是「5,756 个 chunk 名，实际被模块 import 的只有 1,752 个」。
实测下来**两个数都不是这样读的**：

| 说法 | 实测 | 说明 |
| --- | --- | --- |
| 「5,756 个 chunk 名」 | **5,756 = 2,878 × 2 条目** | 名字只出现 **2878 个唯一值**，每个恰好出现两次，且**两两紧邻**（对内间隔 = 0） |
| 「被 import 的 1,752 个」 | **静态 `from` 目标 = 1,764** | 1,752 找不到任何计时口径能得出；最接近的是 1,764 |

复算命令（在仓库根）：

```bash
python - <<'PY'
import re
data = open("claudecode319/claude.exe","rb").read()
tail = data[0x144f842f+4482 : 0x148d56a0]
DUP = re.compile(rb"B:/~BUN/root/(chunk-[a-z0-9]{6,10}\.js)\x00"
                 rb"B:/~BUN/root/(chunk-[a-z0-9]{6,10}\.js)\x00")
rows = list(DUP.finditer(tail))
print(len(rows), len(set(m.group(1) for m in rows)))   # 2878 2878
PY
```

### 8.2 尾部是三段，不是一段

`tail = 4,047,087 B`（`head` 4,482 B 之后）严格分成三段：

| 段 | 偏移（相对 tail） | 大小 | 占比 | 内容 |
| --- | --- | ---: | ---: | --- |
| **A** | `0` .. `0x37d53a` | 3,659,066 B | 90.4% | **141 个 zstd 帧**，解压合计 7,743,265 B |
| **B** | `0x37d53a` .. `0x3a8f06` | 178,636 B | 4.4% | **2,878 个唯一 chunk 名，每条重复两次** |
| **C** | `0x3a8f06` .. 末尾 | 209,385 B | 5.2% | **247 个 `B:/~BUN/root/` 资源名** + 二进制体 |

§4.4 说的「chunk 索引表」只是 **B 段**（4.4%），不是整个 3.86 MB。
把整段称作"索引表"是把 90% 的 zstd 数据一起算进去了。

### 8.3 A 段是嵌入文档与 bundle，不是字节码

第一帧的 zstd 头（`tail[2]` 起）：

```
28 b5 2f fd            zstd magic（注意 tail[0..1] 是 0a 00）
a0                     Frame_Header_Descriptor: FCS_flag=2, Single_Segment=1, no checksum
04 78 01 00            Frame_Content_Size = 96,260 B
```

141 帧解压后的内容按开头分类：

| 类别 | 帧数 | 样例 |
| --- | ---: | --- |
| `#` 开头的 markdown 文档 | 95 | `## Environment / Three kinds of slot...` |
| `/*!` 开头的第三方 bundle | 1 | Chart.js v4.5.1、highlight.js 11.11.1 |
| 其它（多为源码 / 文本） | 45 | `//// collector/collector.js` |

也就是说：**A 段里没有一条模块标记（`// @bun @bytecode`），也不是可执行字节码**——
它是 Bun 打包时内嵌的**文档与资源正文**（prompt 文档、技能说明、图表库等），
以 zstd 逐块压缩存放。这一点与 §4.4 的"模块标记 0 次"一致，但原因不是"索引表"，
而是"这里是资源正文，不是模块"。

### 8.4 B 段为什么每个名字出现两次

```text
B:/~BUN/root/chunk-wt4dg253.js\x00B:/~BUN/root/chunk-wt4dg253.js\x00
B:/~BUN/root/chunk-drx9cnw1.js\x00B:/~BUN/root/chunk-drx9cnw1.js\x00
...
```

配对结构严格成立：**2,878 对，2,878 唯一名，对内间隔一律 0**。
唯一不对齐的地方是 3 个插入点（对间夹带 30 / 34 / 136 B），
它们是 `audio-capture.js`、`cli` 以及一条 `src/plugins/functionHooks/...` 路径——
非 chunk 的条目混在同一串里。

这解释了 5,756 的来历：**它不是 2,878 + 2,878 之外的额外数据，就是 2,878 × 2 的条目数。**

### 8.5 那张「带 6 字节记录」的表是另一处

`.bun` 段前部（`0x99b0000`、`0x99c0000`、`0x99f0000`、`0x9a00000`）另有一张表，
每条是「名字 + `00 1e 00 00 80 XX`」，共 **2,743 条**：

```text
B:/~BUN/root/chunk-wxztkjve.js\x00\x00\x1e\x00\x00\x80 nB\xf4
B:/~BUN/root/chunk-vyjvp8sa.js\x00\x00\x1e\x00\x00\x80 8"\xc9
```

两张表的集合关系是干净的嵌套：

| 集合 | 数量 |
| --- | ---: |
| 带 6 字节记录的注册表 | 2,743 |
| marker 2882 尾部的成对名表 | 2,878 |
| 两者共有 | 2,743 |
| **只在成对表里** | **135** |

那 135 个里，除 1 个（`chunk-9avz3w9r.js`）外**全部被模块 import**——
包括 `chunk-sa45ym56.js`（marker 2882 自己 import 的原子状态库）。
所以成对名表比注册表更全，覆盖了后期追加的 chunk。

### 8.6 真正「从未被引用」的只有 7 个

把模块侧的四种引用形态全部算上：

| 形态 | 唯一名 |
| --- | ---: |
| 具名导入 `import {...} from "…"` | 1,764 |
| **副作用导入 `import "…"`** | **1,371** |
| 动态 `import("…")` | 762 |
| `require("…")` | 372 |
| **合并** | **2,871** |

> 注意第二行：**1,371 个 chunk 只被副作用导入引用**（`import"B:/~BUN/root/chunk-x.js";`），
> 没有任何 `from`。这是模块侧唯一被长期漏算的形态，也是"1,752"这类数字出现偏差的根源——
> 只统计 `from` 会把这 1,371 个整批丢掉。

对齐结果：

| 项 | 数量 |
| --- | ---: |
| 成对名表 unique | 2,878 |
| 被任意形态引用 | 2,871 |
| **从未被引用** | **7** |
| 被引用但不在表里 | 0 |

这 7 个（`2awzp8k8` / `2e8nmqpa` / `9avz3w9r` / `9phsrvp2` / `cjp8sjkp` / `td1tv06m` / `xn7tkg1s`）
全 exe 各只出现 **4 次** = 成对名表 2 次 + `file:///B:/%7EBUN/...` 2 次，
既没有 `@bun @bytecode` 模块头，也没有任何 import 指向它们。

### 8.7 结论

> **没有"4,000 多个指向未知的 chunk 名"这件事。**
> 5,756 是 2,878 个名字各出现两次的**条目数**；2,878 里 2,871 个都能在模块侧找到引用；
> 真正孤立的只有 **7 个**，且这 7 个是 Bun 自身生成的 chunk 占位条目
> （只出现在名表与 file-URL 表里，无源码、无引用）。
>
> 尾部的 90% 不是索引表，而是 **141 帧 zstd 压缩的内嵌文档与第三方 bundle**。

这个结论比原来的"未使用打包残留 / 另一套索引"更具体：
**B 段是打包器生成的 chunk 清单（每名两条，一条指向源码路径、一条指向字节码路径），
A 段是内嵌资源正文，C 段是资源名索引。三者都不是"未使用的残留"。**
