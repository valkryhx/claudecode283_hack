## 0. 结论先行

| 问题 | 结论 |
| --- | --- |
| 这套状态库给谁用 | **插件**。插件从虚拟模块名 `"claude-code"` 导入 `atom / derive / memberOf / read / update` |
| 为什么要静态扫描 | 因为状态键 `{plugin, key}` **被强制要求是字符串字面量**，从而能在编译期枚举出 `{reads, writes}` 清单 |
| 清单用来干什么 | **授权校验**：`xn()`（m2429）用两条硬规则核对 —— ①只有 owner 能写 ②读写必须已声明 |
| 「已声明」从哪来 | 插件的 `.d.ts` 里 `declare module 'claude-code' { interface PluginState { … } }`，由 `plugin.json` 的 `types` 字段指向 |
| 运行期还有校验吗 | **有，但只守一半**：每次 `state.*` 都跑 `xxxProblem` 预检（规则 A / render 禁写 / NUL 注入 / JSON / ifVersion），**不**复核声明（规则 B） |
| 和 `mods` 是同一机制吗 | **是同一概念的不同语域**：`mod` 是对人的说法，`plugin` 是工程/API 侧说法；`mods/` 是内置插件目录名 |
| 是 319 新增的吗 | **不是**。283 就已有完整实现（`m0084_0xc08d389.js`），303 也有（`m0103_0xe5f36a9.js`）。319 的变化只是**把它拆成独立 chunk**，因而首次可读 |
| 外部插件走同一套扫描吗 | **走**。全仓唯一的扫描入口 `Baa()` 只有 1 个调用点，对任意插件目录一视同仁；按来源分流的地方全链路只有 1 处（`anthropic` telemetry 流准入，且是**收紧**外部插件）。详见 §9 |
| 属于重大机制吗 | **是**。这是插件体系的**状态隔离与能力边界**底层，层次比产品层的 "mods" 更深 |

### 两层检查的分工（关键区分）

| 规则 | 静态校验 `plugin validate`（m2429） | 运行期 `state.get/set`（m0452） |
| --- | --- | --- |
| A. 只有 owner 能写 | ✅ | ✅（**双重把关**） |
| B. 读写必须已声明 | ✅ | ❌ **只在静态侧** |
| render 期禁写 | — | ✅ 运行期独有 |
| 引用形状 / NUL 注入 | — | ✅ 运行期独有 |
| 值 JSON + 长度上限 | — | ✅ 运行期独有 |
| `ifVersion` 合法性 | — | ✅ 运行期独有 |
| 按插件来源（builtin/外部）分流 | ❌ 不分 | ❌ 不分（见 §9.5） |

**静态侧管「你能不能碰」，运行侧管「你碰的方式对不对」+ 再守一次所有权。**
不要把结论说过头：运行期并非什么都不查，但也**不**复核声明。

这一点很重要，因为 `xn()` 的 `unchecked` 降级逻辑正是建立在此之上 ——
声明面本来就不是运行时强制的。

### 1.2 引用三元组：`{plugin, key, id}`

```js
// m2882:58
function frozenRef(ref, id = ref.id) {
  const { plugin, key } = ref;
  return Object.freeze(id === undefined ? { plugin, key } : { plugin, key, id });
}
```

三个字段的语义**不对称**，这是整个设计的支点：

| 字段 | 是否必须字面量 | 用途 |
| --- | --- | --- |
| `plugin` | **是** | 静态枚举：这个状态槽属于哪个插件 |
| `key` | **是** | 静态枚举：插件内的哪个槽 |
| `id` | **否**（可计算） | 运行时隔离，不参与枚举 |

扫描器的错误信息直接把这条写死：

> `only id may be computed`

### 1.3 品牌用 `Symbol.for` 而非 `instanceof`

```js
// m2882:8, m2882:55
const ATOM_BRAND = Symbol.for('claude-code.state.atom');
const DERIVED_BRAND = Symbol.for('claude-code.state.derived');
```

```js
// m2882:74
const hasBrand = (source, brand) => typeof source === 'object' &&
    source !== null && source[brand] !== undefined;
```

`Symbol.for` 走**全局符号注册表**。这不是风格选择：如果多个 chunk 各自打包一份
这个库，`instanceof` 会因构造函数不同而失效，`Symbol.for` 不会。

**这与静态扫描是同一个前提的两面**：扫描器分析的是**文本**，不是运行时实例；
所以运行时的品牌判定也必须是「全局可比对」的。

### 1.4 深冻结

```js
// m2882:21

  [ATOM_BRAND]: true,
  ref: frozenRef(ref),

```

`deepFrozen`（m2882:31）递归冻结到叶子。目的：**调用方无法通过持有的 `initial`

### 1.5 派生 atom 的缓存失效靠「版本号拼接」

```js
// m2882:106-112

const key = versions.join(',');

```

只有上游任意一个源的**版本号**变了才重算。不用引用相等，用版本签名 ——
因为深冻结之后引用是稳定的，引用相等无法反映内容变化。

### 1.6 写入是 CAS + 64 次重试（乐观并发）

```js
// m2882:129-147
const UPDATE_TRIES_MAX = 64;

export const update = async ($, target, change) => {
  const state = $.state;
  const ref = isAtom(target) ? target.ref : target;
  for (let tries = 0; tries < UPDATE_TRIES_MAX; tries += 1) {
    const held = await state.get(ref);
    const current = isAtom(target) ? atomValueOf(target, held.value) : held.value;
    const next = change(current);
    const stored = isAtom(target) ? storedValueOf(target, next) : next;
    const wrote = await state.set(ref, stored, { ifVersion: held.version });
    if (wrote.isSet) return next;
  }
  throw new Error('update: the value was written by another every time it was read, up ' +
      'to the bound on tries; nothing was written');
};
```

读 → 算 → 带 `ifVersion` 写回；失败整轮重来。**无锁**，靠版本号做 CAS。
64 次用尽直接抛错，不静默丢写。

这个模块是理解整套机制的钥匙。它不执行插件代码，只**读插件的 AST**。

### 2.3 强制字面量：这是整套设计的硬约束

扫描器会**拒绝加载**插件（`refuse` 抛错），如果状态键不可静态解析。

**(a) `plugin` 和 `key` 必须是字面量**

```js
// m0134:2304
`$.${spelling_2} takes a reference whose plugin and key are string literals
 ({ plugin: "p", key: "k" }, written there or in a const of this file;
 only id may be computed), so the values a module reads and writes can be listed`
```

**(b) `atom` / `memberOf` / `derive` 的产物也算「可读的源」**

```js
// m0134:2529
`the state library's ${n} takes a source the scan can read: a reference whose
 plugin and key are string literals, or what atom, memberOf or derive (imported
 from "claude-code") made of one, written there or in a const of this file, so
 the values a module reads and writes can be listed`
```

**(c) 承载引用的 `const` 不能被改写或外传**

```js
// m0134:2506
`the const ${name}, read as the reference of a $.${spelling} call, is also
 written through, handed on or exported here, and const does not freeze: what it
 holds at the call could not be listed. Use it only as the reference of $.state

 and in a spread into an object literal ({ ...${name}, id }), or write the

```

注意 `or write the reference at the call` —— **允许把引用直接内联写在调用点**，
因为那样扫描器能直接读到字面量。

**(d) `$` 只能作为 `read`/`update` 的第一个参数**

```js
// m0134:2358
`$ is passed to the state library's ${k} other than as the first argument of
 read($, source) or update($, target, fn)`

// m0134:2360
`$ itself is ${qo(c, y)} (bound, passed, spread, returned or read)`
```

`$` 是状态句柄，**禁止逃逸**：不能绑定、传参、展开、返回、单独读。

**(e) `const` 不冻结 —— 设计者认知写在这里**

> `const does not freeze`

这是 JavaScript 的事实（`const` 只锁绑定不锁内容），扫描器以此为由拒绝
「事后被改写的引用」。

## 3. `mods` 是什么（辨析）

319 全量里 `mods` 出现在 27 个文件。逐个查证后**没有一个**指向「独立的 mods 机制」：

| 模块 | 处数 | 实际含义 | 判定 |
| --- | ---: | --- | --- |
| `m0701_0x122b603a.js` | 13 | **键盘修饰键**：`mods.shift` / `mods.alt` / `mods.ctrl`，TUI 指针事件 | 无关 |
| `m0591_0x11be624e.js` | 32 | **`dev-mods`**：会话级开发插件文件夹，写进会话转录（`saveDevModsFolder`） | 相关但属产品层 |
| `m0134_0x113da929.js` | 2 | **常量目录名** `Ao = "mods"`、`vo = "mods/"` | 内置插件代码目录 |

### 3.0 【重要】`mod` 与 `plugin` 是同一个概念，只是语域不同

产品文案里两者**互换使用**，出题人的直觉是对的 —— 这正是同一个机制：

> `a mod is kept and passed on as a plugin file handed over in the chat`

> `A mod is a small program that changes how Claude looks or behaves here.`

> `Claude wrote these mods, and they run with the same access you have`

> `Use this when the person asks to share or publish a plugin or a mod with their team`
> `("share this mod with my team", "publish this plugin to the org")`

> `for a mod that has no manifest yet, the folder that holds its hooks/`

> `A mod that lists this plugin under dependencies gets the contract laid at
> .claude-plugin/types/<plugin>/index.d.ts`

**结论：`mod` 是对人的说法（面向非工程用户），`plugin` 是工程/API 侧的说法。**
同一份代码：`.claude-plugin/plugin.json` 是 manifest，`hooks/` 是入口，
`claude plugin ...` 是 CLI 前缀。

`mods/` 这个名字就来由于此 —— **存放 mod（= plugin）的目录**。

## 4. 三层结构串起来

```
┌─ 状态库 m2882（4,482 B）
│    品牌(Symbol.for) + 深冻结 + 版本签名缓存 + CAS(64 次重试) + requestId 隔离
│    API 面 = { atom, derive, memberOf, read, update }
│
├─ 静态扫描器 m0134（3,343 行）
│    强制 plugin/key 为字面量；$ 不得逃逸；const 不得被改写
│    → 编译期产出 { reads: [...], writes: [...] }
│
└─ 插件运行时（builtinPlugins / cc-plugin-* / dev-mods）
     内置插件：builtin:<name>/hooks/register.ts，代码在 mods/
     外部插件：settings.enabledPlugins 里的 name@marketplace
```

### 4.1 内置插件的注册链（m0134:3186-3240）


内置插件同样走标准 manifest 结构（`name` / `description` / `version` /
`defaultEnabled` / `userConfig`），只是 `isBuiltin: true` 且允许携带
`hooksConfig` / `mcpServers` / `hooksModule`。

### 4.2 为什么这套设计是「重大机制」

**它在插件加载前就确定了插件的状态访问面。** 因为 `plugin`/`key` 被强制为字面量，
扫描器可以完全静态地算出 `{reads, writes}`，**不需要信任运行时的行为**。

配合：
- 深冻结 → 插件拿不到可变引用
- `requestId` 隔离 → 一个请求不污染另一个
- `$` 禁止逃逸 → 状态句柄不能转手
- `Symbol.for` 品牌 → 跨 chunk 多份库实例可互认（否则扫描器和运行时对不上）

这四条共同构成**插件状态的安全边界**。

### 5.3 授权规则本体：`xn()`（m2429:401）

```js

    keys.forEach(item => h.add(item));

        only a value's owner writes it (to change what is written, hook
        ${plugin}'s state.set and rewrite e.value)`);

  // 3) 规则 B：读/写都必须在该 plugin 的 PluginState 契约里声明过
  for (let { plugin, key } of [...names.reads, ...names.writes]) {

        v = h || others !== void 0,
```

### 5.4 两条硬规则

| 规则 | 语义 | 错误信息（原文） |
| --- | --- | --- |
| **A. 只有所有者能写** | 插件 A 不能 `update` 插件 B 的状态槽 | `which ${plugin} owns: only a value's owner writes it (to change what is written, hook ${plugin}'s state.set and rewrite e.value)` |
| **B. 必须声明过** | 读写任何状态键，都必须在某个 `PluginState` 契约里出现 | `${b} is not declared: ${S} must name it in interface PluginState { ${plugin}: { ${key}: ... } }` |

**规则 A 还给了正规替代路径**：要改别人的值，去 hook 那个所有人的 `state.set`
并重写 `e.value` —— 也就是**走事件拦截，而不是直接写**。

**规则 B 的输出分两类**：

- `problems` → 进 `errors`，`success: false`，**校验失败**
- `unchecked` → 进 `notes`，只是提示（对方插件没启用，无法静态确认）

### 5.5 `PluginState` 是 TypeScript 声明合并

也就是说：**插件在 `plugin.json` 里用 `types` 字段指向一个 `.d.ts`，那个 `.d.ts` 里用

`types` 字段的 schema 描述（来自 manifest zod schema）：

> a self-contained `.d.ts` (no import, export-from, require or reference) that exports
> the types of the noun the plugin's hooks module adds in `engine.create` at its top
> level and declares the noun in a `declare module 'claude-code' { interface
> EngineInterface { ... } }` block, nothing else.

约束：必须以 `.d.ts` 结尾、不能含 `..` 路径段（不能逃出插件目录）、自包含（无 import/export-from/require/reference）。

## 9. 【已查实】外部插件走不走同一套扫描 —— 走，而且用的是同一个 `Baa`

这是 §6.8 遗留的第一条待办。结论先行：

> **扫描不按插件来源分流。** 全 319 里唯一的扫描入口是 `Baa()`，
> 它**只有 1 个调用点**，在静态校验器 `m2429` 里，对磁盘上的任何插件目录/文件都会走到。
> 门禁链上的 `isBuiltin` 只有 **5 处，其中 1 处是算出来的**（同文件另有 7 处属于别的子系统，见 9.3.1），
> 而它唯一的作用是限制「能不能站在 `"anthropic"` telemetry 流上」这一件事。

### 9.1 扫描入口只有一个，且完全不分辨来源


`Baa` 的函数体里**没有任何来源判断**：不吃 `isBuiltin`、不查插件表、不看 marketplace。

全仓库检索 `Baa(`：

### 9.2 `Tt()` 的调用者只有两个，都不看来源

### 9.4 另外两处硬编码 `!1`：宿主核对，把「扫到的」和「注册的」对齐

这两处容易被误读成「只对 builtin 做检查」，实际相反 —— 它们是**对所有插件都做**的核对。

```js

      throw new $e(`${e}: registered ${s}, which the scan of its hooks module did not see (host check)`)

```

调用点（`m0591:169572`）在运行期装载器 `Uut()` 里，就在 `y.load(...)` 之后：


`isBuiltin: !1` 在这里传给 `non()`。而 `non()` 是：

```js
// m0134:1742

```

`dV(e, o)` 是「两个事件名相等」的基本判定；`to(x)` 是「这是不是内置事件名」。
`isBuiltin === false` 时，`non()` 要求 **两端要么都不是内置事件，要么都是** ——
即**不允许外部插件把自己的自定义事件伪装成内置事件名**。传 `true` 反而放宽。

所以这两处 `!1` 的语义是：**「按外部插件的更严标准核对」**，而不是「跳过核对」。

### 9.5 静态扫描一视同仁，运行期门禁另有来源判断

两者的分工并不对称，这是本节最重要的结论：

| 环节 | 是否按来源分流 | 依据 |
| --- | --- | --- |
| AST 扫描（`Baa`） | ❌ 完全不分 | `m0591:44021-44036` 无来源参数；唯一调用点 `m2429:1438` |
| 静态校验（`xn` 规则 A/B） | ❌ 完全不分 | `m2429:1516-1526` 只吃 `owner`/`declared`/`others` |
| 宿主核对（`wzt`） | ❌ 一律按更严标准 | `m0591:43799` `isBuiltin: !1` |
| telemetry 流准入（`Igi`） | ✅ **分**（唯一一处） | `m0591:44114` `isBuiltin: bq(r)` |
| 运行期 `state.set` 规则 A | ❌ 完全不分 | `m0452:9275-9290` 只比 `e.plugin === n.plugin` |

运行期那一栏值得再强调一次：`oao()` 里根本没有 `isBuiltin` 这个概念，
它只问「你要写的槽的 owner 是不是你自己」。
**内置插件同样不能跨插件写别人的状态** —— 门禁比静态侧更统一，不搞特权。

### 9.6 与 §5.8 的关系（修正一处措辞）

§5.8 记的是 `m2429:1530` 那句提示：

```js

```

当时读作「校验依赖对方插件启用」。结合本节可以写得更准确：

用来补全「别人声明了哪些状态键」：

```js

if (s === void 0) return;                       // ← 没有会话 → 什么都不知道
...
if (!((types !== void 0 || i.isBuiltin !== !0) && y.resolve(i.path) !== y.resolve(e))) continue;
```

所以「未启用就 unchecked」的真正原因是**运行时拿不到对方的 `.d.ts`**，
不是「故意不管外部插件」。一旦对方在会话里，外部插件与内置插件**用同一段代码**取契约。

### 9.7 `JSo.registerScan` / `JSo.register`：两个 Map，一条岔路

这是 §6.8 的第二条待办，答案很短。

```js
// m0134:445-468
function xUn() {                      // 一个极简 Map 包装
  let e = new Map();
  return {
    get: o => e.get(o),
    set: (o, t) => { e.set(o, t) }
  }
}
function Pt() {                       // 两张表
  let e = xUn(), o = xUn();
  return {
    register:     (t, r) => { e.set(t, r) },   // e: 「已装好的源文本」
    source:       t => e.get(t),
    registerScan: (t, r) => { o.set(t, r) },   // o: 「包装好的扫描结果」
    scan:         t => o.get(t)
  }
}
var JSo = Pt();
```

调用时机只有一处：

```js
// m0134:3189-3195   内置插件注册（__）
function __(e) {
  Fr().builtinPlugins.set(e.name, e);
  let hooksModule = e.hooksModule;
  if (hooksModule === void 0) return;
  let t = dt(e.name);                                    // "builtin:<name>/hooks/register.ts"
  if ("scan" in hooksModule) JSo.registerScan(t, hooksModule.scan);
  else if ("shipped" in hooksModule) JSo.register(t, hooksModule.shipped);
}
```

要点三条：

1. **只有内置插件会写这两张表** —— `__()` 是内置插件注册函数，
   它的 key 是 `dt(name)` = `builtin:<名>/hooks/register.ts`（`m0134:218-219`）。
   磁盘上的外部插件从不经过这里。
2. **两条岔路等价**：`hooksModule` 带 `scan`（已经是扫描结果）就进 `o` 表；
   带 `shipped`（还是源文本）就进 `e` 表。语义上是「有的内置插件随包附扫描结果，有的附源文本」。
3. **读取端就是一条捷径**：

```js
// m0591:44061-44069   _ke()：先查表，查不到才真扫
async function _ke(e, n, r) {
  let s = JSo.scan(e);
  return s === void 0 ? yke(e, await PUn(e, n, r), r)      // 未登记 → 完整扫描
                      : { source: "", linked: [], links: [], scan: s }  // 已登记 → 直接用
}
```

以及 `m0134:1440` 的 `JSo.source(file)`，同样是一层「有就用、没有算」的命中缓存。

> **所以 `JSo` 不是「插件分类器」，是内置插件的扫描结果旁路缓存。**
> 外部插件永远走 `PUn()` + `lPr()` 真实扫描这条路，
> 唯一的后果是**外部插件没有这个加速**，不是「不被扫描」。

### 9.8 一句话总结

> **扫描对所有插件一视同仁；分流只发生在「扫完之后怎么判」这一层，
> 而且全链路只有一条规则按来源分流（`anthropic` telemetry 流准入，且是收紧外部插件）。
> 运行期 `state.set` 的 owner 独占规则连这条分流都没有 —— 内置插件同样不许跨插件写。**

这比 §5.8 当时设想的「要么统一、要么分裂」更精确：
**扫描统一，判据几乎统一，只有一处刻意的特权边界。**
